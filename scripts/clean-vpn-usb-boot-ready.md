# USB boot investigation, 2026-11-01

Пользователь подтвердил, что VPN заработал после TLS repair; остаётся редкое
отсутствие Ethernet IP после загрузки. В сохранённых boots -3/-1 iPhone получил
DHCPACK; текущая загрузка Mac тоже успешна. В boot -3 dnsmasq запущен до usb0.
Это не доказательство причины всех отсутствующих IP: wildcard dnsmasq принимает
поздно появившийся интерфейс и в той же загрузке успешно выдал адрес.

Первый кандидат 2c6d54a пытался назначить адрес перед UDC bind. Физическая
перезагрузка выявила несовместимость: vendor kernel создаёт usb0 только при
bind, поэтому startup завершился Cannot find device usb0. Изменение отменено
через независимый Wi-Fi, оригинал восстановлен; gadget подключён без пересоздания,
Mac снова получил адрес. Код кандидата отозван коммитом 999af69. Его mock-тесты
не проверяли жизненный цикл сетевого интерфейса в настоящем USB-драйвере.

Узкое исправление `scripts/clean-vpn-usb-boot-order.py [--apply]` сохраняет
UDC bind до настройки usb0. Новый drop-in запускает gadget после завершения
старта dnsmasq; Wants позволяет USB rescue работать даже при отказе DHCP.
В старом gadget script удалён address flush: используется address replace,
чтобы не удалять адрес, параллельно установленный rescue. Состав USB functions,
Mass Storage, MAC, DHCP pool и маршруты не меняются. Применение не перезапускает
службы; оригинал сохраняется в `/var/lib/meshpn-usb-boot-order`.
Для отката восстановить оригинал с режимом 0755, удалить только
`/etc/systemd/system/usb-gadget.service.d/40-meshpn-dhcp.conf`, daemon-reload;
не перезапускать старый gadget script на живом интерфейсе.

Также обнаружен независимый отказ: часы Radxa отстали на 35125 секунд,
VPN остановился с auth_clock_skew. Автоматический SSH bootstrap исчерпал
одну попытку из-за clock_round_trip_exceeded. Свежая pinned SSH-проба прошла
за 1715 ms; операторская коррекция при остановленном VPN восстановила ready.
Запись автоматической попытки сохранена, trust/certificate verification не
ослаблены. Надёжность однократного bootstrap на ранней сети остаётся открытой.

Физическая штатная перезагрузка исправленного варианта прошла:
dnsmasq active на 13,24 s → gadget start 13,28 s → gadget ready 14,46 s →
DHCPACK Mac 192.168.7.19 на 15,86 s. USB configured, rescue и guard активны.
После Wi-Fi native combo сам перешёл в ready. USB DNS A/AAAA UDP/TCP — 4/4,
реальный TLS1.3 с проверкой сертификата и application bytes — 286 ms.
Это один warm reboot с Mac, не доказательство устранения всех редких cold-boot
отказов iPhone. Нового теста на телефоне пока не проводилось.

## Повторное развёртывание

Это provisioning USB/DHCP, не исправление native engine. Скрипт в репозитории
проверяет точный SHA прежнего пользовательского gadget-start.sh и откажется
переписывать другую конфигурацию. Native installer сам его не вызывает.
Для другой платы нужно сначала определить USB driver/gadget/link owner/DHCP,
проверить зависимость служб и получение адреса после загрузки; установка VPN
не доказывает готовность этого слоя. Для совпадающего профиля применяется
отдельный installer выше. Маскировать несовместимость автоматическим USB reset
или безусловно переносить конфигурацию этой Radxa на другие платы нельзя.
