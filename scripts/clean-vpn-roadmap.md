# clean-vpn: цели и порядок дальнейшей работы

Зафиксировано 2026-10-04 по целям пользователя. База кода: `b50209f`.
Это план, не заявление о готовности перечисленных возможностей.
Актуальное уточнение 2026-10-07: production legacy client/exit отсутствуют.
Приоритет — полный native data plane на обеих сторонах, включая последующий
перенос transparent/combo. Совместимость с Node packet path больше не является
обязательным критерием архитектуры/приёмки; старые fixtures могут оставаться
регрессионными тестами. Все новые этапы проверяются в лаборатории, без изменения
Radxa/VPS. Измерение скорости отложено до полностью native client↔exit;
подготовленный legacy/native benchmark не блокирует эту работу.

Порядок оставшегося native-перехода: многосессионный boring-tls exit с отдельными
ключами/адресами и bounded admission → native-only lifecycle/provisioning и
проверки client/exit в изолированной VM → native transparent relay с защищённым
non-HTTPS путём → native combo. UI, новые профили и последующие продуктовые
этапы идут после этой основы. Это поручение продолжать native, а не ограничение
старого M1 «остановиться и не начинать M2» ниже; исторические приёмки сохранены.
Текущая реализация и незакрытые пункты: [полный native-переход](clean-vpn-native-transition.md).
Дополнительно проверен [прямой C++ systemd lifecycle](clean-vpn-native-service.md):
два real-TUN клиента, native exit, restart/crash и сохранение guard.
Добавлен [fresh native installer и трёхзагрузочная VM](clean-vpn-native-install.md):
отдельные установленные client/exit, reboot и отказ guard до поднятия uplink.
Дополнительно реализован [route coordinator для native service](clean-vpn-native-routes.md):
журналируемая смена DHCP-адреса/gateway, отказ при чужих маршрутах, остановка
клиента при падении coordinator. Data plane остаётся в C++.
Добавлен [единый native-only site profile](clean-vpn-native-network.md): fresh
bundle client/exit, TUN/guard/DNS/SNAT/MSS, gate поднятия интерфейсов и общий
systemd target. Приёмка — изолированная VM с LAN и внешним тестовым origin.
Финальная site-приёмка: 17/17 gates на двух загрузках, 349/349 native/routes
регрессий; хеши и ограничения сохранены в `fixtures/clean-vpn-native-site-report.json`.
Следующий лабораторный шаг — C++ transparent relay, затем native combo.
Начат [native transparent checkpoint](clean-vpn-native-transparent.md): bounded
ClientHello/SNI codec и HRR gate, 18 full/resumed TLS-handshake в C++ memory BIO.
Добавлены native enc-SNI auth, bounded durable replay, явный destination
allowlist и TCP relay с backpressure/half-close; real-TCP fixture не меняет сеть
хоста. Экспериментальный engine client/exit подключён к SO_ORIGINAL_DST;
изолированный REDIRECT-прогон включает SIGKILL exit и replay после restart.
Общая Internet policy, lifecycle interception в site profile и combo ещё впереди;
готовым основным транспортом остаётся boring-tls.
Это dedicated-host контракт: адреса/DHCP/default предоставляет внешний link
owner. Адаптация к конкретному distro/network manager, обновление существующих
установок и физический boot остаются отдельной эксплуатационной работой.
Уточнение пользователя: транспортный data plane переносится в C++ **до**
дальнейшего существенного развития профилей и многотранспортности; Node остаётся
слоем управления. Прежний M1 с переносом двух Node-адаптеров заменён native M1 ниже.

## Конечные цели

1. Основные транспорты: **boring-tls, transparent-tls, combo-tls**.
   Позже — дополнительный зашифрованный UDP-транспорт, возможно WSS.
   Обычный Node `tls` остаётся базой сравнения и совместимости, но не заменяет
   целевую тройку.
2. Добавление сохранённых браузерных ClientHello-профилей через посещение
   специальной страницы на Radxa или VPS. Одна система профилей для
   самостоятельного boring-tls и его ветки в combo-tls.
3. Интерфейс clean-vpn на Radxa/VPS: настройка транспорта и соединения;
   выбор, добавление и удаление профилей; проверка соответствия выбранному
   профилю на **реальных запросах к серверу**, с показом расхождений.
4. Несколько одновременно поднятых транспортов и быстрое переключение
   между ними без перезапуска процессов client/exit.
5. Два варианта шлюза: `client → USB → Radxa → clean-vpn → VPS` и
   `client → WireGuard → VPS → clean-vpn → другой VPS`.
6. Позднее — гео-роутинг: выбранные направления напрямую, остальные через
   VPN либо другая явно выбранная политика. Семантика ещё не согласована;
   архитектура должна позволять добавить её без переделки транспортов.
7. Последующее использование clean-vpn как отдельных транспортных компонентов
   mesh VPN, без обязательного владения системными маршрутами внутри транспорта.
8. Native data plane на client **и** exit: пакеты, транспортные потоки и их
   обработка не проходят через Node.js. UI, API и управление остаются в Node.

## Целевая граница Node / C++

```text
Node: UI / API / конфигурация / реестр профилей / установка
                         ↕ команды и статусы (IPC)
C++: TUN ↔ обработка пакетов и потоков ↔ транспортные сессии ↔ сеть
```

- C++: чтение/запись TUN, framing, очереди, backpressure, TLS/BoringSSL,
  транспортный HTTP/2, auth, таймеры, health-check, reconnect, а позднее
  transparent relay и выбор подготовленного транспорта.
- Node: подготовка и валидация конфигурации, управление жизненным циклом engine,
  пользовательскими профилями, системными маршрутами/DNS/guard через согласованный
  координатор. Native engine также проверяет входную конфигурацию и capabilities.
- DNS: если запросы обрабатываются нашим data plane, они не передаются в Node
  для обработки каждого запроса. Настройка системного resolver остаётся control plane.
- Через ограниченный IPC идут команды, статусы, агрегированные метрики и
  диагностические события, **не поток пакетов или его копия**. Секреты не попадают
  в argv, обычные логи или диагностические ответы; механизм их доставки проектируется.
- Начальная модель — отдельный native engine-процесс, а не пакетные callback
  в Node-addon. Его падение не должно снимать guard или уничтожать независимый
  административный доступ. Политику отказа/рестарта проверять отдельно.
- Существующие TUN-addon и BoringSSL helper — исходные наработки, не доказательство
  готового native data plane. Одного переноса TLS-handshake недостаточно.

Ожидаемую пользу по CPU/RSS/задержкам измерять, не обещать заранее. C++ добавляет
риски ошибок памяти; ограничение ресурсов, проверки входа и native-тесты обязательны.

## Что уже принято и что не расширяем автоматически

Пользователь принял текущий этап Radxa/USB на `b50209f`:

- VPN, SNAT и оба MSS-правила восстановились после reboot; guard — cvks4.
- HTTPS самой платы и Mac через USB выходит через ожидаемый exit.
- При проверенном обрыве процесс VPN сохранил PID, NRestarts=0.
- По одному монотонному журналу DHCP → подключение VPN: **2,003 с**
  и **0,961 с**. HTTP 200 с Mac восстановился; после второго подключения
  успешные пробы шли более минуты.
- Долгое ожидание Wi-Fi и повторный обрыв carrier не считаем задержкой VPN.
  **Роутер вне проекта; его не диагностируем. Настройки Mac не меняем.**

Это не приёмка всех транспортов, всех видов отказа, отсутствия любых утечек
или миграции существующих TCP-сессий. Отложенные проверки часов, аварии процесса,
блокировки при остановке VPN и других сценариев остаются в
[чек-листе Radxa](clean-vpn-radxa-next-checks.md), но не должны бесконечно
отодвигать основные продуктовые цели.

## Исходная точка

- boring-tls: BoringSSL helper, сохранённый JSON-профиль и часть диагностики есть;
  законченного пользовательского управления профилями и полной мимикрии нет.
- transparent/combo: реализация relay и стенды есть; успех компонента не означает
  эксплуатационную готовность всего режима. У standalone transparent-tls
  оставшийся сырой неаутентифицированный TUN TCP — отдельный обязательный пробел.
- Захват: есть `ja3-snif-server.mjs`, но это ещё не законченный workflow/UI.
- WG ingress: есть пилотный `--from-tun=wg0`, не законченный аналог защищённого
  USB-шлюза с установкой и автозапуском.
- Система управления несколькими экземплярами транспорта ещё предстоит.

Сведения выше относятся к базе плана. При реализации сверять с кодом;
старые security/design-документы могут описывать уже заменённые протоколы.

## Этапы

### 1. Native data plane и граница управления

Разделить приём трафика (host/USB/WG/mesh), политику выбора пути, транспорт
и управление конфигурацией/жизненным циклом.

Владение ресурсами единообразно: C++ владеет packet I/O и транспортными сессиями,
control plane — согласованной системной конфигурацией. Несколько транспортов
не должны конкурировать за default route или снимать guard при своей остановке.
Решения `direct / transport / block` относятся к отдельной политике, не к
BoringSSL helper или USB-скриптам. Это задел для гео-роутинга, не включение
новых прямых исключений сейчас.

Первый ограниченный шаг — native M1 ниже: один boring-tls тракт на client/exit,
совместимый wire protocol, без новой многотранспортной маршрутизации. Делаем
до серьёзного расширения профилей и менеджера переключения, чтобы не реализовывать
их сначала в Node, а затем повторно в C++.

### 2. Общий уровень надёжности целевых транспортов

На native-основе сначала boring-tls, затем transparent-tls/combo-tls: единый жизненный цикл,
аутентификация, обрыв/возврат, DNS, MTU, память и остановка под защитой.
Проверки Node tls не засчитываются автоматически за другие реализации.
Отдельно решить защищённую судьбу non-HTTPS трафика standalone transparent-tls.
Учесть различия восстановления времени: текущий helper-путь не получает
автоматически поддержку Date-коррекции из Node TLS.

### 3. Браузерные профили как законченная функция

Путь пользователя: страница захвата → измерения → сохранённый профиль →
проверка совместимости → применение → независимая проверка реального соединения.

- ClientHello измеряется у TLS-приёмника, не JavaScript страницы. Терминирующий
  reverse proxy перед ним может скрыть исходное рукопожатие.
- Разделять исходные измерения, нормализованный профиль и effective configuration.
- Один ClientHello — образец, а не полное поведение браузера. Фиксировать
  браузер/build, условия и поддержанные cold/resumed/HRR-сценарии.
- Серверный отчёт: фактические поля/порядок/допустимая вариативность и расхождения;
  совпадение JA3/JA4 не означает полную неотличимость от браузера.
- Не переносить приватные ключи, tickets, cookies и другие секреты в профили.
  Неподдержанные возможности явно отклонять либо помечать, не обещать их применение.
- Общий реестр профилей для boring-tls и Boring-ветки combo-tls. Transparent-ветка
  сохраняет TLS приложения: произвольный профиль поверх него не подставляется.
- Динамическое per-flow клонирование текущего ClientHello приложения не возвращаем:
  речь о сохранённых пользовательских профилях.

Подробная основа: [план мимикрии](../docs/browser-profile-mimicry-plan.md).

### 4. Одновременные транспорты и переключение

Несколько экземпляров client/exit, проверка готовности нового пути,
переключение без рестарта процессов. Независимые состояния/ошибки/ограничения
ресурсов и отсутствие изменения общей защиты при остановке одного экземпляра.

Различать переключение новых потоков и бесшовную миграцию существующих.
Начальная стратегия — старые потоки остаются на прежнем пути до завершения,
где это поддерживается. Для IP/TUN и смены exit требуется отдельная проверка
адресации, NAT и состояния сессий; сохранение всех соединений не обещается.

### 5. Управление и VPS/WG

UI строить постепенно поверх общего API, не вторым независимым владельцем
сетевой конфигурации. Конфигурация, экземпляры, профили, capture/verify,
активный путь, безопасные статусы и ошибки. Авторизация администратора обязательна;
право посещения capture-страницы не равно праву изменения настроек.
Публичный API и способ его защиты проектируются отдельно, не открываются
автоматически вместе с первой внутренней реализацией менеджера.

Довести [WG ingress](clean-vpn-from-tun.md) до законченного режима шлюза:
установка, autostart, DNS, IPv6-политика, MTU, fail-closed и независимый admin access.
Не копировать USB-правила простой заменой usb0 на wg0. Не перенаправлять весь
OUTPUT VPS по умолчанию и не менять уже работающий WireGuard без отдельного плана.

### 6. Зашифрованный UDP, возможный WSS, гео-политики и mesh

UDP: выбрать протокол отдельно; нужны шифрование, аутентификация, anti-replay,
сессии, MTU и контроль ресурсов. Существующий plain UDP не становится защищённым
от смены названия. WSS также требует VPN-аутентификации, не только TLS-обёртки.

Гео-роутинг — после определения желаемой политики, источника/обновления баз,
поведения DNS и отказов. До этого не вводить неожиданный direct fallback.
Mesh получает транспортный интерфейс без обязательного TUN/system routing;
маршрутизация mesh остаётся ответственностью mesh.

к одному закреплённому IP Cloudflare и sampled CPU/RSS клиентского дерева Radxa.
Никакого изменения exit, fault injection или установки native по умолчанию.
Конечная точка — физический отчёт с полными тремя циклами и проверенным rollback;
результаты интерпретировать с учётом разброса сети и коротких передач. Не обещать

Существующий рабочий путь сохраняется для сравнения и возврата; native engine
включается явно в лаборатории, не становится production default автоматически.
Нельзя заменять native-бинарники действующих client/exit ради стенда.
Слияние в main, пуш и развёртывание — отдельные действия по поручению пользователя,
не следствие успешного теста. Приёмка M1 не означает автоматическое слияние.

## Ближайший этап M1: один native boring-tls тракт

**Цель:** работающий и проверенный в лаборатории путь
`TUN → C++ → сеть → C++ → TUN` на client/exit, управляемый из Node,
без обработки пакетов и транспортного HTTP/2 в Node.
Статус на 2026-10-05: реализовано и проверено в лаборатории на feature-ветке.
Это не приёмка на физической Radxa и не разрешение на production-развёртывание.

Работы:

1. Составить карту нынешних связей: TLS/helper, auth, H2 health, reconnect,
   очереди пакетов, TUN, DNS и маршруты. Зафиксировать владельцев ресурсов
   и границу control/data plane до переноса кода; отделить системный DNS от
   обработки DNS-трафика. Определить точный поддержанный wire/ALPN-профиль M1.
2. Определить внутренний контракт и ограниченный IPC: identity/capabilities,
   lifecycle/state, готовность после аутентификации, ошибки, отмена и закрытие.
   Не сводить будущие packet и stream/relay режимы к фиктивно одинаковым свойствам.
3. Реализовать минимальный C++ engine с TUN I/O, очередями, framing, TLS/BoringSSL,
   H2 и авторизацией для одного boring-tls тракта на обеих сторонах. Сохранить
   совместимый wire/auth; проверить совместимость с прежним endpoint там,
   где объявляется поддержка. Не ослаблять проверку сертификата/channel binding.
4. Реализовать native health-check/reconnect, ограниченные очереди/backpressure
   и cleanup. Node управляет engine командами, не пересылает его пакеты. Оставить
   защиту независимой от жизни engine; никаких новых direct fallback.
5. Проверить реальные соединения и передачу TCP/UDP внутри туннеля, DNS-путь,
   MTU/крупные пакеты, ошибки/отмену, обрыв/возврат, падение engine, защиту и USB
   admin access. Нужны unit/negative native-тесты, проверки памяти средствами
   инструментирования и относящиеся к переносу регрессии/изолированная VM.
6. Измерить CPU, RSS, скорость и задержки на сопоставимой нагрузке старого и
   нового пути. Записать сборки, условия, результаты и ограничения; отсутствие
   выигрыша не скрывать и не компенсировать ослаблением защиты/тестовых лимитов.

**M1 завершён, когда:** один native boring-tls client↔exit тракт прошёл указанную
лабораторную приёмку; packet I/O, framing, TLS/H2 и необходимые обработчики
data plane выполняются вне Node; команды управления работают; после cleanup
не остаются процессы/дескрипторы/таймеры; падение engine не открывает прямой выход;
есть воспроизводимый отчёт и сравнение ресурсов. Неподдержанные режимы объявлены
явно, не включаются скрыто через старый Node data plane.

**Вне M1:** новая система браузерных профилей и capture UI, перенос transparent/combo,
несколько одновременно активных транспортов и переключение пользовательских
потоков, UDP/WSS как внешние транспорты, гео-политики и развёртывание VPS/WG.
Архитектурные границы для них учитываются, реализация не включается в M1.

**На этой точке остановиться и показать результат пользователю.** Не переходить
автоматически к M2, не менять рабочую Radxa/exit, Mac, роутер, WireGuard или
гео-политику. Слияние ветки, пуш и развёртывание — по отдельному поручению.

После M1 согласовать следующий ограниченный этап: развитие native transparent/combo
или законченный capture/verify workflow сохранённых браузерных профилей на
native boring-tls. Оба направления развиваются уже на целевой C++-основе. При обнаружении
обязательного транспортного/security-пробела сначала явно согласовать его
приоритет; не превращать M1 в неограниченную переделку проекта.
