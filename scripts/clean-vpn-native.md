# clean-vpn: нативный путь данных и возможный kernel offload

Дата обсуждения: 2026-09-23.

**Статус: отложенная архитектурная заметка. Реализация не начата.**
Вернуться к ней при необходимости повысить скорость или снизить CPU/RAM.
Это не замена текущего плана DNS/эксплуатационных проверок и не поручение
автоматически переписывать проект. Production-статусы транспортов не меняются.

Область: самостоятельный `scripts/clean-vpn.js`, прежде всего `tls`, `boring-tls`
и `combo-tls`. Mesh из `src/` и остальные экспериментальные транспорты в оценку
не включены. Описание соответствует коду на момент обсуждения; перед работой
нужно повторно сверить реализацию и возможности целевых Linux-ядер.

## Основной вывод

Полностью перенести нынешнюю функциональность clean-vpn в ядро — существенно
сложнее, чем убрать Node.js из обработки каждого пакета. Для этого проекта
предпочтителен сначала **нативный userspace data plane при сохранении Node.js
для управления**, затем — выборочный offload, если измерения подтвердят пользу.

Написать на C/C++ **не означает** перенести в ядро. Нативная программа,
читающая TUN и записывающая сокеты, остаётся userspace-программой: переходы
kernel/userspace и часть копирований сохраняются. Замена языка сама по себе
не гарантирует ни конкретной скорости, ни снижения всех накладных расходов.

## Что уже есть в текущем коде

- [TUN-addon](../native/tun_linux/tun_linux.cc) написан на C++: до32 пакетов на
  вызов JS callback, пул памяти и external ArrayBuffer. Пакетное чтение здесь
  означает несколько `read()` с одним последующим callback, не один syscall
  на весь batch. Передача памяти в JS не устраняет чтение из TUN.
- [BoringSSL-helper](../native/boring_tls/helper_main.cc) тоже нативный. Само
  TLS-шифрование не выполняется JavaScript-кодом.
- В [clean-vpn.js](clean-vpn.js) остаются framing, batching, очереди и обработка
  потоков. Для boring-tls данные дополнительно идут через stdin/stdout отдельного
  helper-процесса (`boringTlsHelperToDuplex`).

Упрощённый исходящий TUN-путь boring-tls:

```text
ядро → TUN-addon → JS framing/HTTP → pipe → BoringSSL-helper → TCP → ядро
```

Это кандидаты на измерение: копирование и сборка буферов, аллокации/GC,
JS/native callbacks, syscalls, IPC, очереди/backpressure, загрузка отдельных ядер.
**Профилирование пока не установило, что главным ограничением является Node.js.**
Существующие soak доказывают прохождение определённых сценариев устойчивости
и ресурсных бюджетов, а не установленный предел пропускной способности.

## Почему сравнение с WireGuard не сводится к kernel/userspace

Linux-реализация WireGuard работает в ядре, но её производительность связана
также с устройством протокола, параллелизмом и интеграцией с сетевым стеком.
Существуют и userspace-реализации: [WireGuard cross-platform interface](https://www.wireguard.com/xplatform/).

Userspace не обязательно означает низкую скорость: разработчики Tailscale
показывали более10Гбит/с на оптимизированном wireguard-go в своих условиях,
используя batching и сетевые offload-интерфейсы. Это **не прогноз для clean-vpn**
и не универсальное сравнение всех реализаций.
[Разбор производительности](https://tailscale.com/blog/more-throughput).

У clean-vpn дополнительные требования: TLS, HTTP/2, авторизация, сохранённые
ClientHello-профили и BoringSSL-патчи, enc-SNI, обработка HRR и две ветки combo.
Замена всего этого WireGuard была бы сменой протокола и свойств наблюдаемого
трафика, а не прозрачной оптимизацией существующей реализации.

Кроме того, TUN-ветка TLS-транспортов несёт внутренний TCP поверх внешнего TCP.
На потерях взаимодействие повторных передач и задержек может ограничивать
производительность независимо от языка и места исполнения. Перенос в ядро
этого сам по себе не исправляет.
[TCP-in-TCP, RFC9329 §9.1](https://www.rfc-editor.org/rfc/rfc9329.html#section-9.1).

## Варианты архитектуры

### 1. Нативный userspace data plane — предпочтительный первый вариант

Node.js сохраняет конфигурацию, CLI, запуск, диагностику и управление жизненным
циклом. Нативный компонент сам владеет TUN и транспортными соединениями;
Node передаёт команды/параметры и получает события/статистику, **не каждый пакет**.

Для TUN через BoringSSL: объединить чтение TUN, framing, HTTP-транспорт и TLS
в нативном компоненте на client и соответствующий горячий путь на exit.
Сохранить wire-format, CA/hostname validation, PSK/exporter-авторизацию,
BoringSSL-профили и ограничения ресурсов. HTTP/2 framing/flow control тоже
нельзя оставить в Node на каждом блоке данных и считать JS исключённым из пути.

Просто вынести ещё одну функцию в addon недостаточно, если пакеты продолжают
проходить через JS или stdin/stdout helper. Выбор C++/Rust и модели процесса
нужно делать отдельно; существующий C++ helper — полезная отправная точка,
не готовая реализация всего data plane.

### 2. Выборочное ускорение transparent HTTPS

Эта ветка не расшифровывает TLS приложения. После необходимой обработки
handshake основная задача — пересылка уже зашифрованных байтов между сокетами.
Можно исследовать kernel-assisted forwarding, например
[SOCKMAP/SOCKHASH](https://kernel.org/doc/html/next/bpf/map_sockmap.html).

Это гипотеза для отдельного прототипа, не обещание готового fast path.
Нужна безопасная граница переключения с учётом HRR/повторного ClientHello,
фрагментации, уже накопленных байтов, обоих направлений, FIN/RST, backpressure,
таймеров и отмены. Нельзя просто передать поток в offload сразу после первого
ClientHello, потеряв последующую обработку. Необходимо повторно доказать
сохранность TLS-байтов и всех ограничений relay.

### 3. kTLS — частичный offload, не перенос всего VPN

kTLS обрабатывает TLS records, но не заменяет TLS-handshake, HTTP/2 и VPN-логику.
Handshake обычно остаётся у userspace agent/library; ключи и состояние
передаются в ядро. Применимость к patched BoringSSL helper, необходимым TLS
возможностям и целевым ядрам нужно проверять отдельно. Это не флаг, который
автоматически уберёт JS, TUN-копирования и framing.
[Kernel TLS](https://kernel.org/doc/html/latest/networking/tls.html),
[TLS handshake service](https://cdn.kernel.org/doc/html/latest/networking/tls-handshake.html).

### 4. Собственная реализация в ядре

Это новая архитектура: kernel API, владение памятью, конкурентный доступ,
очереди, криптография, таймеры, уничтожение объектов и сетевых namespace.
Дополнительно — сборка/установка модуля, совместимость с ядрами и возможность
его загрузки на целевом VPS. Ошибка может затронуть весь хост, не только процесс.

Обычный C++-код с BoringSSL нельзя просто собрать как Linux kernel module.
Стандартные языки разработки ядра — C и поддерживаемые Rust-интерфейсы, не
обычное userspace C++-окружение.
[Programming language](https://www.kernel.org/doc/html/next/process/programming-language.html).

Готовая JS-логика помогает как спецификация поведения; сетевые сценарии и
fixtures можно адаптировать для проверки новой реализации. Однако kernel
concurrency, память и жизненный цикл не получаются механическим переводом JS.
Перенос всех экспериментальных транспортов был бы ещё более широким проектом.

## Предварительная оценка трудозатрат

Ориентир порядка величины для одного опытного разработчика Linux networking,
с ограниченным охватом tls/boring-tls/combo-tls, без mesh. Не обещание сроков,
ускорения, завершённого security audit или поддержки произвольных ядер.

| Вариант | Порядок трудозатрат |
| --- | --- |
| Профилирование и поиск основного ограничения | Несколько дней — пара недель |
| Нативный data plane, Node остаётся для управления | Несколько недель на прототип; ориентировочно2–4 месяца на проверенную ограниченную реализацию |
| Собственная kernel-реализация с сохранением текущих возможностей | 6–12 месяцев и более, большая неопределённость и постоянное сопровождение |

## С чего начать, если вернёмся к этому

1. Зафиксировать цель: нужные Мбит/с и packets/s, железо client/exit, число
   потоков, допустимые CPU/RAM и задержки, RTT/потери, версии Linux.
2. Измерить прямую сеть и отдельно tls, boring-tls, обе ветки combo. Собирать
   user/system CPU, загрузку каждого ядра и helper, RSS/GC, syscalls/context
   switches, размеры пакетов, throughput и задержки. Один speedtest недостаточен.
3. Выбрать подтверждённый bottleneck. Сначала узкий совместимый нативный
   прототип, без одновременной смены протокола, TLS-профиля и маршрутизации.
4. Сравнить его с текущим кодом на одинаковой нагрузке; повторить проверки
   авторизации, сертификатов, TLS/HRR/resumption, backpressure, обрывов,
   освобождения ресурсов и pcap. Сохранить возможность вернуться к старому пути.
5. Только при оставшемся измеренном ограничении исследовать SOCKMAP/kTLS
   или собственный kernel data plane. Меньший CPU процесса не означает меньший
   общий CPU: при offload нужно учитывать работу ядра.

Итоговая рекомендация обсуждения: **не начинать с полного переноса в ядро;
сначала измерить и убрать JS/IPC из горячего пути, сохранив протокол и мимикрию.**
