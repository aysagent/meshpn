# USB UDP / PMTU: изолированная лаборатория

Стенд не меняет Radxa, Mac или сеть хоста. Использует тот же NIC-less QEMU,
реальный installer, VPN TLS/TUN, SNAT/MSS и cvks4, что и
[полный USB E2E](clean-vpn-usb-e2e-lab.md). Адреса публичных origins существуют
только внутри namespace VM; никакие пакеты не отправляются в настоящий интернет.

```bash
MESHPN_LAB_NODE_HEADERS=/absolute/node/include/node \
node scripts/clean-vpn-usb-e2e-lab.mjs \
  /var/tmp/meshpn-host-boot-rrhsPo \
  /tmp/meshpn-dns-vm-tools.dXb7TM/root --pmtu
```

Пути — сохранённые проверенные образы текущего окружения, не универсальные
пути установки. Нужен host `gcc` со статической libc для сборки маленькой
пробы; бинарник копируется в VM и не устанавливается на хост/Radxa.
В отчёт входят SHA-256 исходников и бинарника пробы.

## Что проверяется

- UDP на нестандартном порту 38474: payload 1200, 1372, 1373, 1472, 1473,
  4096 байт. Независимый положительный контроль exit → origin через veth,
  затем host и forwarded USB через настоящий TLS/TUN.
- Upload и download с разрешённой фрагментацией. Проверка размера и
  побайтного совпадения на обеих сторонах; FNV-1a в журнале — контрольная
  сумма тестовых данных, не криптографическая аутентификация.
- DF с обходом кеша PMTU (`IP_PMTUDISC_PROBE`): различаем локальный
  `EMSGSIZE` и полученный сетевой ICMP type 3/code 4 с конкретным MTU.
  Слишком большой DF-ответ: origin должен получить такую ошибку, а не
  просто исчезнуть пакет. Затем уменьшенный пакет должен пройти.
- Более узкий путь после VPN: только маршрут к синтетическому origin в
  namespace exit получает MTU 1280; ошибка возвращается через TLS/TUN и NAT.
  Следующая отправка с payload 1252 проходит; 4096 с фрагментацией проходит.
  Проверочный маршрут удаляется в `finally`, настройки основного guard не меняются.
- Переподключение по первому UDP-пакету после простоя, без разогрева HTTPS.
  Только в PMTU-стенде обе стороны запускаются с `--keep-alive=5`; перед
  пробой `ss` должен подтвердить отсутствие установленного outer TCP к exit:443.
  Остальная MTU-матрица явно прогревает туннель, чтобы не смешивать отказы
  подключения и обработки больших пакетов.
- Реальные изменения счётчиков kernel `FragCreates` / `ReasmOKs`.
- После остановки VPN ни один большой UDP-запрос USB не достигает origin;
  новые SSH-входы на 22/2222 сохраняются. После запуска снова проходит 4096/4096.

Всего 62 UDP-сценария плюс общие E2E-проверки установки, DNS, защиты и SSH.
Проверяющий код требует полную упорядоченную матрицу: один таймаут не может
быть засчитан как успешная PMTU-проверка или доказательство блокировки.

Семантика ошибок сверена с первичной документацией Linux:
[UDP](https://www.man7.org/linux/man-pages/man7/udp.7.html) и
[IP_MTU_DISCOVER](https://www.man7.org/linux/man-pages/man2/IP_MTU_DISCOVER.2const%40%40man-pages.html).
UDP-приложение само должно уменьшить датаграмму или обработать ошибку;
TCP MSS не является универсальным исправлением UDP.

## Ограничения

Это Linux-peer, не macOS; veth, не USB gadget или Wi-Fi. Проверяется IPv4 и
фиксированный native TLS-профиль, не все транспорты clean-vpn и не все IP-протоколы.
IPv6 forwarding в текущем USB-профиле намеренно заблокирован. Проба не доказывает,
что произвольный внешний сервер/провайдер пропускает ICMP или IP-фрагменты.
Потери и переупорядочивание фрагментов отдельно не моделируются.

## Результат 2026-10-04

`/var/tmp/meshpn-usb-e2e-NDK3kV/report.json`: **passed**, 117 общих проверок
и все 62 UDP-сценария. Boot ID `6b5ee7ad-6058-47dd-92a1-98073f61e745`.
Текущий валидатор повторно принял отчёт; sync/unmount/poweroff подтверждены.
Все 411 хешей включённых исходников совпали с рабочей копией.
Производственный VPN/installer из `5a0852c` не менялся.

- Payload до 4096 байт доставлен побайтно в обе стороны с разрешённой
  фрагментацией, отдельно для host и forwarded USB.
- Слишком большие DF-запросы вернули локальный `EMSGSIZE` или сетевой
  ICMP 3/4 с MTU 1400/1500, в зависимости от места ограничения.
  Слишком большой DF-ответ вернул origin ICMP с MTU 1400.
- Более узкий путь после exit вернул host и USB-клиенту ICMP 3/4 с MTU 1280
  и правильным ID исходной пробы. Payload 1252 прошёл с DF; 4096 — с фрагментацией.
- Первый UDP после подтверждённого закрытия outer TCP/TLS прошёл без HTTPS-разогрева.
- При остановленном VPN шесть размеров не достигли origin; SSH:22/2222 работал.
  После запуска VPN снова прошёл обмен 4096/4096.
- Суммарный прирост `FragCreates` на host/exit/peer — 104, `ReasmOKs` — 37.

Предварительные отчёты `tpGh4N`, `NehQmw`, `pz4o0x` сохранены как этапы
разработки стенда. В них матрица была меньше либо «холодная» UDP-проба ещё
не подтверждала закрытие TLS; окончательная приёмка выше не опирается на это
предположение. Исправление production-кода по этой матрице не потребовалось.
Физические проверки остаются в [чек-листе](clean-vpn-radxa-next-checks.md).
