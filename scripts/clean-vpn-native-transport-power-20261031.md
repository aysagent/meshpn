# Radxa: выбор транспорта, восстановление запуска и питание

2026-10-31. Изменения `05a579d`, `e04b336`, `f3b0471` установлены на Radxa
штатным `admin/install.mjs --update`. Native ELF не менялся; endpoint — `443`.

## Что изменено

- Host-клиент с установленной combo-конфигурацией действительно переключается
  между `boring-tls` и `combo-tls`. В boring используется плоский packet config
  без HTTPS REDIRECT; в combo восстанавливается relay. Неактивная конфигурация
  сохраняется приватно, без экспорта ключей через API. Exit перезапускать не нужно.
- Config, network config и настройки broker применяются через журнал из трёх
  файлов. Старый network owner сначала завершает cleanup со своим прежним config.
  При ошибке восстанавливаются все три файла; при прерывании восстановление
  выполняется до новых изменений через API.
- Обнаруженная на плате гонка исправлена: `Type=exec` делал network unit active
  раньше подготовки TUN. Broker больше не запускает engine преждевременно;
  свежий owner запускает его после prepare, broker ожидает readiness.
- Админка показывает фазу/длительность операции. `connect_deadline` означает
  таймаут с повторной попыткой, а не подключённый VPN. Сохранение настроек
  сохраняет выбранный TLS-профиль, включая корректный внешний configured profile.
- «Устройство → Питание»: обе кнопки показывают отдельный браузерный confirm.
  Отмена не отправляет запрос. API дополнительно требует `confirm:true`,
  авторизацию и CSRF. Подтверждённая команда ставит обычный systemd reboot/poweroff
  с задержкой три секунды; контейнер и exit этих действий не предлагают.

Transparent-only и смена режима контейнера пока не реализованы.

## Приёмка

- Linux Podman: **86/86**, включая process death на семи границах журнала,
  rollback трёх файлов и асинхронную подготовку owner без раннего engine start.
- Реальный Chrome, локальный fixture: выбор режима, сохранение выбора при poll,
  отмена и подтверждение обеих команд питания. Принятые команды выполнялись
  только через fake RPC; настоящих power actions в этих тестах нет.
- Реальный Chrome с админкой Radxa: оба режима доступны; отмена обоих диалогов
  отправила **0** power requests. Настоящий API отклонил `confirm:false`
  для обоих действий с HTTP 409. Физического reboot/poweroff в этом прогоне нет.
- Первое переключение выявило гонку TUN и оставило recovery journal. После
  исправления обновлённый broker самостоятельно восстановил combo и очистил
  журнал. Ручное удаление journal не использовалось.
- Затем физически прошли combo → boring (**32,217 s**), boring → combo
  (**29,928 s**), combo → boring (**32,044 s**). Сохранён профиль
  `native-daily-installed.json`, guard активен, pending journal отсутствует.
- После перезапуска только broker engine остался `ready`, PID **38831**
  сохранился. Selector по-прежнему предлагает оба режима. В boring network config
  не содержит `combo_redirect`, правил `CVPN-CT-` нет.
- VPS exit сохранил PID **831794**; переключения клиента его не перезапускали.
- Отдельный Chrome 156 через процессный USB proxy завершил настоящий Speedtest
  в boring: **40,64 / 44,91 Мбит/с**, ping **86 ms**. Это функциональный WAN
  прогон, не сравнительный benchmark. Proxy ограничен 150 s и 512 MiB.
- После нагрузки restart через настоящий API занял **1,602 s**: engine вновь
  `ready`, PID **41511**, guard включён, pending journal отсутствует.
- После restart с USB прошли A/AAAA по UDP/TCP (**4/4**), HTTPS с обычной
  проверкой сертификата через exit (**3/3**) и download ровно **1 048 576 bytes**.

## Граница найденной причины

Начальный отказ reconnect нельзя целиком приписать гонке запуска. До изменения
конфигурации двухсторонний tcpdump показал TCP handshake, первую часть
ClientHello и потерю продолжения/ответных ACK между Radxa и VPS. Exit закрывал
неполученный ClientHello по таймауту. Причина потерь не установлена. Позднее
одноразовый discovery и служба с тем же сохранённым профилем заработали.
Профиль и проверка сертификатов для этого не отключались.

Отдельный следующий пункт: проверить часы при relay. Packet authentication имеет
значительно большее допустимое окно, чем relay token (±30 s), поэтому packet
`ready` сам по себе не доказывает пригодность часов для transparent-ветки.
В конце этого прогона Radxa сообщает `NTPSynchronized=yes`; механизм проверки
малого расхождения часов этим изменением не добавлялся.

Системные Wi-Fi, маршруты, DNS, proxy, часы и trust Mac не менялись. USB-проверки
используют только сокеты тестового процесса, привязанные к существующему `en9`.
