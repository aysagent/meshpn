# IPv6 в clean-vpn — план

Документ в репозитории: см. задачи и последовательность реализации. Обзор см. ниже.

**Обзор:** добавить полноценный IPv6 в clean-vpn — задача средней/большой сложности: общий фрейминг по транспортам уже «прозрачный байтовый поток», но бóльшая часть логики (валидация, маршруты, NAT, transparent-tls, native `SO_ORIGINAL_DST`) жёстко заточена под IPv4 и потребует параллельных IPv6-путей. **CLI:** флаги `-4`/`-6` (как curl) — по умолчанию оба стека, иначе только выбранное семейство для tun/маршрутов/NAT.

## Чеклист реализации

- [ ] **bridge-ipv6-validator:** валидация IPv6 и пропуск v6-кадров в `attachTunBridge` / обобщить `isIpv4Bridgeable`
- [ ] **routes-nat-v6:** split-default IPv6, exit `ip6tables` forward/NAT, адресация tun IPv6
- [ ] **ttl-v6-optional (фаза 2):** `ip6tables` REDIRECT transparent-tls + `originalDst` IPv6 в `tun_linux.cc`
- [ ] **cli-ip-family-flags:** парсинг `-4`/`-6` (и при необходимости длинные алиасы), прокидка в маршруты/NAT/мост/trans-tls; валидация комбинаций

---

## Насколько это сложно

**Кратко: не «только TUN и ip route»** — это был бы минимальный кусок. Реалистично это **промежуточная / крупная** фича: много разрознанных мест с явным IPv4 (см. ниже), плюс тестирование **каждого** используемого `--type`, NAT и corner cases (ICMPv6, PMTU, RA/ND на exit).

## Что уже «универсально» и что нет

### Почти общее для всех транспортов с TUN

Протокол данных по TCP/WebSocket/UDP/… — в документации и коде описан как **`uint32 BE (длина тела) + сырое содержимое`** ([шапка](clean-vpn.js), [`StreamFramer`](clean-vpn.js) ~3054+). По смыслу это **не привязано к IPv4**, пока оба конца согласны, что в теле — полный L3-пакет. Лимит **65535** ([`MAX_PKT`](clean-vpn.js)) покрывает типичные TUN-кадры (в т.ч. IPv6 до обычного MTU; экзотические jumbogram можно отложить).

То есть **не нужно заново изобретать транспорт «под каждый type»**, если этот type **только** гонит те же кадры через [`attachTunBridge`](clean-vpn.js): socket, http, tls/boring/combo TUN-часть, websocket, quic(quic-ext), webrtc-dc и т.д. — **один раз** расширив «что кладём в TUN / что читаем из TUN», остальная обвязка того же типа остаётся.

### Где обязательно трогать больше, чем «туннель»

1. **Фильтрация и валидация пакета**  
   Сейчас в мост явно пропускается только IPv4: [`isIpv4Bridgeable`](clean-vpn.js) (`version nibble === 4`, IHL, total length). Для IPv6 нужен отдельный путь проверки (минимум версия 6, длины payload, аккуратно с расширениями при MVP — можно начать с «простых» кадров без длинной цепочки расширений).

2. **Split-default и маршрутизация на client**  
   Сейчас — только IPv4: `0.0.0.0/1`, `128.0.0.0/1`, RFC1918 через uplink ([`setupClientRoutesAsync`](clean-vpn.js) ~3622+). Для IPv6 нужна **отдельная политика** (аналог сплита через **`::/1` и `8000::/1`**, или иной дизайн default) и **восстановление** при выходе. Это не косметика.

3. **Exit: форвардинг и NAT**  
   IPv4 NAT/MASQUERADE/forwarding в коде завязан на **iptables** и IPv4-адресацию пира ([`setupExitNat`](clean-vpn.js) и связанные вызовы). Для IPv6 нужны **`ip6tables`/nftables**, **MASQUERADE/forward** для `ip -6`, политика адресов на `tun` (ULA/глобалка, NDP), иначе трафик не уйдёт в интернет корректно.

4. **transparent-tls / combo-tls (перехват HTTPS)**  
   Сейчас — только **IPv4**: `iptables` REDIRECT/PREROUTING, и в native — только **`SO_ORIGINAL_DST` для AF_INET** ([`originalDstIpv4FromFd`](../native/tun_linux/tun_linux.cc)). Для IPv6 HTTPS на том же дизайне потребуется **ip6tables + отдельный API в addon** для оригинального dst **IPv6** (если вообще доступен так же через netfilter).

5. **LAN за клиентом (`--client-lan-subnet`)**  
   Сегодня только **IPv4 CIDR** и SNAT IPv4→туннель. Для IPv6 — отдельный префикс, **NDP**/**радиксы** при необходимости, **ip6tables** FORWARD/SNAT или NPT — отдельный блок работы.

6. **Вспомогательная логика**  
   ICMP echo reply для «локального» IP на TUN ([`tryBuildTunIcmpEchoReplyForLocalIp`](clean-vpn.js)) — сейчас под IPv4; для полного IPv6 нужен **ICMPv6** (RS/RA, neighbor — по политике).  
   **Keep-alive / lazy reconnect** в комментариях явно говорит, что **не-IPv4 с TUN не поднимает сессию** — это придётся пересмотреть, если хотите IPv6 default через туннель.

7. **Нативный TUN**  
   `IFF_TUN | IFF_NO_PI` уже отдаёт **сырые IP-пакеты**; с точки зрения драйвера IPv6 обычно не требует другого «типа» интерфейса, но **нужно правильно выставить IPv6-адреса на интерфейсе** и маршруты (сейчас в коде в основном IPv4 point-to-point картинка).

## Ответ на вопрос «все ли транспорты дотюнивать»

| Уровень | Нужно ли трогать каждый `--type` отдельно? |
|--------|---------------------------------------------|
| Фрейминг `uint32+L3` для типов, которые только гонят TUN через общий мост | **Нет** — достаточно единого изменения «bridge принимает/отдаёт и v4 и v6», если нет type-специфичной фильтрации L3. |
| Маршруты, NAT, LAN, split-default | **Да**, и это **общее** для почти всех сценариев с default через tun. |
| transparent-tls / combo-tls перехват | **Да**, отдельно и тяжелее остального. |
| TLS mux / HTTP/2 Bearer / QUIC ALPN | **Скорее нет** для «голого» переноса IPv6 внутри уже установленного туннеля — пока не смешиваете семейства в одном нестандартном кадре. |

## Практичная последовательность (если делать)

1. Модель данных: второй префикс/адреса на tun, валидатор **IPv4 | IPv6**, обновить drop-логику в мосту; **учёт флагов `-4`/`-6`** (какой трафик форвардить и какие маршруты ставить).
2. Маршрутизация client **IPv6 default** (или opt-in флаг); **split v4/v6** согласована с `-4`/`-6`.
3. Exit: forward + **ip6tables** MASQUERADE.
4. Опционально позже: **transparent-tls IPv6** (iptables + addon), LAN IPv6.

**Итого:** сложность **средняя+**; узкое место — не транспортные обёртки, а **политика IP (v6 routing/NAT)** и всё, что сейчас завязано на iptables/nat и `originalDst` только для IPv4.

## Проверка работы (после реализации)

Цель — убедиться, что **дефолт IPv6** реально уходит в туннель и возвращается, а не «бьёт» в uplink или ломается на NAT.

**На стороне client (после поднятия VPN и IPv6-маршрутов):**

- Маршрут к глобальному v6: `ip -6 route get 2001:4860:4860::8888` (или другой известный адрес) — в выводе должен быть **`dev tun*`** (или ожидаемая политика сплита), а не только `eth0`/`wlan0`.
- Внешний IPv6 «как у exit» (если выход в интернет через NATexit): **`curl -6 --max-time 10 https://ifconfig.co/ip`** или **`curl -6 https://api64.ipify.org`** — адрес должен совпадать с ожидаемым у **exit** (или с выданым префиксом, если без NAT).
- DNS по IPv6: **`curl -6 https://example.com`** — проверяет не только ICMP, а **TCP/443 по v6** (MTU/фрагментация на стороне туннеля).
- Пинг: **`ping6 -c 3 2001:4860:4860::8888`** — базовая проверка ICMPv6; если блокируется файрволом, опирайтесь на `curl -6`.

**На стороне exit:**

- **Форвардинг и masquerade**: `sysctl net.ipv6.conf.all.forwarding`, счётчики **`ip6tables -t nat -L -n -v`**, **`ip6tables -L FORWARD -n -v`** (пакеты растут при трафике с client).

**Низкоуровнево (отладка):**

- Снимок на **`tun`**: `tcpdump -ni tun0 ip6` на client или exit — видны **сырые IPv6** кадры в нужную сторону.
- Разделить проблемы «маршрут» vs «NAT» vs «транспорт»: если **`curl -4`** уже работает через тот же `--type`, а **`curl -6`** нет — чаще виноваты **маршруты v6 / ip6tables**, а не TLS/socket-слой.
- **Режимы `-4`/`-6`:** прогнать те же проверки с **`node ... clean-vpn.js ... -4`**, **`... -6`**, без флагов и с **`-4 -6`**: при только `-4` не должно быть рабочего default v6 через tun; при только `-6` — наоборот (после реализации v6).

**transparent-tls / HTTPS по IPv6 (если делали фазу 2):** отдельно **`curl -6 https://…`** с хоста за перехватом и проверка, что сессия уходит в CVPTX/relay, аналогично текущим проверкам для v4.

## CLI: `-4` / `-6` (как у curl)

**Цель:** на **любом** `--type` с TUN явно выбрать, какие **стеки IP поднимаются внутри VPN** (адреса/mаршруты/NAT/LAN-правила HTTPS-перехвата для соответствующего семейства). По умолчанию — **оба включены** (после того как IPv6 будет реализован).

**Семантика (предлагаемая):**

| Вызов | Поведение |
|--------|-----------|
| без флагов | **IPv4 + IPv6** (когда v6-логика появится): поднимаются оба набора маршрутов/адресации на `tun`, оба NAT на exit при необходимости, оба перехвата для transparent-tls при включённой фазе v6. |
| **`-4` только** | только **IPv4-ветка**: split-default и RFC1918-bypass только для v4; на exit только **iptables**/IPv4 NAT; на client в мост **не** ставить v6 default / **не** выдавать v6 на tun; кадры IPv6 с TUN можно **отбрасывать** в мосту (или не конфигурировать v6 вообще). Перехват HTTPS — только **ipv4**-цепочки. |
| **`-6` только** | зеркально: только **IPv6** (маршруты `::/1`+…, `ip6tables`, адреса на tun, без v4 split-default). IPv4-кадры в мосту отбрасывать / v4 на tun не поднимать. **Осторожно:** до появления v6 полностью такой режим для многих сценариев бесполезен; флаг нужен для тестов и «чистого v6». |
| **`-4` и `-6` вместе** | явное «оба» — эквивалент **отсутствия флагов** (как у `curl`: `-4 -6` = оба семейства разрешены). |

**Парсинг:** короткие **`-4`** и **`-6`** как отдельные argv (аналогично curl). Опционально в документации длинные форматы `--ip4-only` / `--ip6-only` если нужно избежать путаницы с «числовыми» флагами в других инструментах — но primary UX как у curl.

**Границы действия флагов:**

- Затрагивают **policy семейства для туннелируемого трафика и интерфейса tun**, не обязательно **семейство TCP/TLS к `--server`** (подключение к VPS может оставаться тем, что даёт DNS/система — отдельная тема, при желании позже `-4`/`-6` для **bootstrap** соединения).

- **Проверка:** с **`-4` только** — `curl -4` через VPN должен работать, `curl -6` — не должен уходить в туннель (или не должно быть v6-маршрута). С **`-6` только** — наоборот.

- **Конфликты:** только `-6` при конфиге, который сейчас **только IPv4** (напр. старый сценарий до реализации v6) — явная ошибка или предупреждение в `parseArgs`.
