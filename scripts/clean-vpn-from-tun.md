# Шлюз только для входящего интерфейса: `--from-tun`

Новый opt-in режим clean-vpn client, пока для контролируемого пилота. Пример: устройства подключены к WireGuard `wg0`, а их внешний IPv4 нужно отправлять через clean-vpn на другой exit. Сам шлюз и устройства на других интерфейсах сохраняют прежнюю маршрутизацию.

```bash
sudo env "PATH=$PATH" node scripts/clean-vpn.js \
  --role=client --type=tls --server=203.0.113.10:443 --from-tun=wg0 \
  --tls-cert-dir=/etc/clean-vpn/trust \
  --shared-hmac-key=/etc/clean-vpn/clean-vpn-hmac.key \
  --tls-server-name=vpn.example.com --tls-client-sni=vpn.example.com
```

Адрес, домен и пути заменить своими; подготовка CA/PSK/exit — в README. Exit не требует новой опции. Это **не** подключение native helper к существующему `/dev/net/tun`: ядро пересылает пакеты из входного интерфейса в отдельный TUN clean-vpn. Поддерживаются также другие L3-интерфейсы, не только WireGuard.

## Условия и область действия

- Только `--role=client`, один экземпляр этого режима в network namespace. Нельзя сочетать с `--split-default`, `--client-lan-subnet`, `--transparent-tls-lan-bind`. Для transparent/combo нельзя задавать тестовый фиксированный `--tunnel-peer`.
- Уже работающий шлюз: входной интерфейс существует и UP, `net.ipv4.ip_forward=1`, корректные обратные маршруты к peer-адресам и WireGuard AllowedIPs. Опция не настраивает WireGuard, его ключи, маршруты на устройствах и глобальный forwarding. Нужны root/CAP_NET_ADMIN, `ip`, `iptables`, `ip6tables`, `sysctl`, обычные зависимости clean-vpn.
- Первый пилот запускать напрямую через CLI. Существующий systemd-установщик добавляет собственный host kill-switch; его совместимость с ingress-only режимом отдельно не проверена, автоматически комбинировать их нельзя.
- Выделяются IPv4 table **19999**, rule priority **10999**, цепочки **CVPN-INGRESS** и **CVPN-INGRESS-HTTPS**. Занятые ресурсы и ранние нестандартные policy rules приводят к отказу запуска, а не перезаписи. При сложной существующей policy routing нужна отдельная проверка.
- Только пакеты **пришедшие через интерфейс**, а не все пакеты с похожим source IP. Локальный процесс с bind на адрес wg0 всё ещё является процессом хоста и не выбирается этим режимом.
- Основная таблица, host `OUTPUT`, DNS хоста и глобальный `rp_filter` не меняются. На входном и собственном TUN интерфейсах временно устанавливается loose `rp_filter=2`. FORWARD-разрешения для выбранного входа/TUN вставляются перед существующими правилами; это явное разрешение его VPN-пересылки, не сохранение прежних ограничений FORWARD для этих потоков.
- TUN-путь выполняет SNAT в `10.99.0.2`, потому что exit ожидает этот адрес. Раздельная идентичность peer-адресов на exit не сохраняется. MTU/PMTU для вложенного WireGuard нужно проверить на реальной сети.
- Фиксированные `10.99.0.1/10.99.0.2` должны быть свободны от других назначений на этом клиенте. Одновременный clean-vpn exit+client в одном network namespace этим режимом не решён; для такого VPS нужна отдельная схема изоляции и проверка маршрутов.

## Что считается внешним трафиком

В туннель идёт внешний IPv4, включая TCP, UDP/QUIC и прямые запросы к внешнему DNS. Исключены RFC1918, `100.64/10`, loopback, link-local, `0/8`, multicast/reserved `224/4`, `240/4`, а также непосредственно подключённые IPv4-префиксы из main на момент запуска. Для исключений остаётся существующая маршрутизация/firewall, они **не защищены** этим режимом. Сервисы самого шлюза также остаются локальными. Изменение LAN-маршрутов во время работы не обновляет снимок исключений автоматически.

IPv6 через clean-vpn не поддержан: **вся IPv6-пересылка из выбранного интерфейса блокируется**, включая межсетевой локальный IPv6. IPv6 самого хоста и других входных интерфейсов не меняется; IPv6 INPUT к локальным сервисам не блокируется этим режимом.

Если устройство использует DNS-прокси на самом шлюзе, дальнейшие запросы прокси — это уже host OUTPUT: они не становятся туннельными от одного `--from-tun`. Аналогично DNS на исключённом LAN-адресе идёт прежним путём. Настройка защищённого DNS для устройств — отдельная задача; эта опция не является системной DNS-интеграцией и не исправляет DNS автоматически.

## Транспорты

Выбор входа общий для транспортов и не меняет их шифрование/авторизацию. Начинать с `tls`; `boring-tls` требует собранного helper. `combo-tls` остаётся пилотным, самостоятельный `transparent-tls` не становится безопасным full VPN.

Для combo/transparent внешний **TCP/443** из выбранного входа перенаправляется через PREROUTING на relay, слушающий собственный TUN IPv4. HTTPS самого хоста не перехватывается. Приём на relay разрешён только для соответствующего DNAT из выбранного интерфейса; прямой доступ к его порту закрыт. UDP/443 не является TLS-over-TCP и идёт обычным TUN-путём. Остальные транспорты используют только общую TUN-ветку.

## Обрыв, остановка и восстановление

- При разрыве транспорта активные маршруты остаются на TUN: обычного uplink fallback нет. При исчезновении TUN в отдельной таблице остаётся `unreachable default`; scoped FORWARD guard дополнительно запрещает внешний IPv4 мимо TUN. IPv6 guard остаётся.
- **Без `--from-tun-restart-safe` штатные SIGINT/SIGTERM** снимают установленные правила/маршруты и восстанавливают сохранённые per-interface rp_filter. Тем самым намеренная остановка **возвращает прежний прямой forwarding**, если он был настроен. Это не постоянный firewall kill-switch после отключения VPN.
- При аварийном завершении после успешной установки routing, включая SIGKILL, guard/rules сохраняются. При обработанном fatal error скрипт также оставляет их. Новый запуск без restart-safe отказывается присваивать оставшееся состояние: сначала нужен явный recovery из журнала. После перезагрузки неперсистентные правила исчезнут: защита до автозапуска/после reboot в этой версии не предоставляется.
- Ошибка установки откатывает успешно сделанные изменения; если очистка сама не удалась, она останавливается до удаления оставшихся защитных правил и сообщает об ошибке. Не запускайте второй экземпляр поверх такого состояния.

### Восстановление из журнала

Новые запуски `--from-tun` автоматически сохраняют журнал в `/run/clean-vpn-ingress-NETNS/journal.json` (NETNS — номер network namespace). Каталог имеет права `0700`, файл — `0600`. Нужен `flock` из util-linux. Можно выбрать существующий доверенный родительский каталог через `--from-tun-state-dir=/absolute/path`; сам каталог создаётся, symlink-компоненты запрещены. При recovery тогда требуется тот же `--state-dir=/absolute/path`. Системный namespace-lock остаётся общим и при разных путях журналов.

Сохраняются исходные `rp_filter` обоих интерфейсов, их идентификаторы, исключения маршрутизации и прогресс установки. Перед каждой командой записывается намерение с `fsync` и атомарной заменой журнала. Это **не снимок всего firewall**, DNS или всех sysctl: снимаются только изменения этого режима. TUN, созданный процессом, исчезает при его завершении.

После аварии остановите поступление трафика (`wg0`/его peers), если прямой выход недопустим. В том же network/user namespace и от того же пользователя (обычно root):

```bash
# Проверить журнал и текущее состояние; сетевые настройки не меняются.
sudo node scripts/clean-vpn-recover.mjs --from-tun=wg0

# Вернуть состояние ДО запуска VPN — прежний прямой forwarding также вернётся!
sudo node scripts/clean-vpn-recover.mjs --from-tun=wg0 --apply

# После этого можно запустить client обычной командой с --from-tun=wg0.
```

Проверка без `--apply` может создать каталог/lock-файл, но не меняет сеть. Живой владелец блокирует recovery через process-lifetime flock. Чужие правила в наших цепочках/таблице, изменённый `rp_filter`, подменённый интерфейс, повреждённый журнал или другая загрузка/namespace приводят к отказу. Чужие правила вне нашей области не снимаются. Исчезнувший TUN и уже удалённые наши правила допустимы; повторный recovery безопасен. Если само восстановление оборвалось, повторите ту же команду: прогресс также сохраняется. Не изменяйте firewall/интерфейсы параллельно с установкой/восстановлением: flock координирует clean-vpn, а не сторонние менеджеры.

Успешное завершение помечает журнал `released`; следующий запуск обновляет его. Не удаляйте журнал или lock-файл работающего/аварийного экземпляра вручную. Временные `journal-*.tmp`, оставшиеся после аварии записи, не используются как источник восстановления.

Выполняйте recovery той же версией clean-vpn, которая создала журнал; перед обновлением завершите восстановление (без restart-safe достаточно штатной остановки). При этом возвращается прямой forwarding — заранее приостановите peers, если он недопустим. Этот механизм относится только к `--from-tun`, не к прежним маршрутам `--split-default`, настройкам exit или отдельному DNS backend.

Граница поддержки — **авария процесса в пределах одной загрузки**. `/run` очищается при reboot; изменённые здесь настройки ядра также непостоянны. Старый журнал в пользовательском постоянном каталоге не применяется к новой загрузке. Не сохраняйте временные `CVPN-INGRESS*`/`cvpn-hold-*` правила сторонним firewall-persistence сервисом: их восстановление после reboot без соответствующего журнала не поддержано. Постоянный boot kill-switch и установка systemd supervisor остаются отдельными задачами.

### Перезапуск без окна прямого выхода

Добавьте **ко всем запускам клиента** `--from-tun-restart-safe`:

```bash
sudo node scripts/clean-vpn.js --role=client --type=tls \
  --server=EXIT_IP:443 --from-tun=wg0 --from-tun-restart-safe \
  --tls-cert-dir=/path/to/certs --tls-server-name=vpn.example.com \
  --shared-hmac-key=/path/to/shared.key
```

Подставьте свои существующие TLS-параметры; флаг одинаков для транспортов и не повышает их безопасность/production-статус.

- SIGINT/SIGTERM теперь **паркует** клиент: под временным guard снимает его маршруты/перехват, восстанавливает исходные rp_filter и оставляет блокировку forwarding из `wg0` для IPv4/IPv6.
- Следующий запуск **той же команды** держит namespace-lock, проверяет журнал/интерфейсы, очищает остатки под guard и устанавливает новый TUN-путь. Незавершённый schema 1 журнал после аварии также можно принять с этим флагом; чужое состояние не присваивается.
- Временный guard снимается только после установки транспортных обработчиков/слушателей и проверки всего плана маршрутизации/перехвата. Для lazy-транспорта это не означает уже установленный handshake с exit: первые пакеты могут инициировать соединение. Недоступный exit не разрешает прямой uplink fallback.
- Во время парковки/перехода блокируется **вся пересылка из выбранного интерфейса, включая LAN**, и IPv4 INPUT с conntrack DNAT из него. Последнее не даёт старым HTTPS DNAT-записям попасть в посторонний локальный listener. Host OUTPUT, другие входы и обычные не-DNAT сервисы шлюза этим guard не блокируются.
- Это не сохранение TCP/TLS-сессий: соединения при рестарте оборвутся. Флаг не убивает живого владельца и не запускает новый процесс самостоятельно; сначала остановить текущий клиент, затем запустить команду снова. При неудачном повторном запуске ранее установленная блокировка остаётся. До первой успешной установки guard защиты нет.
- Для **полного отключения** после остановки: сначала dry-run `sudo node scripts/clean-vpn-recover.mjs --from-tun=wg0`, затем та же команда с `--apply` (и прежний `--state-dir`, если задавался). У припаркованного клиента `operations: 0` означает уже снятые основные маршруты, но `restartGuardOperations: 3` — оставшуюся защиту. Только explicit apply возвращает прежний прямой forwarding. Обычный запуск без restart-safe откажется присваивать припаркованный guard.

Первое включение этого режима не закрывает окно, которое уже возникло после остановки старого клиента **без** флага. Для такого перехода сначала приостановите трафик peers. Защита restart-safe действует в пределах текущей загрузки; не заменяет boot kill-switch и не настраивает DNS.

Для старых запусков до появления журнала автоматического восстановления нет: исходное значение `rp_filter` неизвестно. Для ручного read-only осмотра:

```bash
ip -4 rule show
ip -4 route show table 19999
iptables -S
iptables -t nat -S
ip6tables -S
```

Для legacy-состояния удалять только проверенные правила `clean-vpn-from-tun` и цепочки `CVPN-INGRESS*`, соответствующее `iif wg0 lookup 19999` и принадлежащие этому запуску маршруты table 19999. Не использовать общий `iptables -F` / сброс main. Исходный legacy `wg0.rp_filter` восстанавливать по собственной конфигурации, не угадывать. Новые правила маркируются уникальным `cvpn-TRANSACTION_ID`; recovery не присваивает чужие/старые правила.

## Проверки без сети хоста

```bash
npm run test:ingress-routing
npm run test:ingress-routing-real
npm run test:ingress-recovery-real
npm run test:ingress-restart-real
# Для реальных TUN и TLS CLI нужны /dev/net/tun, native addon и BoringSSL helper:
npm run test:ingress-transport-real
```

Unit-тесты проверяют валидацию, область правил, откат после отказа каждой команды. Реальный routing-стенд запускается в user/network/mount/PID namespaces без внешнего NIC; создаёт только внутренние veth и собственные TCP/UDP endpoints. Проверяет SNAT/обратный путь, host/other ingress, DNS-путь, IPv6, HTTPS DNAT, локальные сервисы, снятие правил и аварийный fail-closed. Его veth-next-hop моделирует TUN: это проверка настоящего Linux forwarding/firewall, **не** доказательство работы всех транспортов или TLS relay end-to-end.

Отдельный transport-стенд запускает настоящий CLI client+exit для `tls`, `boring-tls`, `transparent-tls`, `combo-tls` с реальным TUN, TLS приложения и проверкой сертификата. Если в окружении нет `/dev/net/tun`, используется VM без NIC/host shared filesystem:

```bash
node scripts/ingress-vm-lab.mjs \
  --tools=/absolute/path/to/verified-qemu-tools \
  --kernel=/boot/vmlinuz-MATCHING_LOCAL_RELEASE \
  --resolved=/absolute/path/to/systemd-resolved
```

Подготовка локального QEMU/busybox и проверяемых `.deb` — как в [DNS VM lab](dns-vm-lab.md); root-пакеты не устанавливаются. Здесь переиспользуется только упаковщик initramfs, DNS-жизненный цикл не запускается. Скопированы также собранные addon/helper и JS-зависимости CLI. Deadline VM — 30 минут (до 6 минут на транспорт с тремя запусками клиента); результат, serial log и хеши файлов сохраняются в отдельном временном каталоге. Для старых `.deb`, версии которых уже отсутствуют в локальном APT metadata, можно явно передать `--verified-report=/path/to/previous-passed-report.json`: тогда доверие опирается на **ваш ранее проверенный локальный отчёт**, и все SHA256 пакетов должны совпасть. Автоматического пропуска проверки нет.

В restart-тесте IPv4/IPv6-пробы отправляются каждые 5 мс, принимающая сторона считает их без ответного UDP-трафика. Ненулевой счётчик на обычном uplink означает провал. Это проверка пути и утечек, не benchmark: в TCG-VM бюджет отдельного TLS-запроса — 12 секунд (прочих запросов — 4 секунды), чтобы учитывать инициализацию TLS и работу эмулятора под пробами. На ошибке сохраняются стадия соединения и время ожидания; неуспешный запрос не заменяется успешным повтором.

Стенд моделирует вход `wg0` через veth; настройка настоящего WireGuard/AllowedIPs и пилот на Radxa/VPS остаются отдельной проверкой. Ни проверка маршрутов, ни TLS smoke не повышают статус экспериментальных транспортов до production.
