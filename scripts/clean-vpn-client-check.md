# Одна команда для проверки уже запущенного client

`clean-vpn-client-check.mjs` проверяет **сам host-client**, не устройства за
Radxa и не ingress `--from-tun`. Client и exit пользователь запускает/останавливает
сам. Проверка не меняет маршруты, firewall, sysctl или настройки DNS, не запускает
recovery и не читает ключи/аргументы VPN-процесса.

## Запуск

Нужны Linux, Node, `ip`, `curl` с системными CA, `dig`, `getent` и уже работающий
client. Для обычного внешнего IPv4 в команде **client** нужен `--split-default`.
Предыдущие DNS smoke без этого флага проверяли DNS, а не весь интернет через VPN.

**Сначала Radxa через локальную консоль/USB/LAN.** На VPS, доступном только через
публичный SSH, не включать `--split-default` без независимого доступа: смена
обратного маршрута может оборвать SSH. Скрипт не настраивает исключение для SSH.
IPv6 этим IPv4-туннелем не защищается.

Для текущей пары exit `s` / client Radxa: оставить прежний exit, а к прежней
команде client добавить `--split-default`. Не запускать одновременно второй
client с теми же туннельными адресами на одном exit.

После установления VPN во **втором терминале client**, из корня репозитория:

```bash
sudo env "PATH=$PATH" node scripts/clean-vpn-client-check.mjs --probe --expect-exit-ip=154.62.226.216
```

Скопировать **весь вывод между BEGIN и END**, включая итоговый `status`. Никаких
дополнительных файлов вручную собирать не нужно. Отчёт содержит IP и маршруты;
он не содержит ключей, Bearer, тел HTTP-ответов или журналов служб.

`--expect-exit-ip` — ожидаемый **публичный исходящий IPv4 exit**, а не обязательно
адрес его входящего интерфейса (если exit находится за NAT). Для другого TUN
добавить `--tun=имя`. Без `--probe` — только снимок, без DNS/HTTP-запросов.
Можно использовать `npm run check:client -- --probe --expect-exit-ip=...`, но
для interface binding curl могут потребоваться права root.

## Что проверяется

1. Наличие поднятого TUN с IPv4, policy rules и маршруты IPv4/IPv6.
2. Маршруты к контрольным внешним IPv4 через TUN. Без них сетевые пробы
   пропускаются с `skipped-no-confirmed-host-tunnel-route`, а не дают ложный PASS.
3. Системный NSS и DNS A/AAAA по UDP/TCP. Кешированный ответ допустим: это
   проверка работоспособности, **не доказательство отсутствия DNS-утечки**.
4. Два отдельных HTTPS-запроса к `https://1.1.1.1/cdn-cgi/trace`: проверка
   сертификата, адреса соединения, исходного TUN-адреса и ожидаемого внешнего IP.
5. HTTPS-загрузка ровно 1 MiB с `speed.cloudflare.com`, с заранее разрешённым
   публичным IPv4 и повторной проверкой маршрута до/после запроса.

HTTP-запросы привязаны к TUN; proxy-переменные и `.curlrc` не используются,
редиректы не следуются, TLS-проверка не отключается. DNS-пробы используют
текущий resolver и сами по себе могут пойти напрямую. Общий deadline 90 секунд
(завершение дочернего процесса может добавить до 5 секунд), отдельный curl —
20 секунд. Загрузка ограничена 128 KiB/s, поэтому результат **не speedtest**.
Отправляются только служебные запросы, пользовательские файлы не загружаются.
Ctrl+C прерывает только проверку; уже запущенный VPN остаётся работать.

## Как читать итог

- `ipv4-smoke-passed`: перечисленные IPv4-пробы успешны, внешний IP совпал.
- `incomplete-or-failed`: смотреть `checks` и `probes`; отсутствующий curl,
  неверный IP, ошибка TLS/DNS, неполная загрузка или смена маршрута не дают PASS.
- `inspection-only`: пробы не запрашивались; не результат полноценной проверки.
- `aborted`: сработал deadline или сигнал; не PASS.

`checks.ipv6=direct-route-present-review-required` означает наличие прямого
IPv6-маршрута. Это предупреждение, не доказательство фактической утечки: firewall
этим скриптом не проверяется. Даже `ipv4-smoke-passed` **не** означает готовность
всего VPN, отсутствие утечек, защиту при падении туннеля, проверку загруженных
ключей/шифрования VPN, работоспособность LAN-клиентов, upload или долгих сессий.
Доступность внешних контрольных сервисов тоже влияет на результат.

## Локальные тесты

Живой отчёт Radxa от 2026-09-29 на `5478fcc`: IPv4 smoke успешен, оба HTTPS
показали exit `154.62.226.216`, загрузка 1 MiB полная, DNS A/AAAA UDP/TCP работает.
IPv6 имеет прямой маршрут через wlan0; это ещё не проверка фактического обхода.
Следующий шаг: [DNS capture и IPv6-проба одной командой](clean-vpn-client-leak-check.md).

`npm run test:client-check`: фикстуры маршрутов/ошибок/отмены и настоящий curl
с локальным HTTPS-сервером (доверенный/недоверенный сертификат и 1 MiB).
Loopback-тест проверяет curl-контракт, **не заменяет тест настоящего VPN**.
Скрипт также проверен на машине без TUN: отказ от сетевых проб, exit code 1.

Справка: [опции curl](https://curl.se/docs/manpage.html),
[официальный клиент Cloudflare Speedtest и его download API](https://github.com/cloudflare/speedtest).
