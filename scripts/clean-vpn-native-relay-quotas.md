# Native transparent/combo: квоты relay и ёмкость exit

Продолжение [multi-client проверки](clean-vpn-native-combo-provisioning.md).
Работа локальная: выделенная Linux Podman VM на Mac, вложенный Docker без внешнего
сетевого интерфейса. Radxa/VPS и сеть Mac не меняются.

## Что ограничивается

Один slot — одна активная пересылка HTTPS-соединения: входящий сокет, исходящий
сокет, один worker thread и две ограниченные очереди. Это не клиент, HTTP-запрос
или вкладка браузера. HTTP/2 может обслуживать несколько запросов внутри одного TLS.

Exit применяет два ограничения после проверки ключа, перед connect к origin:

- `sessions`: общий предел авторизованных relay-сессий, по умолчанию **128**;
- `per_client`: предел на один relay-ключ, по умолчанию **64**.

Допустимо `2 <= sessions <= 256`, `1 <= per_client < sessions`.
Один ключ не может занять весь общий предел. Несколько клиентов вместе могут его
заполнить; свободное место каждому постоянно не резервируется. Это ограничение
занятых мест, а не гарантированная полоса пропускания или планировщик запросов.

Отдельно остаются максимум 16 ожидающих авторизации worker'ов и 32 новых admission
за секунду. Они не считаются свободными авторизованными слотами. Медленные и
неавторизованные подключения могут временно исчерпать этот предварительный лимит:
квота ключа не заменяет защиту от сетевого DoS. Пакетная ветка combo продолжает
работать независимо от занятой relay-квоты; новые packet handshakes используют
общий входной admission gate.

## Идентичности и replay

Генератор теперь создаёт **отдельные packet PSK и relay PSK каждому клиенту**.
На exit вместо общего `secret_path` используется массив `peers` (до 32):

```json
{
  "peers": [
    {"id": "client-1", "secret_path": "/config/relay-1.psk"},
    {"id": "client-2", "secret_path": "/config/relay-2.psk"}
  ],
  "limits": {"sessions": 128, "per_client": 64},
  "replay_directory": "/replay/state"
}
```

Это фрагмент `transparent`-конфигурации, не полный файл engine.
Client сохраняет собственный `secret_path`; peer ID не берётся из недоверенного
поля запроса или source IP. Exit проверяет существующий n1 AEAD token против
ограниченного key-ring. Формат ClientHello/n1 и JA3/JA4 из-за квот не меняются;
новый постоянный идентификатор в SNI не добавляется. При успешной AEAD-проверке
выбирается квота, затем обязательно проверяются binding ClientHello, destination,
время и durable replay. Ошибка освобождает временную квоту; connect разрешается
только после всех проверок. Повторяющиеся ключи на exit запрещены.

Копирование одного клиентского ключа на несколько устройств даёт им **одну общую
квоту**, даже при разных IP. Разные ключи имеют отдельные квоты независимо от NAT.
`id` — локальное имя каталога replay, не доказательство идентичности на проводе.

При явном первом `--init-transparent-replay` под существующим private root
создаются каталоги `/replay/state/client-1`, `/replay/state/client-2` и отдельные
durable journals. Повторная инициализация запрещена; missing/corrupt state не
восстанавливается автоматически. Незавершённая первичная инициализация остаётся
для разбора, без скрытого reset. Перезапуск сохраняет состояние каждого ключа.
Удаление peer из конфигурации и перезапуск exit отзывает его доступ; остальные
journals сохраняются. Для нового ключа требуется новое имя/состояние, нельзя
подменять ключ существующего журнала или очищать replay ради запуска.

Старый single-key формат работает как одна идентичность с общей для всех копий
ключа квотой. Он не получает независимых клиентов автоматически. Существующие
комплекты не переписываются: для новой схемы создать отдельный новый bundle и
replay volume. Не переносить старый общий журнал в каталоги новых ключей.

## Создание и настройка

```bash
node scripts/clean-vpn-native-runtime-config.mjs create \
  --directory=/absolute/new/combo-bundle --mode=container \
  --transport=combo-tls --endpoint=192.0.2.10 --exit-address=172.30.77.2 \
  --port=3443 --server-name=vpn.example.net --public-name=relay.example \
  --clients=4 --relay-sessions=128 --relay-per-client=64
```

Адреса заменить. `--check-config` на целевом engine остаётся обязательным.
Изменение лимитов вступает в силу после перезапуска. При полной личной квоте
active relay health этого клиента тоже может вернуть unhealthy; это readiness,
а не основание автоматически перезапускать живой engine. Для standalone transparent
используются те же `limits` и `peers` в его собственном engine JSON.

Каждая relay-очередь ограничена 256 KiB вместо прежнего 1 MiB; чтение приостанавливается
до её переполнения. TCP-буферы ядра учитываются отдельно: RSS процесса не равен
полному расходу памяти VPN. Контейнерный launcher задаёт для combo memory ceiling
`128 + 3 * sessions` MiB и PID ceiling `64 + sessions`, вместо прежних фиксированных
256 MiB/128 PID. Это верхний предел cgroup, не предварительное выделение RAM и не
гарантия пригодности машины с меньшим объёмом памяти. ОС, остальные сервисы,
клиенты, origin и Docker daemon требуют дополнительной памяти.

## Воспроизводимая проверка

```bash
CVPN_CONTAINER_COMMAND='["docker"]' \
CVPN_RUNTIME_IMAGE=localhost/clean-vpn-native-runtime:quota-v2-20261029 \
CVPN_MULTI_CLIENTS=4 CVPN_MULTI_SECONDS=15 \
CVPN_RELAY_SESSIONS=128 CVPN_RELAY_PER_CLIENT=64 CVPN_MULTI_CAPACITY=1 \
node scripts/clean-vpn-native-multi-client-lab.mjs /tmp/relay-capacity128.json
```

Только выделенный Linux engine. Стенд генерирует ключи, запускает четыре client
namespace и один exit, проверяет HTTPS и packet/DNS под совместной нагрузкой.
Затем один клиент занимает всю личную квоту: его новое соединение отклоняется,
а остальные обязаны завершить по 8/8 relay и packet транзакций без отказов.

В capacity-режиме все клиенты вместе заполняют общий предел HTTPS-соединениями
и прекращают читать тела ответов. Проверяются реальные worker/FD counts,
RSS, память cgroup, CPU ticks, отказ сверх общего предела, сохранение packet ветки,
освобождение FD/threads и работа без перезапуска после снятия давления.
Это ограниченный stress-тест, не измерение максимальной пропускной способности
и не длительная эксплуатация на Radxa/VPS. Не трактовать паузу чтения как типичную
нагрузку браузера или RSS после освобождения как обязательный возврат к одному байту.


## Результат локальной приёмки 2026-10-29

| Общий предел / на ключ | Peak RSS engine, MiB | Память exit cgroup, MiB* | Exit threads | FD |
|---|---:|---:|---:|---:|
| 64 / 32 | 19.6 | 155.4 | 66 | 145 |
| **128 / 64** | **31.9** | **205.0** | **130** | **273** |
| 256 / 64 | 55.5 | 260.4 | 258 | 529 |

\* `memory.current` измерен в конце интервала заполненного общего лимита, не
является максимумом за весь запуск. RSS — максимум из samples за этот интервал.
Нагрузки шли отдельными прогонами; kernel buffers/page cache не обязаны расти
линейно. В сценарии остановленного чтения на 128/256 сессиях engine использовал
0.39/1.03 CPU seconds за 21.0/23.2 seconds наблюдения соответственно. Это не
предел CPU при активной передаче и не обещание throughput на физическом VPS.

Во всех трёх прогонах остальные клиенты завершили по **8/8 relay и 8/8 packet**
транзакций, пока первый удерживал всю личную квоту. После заполнения общего
предела новые relay отвергались, packet продолжал работать. После освобождения
нагрузки FD/threads вернулись к baseline, engine PID не менялся, SIGTERM чистый.

Выбор **128/64** даёт восьмикратный общий запас относительно прежних 16 и оставляет
половину slots другим ключам при одном активном клиенте. 256 успешно проверено,
но модель пока thread-per-session; рост до тысяч без изменения native reactor
не предлагается. Для физического узла это стартовая настройка с последующим
контролем памяти/CPU, а не универсально оптимальное значение.

Проверки: 26/26 JS unit, 12/12 CTest, новые quota + существующие fault проверки
под ASAN/UBSAN, TLS 1.2/1.3-HRR socket regression, медленный consumer на 8 MiB,
17/17 combo lifecycle/active health. Отдельный socket-тест подтвердил разные
квоты для ключей с одинаковым source IPv4; полноценная NAT-топология в этом
тесте не моделировалась. Независимый pcap: один packet-profile match и четыре
relay JA3/JA4 matches. Это проверка ClientHello, не полной неотличимости браузера.

64/128 capacity использовали промежуточные сборки, 256 и lifecycle — финальную.
Последняя правка между 128 и 256 сохраняла прежний предел fixture listener без
key-ring; production admission не изменялся. Сборки, границы и hashes указаны
в [машиночитаемом отчёте](../fixtures/clean-vpn-native-relay-quotas-20261029.json).
Следующая проверка — более длительная mixed нагрузка с новыми квотами и churn;
отдельно измерять влияние уменьшенных очередей на throughput/задержку.
