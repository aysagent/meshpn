# DNS на внешнем интерфейсе и прямой IPv6: одна команда

Следующая проверка после успешного [IPv4 smoke](clean-vpn-client-check.md).
Client/exit уже работают; скрипт **не** запускает/останавливает VPN, не меняет
DNS, маршруты, firewall, sysctl или кеши. Только host-client, не LAN-клиенты.

На Radxa, с прежним работающим client `--split-default`, из корня репозитория:

```bash
sudo env "PATH=$PATH" node scripts/clean-vpn-client-leak-check.mjs --probe --exit-ip=154.62.226.216
```

Нужны `tcpdump`, `ip`, `dig`, `curl`, Node и root для захвата. Если tcpdump
отсутствует, отчёт сообщит `tcpdump-required-no-probes-sent`: сетевые пробы не
начнутся. Для Debian/Ubuntu его можно отдельно установить командой
`sudo apt-get install tcpdump`; сам скрипт ничего не устанавливает.
`--exit-ip` — IPv4 сервера из команды VPN client, по его маршруту определяется
uplink; это не параметр ожидаемого исходящего адреса из предыдущего smoke.
`--tun=имя` необязателен, по умолчанию `tun0`.

Скопировать весь блок `CLEAN-VPN CLIENT LEAK CHECK BEGIN … END`.
Обычно проверка занимает несколько секунд; общий deadline 65 секунд плюс
ограниченное завершение subprocess, ориентир до 85 секунд. Ctrl+C отменяет
только проверку. Не выполнять параллельно с остановкой VPN или сменой сети.
Без `--probe` только снимок маршрутов, без capture/DNS/HTTPS.

## Что именно отправляется и собирается

- Восемь свежих случайных имён `cv-….example.com`: A/AAAA, UDP/TCP через системный
  DNS и явно `@1.1.1.1`. Ответ NXDOMAIN допустим — имя служит меткой запроса.
- На TUN и одном обнаруженном uplink одновременно запускается ограниченный
  исходящий capture: обычный UDP/TCP DNS port 53; на uplink также метаданные
  TCP/443 к exit и фиксированному IPv6 endpoint. Promiscuous mode не включается.
- При прямом маршруте IPv6 через тот же uplink выполняется HTTPS к
  `cloudflare-dns.com`, с фиксированным адресом `2606:4700:4700::1111`, без
  proxy, redirect, принудительной привязки к интерфейсу или отключения TLS-проверки.
  **Это намеренная проверка возможного выхода вне IPv4 VPN:** сервис может увидеть
  настоящий публичный IPv6 клиента. Никаких пользовательских файлов/ключей не отправляем.

Текст tcpdump ограничен памятью 512 KiB на процесс и не сохраняется в файл.
В отчёт идут только счётчики и совпадения с нашими случайными именами, не чужие
DNS-имена, raw packets, HTTP-body, ключи или аргументы VPN-процессов. IP и
интерфейсы присутствуют в отчёте.

## Интерпретация

`dnsObservation`:

- `probe-DNS-on-uplink`: собственные контрольные DNS-имена видны открыто на uplink.
- `other-port53-traffic-on-uplink-review`: исходящие пакеты port 53 видны, но наши
  имена в них не распознаны. Это может быть фоновый DNS или неполное декодирование;
  не приписываем трафик конкретному процессу.
- `probes-seen-on-TUN-not-on-uplink`: все восемь запросов получили ответы и
  наблюдались на TUN, на uplink port 53 не обнаружен. Требуются завершившиеся
  захваты без потерь, положительная активность uplink и стабильные контрольные
  маршруты. Это только результат данного окна наблюдения.
- `inconclusive`: нет достаточных данных (ошибка инструмента, кешированный/
  синтезированный отрицательный ответ без запроса на TUN, пропуски capture,
  смена маршрута и т. п.). Пустой/потерявший пакеты capture не считается PASS.

`ipv6.status=bypass-confirmed`: HTTPS действительно установился с IPv6 uplink,
сертификат прошёл проверку, маршрут до/после указывает тот же uplink.
`not-established` или `not-tested` **не доказывают блокировку**. Даже при
неудачном HTTPS счётчик `ipv6TargetOutboundPackets` может показать вышедшие SYN.

Общий результат намеренно не называется «утечек нет»: возможны
`bypass-or-uplink-traffic-observed` (код выхода 2), `inconclusive`/`aborted`
(код 1) или `inspection-only` (код 0). Скопировать отчёт надо при любом коде.
Это не аудит DoH/DoT, других интерфейсов, TCP reassembly/фрагментации, forwarded
peers или поведения при падении VPN. Следующий фикс выбирается по фактам отчёта;
этот инструмент сам ничего не блокирует.

## Проверки реализации

`npm run test:client-leaks` — ошибки, capture drops, смена маршрутов, отмена,
маскирование посторонних данных и классификация наблюдений.

Настоящий локальный capture UDP/TCP, остановка и отмена проверяются отдельно:

```bash
sudo env "PATH=$PATH" unshare --net node --test scripts/test-client-leak-capture-real.mjs
```

Тест отказывается менять сеть PID 1; поднимает только loopback в новом namespace.
Из-за направления loopback libpcap этот тест использует `inout`, тогда как
живой инструмент использует `out` на TUN/uplink. Это не тест настоящего VPN.

Справка по инструментам: [tcpdump](https://www.tcpdump.org/manpages/tcpdump.1.html),
[curl](https://curl.se/docs/manpage.html).
