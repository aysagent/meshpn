## Постоянный USB-режим

На `fc8c50d` пользователь подтвердил IPv4 HTTPS с Mac через `en9`:
после SNAT внешний адрес `154.62.226.216`. Добавлена
[интеграция rescue и SNAT в общий установщик](clean-vpn-usb-gateway.md).
Реальный reboot с новой SNAT-службой, forwarded DNS/IPv6 и повторный
Wi-Fi-outage тест пока не подтверждены. Rescue сохраняется при uninstall.

При расширении VM-проверки обнаружен обход plain DNS через разрешённый LAN:
старый `cvks2` пропускал USB-клиента к DNS роутера. Промежуточный DNS-only
`cvks3` прошёл 450 проверок в двух VM boot (`/var/tmp/meshpn-usb-e2e-4otg9r/report.json`).
По следующему запросу USB-профиль усилен до `cvks4`: любой forwarded USB IPv4
разрешён только в TUN, forwarded IPv6 запрещён, прямые LAN/exit-исключения
хоста не применяются к USB. `--dns-usb=1` перехватывает plain IPv4 DNS от USB
тем же runtime, что у платы. SSH:22/2222 к самой плате сохраняется.
Локальные прокси/SSH-forwarding на Radxa не изолируются по приложениям;
другими интерфейсами Mac эта установка не управляет. Результат v3 не является
приёмкой новой v4-политики.
Отдельная v4-проверка завершена 2026-10-03: 601 проверка (286 + 315),
два реальных boot, миграция и fresh install, stop/start, SSH:22/2222,
DNS и нестандартные TCP/UDP-порты. Отчёт
`/var/tmp/meshpn-usb-e2e-0zRsW7/report.json`: `passed`.
Дополнительно 362 регрессионных теста без ошибок/пропусков.
Это не заменяет отложенную проверку на физической Radxa.
Отдельный последующий SIGKILL-тест с настоящим systemd выявил отсутствие
автоматического recovery: `/var/tmp/meshpn-usb-e2e-mOJxum/report.json`, failed.
После аварии IPv4 journal остаётся active (6 маршрутов, rp_filter pending),
новые процессы отказываются продолжать. Проверенные обходы блокируются,
SSH:22/2222 сохранён. Прежние лабораторные SIGKILL-тесты ниже использовали
**явное** recovery и не доказывали автоматическое восстановление.
Независимый сетевой fault-прогон `/var/tmp/meshpn-usb-e2e-cEunQU/report.json`
прошёл сценарий 120-секундного exit blackhole с сохранением PID/NRestarts,
но завершился failed после carrier loss: DHCP восстановился, USB egress за
180 секунд — нет. Эти отчёты относятся к версии до исправления и не являются
успешной приёмкой. Это не физическая Wi-Fi-проверка.

Добавлены автоматическое восстановление собственных DNS/IPv6/IPv4-журналов
для проверенного USB-профиля (все три блокировки, аудит всех владельцев до первой
записи, строгий guard и отсутствие живого TUN обязательны) и периодическая
проверка uplink-маршрутов независимо от старого TCP-соединения. Старое соединение
закрывается при потере uplink, результат устаревшего TLS connect не принимается.
Следующий fault-прогон восстановил VPN, но выявил отложенную доставку USB UDP
к RFC1918 через exit после исчезновения LAN bypass-маршрутов. Добавлен DROP
USB → RFC1918 перед разрешением USB → TUN; локальные INPUT SSH/DNS не затронуты.
Актуальные результаты и сохранённые неудачные прогоны — в описании E2E-стенда.
Повторный полный аварийный прогон с последней правкой:
`/var/tmp/meshpn-usb-e2e-SqiBVY/report.json`, **passed**, 485 проверок,
SIGKILL + exit blackhole 120 с + carrier/DHCP loss 120 с. Все три восстановления
автоматические, guard/networkd/rescue не рестартовались, оба USB SSH сохранены,
итоговые получатели не зафиксировали прямого или LAN-обхода контрольных проб.
Все 403 хеша исходников совпали; отдельно 383 регрессионных теста прошли.
Тот же окончательный код прошёл и двухзагрузочную приёмку установки:
`/var/tmp/meshpn-usb-e2e-HAsqO4/report.json`, **passed**, 601 проверка (286 + 315),
с подтверждёнными reboot/poweroff и совпадением всех 403 хешей исходников.
Включены миграция, поздний DHCP, stop/start, uninstall и fresh install с сохранением
rescue. Последние два отчёта — актуальная лабораторная приёмка, не результат Radxa.
Для существующей установки есть отдельный проверяемый `--upgrade-usb-dns`,
без снятия guard и без рестарта networkd/USB. См.
[полный USB E2E стенд](clean-vpn-usb-e2e-lab.md) и чек-лист выше.

## Выявленные на Radxa проблемы Wi-Fi reconnect и USB-шлюза

После выключения/включения роутера Wi-Fi/DHCP вернулись (192.168.1.7,

предложен как временное восстановление. Прежняя лабораторная проверка обрыва
транспорта не покрывала удаление bypass-маршрутов сетевым менеджером при DHCP.

Добавлено узкое восстановление собственных uplink-маршрутов из активного журнала
перед повторным TLS-подключением. Проверяются прежние interface identity и
gateway; смена IP DHCP допустима, чужие маршруты не заменяются. Приёмка этой
правки реальным повторным отключением роутера остаётся незавершённой.

Отдельно Mac через en9: forwarding уже включён, но NAT есть только на wlan0,
не на tun0. Подготовлен [runtime-only USB SNAT](clean-vpn-usb-snat.md), без
изменения VPN service, guard или USB rescue. Это не постоянный USB-gateway
автозапуск и не полная приёмка forwarded DNS/IPv6. Позже пользователь подтвердил
HTTPS с Mac после применения SNAT (см. выше); прежние host smoke-тесты сами
по себе не доказывали работу USB-клиентов.

## Часы после длительного отключения питания

На реальной Radxa выявлен дополнительный boot-блокер: часы отставали примерно
на 22 часа, TLS проходил, но exit отвергал Bearer. После коррекции времени через

Добавлена [коррекция из HTTP Date проверенного exit](clean-vpn-http-date.md),
без UDP и изменений systemd/guard/USB. NIC-less VM проверила реальные переводы
часов при нескольких сдвигах, вплоть до года вперёд; 34 проверки прошли.
Сброс за пределы срока сертификата намеренно не обходит TLS-валидацию.
Восстановление часов из Date на Radxa ещё не подтверждено: в предоставленной
выборке журнала после обновления нет `clock-date`. Ранний capture уже получен,
его результат разобран ниже.

## Ближайшая граница готовности

Первый production-кандидат ограничен host-client, TLS/H2 поверх IPv4,
persist guard и systemd-networkd. IPv6 на реальном exit пока отсутствует:
на Radxa требуется блокировка прямого IPv6; полноценный IPv6 через exit
проверяется в VM и не является обязательным условием первой установки.

Критерии первого кандидата:

1. Интегрировать защиту с настоящими networkd **и networkd.socket**, проверить cold boot/reboot,
   позднюю сеть и отказ guard. Отдельно определить доступ через консоль при
   fail-closed отказе: SSH через выключенную сеть работать не будет.
2. Проверить install/update/uninstall с новой сетевой зависимостью; прежние
   успешные lifecycle-тесты её не покрывают.
3. Выполнить read-only preflight, согласовать установку и итоговый прогон на Radxa: запуск,
   DNS/HTTPS/внешний IPv4, отсутствие прямого IPv6, stop/restart и recovery.

Другие network managers, tied-mode, новые транспорты и широкая performance
матрица не включены в этот первый кандидат. Это перечень критериев, не обещание
срока: найденный дефект внутри обязательного этапа надо исправить до перехода
дальше. Успех отдельной трёхзагрузочной VM означает `lab-ready-for-host-review`,
но не production-приёмку Radxa. Её нельзя заменить лабораторным PASS.

## Три загрузки ядра и реальная зависимость networkd

Отдельный runner `scripts/clean-vpn-host-boot-lab.mjs` использует NIC-less QEMU,
собственный новый ext4-диск и один immutable initramfs. Он принимает шесть
обязательных абсолютных путей: `--tools`, `--kernel`, `--resolved`,
`--dns-conntrack`, `--dnsmasq`, `--verified-report`. Последний указывает прежний
успешный отчёт с хешами уже проверенных пакетов QEMU/busybox. Ничего не скачивается.
Это команда лаборатории, **не Radxa**.

Client находится в network namespace PID1, networkd использует штатные service
и netlink socket, работает настоящий udev без container marker. Виртуальный
Ethernet изначально выключен и не имеет адресов. DHCP выдаёт настоящий dnsmasq
в изолированном router namespace. Нет внешнего NIC или общей с хостом ФС.

Матрица вызывает настоящий `autostart/install.sh` с `NETWORKD_GUARD=1`, сохраняет
шесть его файлов на диск, затем загружает новое ядро и восстанавливает эти файлы
до запуска PID1. Это проверка сохранённых installed units/wrappers, не полного
дискового образа Armbian или initramfs конкретной платы. Две штатные перезагрузки
и финальный poweroff обязаны подтвердить sync/unmount; три boot ID различны.

- Первая загрузка: установка, реальная DHCP lease, DNS/HTTPS IPv4/IPv6 через exit,
  stop клиента и блокировка прямых тестовых запросов.
- Вторая: guard предшествует networkd, DHCP задержан до двух неудачных стартов
  клиента; затем автоматическое подключение без ручного recovery/restart.
- Третья: guard намеренно отказывает до установки правил; daemon/socket и VPN
  не стартуют, link остаётся down без адресов. После явного устранения fault
  выполняются подключение, stop, остановка guard с сохранением firewall,
  update на отдельную версию и чистый uninstall.
- Update сохраняет оба networkd drop-in и активный guard; новая версия сначала
  остановлена, затем явно запускается и проходит DNS/HTTPS-пробы через exit.
  Uninstall отсоединяет обе зависимости до снятия guard; networkd/socket остаются
  активными, обычные DNS/IPv4/IPv6 восстанавливаются.

Ранний вариант `2smSsd` выявил дополнительный дефект: зависимость только
`systemd-networkd.service` недостаточна для управляемой остановки guard.
После остановки daemon активный netlink socket мог инициировать новый старт,
а job остановки guard отменялся (`Job ... canceled`). Отчёт этого прогона
сохранён как FAILED; успешные первые две загрузки не скрывают отказ третьей.
Исправление добавляет ту же `Requires/After` зависимость для socket, без его
маскировки. Проверяются также отсутствие повторной активации после stop и
сохранение правил обеих семей IP. Это отличается от прежнего VM-only варианта
ниже, который снимал guard только после опускания link.

Подтверждённый прогон исправленного варианта:
`/var/tmp/meshpn-host-boot-s04xQb/report.json` — PASS, **81 утверждение**
(16 + 18 + 47), три разных boot ID, две штатные перезагрузки, итоговый poweroff,
sync и unmount во всех трёх случаях. Проверены настоящий installer, update,
uninstall и оба networkd drop-in. SHA-256 семи файлов реализации (installer,
gate, install-check, update, uninstall, boot driver и evidence validator)
сверены с `image-manifest.json`. Прототип `yBvvqn` с VM-only зависимостью не
используется вместо этого результата. Локальный регрессионный набор —
**381/381**, без пропусков; host-регрессии включены в общий acceptance manifest.
Это граница `lab-ready-for-host-review`: дальше нужен отчёт с настоящей Radxa.

Ограничения: виртуальный Ethernet вместо Wi-Fi, отсутствие сети в initramfs,
штатные reboot вместо потери питания, один host-client/H2 и отсутствие
конкурентного управления firewall. Реальный IPv6 провайдера пока отложен;
Radxa должна блокировать прямой внешний IPv6 при IPv4-only exit.

### Проверка замены старой установки

Первая фаза расширена проверкой настоящего retirement CLI: audit оставляет
файлы на месте; apply сохраняет побайтно точные backup-копии, удаляет только
четыре файла, не меняет PID networkd и сохраняет прямую IPv4-связность.
Затем запускается настоящий installer и прежняя трёхзагрузочная матрица.
Fixture воспроизводит stopped/disabled main + inactive tied guard; байты guard
в ней — текущая разрешённая v2-версия. Старый Radxa guard `a47c939` сверён по хешу,
но **не исполняется** ни при retirement, ни в этом fixture. Это не эмуляция
USB gadget или полного образа Radxa.

Первый прогон `/var/tmp/meshpn-host-boot-gThnhJ/report.json` завершился FAILED
до удаления файлов: минимальный initramfs не содержал `/var`. В лабораторный
fixture добавлено создание этого обычного родительского каталога. Проверки
доверенных путей retirement не ослаблялись. Backup в этой VM находится в RAM;
его сохранность при потере питания не проверяется. Локальные fault-тесты
проверяют отказы записи/fsync до удаления, каждую точку удаления и daemon-reload:
ошибка останавливает процесс, а отчёт содержит путь backup и уже удалённые файлы.

Итоговый повторный прогон `/var/tmp/meshpn-host-boot-KIEQI2/report.json` —
**PASS: 88 утверждений (23 + 18 + 47)**, три разных boot ID, две штатные
перезагрузки и poweroff, sync/unmount во всех фазах. Проверены retirement,
установка, поздний DHCP, отказ guard до настройки сети, восстановление,
update и uninstall. Хеши девяти файлов реализации (включая retirement CLI/модуль)
совпали с VM image manifest. Локальный регрессионный набор — **415/415**,
без пропусков. Результат остаётся `lab-ready-for-host-review`, не приёмкой Radxa.

## Следующий шаг на Radxa

Preflight на Radxa уже получен: `wlan0` принадлежит networkd
(`ADMIN_STATE=configured`), ручной TUN после stop исчезает, три recovery-журнала
released, guard rules отсутствуют. Исправлена ложная необходимость review,
вызванная ожиданием только `SETUP_STATE`: поддерживается также `ADMIN_STATE`,
а противоречивые значения по-прежнему требуют разбора.

Остались четыре файла прежней disabled/inactive tied-установки. Хеш установленного
guard совпал с `a47c939`; это не работающий VPN и не причина менять USB.
Добавлен `clean-vpn-retire-legacy.mjs`: audit по умолчанию, явный `--apply`
с приватной копией всех четырёх файлов перед удалением и `daemon-reload`.
Не выполняет старые скрипты, stop/start или сетевые setters. Неизвестная версия,
TUN, незавершённый журнал, оставшиеся guard rules, overrides/активаторы либо
небезопасные файлы вызывают отказ. См. [процедуру замены](autostart/README.md#замена-остановленной-старой-tied-установки).

Текущий SSH идёт по USB IPv4 `192.168.7.19 → 192.168.7.1:22`; `usb0` не управляется
networkd. Gadget настраивается отдельной oneshot-службой, которую **не надо
перезапускать**. Первая согласованная установка — только без reboot и без restart
USB/networkd. Это не подтверждение аварийного доступа после cold boot; до reboot
нужно проверить независимый способ восстановления. Обычная остановка нового VPN
не снимает persistent guard, и публичный прямой доступ остаётся заблокированным.

Повторить **read-only** инвентаризацию при изменении окружения можно командой:

```bash
sudo env "PATH=$PATH" node scripts/clean-vpn-host-preflight.mjs --exit-ip=154.62.226.216
```

Копировать весь отчёт BEGIN…END. Client/exit можно пока оставить запущенными:
проверка ничего не останавливает. Она собирает состояния служб, интерфейсы,
маршруты, выбранные поля networkd и наличие инструментов; не читает ключи,
Wi-Fi-конфиги, VPN argv или сетевые журналы, не посылает сетевых проб.
`review-required` не вызывает автоматических изменений. Реальные запуск,
stop/restart и reboot не засчитываются по лабораторным тестам. При отказе guard
на boot сеть/SSH намеренно могут не подняться.

### USB recovery before Radxa reboot

На Radxa после исправления guard подтверждён цикл штатного stop/start:
освобождены три recovery-журнала, guard остался активным, прямые IPv4/IPv6
HTTPS-пробы после stop не соединились; после start снова прошли DNS/HTTPS/egress
через exit. Это не подтверждает boot recovery. `systemctl start` не ждёт
готовности TUN: первый немедленный диагностический снимок попал в настройку,
последующий прошёл без перезапусков сервиса.

Добавлен отдельный [USB rescue candidate](clean-vpn-usb-rescue.md): SSH на
`192.168.7.1:2222`, привязанный к `usb0`, с текущей авторизацией и восстановлением
только отсутствующего USB IPv4-адреса. Он не меняет gadget, firewall или прежний
SSH и не выполняет reboot. Перед любой перезагрузкой требуется реальный вход
второй сессией с USB-компьютера при сохранении первой. Даже после него отказ
самого gadget/ядра не покрывается: это не замена UART и не автоматический откат.

## Активный client и аудит guard: исправление после Radxa

Снимок Radxa на `4615121` выявил пробел прежней приёмки: при активном клиенте
DNS и IPv6 добавляют ограничивающие правила перед `CLEANVPN_KS_OUT`, а guard
требовал, чтобы его hook был первым даже для `status`. Прежняя лаборатория
проверяла `status` после остановки клиента, когда этих префиксов уже нет.
Успешные DNS/HTTPS-пробы не заменяли отсутствующую проверку активного guard.

В исправлении **только read-only аудит** допускает точные известные формы
host DNS/IPv6-префиксов с полной проверкой вложенных цепочек: `RETURN` или
`REJECT`, без `ACCEPT`, goto и произвольных переходов. Для `up/down` остаётся
требование первого hook: проверка состояния не даёт разрешения менять порядок
или снимать guard под работающим клиентом. Offline `audit-snapshot` использует
тот же код и проверяется без root/внешних инструментов на каноническом формате
предоставленного Radxa `iptables-nft -S` (IP/tag обезличены), включая нарушения
содержимого, отсутствие/дублирование hook и опасные вложенные переходы.

Трёхзагрузочная VM теперь проверяет при активном VPN: успешный `status`, точное
совпадение правил до/после, отказ `up`, отказ `down` и неизменность правил после
обоих отказов. Runner принимает дополнительный `--firewall-backend=nft|legacy`
(default legacy). В nft-режиме используются настоящий `xtables-nft-multi`,
соответствующие restore-команды и nft kernel modules, а не подмена version-строки.
Внешней сети и общей с хостом файловой системы по-прежнему нет.

Прогон `/var/tmp/meshpn-host-boot-rrhsPo/report.json` — **PASS, backend nft,
103 утверждения (28 + 23 + 52)**, три отдельных загрузки ядра, sync/unmount
во всех фазах. Прошли новые проверки активного guard, прежние поздний DHCP,
отказ guard до сети, восстановление, stop, update и uninstall. В образе
проверены настоящий nft binary и все четыре ссылки iptables/ip6tables/restore;
хеши шести затронутых файлов реализации совпали с image manifest.
Локально **448/448**, без пропусков, в том числе 50 тестов guard и побайтная
неизменность планов правил в четырёх конфигурациях относительно `4615121`.
Это лабораторная проверка nft на x86-64, не подмена повторной проверки Radxa ARM64.

На Radxa сначала выполнить исправленный `status` **из репозитория** при
работающем VPN. Установленная копия guard автоматически не заменяется;
повторный installer/restart guard для этого не нужен и не разрешён этим тестом.
Успех status относится к представлению `iptables -S`, не является аудитом всего
native nft ruleset, доказательством отсутствия утечек или приёмкой reboot платы.

## Запуск лаборатории

У существующего `scripts/ingress-vm-lab.mjs` появились флаги
`--ipv6 --host-resilience`. Параметры `--tools`, `--kernel`, `--resolved` и
`--verified-report` задают заранее проверенные локальные артефакты, как в IPv6 lab.
Нужен matching kernel/modules; runner не подменяет VM проверкой на рабочей сети.

Отдельная матрица (прежняя IPv6-матрица запускается без `--host-resilience`):

- остановка exit, отказ новых IPv4/IPv6 соединений без прямого fallback;
- запуск exit заново и восстановление новых HTTPS-соединений;
- DROP только внешнего TLS-пути внутри лаборатории, затем снятие DROP;
- два 60-секундных прогона, concurrency 4, upload 32 KiB / download 64 KiB;
  SHA-256 в обе стороны, проверка сертификата и адреса exit, предел 1024 запросов;
- RSS процесса VPN ограничен 256 MiB, число дескрипторов после нагрузки
  сравнивается с baseline (допуск 8); это не доказательство отсутствия медленных утечек памяти;
- lazy reconnect после idle FIN без перезапуска client, до и после нагрузки;
- `autostart/killswitch.sh` v2: новые и уже существующие UDP-потоки IPv4/IPv6,
  повторный `up` под непрерывными UDP-пробами, входящие TCP replies, отказ
  второго commit и повторное применение, чужие правила, явное снятие защиты.

## Как читать отчёт

Отдельный сценарий настоящего systemd PID1 запускается с
`--ipv6 --host-systemd --dns-conntrack=/absolute/path/to/conntrack`
и теми же параметрами tools/kernel/resolved/verified-report. Он не совмещается
с `--host-joint`, `--host-resilience` или DNS subsets. Внешнего NIC и общей с
хостом файловой системы нет. Драйвер отказывает вне специально помеченной QEMU VM.
Сценарий вызывает настоящий `autostart/install.sh`; только `NetworkNamespacePath`
и место вывода логов заданы лабораторными drop-in. Это **не** проверка раннего
boot: сеть в VM подготовлена до установки сервиса. Проверяются persist-mode,
H2, DNS/IPv4/IPv6, start/stop/restart, SIGKILL и явный recovery, чистое удаление.
Результат этого отдельного сценария — `transports[].hostSystemd`.

Добавление `--host-stop-faults` выбирает отдельную матрицу отказов остановки
вместо полного lifecycle/update-сценария. После успешных DNS/HTTPS проб в VM
внедряется ошибка только в cleanup-команду основного VPN cgroup, затем отдельно
проверяется превышение `TimeoutStopSec`. Для второго случая лабораторный
drop-in сокращает лимит до 5 секунд; production-шаблон остаётся 420 секунд.
Это проверка механизма принудительного завершения, не ожидания всех 420 секунд.
Shim не затрагивает guard и recovery. Отчёт требует отдельный точный набор
утверждений и `hostSystemd.stopFaults=true`; обычный lifecycle PASS его не заменяет.

`--host-boot-order` (вместо `--host-stop-faults`) проверяет транзакцию запуска
guard, синтетического сетевого потребителя и VPN. Сеть VM уже подготовлена;
это **не cold boot и не reboot**. Сначала проверяется успешный guard, затем
вводится отказ через его лабораторный `ExecStartPre=/bin/false`. Потребитель
имеет `Wants/After=network-pre.target`, `Before=network.target`, но не требует
guard напрямую. Он выполняет настоящие локальные DNS/HTTPS-пробы до запуска VPN.
Это отдельная проверка гипотезы о недостаточности одного ordering: при её
подтверждении runner возвращает код **2**, `status=reproduced-defect`,
`hostSystemd.failClosed=false`, а не обычный PASS. Успешное выполнение всех
утверждений в `transports[]` в этом режиме означает воспроизведение дефекта.

`--host-network-gate` — отдельный кандидат исправления для **управляемого,
изначально выключенного интерфейса**. Он несовместим с двумя предыдущими
подсценариями. Только в VM синтетический сетевой сервис получает
`Requires/After=clean-vpn-killswitch.service`; поднятие интерфейса выполняется
его `ExecStartPre`, а опускание — `ExecStop`. Production installer таких
зависимостей не устанавливает. Проверяются здоровый старт, отказ guard и
явный повторный старт после устранения fault. Это не проверка networkd или
reboot и не готовая процедура установки на хост.
Также проверяется позднее появление IPv4 default route: минимум две неудачные
попытки настоящего клиента через `Restart=always`, неизменность released
host-журнала, блокировка проб persist guard, затем успешный автоматический
старт после возвращения маршрута без ручного recovery/reset/restart.

`--host-networkd` выбирает отдельную матрицу с настоящим daemon networkd.
Она требует `--ipv6 --host-systemd --dns-conntrack=...` и несовместима с
`--host-stop-faults`, `--host-boot-order`, `--host-network-gate`. Образ дополнительно
включает `/usr/lib/systemd/systemd-networkd`, его ELF-зависимости и штатный
`/usr/lib/systemd/system/systemd-networkd.service`. Матрица требует 75 утверждений:
обычный запуск, отказ guard, поздний carrier с автоматическим retry клиента,
реальная передача через exit, остановка, опускание link и отказ этой операции.

Штатный unit не переписывается. Лабораторный drop-in добавляет зависимость guard,
`NetworkNamespacePath`, опускание link и ограниченные таймауты/логи. Vendor User,
sandbox, основной ExecStart и FileDescriptorStoreMax сохраняются; кроме effective
properties проверяются реальный UID 192 и NoNewPrivs процесса daemon.
Socket activation явно замаскирована только в VM: vendor socket иначе принадлежал бы netns PID1,
а не клиентскому. Udev пока отсутствует; используется container marker.
`.network` совпадает только с `eth0`, задаёт статические IPv4/IPv6 и gateway.
После очистки адресов их создаёт networkd, а не сценарий. Поздняя сеть моделируется
отсутствием carrier, **не DHCP**. При снятии guard зависимость `Requires/After`
останавливает networkd; лабораторный `ExecStopPost` опускает link. Это существенно:
по [документации networkd v255](https://github.com/systemd/systemd/blob/v255/man/systemd-networkd.service.xml)
сам daemon обычно оставляет сетевую конфигурацию после завершения.

Это ещё не полная distro-интеграция, cold boot/reboot или доказательство защиты
интерфейсов, поднятых initramfs/другим менеджером. Перед legacy uninstall
лабораторные drop-in удаляются; production update/uninstall с такой
зависимостью отдельно не принят. На рабочих машинах этот сценарий отказывает
до сетевых изменений; он не является командой для Radxa.
Особенно важно: прежний uninstaller после `systemctl stop` отдельно вызывает
`killswitch down`. При подключении сетевого release-gate этот путь обязан
проверять отказ guard и сетевые предусловия, иначе обойдёт запрет снятия защиты.
Для отказа команды опускания link добавлен VM-only guard ExecStop: он проверяет
остановку networkd, неизменность ifindex/MAC закреплённого uplink и отсутствие
поднятых non-loopback links, затем вызывает прежний killswitch down. При отказе
проверки unit guard станет failed, но его firewall-правила должны сохраниться.
Принципиально проверяется не только ActiveState, но и фактические правила плюс
отрицательные DNS/HTTPS-пробы при остающемся поднятым интерфейсе с default route.
После явного устранения fault повторяются start/stop с корректным опусканием link.
Это не production-интерфейс и не защита от конкурентного администратора/другого
менеджера сети: установщик эту проверку пока не подключает.
Код возврата `systemctl stop` не считается доказательством успешного ExecStop:
матрица проверяет `ActiveState=failed`, `Result=exit-code`, фактические правила
и блокировку трафика независимо от результата команды stop.

`status=passed` означает, что **лабораторные утверждения подтверждены**.
В историческом отчёте аудита старого kill-switch сюда входят отрицательные контрольные случаи:
утечка ранее установленного соединения считается воспроизведённым дефектом,
а не подтверждением безопасности. Итог готовности находится отдельно:
`transports[].hostResilience.acceptance=not-ready-for-deployment`, причины в
`hostResilience.gaps` (runner также выносит их в `deploymentAcceptance` /
`deploymentBlockers`).
Не переносить старый autostart на Radxa только на основании общего `passed`.
Промежуточные результаты сохраняются в `completedChecks` / `partialEvidence`
даже при падении последующего теста. Ошибка нагрузки остаётся ошибкой, а не
автоматически повторяется до получения зелёного результата.

В текущей связке требуют доработки и отдельных тестов:

- старый безусловный `ESTABLISHED,RELATED` разрешал ранее открытый прямой выход;
  v2 удаляет это исключение, оставляя только ответное направление входящего SSH;
- повторный `up` старого kill-switch сначала выполнял `down`; v2 использует
  `restore --noflush`, отдельный commit для каждой семьи IP, без общего flush.
  Старые немаркированные цепочки не мигрируются автоматически;
- старый systemd unit давал лишь 15 секунд на stop; шаблон исправлен на 420 секунд
  и `KillMode=mixed`; базовый persist-mode lifecycle под PID1 проверен ниже,
  ранняя загрузка пока не принята; ограниченный release switch проверен ниже,
  ошибки остановки вынесены в отдельную fault-матрицу;
- незавершённый IPv6 journal после SIGKILL требует явного recovery: обычный
  `Restart=always` сам по себе не является безопасным восстановлением;
- исторический DNS crash-test восстановил DNS, но не весь исходный набор IPv4
  маршрутов (`nonDnsNetworkRestored=false`, отличие `routes`): его успех нельзя
  считать подтверждением общего rollback после SIGKILL. Новый add-only журнал
  и повторная проверка описаны ниже;
- запуск PID1/systemd, ранняя загрузка, restart/update/uninstall и потеря питания
  не проверяются этой namespace-матрицей. Для них нужна отдельная systemd VM.

Guard сам по себе не маршрутизирует ответы публичному SSH-клиенту: проверка
входящего TCP подтверждает лишь firewall-исключение. Удалённое включение полного
туннеля требует отдельного маршрута управления. Лабораторные пробы не являются
доказательством отсутствия утечек при произвольных конкурентных изменениях firewall.
Uninstaller теперь прекращает работу при ошибке stop/guard down и сохраняет
установленные файлы; это проверено как контракт шаблона. Ниже добавлен настоящий
PID1-тест **чистого** удаления, не удаления после аварийной/незавершённой остановки.

DNS-прокси в этой новой матрице выключен. Его failover, SIGKILL/restart,
недоступность exit и повторный SIGINT при cleanup проверяются отдельно:
`ingress-vm-lab.mjs --dns-host-only --dns-conntrack=...`.
Это не заменяет совместную проверку DNS + IPv6 + systemd + kill-switch.
В `--host-resilience` standalone guard проверяется до транспортной матрицы и
снимается перед ней: успешные transport/guard случаи не означают, что их
совместная работа во время SIGKILL уже принята.
Также не проверены непрерывность уже открытого TCP-потока через обрыв,
24-часовой пилот, реальные провайдерские MTU/IPv6 и USB/LAN-клиенты.

## Журнал IPv4 маршрутов host client

Host client теперь сохраняет намерение **до** добавления bypass/split-default/
RFC1918 маршрута или изменения `net.ipv4.conf.all.rp_filter`. Собственные маршруты
помечены `proto 186 metric 42760`. Совместимые существующие маршруты не меняются
и не удаляются при stop; несовместимый маршрут приводит к отказу вместо `replace`.
Это намеренное изменение поведения относительно старого клиента.

Журнал `/run/clean-vpn-host-routes-<netns>/journal.json` привязан к boot ID,
network/user namespace и идентичности интерфейсов, защищён lifetime flock.
Восстановление сначала проверяет весь набор: чужие маршруты, подменённые
интерфейсы или изменённый `rp_filter` требуют ручного разбора. Исчезновение
собственного TUN после SIGKILL допускается; его новый одноимённый экземпляр
не принимается за старый. После штатной остановки журнал становится `released`.

Проверка без изменений:

```sh
sudo env "PATH=$PATH" node scripts/clean-vpn-host-recover.mjs
```

После аварии новый запуск отказывается продолжать до явного восстановления.
`--apply` восстанавливает **только** IPv4 маршруты и `rp_filter`, не DNS, IPv6
или standalone kill-switch. В лабораторном совместном сценарии при остановленном
client recovery выполняется в порядке DNS → IPv6 → IPv4, пока standalone guard
остаётся включённым. Это не автоматическая политика `Restart=always` и не команда
для удалённого применения без проверки текущих журналов и маршрута управления.
Журнал не покрывает LAN firewall/forwarding и потерю питания: состояние в `/run`
действует только в пределах одной загрузки.

Совместная namespace-матрица: `ingress-vm-lab.mjs --ipv6 --host-joint
--dns-conntrack=...` с теми же проверенными VM-артефактами. Включает DNS UDP/TCP,
TLS H1/H2, IPv6, standalone guard, SIGKILL, явное recovery и повторный запуск.
Это по-прежнему не тест настоящего systemd PID1.

Первые совместные прогоны `qmsVd6` и `QPCoAO` остановились на TLS startup.
Диагностика показала входящий TCP на exit с нулём байт ClientHello: клиент уже
запустил таймер TLS, затем заблокировал event loop синхронной установкой DNS.
TLS/boring-TLS outbound bridge теперь ждёт готовности сетевой настройки до
открытия сокета (как eager, так и TUN-triggered connect); отменённый startup
не открывает соединение. Таймауты TLS не увеличены. Регрессии проверяют этот
порядок, отмену startup и последовательность cleanup DNS → IPv6 → IPv4.

Итог совместной матрицы: `/var/tmp/meshpn-ingress-vm-Nxxvmk/report.json`,
**49/49 PASS**, TLS H1 и H2. В обоих случаях подтверждены:

- DNS UDP/TCP и IPv4/IPv6 HTTPS через exit при включённом standalone guard;
- после SIGKILL — отказ прямых IPv4/IPv6/DNS проб и отказ запуска поверх stale journal;
- явное recovery DNS → IPv6 → IPv4 возвращает исходные IPv4 маршруты и `rp_filter`,
  при этом standalone guard продолжает блокировать прямой выход;
- новый запуск после recovery работает, штатная остановка оставляет все три
  журнала `released`, а guard остаётся до отдельного явного `down`;
- после явного `down` положительная контрольная IPv4-проба снова работает напрямую.

Промежуточный прогон `uCDJTf` подтвердил исправленный TLS startup и crash blocking,
но recovery прервал **20-секундный executor стенда**, не 120-секундный бюджет DNS.
Исправлен ограниченный запуск recovery в стенде (150 с, stdout отдельно от progress

## Аудит отказа раннего guard (2026-09-30)

Первый прогон `--host-boot-order`,
`/var/tmp/meshpn-ingress-vm-aL7pal/report.json`, завершился **failed**: после
чистой остановки PID1 выгрузил inactive units, а тест потребовал успешный
`reset-failed` для уже не загруженных units. До проверки отказа guard прогон
не дошёл. Исправлен только сценарий: лишний reset перед start удалён, после
внедрённого отказа сбрасывается только действительно failed guard. Этот отчёт
не является доказательством ни блокировки, ни утечки при отказе guard.

Исправленный сценарий: `/var/tmp/meshpn-ingress-vm-kyWcrS/report.json`.
Выполнены **35/35 утверждений**, но итог **`reproduced-defect`**, код runner **2**,
`failClosed=false`, `finding=network-consumer-ran-after-guard-failure`.
Это не приёмочный PASS. В здоровом случае consumer не смог выполнить ни одну
IPv4/IPv6/DNS пробу до запуска VPN, после чего VPN обеспечил HTTPS через exit.
При отказе `ExecStartPre` guard стал failed, VPN остался без процесса, но
consumer запустился после `network-pre.target`: его IPv4 и IPv6 HTTPS пришли
к origin с исходных адресов client, DNS тоже получил прямой ответ. После
удаления fault drop-in явный запуск guard вновь заблокировал все три пробы;
чистый uninstall вернул исходный IPv4. Хеши сценария, observer, драйвера,
валидатора, installer и kill-switch совпали с manifest образа.

Причина в проверенной транзакции: `Before=network-pre.target` задаёт порядок,
но не делает успешный старт guard обязательным для остальных потребителей
этого target. `Requires` основного VPN защищает его запуск, а не запуск
других сетевых приложений. Существующие правила при ошибке cleanup продолжают
защищать трафик (отдельная stop-матрица выше); здесь проверен другой случай —
guard не успел установить правила вообще.

Ограничения: синтетический consumer, подготовленная сеть, warm job transaction,
не cold boot/reboot и не конкретный дистрибутивный network manager. Нельзя
переносить результат на все этапы загрузки или считать, что dependency одного
network manager защитит уже поднятые другими компонентами интерфейсы.
Локальная регрессия: **339 passed, 0 failed, 0 skipped**; после исправления
лишнего reset повторно прошли все 5 boot-order контрактных тестов.

Следующий шаг перед reboot-приёмкой — спроектировать и проверить обязательную
зависимость поднятия управляемой сети от успешного guard, включая отказ guard
и доступность управления. Простое добавление ещё одного `Before` дефект не
закрывает. Production units пока не менялись; автозапуск остаётся
`not-ready-for-deployment`.

## Кандидат обязательной зависимости сети (2026-09-30)

Матрица `--host-network-gate` не меняет production installer. Она проверяет
`Requires` вместе с `After` на синтетическом сетевом сервисе с реальным
`ip link set eth0 up` в `ExecStartPre`. Перед каждой транзакцией интерфейс
выключен. Guard — настоящий persist unit от installer, с прежним kill-switch.
В здоровом и восстановленном случаях проверяются поднятие link, timestamps
guard/consumer, блокировка до VPN и рабочие IPv4 HTTPS, IPv6 HTTPS и DNS через
exit. При ошибке guard до установки правил нужны отсутствие сетевого consumer
и VPN, отсутствие файла результатов consumer, link без `UP` и отказ всех проб.

Перед снятием guard сетевой сервис останавливается и опускает link.
После отказа для новой транзакции отдельно останавливаются passive targets:
они могли стать active, даже если одна из зависимых работ не выполнилась.
Кандидат сетевого unit удаляется перед вызовом прежнего uninstall — это
**не** проверка интеграции production uninstall с новой зависимостью.

При отказе guard такая схема намеренно оставляет управляемый интерфейс
выключенным, поэтому SSH через него тоже недоступен. Требуется заранее
согласованный доступ через консоль/другой канал; это не «бесшовное» исправление
для удалённого сервера. Уже поднятые другим менеджером/скриптом интерфейсы,
утрата правил у уже active guard и обходы через другие сетевые сервисы здесь
не покрываются. Реальный networkd, cold boot/reboot, проверка фактических правил
перед поднятием сети и интеграция installer/update/uninstall остаются впереди.

Первый прогон кандидата `/var/tmp/meshpn-ingress-vm-VCZ990/report.json` —
**failed**. Link был поднят после guard, пробы до VPN блокировались, но
лабораторный сетевой сервис не восстановил IPv4 default route после link-down.
Клиент завершился с `Не найден default route`, затем рестарты требовали
`Host IPv4 recovery required`. Сценарий исправлен: IPv4 default route теперь
восстанавливается вместе с IPv6 до старта VPN; это не изменение клиента.

Выявлен отдельный **неисправленный startup-блокер**: `hostRoutes.begin()`
создаёт active журнал до проверки default route, а этот ранний отказ оставляет
журнал, препятствующий следующим попыткам старта. Реальный boot с поздним DHCP
поэтому ещё не принят. Нужен отдельный тест/исправление раннего abort без
сетевых мутаций; успешный прогон с заранее готовой маршрутизацией этого не
доказывает. Удалять или автоматически игнорировать незавершённые журналы нельзя.

Исправленный сетевой сценарий `/var/tmp/meshpn-ingress-vm-AciLYQ/report.json`:
**48/48 PASS**. В здоровом и восстановленном циклах guard завершился раньше
consumer, интерфейс поднялся, до VPN пробы блокировались, затем IPv4 HTTPS,
IPv6 HTTPS и DNS работали через exit. При отказе guard сетевой consumer не
выполнился, link остался без `UP`, все три пробы отказали. После завершения
сценария исходный прямой IPv4 восстановлен. Runner проверил полный набор
утверждений и нормальное выключение VM; хеши сценариев, драйвера, валидатора,
installer и kill-switch совпали с manifest.

Локальная регрессия: **343 passed, 0 failed, 0 skipped**; после исправления
IPv4-маршрута повторно прошли 4 контрактных теста кандидата. Результат относится
только к лабораторному сетевому unit. Production installer не изменён, новый
startup-блокер остаётся неисправленным, статус — `not-ready-for-deployment`.

без оставленного пустого active-журнала, затем интеграция с реальным networkd.

## Исправление раннего отказа без default route (2026-09-30)

`hostRoutes.begin()` перенесён из `runClientImpl()` в `setupClientRoutesAsync()`
после успешной read-only проверки IPv4 default route, но до первой мутации
маршрутов/rp_filter. Прежний `assertAvailable()` остаётся до создания нового
TUN: чужой/незавершённый журнал не игнорируется и не удаляется. Это узкое
исправление отсутствующего default route, не автоматический rollback любого
startup-отказа. Временный TUN ранней неудачной попытки закрывается при выходе
процесса.

Тесты исполняют настоящую функцию setup с подставленным kernel IO и настоящим
durable-журналом: три отказа подряд не создают журнал и не изменяют прежний
released-журнал; после появления маршрута старт и restore проходят. Отдельно
проверены ошибка чтения маршрута, ingress без host default и сохранение раннего
stale-ownership gate. Локальная регрессия: **347 passed, 0 failed, 0 skipped**.

В `--host-network-gate` добавлен сценарий настоящего `Restart=always` с поздним
маршрутом. Он не вызывает `recovery --apply`, `reset-failed` или ручной restart
для успешного старта после появления маршрута; существующие проверки guard
не заменяются этим сценарием. Полная матрица теперь требует **59 утверждений**.

Прогон `/var/tmp/meshpn-ingress-vm-ecc1rT/report.json`: **59/59 PASS**,
