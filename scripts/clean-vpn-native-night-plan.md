## Цель и отсечка

Один native engine и сохранённый Chromium-derived partial профиль должны
работать двумя способами: непосредственно на Linux и в runtime-контейнере
Docker/Podman. Проверить lifecycle, DNS, профиль на wire и восстановление.
К окончанию работы — воспроизводимые команды, тесты, отчёт и логические коммиты;
на физических узлах не оставлять новый постоянный VPN или автозапуск.

Существующий `scripts/containers/clean-vpn-native-lab.Containerfile` содержит
компиляторы, QEMU/kernel/systemd и служит лабораторией. Он не заменяет компактный
runtime image VPN. Использовать его кэш и стенд, но оформить runtime отдельно.

## Порядок реализации

1. Определить общий runtime-контракт client/exit: config, CA/PSK, TLS profile,
   TUN ownership, readiness, status и graceful shutdown. Payload остаётся C++;
   provisioning/control может выполнять отдельный управляющий компонент.
   Сохранить возможность запуска без Docker/Podman и без обязательной установки.
2. Сделать отдельную многостадийную сборку runtime image для Linux amd64/arm64.
   Не включать ключи и индивидуальные конфиги в image/layers. Входные config,
   CA/PSK/profile подключать явно; для изменяемого состояния отдельный volume.
   Версии зависимостей и происхождение бинарника фиксировать. Сборку ARM64
   действительно проверить, не объявлять поддержку только по имени platform.
3. Добавить примеры Docker/Podman запуска client и exit и compose-пример пары.
   Сначала boring-tls с проверенным partial профилем. По умолчанию собственный
   network namespace; не использовать blanket privileged или host network.
   Указать необходимые device/capability grants и проверить отказ без них.
   Rootless TUN/gateway поддержку не обещать без отдельной проверки.
4. Разделить источники трафика: приложение в сети client-контейнера и явно
   подключённый gateway/LAN-источник. Контейнерный запуск не должен самовольно
   менять default route/DNS хоста. Для gateway отдельно описать и проверить
   host-side wiring и его rollback, а не считать существующий host wg0/usb0
   автоматически доступным внутри контейнера.
5. В лаборатории проверить настоящий TUN, DNS UDP/TCP, IPv4 HTTPS/обычный TCP/UDP,
   неверные CA/name/PSK, недоступность exit/upstream, рестарт/пересоздание
   контейнера, SIGTERM/SIGKILL engine и управляющего процесса. Проверить сохранение
   чужих rules, отсутствие выбранного direct fallback, освобождение ресурсов.
   Readiness должна различать живой PID и рабочий tunnel/DNS.
6. Проверить сохранённый TLS профиль независимым capture для standalone и
   контейнерного запуска; показать фактические JA3/JA4 и известные отклонения
   от исходного Chromium. Не менять caps/crypto policy ради совпадения хеша.
7. Настоящий systemd/boot/reboot и clock-fault сценарии — в изолированной VM.
   RTC Radxa уже исправлен после NTP sync, но reboot/power-loss retention ещё
   не доказан. Не обходить проверку сертификатов ради time bootstrap.
8. После лабораторных проверок — bounded physical smoke на доступных узлах,
   только временные units/containers, точные owned rules и независимый rollback.
   Не устанавливать системный container runtime на узел только ради теста:
   если нужного runtime нет, проверить этот вариант в лаборатории.
   Существующие Docker/x-ui, USB rescue, guard и посторонние контейнеры сохранять.
9. Оставшееся время — ограниченный soak (целевой интервал 1–2 часа), повторные
   подключения и малые передачи, DNS, RSS/FD/socket/process counters и latency.
   Объём трафика/время ограничить, ошибки и пропуски сохранить в отчёте.

## Расширение только после основных критериев

Проверить совместимость runtime-упаковки с combo-tls/transparent-tls и
персистентным replay state. Зафиксировать support matrix; экспериментальные
режимы не объявлять production из-за наличия image. Node TLS не выдавать за
отдельный C++ transport: сначала проверить действительные capabilities engine.
Полное Chromium fidelity, tickets/trust anchors, H2 tuning и расширение DNS
backends остаются за основной отсечкой, не заменяют незавершённые lifecycle tests.

## Границы автономной работы

- Mac: только код, git и выделенная лаборатория; Wi-Fi/routes/DNS/firewall не менять.
- VPS/Radxa: никаких постоянных install/enable, миграции legacy или reboot хоста
  в этой ночной программе. Весь новый runtime временный, с проверенным cleanup.
- Не делать flush/replace чужих firewall tables и не отключать guard ради успеха.
- Коммитить на Mac логическими частями, fetch перед push; узлы обновлять git
  fast-forward, при недоступном GitHub — проверенным git bundle через USB.
- Не включать чужие параллельные device-изменения в свои коммиты.
- При отсутствии узла продолжать независимые lab-задачи; физические проверки
  честно оставить непроверенными. При сбое gates исправлять причину, не снижать
  требования. Повторно использовать текущие успешные проверки без лишних прогонов.

## Итоговый отчёт

Отдельно указать standalone / Docker / Podman и amd64 / arm64: build, actual
runtime, functional probes, profile capture, recovery, soak, ограничения.
Приложить команды запуска/остановки, resource grants, расположение приватных
конфигов/state, результаты cleanup и список оставшихся задач. Образ или unit,
который лишь собрался, не считать проверенным VPN. Отчёт не должен заявлять
готовую ежедневную установку на физических узлах: она сейчас исключена из scope.
