# План: выбор режима клиента при общем combo-exit

Требование пользователя, 2026-10-31. **Запланировано, не реализовано.**
Это развитие native client/exit и админки, а не миграция старого Node VPN.

## Ожидаемое поведение

На VPS достаточно включить `combo-tls` на одном endpoint (по умолчанию 443).
На клиенте пользователь выбирает `combo-tls`, `boring-tls` или
`transparent-tls`, сохраняя тот же exit, свою клиентскую идентичность и
подготовленный комплект доступа. Перевыпуск ключей, переустановка и ручное
изменение маршрутов/firewall для каждого переключения не требуются.
Выбор одного клиента не требует перезапуска exit и не прерывает других клиентов.

| Режим exit | Поддерживаемые режимы клиента |
| --- | --- |
| combo-tls | boring-tls, transparent-tls, combo-tls |
| boring-tls | boring-tls |
| transparent-tls | transparent-tls |

Последние две строки — минимальный контракт совместимости; расширять его только
после реализации и проверки. Режимы с несовместимым exit должны быть объяснимо
отклонены до изменения действующей конфигурации.

«Бесшовный выбор» — единый пользовательский процесс без ручной перенастройки
узлов. Требования к сохранению уже открытых соединений при смене режима нужно
отдельно определить и испытать. Не считать обычный restart сохранением TCP-сессий;
в API/UI явно показывать применение, переподключение, готовность или откат.

## Что уже есть и что мешает

- `native/clean_vpn/combo.hpp`: общий exit listener классифицирует ClientHello
  и передаёт соединение в boring либо transparent. Классификация не заменяет
  аутентификацию; некорректный relay token не должен попадать в boring как fallback.
- Нативные режимы существуют, но это не приёмка всей матрицы client → combo-exit.
- `admin/broker.mjs`: `capabilities.transports` сообщает только текущий режим;
  `/vpn/settings` не принимает выбор транспорта и меняет текущую packet-ветку.
- Host/container controllers, DNS, readiness, clock bootstrap и независимый
  observer имеют разные предположения о наличии packet-ветки/TUN. Для
  standalone transparent нужно согласовать их, а не только добавить select в UI.

## Порядок работ

1. Зафиксировать и проверить протокольную матрицу с одним native combo-exit:
   три режима клиента, одинаковый endpoint, разные клиенты одновременно,
   H1/H2 для boring-ветки, TLS 1.2/1.3/HRR для relay. Сохранить отдельные packet
   и relay PSK, CA/name checks, квоты и replay state. Проверить отказ чужих и
   отозванных ключей, неверных имён и несовместимых режимов без обхода защиты.
2. Определить общий сохранённый комплект клиента: настройки обеих ветвей,
   ссылки на секреты, CA, TLS/HTTP-профиль и правила перехвата. Переключение
   активного режима не должно терять параметры неактивной ветки. Enrollment,
   export/import и информация о поддержке exit должны сохранять этот контракт;
   возможности exit получать из конфигурации/доверенного provisioning либо
   аутентифицированного обмена, не угадывать по одному успешному TLS handshake.
3. Согласовать сетевую семантику каждого режима. Boring несёт packet-трафик;
   combo добавляет relay для подходящего HTTPS. Для transparent-only явно
   определить DNS, bootstrap, неподдерживаемые TCP/UDP/QUIC и маршруты.
   Не наследовать старый сырой неаутентифицированный TCP fallback, не выпускать
   DNS/остальной трафик напрямую и не ослаблять guard ради успешного переключения.
   Если безопасная схема ещё не поддержана — режим недоступен с понятной причиной.
4. Сделать типизированное API выбора режима и транзакционное применение:
   native validation до замены файлов; согласованная смена engine/network/DNS;
   readiness именно выбранного режима; rollback и восстановление после аварии.
   Остановленный VPN остаётся остановленным. Сохранять USB-админку и kill switch.
   Проверить все шесть направлений переключения и недопустимые комбинации.
5. Добавить переключатель режима в админку с фактическими возможностями exit,
   прогрессом и результатом. Browser-профиль применяется к boring-ветке;
   transparent использует TLS приложения. Observer и диагностика должны
   показывать выбранный режим и соответствующую ветку, не смешивая отпечатки.
6. Приёмка сначала в изолированных Linux netns/VM и Docker/Podman:
   DNS/HTTPS/upload, failure/restart/rollback, SIGKILL на границах переключения,
   чужие правила и другие клиенты, отсутствие прямого выхода и утечек ресурсов.
   Затем отдельная физическая проверка Radxa ↔ VPS. LuCI использует тот же
   контракт возможностей и переключения, когда её backend будет реализован.

## Критерий завершения

Один работающий combo-exit принимает все три режима клиента; клиент выбирает
их через админку без изменения exit, замены комплекта доступа и ручной работы
с сетью. Матрица переключений, изоляция других клиентов, безопасность DNS/guard
и аварийный откат подтверждены тестами. Известные перерывы существующих сессий
явно описаны и соответствуют принятому контракту. До этой приёмки не объявлять
выбор транспорта доступной функцией.
