# clean-vpn за nginx

Кратко про возможность прятать TLS и WebSocket за nginx, смысл и узкие места.

## Можно ли?

Да, но по-разному для разных режимов clean-vpn.

| Что прячете | Типичная схема | Совместимость с `--type=tls` на Node как сейчас |
|-------------|----------------|--------------------------------------------------|
| Только «лицо» сервера | Nginx принимает TLS и проксирует **сырой TCP** на Node (`stream { proxy_pass … }`) | **Да**: до Node доходит тот же TLS, что прислал клиент (если не делаете TLS termination на nginx). Clean-vpn продолжает парсить ClientHello и т.д. на Node. |
| TLS на nginx, до Node — plain | `http`/`websocket` на localhost, снаружи `https`/`wss` через nginx | **Нет**, это уже не «тот же» `--type=tls` на exit: нужен клиент на **http/wss**, а на VPS — **`--type=http`** или **`--type=websocket`** (+ nginx с сертификатом). |

**WebSocket за nginx** — обычная практика: `proxy_http_version 1.1`, заголовки `Upgrade` / `Connection`, часто **`proxy_buffering off`**, увеличенные таймауты.

## Есть ли смысл?

**Имеет смысл**, если цель — эксплуатация, а не обязательно усложнение обхода DPI:

- Один нормальный выпуск/обновление сертификатов (Certbot, ACME), привычные логи и лимиты.
- Закрыть прямой доступ к порту Node снаружи, оставить только 80/443 у nginx.
- Опционально: несколько сервисов на одном IP/имени.

**Смысла мало или он другой**, если цель — «спрятать VPN от DPI»: nginx перед Node не добавляет нового шифрования поверх уже TLS (при stream-pass-through); при терминации TLS на nginx для наблюдателя картина та же — HTTPS/WSS к вашему домену. Узкое место обхода чаще в **профиле приложения** (пути, ALPN, поведение), а не в том, nginx ли первый процесс на 443.

## Узкие места nginx в такой связке

1. **Буферизация WebSocket** — по умолчанию может ломать или задерживать поток; для VPN нужна отключённая буферизация на апгрейде и адекватные `proxy_read_timeout` / `proxy_send_timeout`.
2. **Лимиты размера и времени** — `client_max_body_size`, таймауты соединения; длинный idle-туннель может обрываться раньше, чем ожидает `--keep-alive` в clean-vpn.
3. **`stream` TCP proxy** — отдельные лимиты (`proxy_timeout`), меньше «магии» HTTP; нужно следить за **исчерпанием файловых дескрипторов** и **connection backlog** при многих клиентах.
4. **Двойной TLS** — если клиент → nginx TLS и nginx → Node снова TLS, лишняя CPU-латентность; для VPN обычно делают nginx → Node по **локальной сети без TLS**.
5. **Потеря функций clean-vpn `--type=tls`** при терминации на nginx: пропадает сценарий **passthrough по SNI / probe-target** на самом Node — его должен как-то заменять nginx (разные `server_name`, отдельные upstream), иначе поведение изменится.
6. **Корреляция метаданных** — для злоумышленника VPS всё равно виден ваш домен/IP и статистика соединений; nginx это не «убирает».

## Итог

За nginx имеет смысл ставить TLS или WSS для удобства и изоляции Node; для сохранения текущего **`--type=tls`** с passthrough на Node используйте **`stream` без расшифровки**. Узкие места — таймауты, буферы WS, FD/CPU на TLS termination и осознанный выбор: один TLS (на nginx) или сквозной TLS до Node.

## Диагностика: TLS к VPS не доходит, QUIC/HTTP работают

Симптом: на exit в логе только `[clean-vpn] tls: входящий TCP с …`, дальше нет строк про ClientHello; на клиенте таймаут рукопожатия (`TLS_CLIENT_HANDSHAKE_MS`). При этом **UDP (`quic-ext`) или голый TCP (`http` / `socket` / `websocket`)** на том же IP проходят.

Частая причина — на маршруте клиента режется именно **TLS record / handshake**, а не весь IP (не ошибка Bearer или `--tls-public-name`). Уточнение без правок кода:

- С клиента: `openssl s_client -connect VPS:443 -servername ваш host`; если виснет так же — проблема не в приложении clean-vpn.
- На VPS: `tcpdump -nn host IP_клиента and port 443` — есть ли полезная нагрузка после SYN от клиента.

Дополнительные логи в процессе: **`CLEAN_VPN_TLS_MUX_DEBUG=1`** на exit и client (см. шапку [`clean-vpn.js`](clean-vpn.js)): первый chunk до разбора ClientHello, таймаут 60 с без Hello, закрытие/error до mux.

**Обход**, если именно Node TLS режут: не полагаться на `--type=tls` между узлами; использовать **`quic-ext`**, **`websocket`** или **`http`**, либо **терминировать TLS в nginx** (или CDN) и проксировать на localhost уже **`--type=http`** / **`websocket`** без второго TLS (см. таблицу выше).
