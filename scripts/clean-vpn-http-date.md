# Восстановление часов из HTTP Date проверенного exit

Для native Node TLS (`--type=tls`, также native TLS-путь `combo-tls`),
HTTP/1.1 и HTTP/2. Включено автоматически; новых флагов, UDP-портов,
ключей, systemd units и firewall-исключений нет.

## Обмен

Exit добавляет стандартный `Date` (UTC, с секундами) в успешный VPN-ответ
и во все обычные cover-ответы. Ошибка Bearer по-прежнему возвращает обычную
страницу `200 text/plain`, без специальной ошибки или заголовка VPN-времени.
Причину отказа серверу определять не требуется; алгоритм, формат и допустимые
окна Bearer не меняются.

Клиент различает `200 application/octet-stream` (VPN) и cover-ответ.
Ранее он ошибочно объявлял любой `200` успешной авторизацией.
При отказе клиент может использовать Date, только если:

- CA и имя exit уже проверены штатным TLS; `authorized=true`, нет authorizationError;
- ответ получен не позже 5 секунд с начала HTTP-обмена по монотонным часам;
- присутствует ровно один корректный Date в IMF-fixdate; нет `Age`;
- окно часов клиента за пределами серверного ±1 окна по 15 минут,
  с учётом секундной точности Date и задержки доставки на границе окна;
- за время обмена часы не поменялись другим механизмом;
- предлагаемое время входит в срок действия полученной цепочки сертификатов;
- в этом процессе ещё не было попытки установки часов.

Клиент вызывает `/usr/bin/date -u -s @<epoch-seconds>` без shell, с фиксированным
окружением и таймаутом 3 секунды, проверяет результат и заново соединяется.
Новый TLS handshake без повторного использования сессии и новый Bearer обязательны.
Дополнительного округления до минуты нет. Неправильный ключ остаётся неправильным:
время может исправиться, но доступа к VPN это не предоставляет.

Успех виден в логе `clock-date: UTC ... -> ... по Date проверенного exit`.
Причины отказа в коррекции дописываются к ошибке авторизации как `clock-date=...`.
Неудачная установка времени тоже расходует единственную попытку процесса.
Счётчик сбрасывается при новом запуске процесса, это не персистентный лимит.

## Границы доверия и совместимости

- Exit становится доверенным источником **системного** времени. Его часы должны
  поддерживаться корректными, например NTP. Заголовок Date и сертификат не
  доказывают NTP-синхронизацию; клиент не может обнаружить ложное время от
  взломанного/неправильно настроенного доверенного exit в пределах валидности
  сертификатов. Перевод времени влияет и на другие приложения Radxa.
- Не отключается проверка сертификата. При сбросе часов в 2017 год TLS может
  отказать раньше HTTP; такой случай не восстанавливается этим механизмом.
  Требуется доверенная внешняя коррекция (например через уже проверенный USB SSH).
- Это разовая загрузочная коррекция, не замена NTP. RTC, NTP-настройки, маршруты,
  kill-switch, USB rescue и зависимости systemd не меняются.
- `boring-tls` через helper пока **не переводит часы**: у его pipe-обёртки нет
  используемых здесь данных проверенной цепочки. Исправление распознавания cover
  применимо и к нему. Другие транспорты не получают этот механизм.
- Старый exit без Date в HTTP/1.1 не сможет восстановить время нового клиента,
  но обычная работа с верными часами сохраняется. Обновлять следует обе стороны.
- Установленный сервис читает код из своего репозитория. Для активации потребуется
  перезапуск только процесса VPN после обновления кода. Переустановка службы,
  перезапуск guard/networkd/USB и reboot не нужны.

## Проверка без изменения часов разработческой машины

```sh
node --test scripts/test-vpn-http-date.mjs scripts/test-vpn-http-date-tls.mjs
```

Unit-тесты проверяют границы окон, повторные коррекции, неверные/повторные Date,
недоверенный TLS, сроки сертификатов, timeout, конкурентное изменение часов и
отказ setter. Loopback-интеграция выполняет реальные TLS/HTTP/1.1/HTTP/2 и Bearer
из функций `clean-vpn.js`, заменяя только JS-часы клиента и setter. Проверяются
разные сдвиги, повторный handshake, неверный PSK и неверное имя сертификата.
TUN и сетевые правила эти тесты не создают.

Отдельный `clean-vpn-http-date-lab.mjs` принимает два абсолютных пути к ранее
проверенному host-boot стенду и извлечённым QEMU tools. Это команда лаборатории,
**не Radxa**. Он создаёт NIC-less QEMU без общей с хостом ФС. Только внутри
гостя меняется настоящий CLOCK_REALTIME; Date exit получается от независимых
логических часов на базе монотонного таймера (netns не изолирует CLOCK_REALTIME).

Результат `/var/tmp/meshpn-http-date-lab-pwSBF1/report.json`: **PASS, 34 проверки**.
Для обеих версий HTTP проверены −1, −2, −30, +30, +365 дней: перевод настоящих
часов production-setter, новый TLS handshake, успешный Bearer. Сброс в 2017
и перенос в 2040 приводят к отказу сертификата без обхода и без коррекции.
Отчёт содержит хеши исходников; временный образ удалён, лог и отчёт сохранены.
Это проверка TLS/time-компонента, не новая полная приёмка VPN/TUN или загрузки Radxa.

Реальная проверка обновлённого кода на Radxa/exit ещё не выполнена.
