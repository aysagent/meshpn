# Native H2: доставленная скорость через настоящий TUN

2026-10-26. [Полный отчёт](../fixtures/clean-vpn-native-h2-goodput-report.json).
Production caps не изменены. Все 24 передачи завершились с проверкой данных;
это **не** означает отсутствие потерь пакетов или готовность постоянной установки.

## Повторение

```sh
npm run lab:native:mac -- --h2-goodput
```

Нужен подготовленный кэш macOS Podman lab (образ, kernel, QEMU, build dependencies).
Команда собирает актуальные бинарники, выполняет CTest и запускает отдельный
Linux guest: TCG, 2 vCPU, 1536 MiB, без NIC, дисков и общей с Mac файловой системы.
Внешний контейнер запускается с network=none и cap-drop=all. VM имеет предел
20 минут; отдельная передача — 60 секунд. Весь TUN/netns/netem существует внутри VM.
Mac, VPS и Radxa не перенастраиваются. JSON и serial log остаются в
`~/Library/Caches/meshpn-clean-vpn-lab/results/clean-vpn-h2-goodput-*.json*`.

## Что измеряем

Один exit, четыре клиента с отдельными ключами/адресами, настоящий TUN и TCP.
Один клиент передаёт 8 MiB download, затем upload. Остальные три постоянно
обмениваются 32-байтовыми echo-запросами. C++ workload проверяет каждый блок
получателя; Node только управляет процессами и снимает счётчики. Маршрута к
адресу origin через veth нет: bulk действительно проходит через TUN и VPN.

Сравниваются начальные stream/connection receive windows клиента:
1/1 MiB и fixture-only 6/15 MiB. Проверяется реальная сериализация SETTINGS и
WINDOW_UPDATE для каждого из четырёх соединений. Все остальные лимиты прежние.
Размер receive window exit одинаков; upload — контроль направления, а не
симметричная проверка увеличенных окон. Production config отдельно валидируется.

Два канала, три повтора, порядок режимов чередуется: 24 bulk-передачи.
Каждый клиент имеет собственный full-duplex канал с netem в обоих направлениях;
общей узкой полосы доступа нет. Условия: 20 Мбит/с / RTT 40 мс и
100 Мбит/с / RTT 120 мс. Дополнительные прямые TCP передачи калибруют стенд.
Таймер bulk начинается после соединения и заканчивается подтверждением
получения всех данных. Это конечная передача с TCP slow start, не steady-state.
Сессии TLS новые для каждого режима; upload следует после download.

Снимаются RSS/CPU каждого engine, суммарные TCP send queued/receive alloc,
engine dropped_packets, TCP retransmits по всем namespace и netem counters.
CPU ticks относятся к полному интервалу измерения, включая probes/status/завершение;
это не чистая стоимость шифрования одного bulk. Задержки probes берутся только
для запросов, целиком попавших в интервал bulk. Проверяются сохранение процессов,
4 живые сессии exit, лимиты очередей и прогресс всех трёх остальных клиентов.

## Результаты

Медиана трёх прогонов; в скобках минимум–максимум, Мбит/с:

| Канал | Направление | 1/1 MiB | 6/15 MiB |
| --- | --- | ---: | ---: |
| 20 Мбит/с, 40 мс | download | 15.42 (15.38–16.59) | 16.81 (16.39–17.15) |
| 20 Мбит/с, 40 мс | upload | 17.12 (15.95–17.19) | 17.08 (15.23–17.19) |
| 100 Мбит/с, 120 мс | download | 24.62 (23.52–24.84) | 35.60 (24.55–39.72) |
| 100 Мбит/с, 120 мс | upload | 25.13 (25.05–25.18) | 22.45 (17.61–25.06) |

Прямой shaped TCP: 18.45/18.43 и 44.01/44.02 Мбит/с download/upload.
Даже контроль не достигает номинальных 100 Мбит/с на конечных 8 MiB при 120 мс;
вычитать разницу до 100 как накладные расходы VPN нельзя. Unshaped TCP дал
3.53/3.97 Гбит/с; это виртуальный короткий путь, не оценка скорости VPN на ARM.

На канале 100/120 пик RSS exit: 7716 KiB baseline, 7460 KiB large windows;
пик суммы TCP send queued: 932 и 1666 KiB. На 20/40: 6648/6632 KiB RSS и
711/764 KiB send queued. Сумма охватывает exit и четыре клиента; это sampled
метрики, не полный расход kernel memory. Для многоклиентского no-drain случая
сохраняют силу более высокие значения [предыдущей матрицы](clean-vpn-native-h2-kernel.md).

На 100/120 download median per-client p95 echo: 129.5/136.1 мс;
максимум этих p95: 195.9/143.4 мс. На upload максимум p95: 127.1/278.7 мс.
Это агрегация девяти p95 (три клиента × три повтора), не общий percentile сырых
samples. У всех peers есть успешные ответы во время каждой bulk-передачи.

**Потери не скрыты:** netem drops=0 в обоих каналах, но на 100/120 baseline
exit dropped_packets вырос на 51/69/200, TCP retransmits по namespace —
51/72/201. При large windows download engine drops=0, retransmits=3/6/3.
В одном large-window upload зарегистрировано 20 TCP retransmits, engine drops=0.
На 20/40 встречались единичные engine drops, один TCP retransmit за серию.
Агрегат dropped_packets включает невалидный/не-IPv4 пакет, отсутствие владельца
и переполнение очереди; конкретную причину этот отчёт не различает.
Сопоставление счётчиков указывает на необходимость отдельной диагностики TUN
backpressure, но само по себе не доказывает причину каждого drop.

## Решение и следующий шаг

Не увеличиваем production caps. Есть положительный сигнал для download с большим
RTT, но только три повтора, заметный разброс и отсутствие выигрыша на upload.
Следующая ограниченная задача — раздельные причины drops и проверка bounded
очереди выхода из общего TUN: воспроизвести 100/120, сохранить прогресс других
клиентов и проверить решение без снятия лимитов памяти. Затем — более длинные
передачи, более одного bulk-клиента и контролируемые потери при необходимости.
TCG-результаты не заменяют физический benchmark или доказательство browser fidelity.
Ticket lifecycle и trust-anchor chain selection/retry остаются отдельными задачами.

Для обычного boring-tls пилота полное совпадение с Chromium не требуется.
Нужны отдельный актуальный физический smoke, постоянная native service-конфигурация,
проверки DNS/остановки/аварийного восстановления и загрузки. Восстановление времени
по HTTP Date пока реализовано только в Node TLS; C++ его не выполняет.
NTP/RTC или отдельно спроектированный native bootstrap необходимы для автономной
Radxa с неверными часами. Лабораторное сравнение ничего не устанавливает на узлы.
