# Когда Radxa снова будет под рукой

Обновлено 2026-10-04. Это чек-лист отложенной проверки, не отчёт об успехе.
Опубликованная база проверок: `bfaced8` (UDP PMTU и измеренный soak;
постоянный TCP MSS для USB — в `5a0852c`).
На Radxa уже подтверждены `7df8bcf`, строгий USB-профиль `cvks4`, постоянный
SNAT и rescue. **Именно постоянное MSS-обновление ещё не принято на плате.**
Начать с разделов 1 и 2; старую DNS-миграцию повторять не нужно.

Без платы повторно проверен production-код `5a0852c`: 463 регрессионных теста,
601 проверка полного E2E в двух загрузках и 485 аварийных проверок — **passed**.
Отчёты `PUPW3U` / `3FDxgC` и ограничения — в
[описании стенда](clean-vpn-usb-e2e-lab.md). Новый [UDP/PMTU стенд](clean-vpn-usb-pmtu.md)
прошёл 62 сценария + 117 общих проверок (`NDK3kV`): крупные UDP в обе стороны,
DF/фрагментация, ICMP MTU 1400/1280 через NAT, остановка/возврат VPN и USB SSH.
Результаты повторного длительного прогона и исследования памяти сохраняются
отдельно в [USB soak](clean-vpn-usb-soak.md).
Ни один лабораторный результат не отмечает пункты физической платы выполненными.

Аварийная проверка 2026-10-03 выявила два дополнительных отказа: цикл рестартов
после SIGKILL из-за незавершённых журналов и отсутствие возврата USB-интернета
после потери carrier, хотя DHCP уже восстановился. Добавлены совместное
восстановление DNS/IPv6/IPv4 под строгим guard и контроль собственных uplink-маршрутов
независимо от состояния старого TCP-соединения. Повторный fault-тест обнаружил
также отложенную доставку USB-пакета к частному адресу через exit после обрыва:
теперь RFC1918 блокируется в FORWARD до разрешения USB → TUN, независимо от маршрутов.
Предыдущая аварийная приёмка: 485 проверок, `passed`,
`/var/tmp/meshpn-usb-e2e-SqiBVY/report.json`; 383 регрессионных теста также прошли.
Подробности — в [отчёте стенда](clean-vpn-usb-e2e-lab.md). Проверку SIGKILL на
Radxa проводить только после обновления и проверки второго USB rescue-входа,
как описано ниже. Результат VM не заменяет проверку платы.

## 1. Сначала проверить независимый USB-доступ

На Mac (имя интерфейса может измениться после переподключения кабеля):

```bash
ifconfig en9
ssh root@192.168.7.1
```

Оставить эту сессию открытой. Из другого терминала Mac:

```bash
ssh -p 2222 root@192.168.7.1 'printf "USB rescue OK\n"; uptime'
```

- [ ] Оба входа прошли аутентификацию, а не просто показали открытый порт.
- [ ] Mac имеет USB IPv4 в `192.168.7.0/24`; известный адрес был `192.168.7.19`.

Если rescue не работает — не перезагружать и не переходить к обрывам сети/часам.
Сначала разобраться, сохранив рабочий SSH:22.

## 2. Текущая Radxa: обновить только постоянный MSS

После нового аутентифицированного rescue-входа из раздела 1, на Radxa:

```bash
cd /root/dev/meshpn &&
git pull --ff-only &&
git log -1 --oneline &&
sudo env "PATH=$PATH" node scripts/clean-vpn-usb-gateway.mjs &&
sudo env "PATH=$PATH" bash scripts/autostart/install.sh --usb-gateway
```

При отказе остановиться и сохранить вывод. Временные тестовые правила не
очищать общим flush: неизвестные правила требуют отдельного разбора.
Перезапускается только SNAT/MSS-служба; VPN, guard, SSH и сеть не рестартуются.
Запуск службы асинхронный. Проверить после её готовности:

```bash
systemctl --no-pager show clean-vpn-usb-snat.service \
  --property=ActiveState,SubState,Result,NRestarts
sudo env "PATH=$PATH" node /usr/local/bin/clean-vpn-usb-snat.mjs --status
sudo /usr/local/bin/clean-vpn-killswitch.sh status
```

- [ ] Служба `active/exited`, status `ready`, `mss.present=2`, MSS 1360.
- [ ] Guard остался `cvks4` для обеих семей; новый SSH:2222 работает.
- [ ] Сохранены ревизия, вывод установки и путь резервной копии helper.

Далее перейти прямо к разделу 3. Подраздел ниже — только для старых установок.

### Загрузить исправления восстановления и native-памяти

[Лабораторная приёмка ускорения](clean-vpn-fast-recovery.md) сначала остановилась
по ограничению памяти. После [исправления native-памяти](clean-vpn-native-memory.md)
прошли 531 регрессионный тест, 645 проверок длительного прогона и 62 UDP/PMTU
сценария + 117 общих проверок на обычной сборке. Шесть первых USB HTTPS-ответов
после возврата сети/exit — 6,41–7,86 секунды. Это не замеры физической Radxa.
Ниже — порядок установки опубликованного исправления, не рабочего дерева.

После публикации и `git pull` нового кода одного обновления файлов недостаточно:
уже запущенный Node-процесс продолжает выполнять старую версию, а TUN-addon
требует пересборки на Radxa. При рабочем новом входе SSH:2222 и сохранённой
сессии USB:22, из `/root/dev/meshpn` под root:

```bash
(
  set -e
  cv_native_backup=$(mktemp -d /root/clean-vpn-native-backup.XXXXXX)
  cp -p native/tun_linux/build/Release/tun_linux.node "$cv_native_backup/"
  printf 'Native backup: %s\n' "$cv_native_backup"
  systemctl stop clean-vpn.service
  npm run build:tun-linux
  systemctl start clean-vpn.service
  systemctl show clean-vpn.service -p MainPID -p NRestarts -p ActiveState
)
```

Это прерывает VPN-трафик на время сборки; guard, USB и rescue не перезапускать.
При ошибке сборки VPN остаётся остановлен под guard: сохранить ошибку и путь
резервной копии, не очищать правила и не перезагружать сеть. Не продолжать обрывы.
Дождаться успешных проверок раздела 3, затем проводить раздел 4 **без** ручного
рестарта при обрыве. Обновление exit ради H2 PING не требуется; для исправления
памяти exit потребуется отдельная пересборка его TUN-addon.

### 2а. Архивный путь: миграция старого cvks2 / добавление USB-режима

**На текущей Radxa уже выполнено. Не повторять для установки MSS.**

На Radxa:

```bash
cd /root/dev/meshpn && git pull --ff-only
git log -1 --oneline
sudo env "PATH=$PATH" node scripts/clean-vpn-usb-dns-upgrade.mjs
```

Последняя команда — только план. При отказе остановиться и сохранить ошибку;
не обходить проверки владельцев файлов, профиля или firewall.
После успешного плана:

```bash
sudo env "PATH=$PATH" bash scripts/autostart/install.sh --upgrade-usb-dns
```

Этот явный режим штатно останавливает VPN и установленную SNAT-службу,
**не снимает guard и не рестартует networkd/USB/rescue**. Сохраняет резервные
копии заменённых файлов. При ошибке остановиться и сохранить вывод; никаких
автоматических down/rollback. При `upgraded-stopped` запустить перечисленные
в ответе `startUnits`. Для платы без постоянной SNAT-службы:

```bash
sudo systemctl start clean-vpn.service
```

Если в `startUnits` есть `clean-vpn-usb-snat.service`, запустить и её.
Дождаться готовности VPN и повторить client-check из раздела 3. Затем:

```bash
sudo env "PATH=$PATH" node scripts/clean-vpn-usb-gateway.mjs
```

После успешного плана добавления:

```bash
sudo env "PATH=$PATH" bash scripts/autostart/install.sh --usb-gateway
```

Это добавление rescue/SNAT, без рестарта основного VPN, Wi-Fi или USB.
Не использовать здесь fresh-install команду с аргументами VPN.

```bash
systemctl --no-pager show clean-vpn.service clean-vpn-killswitch.service \
  clean-vpn-usb-snat.service clean-vpn-usb-rescue.socket \
  clean-vpn-usb-rescue-address.service \
  --property=Id,ActiveState,SubState,Result,NRestarts,UnitFileState
sudo /usr/local/bin/clean-vpn-killswitch.sh status
sysctl net.ipv4.ip_forward
sudo iptables -w 5 -t nat -S POSTROUTING
```

- [ ] VPN `active/running`, guard и готовый SNAT `active/exited`, rescue `active/listening`.
- [ ] Guard status показывает `cvks4:both:block:tun0:154.62.226.216:22` для обеих семей.
- [ ] Wrapper VPN содержит `--dns-usb=1`; plain IPv4 DNS от USB идёт через общий tunnel-DNS.
- [ ] Учтено изменение политики: USB-клиент больше не может напрямую обращаться
  через плату к домашней LAN/роутеру, ни на стандартных, ни на других портах.
  SSH к самой Radxa на 22/2222 сохраняется; на Mac настройки не меняем.
- [ ] SNAT-служба и rescue socket включены (`enabled`).
- [ ] IPv4 forwarding равен 1. Установщик не включает его сам.
- [ ] Ровно одно правило с `--comment clean-vpn-usb-snat-v1`:
  source `192.168.7.0/24`, выход `tun0`, SNAT в `10.99.0.2`.
- [ ] Повторный вызов `install.sh --usb-gateway` не создаёт дубликатов и не рвёт SSH.

SNAT может сначала повторять попытки, пока VPN не готов. Если так и остаётся
в ожидании, собрать `journalctl -b -u clean-vpn-usb-snat.service --no-pager -n 40`.
Не снимать guard ради запуска SNAT.

## 3. Проверить оба пути и затем автозапуск

На Radxa, когда туннель готов:

```bash
sudo env "PATH=$PATH" node scripts/clean-vpn-client-check.mjs --probe --expect-exit-ip=154.62.226.216
```

На Mac:

```bash
curl -q -4 --noproxy '*' --interface en9 \
  --connect-timeout 5 --max-time 15 https://ifconfig.me/ip
curl -q -4 --noproxy '*' --interface en9 \
  --connect-timeout 5 --max-time 15 https://1.1.1.1/cdn-cgi/trace
```

- [ ] Сама Radxa проходит проверку, Mac получает `154.62.226.216`.
- [ ] Оба HTTPS с Mac успешны минимум в пяти новых запусках каждый, в том
  числе после паузы 30 секунд. У trace поле `ip=154.62.226.216`, нет TLS timeout.
  Несколько успехов не доказывают устранения всех MTU/PMTU-проблем.
- [ ] Rescue SSH:2222 по-прежнему принимает новый вход.
- [ ] После этого выполнить штатный `sudo reboot`, переподключиться по USB
  и повторить входы, status и HTTPS **без повторной установки и ручного
  применения SNAT/MSS**. При таймаутах сохранить вывод до вмешательства.
- [ ] Отдельно проверить холодный старт: сначала штатно выключить плату,
  затем снять/вернуть питание. Не выдёргивать питание работающей файловой системы.
- [ ] После холодного старта VPN, rescue, forwarding и SNAT восстановились автоматически.

Постоянство SNAT/rescue после reboot уже подтверждено; теперь требуется
отдельная приёмка автозапуска обоих MSS-правил. Холодный старт — отдельный пункт.

## 4. Повторить обрыв Wi-Fi с сохранением USB

Перед тестом подтвердить работающий VPN и новый вход по rescue. Выключить и
включить роутер; VPN вручную не рестартовать, иначе проверка автовосстановления теряет смысл.
После возврата Wi-Fi собрать на Radxa:

```bash
ip -brief addr show wlan0
ip -4 route show default
ip -4 route get 154.62.226.216
ip -4 route get 1.1.1.1
sudo journalctl -b -u clean-vpn.service --no-pager -o short-monotonic \
  --grep='uplink-repair|uplink-watch|h2-health|TLS attempt|deadline|usb-recovery|таймаут|No route|default route|Error|failed'
```

- [ ] Wi-Fi ассоциировался, DHCP/default вернулись.
- [ ] Exit `154.62.226.216` идёт через `wlan0` и роутер, **не через tun0**.
- [ ] `1.1.1.1` идёт через `tun0`; проверки Radxa и Mac снова проходят без рестарта.
- [ ] Записать длительность восстановления после возврата DHCP, изменение IP
  и наличие `uplink-repair`. Отсутствие записи не ошибка, если маршрут не исчезал.

После установки [быстрого восстановления TLS/H2](clean-vpn-fast-recovery.md)
цель — первый успешный ответ за единицы секунд после возврата DHCP/default,
а не ожидание нескольких минут. В лаборатории введён предел 10 секунд.
Если на плате он превышен — сохранить диагностику до ручного вмешательства;
это не основание отключать guard или перезапускать USB/networkd.
Замерять запросом по IP, чтобы отдельно исключить DNS Mac; использовать новые
curl-соединения, фиксировать время DHCP и первого HTTPS 200. Сохранить MainPID /
NRestarts до и после. Проверить `negotiated ALPN=h2`: HTTP/1.1 silent blackhole
этим механизмом пока не покрыт. Долгое подключение самого Wi-Fi/DHCP измерять
отдельно, не относить к времени восстановления VPN после DHCP.
Текущий ремонт поддерживает новый DHCP-адрес при прежних gateway и interface
identity. Смена gateway/интерфейса — отдельный, пока не поддержанный сценарий.

## 5. Отложенные проверки — отдельными контролируемыми этапами

- [ ] **Авария процесса после обновления.** Только со второй проверенной сессией
  rescue SSH:2222 и действующим `cvks4`: однократно завершить главный процесс
  `clean-vpn.service` через SIGKILL, не трогая guard/networkd/USB. Зафиксировать
  `usb-recovery` в журнале, возврат USB HTTPS/DNS через exit без ручного recovery,
  стабильный NRestarts после восстановления и доступность SSH:22/2222.
  Измерить реальную задержку: VM-бюджет 420 секунд включает медленный TCG и
  не является нормой для платы. Если сервис зациклился — сохранить логи до
  вмешательства, не снимать защиту ради возврата интернета.
- [ ] **Mac при остановленном VPN.** Проверить блокировку forwarded IPv4/IPv6
  и DNS, одновременно сохраняя USB SSH; затем штатно запустить VPN и убедиться
  в восстановлении без ручного SNAT. Kill-switch не останавливать.
  Перед тестом подготовить точные запросы и ограниченный захват на Radxa.
- [ ] **DNS именно Mac.** Host `client-leak-check` не проверяет forwarded-клиента.
  Другой VPN/Wi-Fi на Mac может обслуживать DNS отдельно от `curl --interface`.
  Нужны контрольные имена и наблюдение usb0/tun0/wlan0. Обычный успешный HTTPS
  и один таймаут не доказывают отсутствие утечек.
  Старый `cvks2` разрешал прямой DNS к LAN-роутеру вне VPN. После обновления
  на `cvks4` проверить, что IPv4 UDP/TCP:53 к `192.168.1.1` при active
  перехватывается и уходит через TUN, а при stopped блокируется. Запросы к
  публичному DNS и resolver платы также работают только через готовый VPN.
  IPv6 DNS роутера должен блокироваться, если такой путь есть.
  Запрос должен быть замечен на `usb0`, иначе таймаут на Mac ничего не говорит
  о фильтрации Radxa. Не выключать guard ради положительного контроля на плате.
  Успешный DNS-ответ при active не означает прямого доступа к роутеру:
  проверить фактический путь запроса. Не менять
  настройки остальных интерфейсов/VPN Mac вслепую ради прохождения проверки.
- [ ] **IPv6 именно Mac.** Сначала подтвердить, что проверяемый путь вообще
  мог бы работать: отказ из-за отсутствия IPv6-адреса/маршрута нельзя приписывать guard.
  В VM IPv6 DNS-фильтрация проверяется со статическими соседями. Обнаружено
  отдельное ограничение прежнего host-only IPv6 guard: unicast NA к ULA/GUA
  не разрешён. Динамический NDP/RA и полноценный IPv6-шлюз для Mac не приняты;
  текущий USB-профиль — IPv4 VPN с блокировкой всего forwarded IPv6.
- [ ] **Нестандартные порты и LAN.** TCP/UDP к публичному контрольному серверу
  через USB должны идти через exit при active и не достигать сервера при
  stopped. TCP/UDP к домашней LAN через Radxa блокируются в обоих состояниях.
  Проверить SSH 22/2222 к самой плате до/после, не менять маршруты Mac.
- [ ] **Часы после длительного простоя.** Сравнить UTC платы и exit до ручной
  коррекции, найти `clock-date` в журнале и подтвердить восстановление VPN.
  Не привязывать сценарий к одному дню: интересуют несколько суток/неделя и
  границы допустимого времени сертификата. Для искусственного сдвига сначала
  подготовить возврат точного времени через проверенный USB-доступ и исключить
  вмешательство NTP в измерение. Команд перевода часов в этом чек-листе нет.
  За пределами срока сертификата TLS-проверка не обходится; это ожидаемый отказ,
  не обещание автоматического восстановления из любой даты.
- [ ] **Ранний boot capture.** Если прежние временные capture-gates ещё стоят,
  сохранить отчёт и решить отдельно, оставлять ли диагностику. Не переустанавливать
  и не удалять её вслепую; она не требуется для постоянного SNAT/rescue.

Отказ guard и полный uninstall не включать в обычную проверку реальной платы.
SIGKILL — только отдельный контролируемый этап с условиями выше; его не нужно
выполнять для обычного обновления или проверки интернета.

## Что сохранить по итогам

Ревизию, способ старта (reboot/cold boot), вывод units/guard/NAT, результаты
Radxa и Mac, факт нового входа SSH:2222 и время восстановления после обрыва.
Отмечать пункты только после реального результата. Не включать ключи,
Bearer, пароли, полный argv или необработанный захват пользовательского трафика.

Все эти этапы выполнены в изолированной VM без Radxa, внешнего роутера
и изменения Mac/сетевых настроек хоста. VM не воспроизводит драйвер Wi-Fi/USB
платы и сетевой стек macOS. Реальные проверки выше остаются отложенными.

### Общий лабораторный охват и прежние результаты

1. Полный lifecycle USB-установки в VM: настоящий shell installer, настоящий
   VPN/TLS/TUN и Linux USB-peer вместе; установка с нуля и добавление к существующей,
   сохранение на диск и следующая загрузка. Новый стенд —
   [clean-vpn-usb-e2e-lab.mjs](clean-vpn-usb-e2e-lab.md): настоящий VPN вместо
   прежней fixture готовности; сохранение именно опубликованных файлов.
2. Приёмка forwarded DNS/IPv6 и fail-closed в VM: положительный контроль,
   блокировка без TUN, восстановление, отсутствие влияния на rescue.
   Подготовить безопасную аналогичную процедуру для настоящего Mac.
3. Ошибки lifecycle: сбой публикации, чужие файлы/drop-ins/rules, повторная
   установка, удаление с остановленным VPN; затем crash/recovery без снятия guard.
4. Длительный прогон с реальным TLS в VM: пропадание uplink, удаление маршрутов
   при DHCP, новый адрес, поздняя сеть/exit, длинные соединения и повторные reconnect.
5. После выявления требований — уменьшить привязку USB-режима к конкретному
   адресу exit и профилю. Это отдельное расширение, не ослабление текущих проверок.

В первом прогоне полного стенда обнаружен обход DNS через LAN-исключение
`cvks2`. Промежуточный `cvks3` проверен в VM (450 утверждений, два boot,
`/var/tmp/meshpn-usb-e2e-4otg9r/report.json`). Теперь он заменён строгим `cvks4`
с общим DNS-перехватом USB/host; результаты v3 не доказывают готовность v4.
Обновление существующей установки проверяется тем же стендом с DNS роутера
по IPv4/IPv6 и локальным DNS-прокси.
Лабораторный PASS не заменяет пункты на Radxa выше.
