# Разрыв combo после нагрузки: IP queue и TLS liveness

Исправление `18644a2`, 2026-10-31. Пользователь сообщил об отказе **iPhone по USB**
после Speedtest и безуспешном возврате на boring. Предыдущие прогоны Chrome
через HTTP proxy не воспроизводили этот клиент и не закрывают его приёмку.

## Найденный дефект

Packet-ветка обслуживает IP DATA и PING/ACK в одном TLS-потоке. При заполнении
очереди IP-пакетов к TUN движок полностью прекращал `SSL_read`. Ответ PING
оставался за DATA, и через пять секунд соединение закрывалось как мёртвое.
Это относится к boring и packet-ветке combo, к H2 и H1.

В физическом прогоне UDP-нагрузки и последующем наблюдении зафиксированы
`h2_ping_timeout` на exit, `tls_read` на клиенте и новые reconnect. В отличие
от исходного пользовательского отказа, в этих пробах reconnect завершался.
Это реальный воспроизведённый дефект, но ещё не доказательство единственной
причины отказа iPhone и прежних TLS-handshake timeouts.

Теперь чтение TLS продолжается с прежним ограничением работы за tick.
Полная очередь отбрасывает только проверенный внутренний IP-пакет, учитывая его
в `dropped_packets`. Проверка источника/назначения и framing выполняется до
отбрасывания. Очередь ограничена прежним 1 MiB; дополнительные буферы не вводятся.
Внутренний TCP восстанавливает потерянные IP-пакеты своим механизмом повторов;
UDP при перегрузке может терять пакеты. Управляющие сообщения не блокируются
на заполненной очереди получателя.

## Регрессия и границы

Прежняя pressure-проверка длилась 1,5 s и заканчивалась до пятисекундного timeout.
Теперь получатель не читает пакеты ещё 10 s при продолжающемся producer; тест
требует неизменного ready без session events, реального переполнения со счётчиком
drop и двусторонней передачи после ограниченного drain очереди.

- Прежний lab fixture: новый тест падает с точным `h2_ping_timeout` и отдельно
  с `h1_ping_timeout`.
- Исправленный fixture: H2 и H1 проходят sustained pressure, передачу после него,
  настоящий blackhole с восстановлением и проверку CA/имени/PSK — **2/2**.
- Связанные multi-peer, H1 independent peer, session events и reload — **38/38**,
  без skips.
- VPS: native сборка и CTest **14/14**, новый engine установлен штатным updater
  с rollback; pending journal отсутствует. Проектный временный swap после
  сборки отключён и удалён, fstab и другие службы не менялись.
- Radxa: собственная сборка и CTest **14/14**, engine установлен тем же updater
  с rollback, без изменения network owner или guard. Native restart через API
  занял 1,767 s; USB DNS A/AAAA UDP/TCP **4/4**, HTTPS через exit **3/3**,
  download ровно 1 MiB.
- Независимый admin observer: настоящий packet ClientHello `matched`,
  `differences=[]`, kernel drops 0. Профиль `chromium-156-bounded-cold-v1`,
  JA4 `t13d0915h2_f91f431d341e_54d72502093d`; это ограниченный профиль,
  не доказательство полной браузерной неотличимости.
- На исправленной паре повторены UDP upload 40 Mbit/s (без потерь) и
  download 80 Mbit/s (около 45,7% UDP loss при перегрузке). Одновременно полный
  Chrome Speedtest завершился **42,57/44,29 Мбит/с**. До последующего намеренного
  переключения режима клиент сохранил PID 29212, один `ready` и **0 session ends**.
  Это функциональный прогон при смешанной нагрузке, не benchmark и не iPhone.
- После этой нагрузки проверены combo → boring (32,536 s) и boring → combo
  (30,572 s). В boring с USB снова прошли DNS 4/4, HTTPS 3/3 и download 1 MiB.
  Пара оставлена в combo; профиль и guard сохранены, recovery journal отсутствует.

## Физические диагностические прогоны до исправления

На прежнем клиенте три Chrome 156 Speedtest через процессный USB proxy завершились:
22,10/46,36, 43,43/45,78 и 44,12/47,04 Мбит/с. Шесть download по 8 MiB и шесть
upload по 4 MiB через HTTPS 443 тоже прошли. Эти результаты относятся к TCP
через proxy, а не к iPhone/QUIC/ECH.

Отдельный iperf на `10.99.0.1:18331`, только внутренний адрес exit, ограничен
transient systemd runtime. Маршруты и firewall для него не менялись. Корректная
проба использовала `--bind-dev tun0`: отправка 40 Mbit/s, 20 s — без UDP loss;
приём 80 Mbit/s, 25 s — около 44% loss при перегрузке и около 43,9 Mbit/s
полезной скорости. Параллельные HTTPS 8/8 прошли. Первый iperf без bind-dev ушёл
по существующему private-LAN bypass и **не считается** UDP-проверкой; повторный
запуск после завершения сервера получил connection refused, тоже не успех.

## Что ещё проверять

Снять именно iPhone по USB: первый и следующий Speedtest, затем HTTPS и состояние
packet/relay в момент отказа. На Radxa используется bounded phone recorder;
Wi-Fi SSH сохраняет доступ при переносе USB. На VPS режим pcap rotation завершался
segfault внутри tcpdump; вместо него используется ограниченная текстовая запись
TCP-метаданных. Системные пакеты VPS для этого не заменялись.

Начальные потери продолжения ClientHello/обратных ACK на пути к 443 остаются
отдельным наблюдением без установленной причины. Исправление очереди не даёт
оснований объявить этот сетевой отказ устранённым. Порт 443, ключи, TLS-профиль,
проверки сертификатов и guard сохраняются. Системная сеть Mac не меняется.
