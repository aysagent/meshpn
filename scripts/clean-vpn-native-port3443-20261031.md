# Radxa ↔ VPS: рабочий combo endpoint переведён на 3443

2026-10-31, после явного подтверждения пользователя «переключи».

Рабочая пара теперь использует `154.62.226.216:3443` для обеих веток combo.
Изменены только поля:

- exit `/opt/clean-vpn-native/combo-daily-exit/config.json`:
  `boring.port`, `transparent.listen.port` — 443 → 3443;
- client `/opt/clean-vpn-native/combo-daily/config.json`:
  `boring.port`, `transparent.exit.port` — 443 → 3443.

Оба отдельных candidate проверены установленным `engine --check-config`.
Перед применением каждый candidate сравнен с актуальным конфигом: допустимы
только эти два изменения. Сохранены приватные резервные копии, затем рабочие
конфиги заменены атомарно с fsync. Перезапущены только native engine units,
без перезапуска владельцев маршрутов. Ключи, CA, SNI, выбранный профиль,
DNS, маршруты и правила guard сохранены. Промежуточный TCP proxy не установлен:
3443 слушает сам native exit.

Резервные копии `config-before.json` и метаданные `change.json`:

- VPS: `/var/lib/clean-vpn-port3443-sejys5ys/`;
- Radxa: `/var/lib/clean-vpn-port3443-8e_1iixx/`.

Для отката нужны обе исходные конфигурации и перезапуск соответствующих engine
units. Односторонний откат оставит несовпадающие endpoint-порты.

## Что наблюдалось до смены порта

Автономная запись после загрузки содержит запросы USB iPhone. DNS Yandex
получал ответ, ClientHello поступал в local REDIRECT, но ServerHello телефону
не возвращался; примерно через 10 секунд relay закрывал соединение.

Одновременные tcpdump Radxa/VPS сопоставлены по TCP sequence numbers:
Radxa отправляла два сегмента ClientHello, VPS видел только первый (1288 байт).
Отправленный VPS ACK первого сегмента отсутствовал в записи Radxa; на Radxa
продолжались retransmissions. INPUT/OUTPUT VPS имели ACCEPT, служба слушала.
Отдельные короткие и длинные TLS ClientHello (517 и 1614 байт) через временный
ограниченный byte-echo на 3443 возвращались полностью. На 443 TLS probes
зависали. Уменьшение TCP_MAXSEG и разбиение TLS records не помогли.

Это свидетельство проблемы пути для наблюдавшихся соединений на 443,
не точная атрибуция оператору, hotspot, DPI или конкретному устройству.
Диагностический echo завершён; постоянно работающего echo/proxy нет.

## Проверки после переключения

Физическая Radxa: `native-combo-daily.service` active, StatusText ready,
реальный TCP socket к exit:3443 ESTABLISHED. Exit native listener:3443 active.
Владелец сети и kill switch active. Админка читает новый endpoint из конфига.

С Mac через привязку отдельных сокетов к USB en9, без изменения настроек Mac:

- `https://internet.yandex.ru` с переходом на `https://yandex.ru/internet/`: HTTP 200;
- `https://www.speedtest.net`: HTTP 200;
- `https://example.org`: HTTP 200;
- DNS UDP и TCP к 1.1.1.1: NOERROR, непустые A-ответы;
- HTTPS POST через httpbin.org: HTTP 200, 276000 синтетических байт переданы
  за 2.64 с; echo body совпал побайтно, SHA256
  `5cef619c45fdf543420c71a348fcc260439553c7518da4ed6d9e8f41ffed2567`.

Это проверка загрузки страниц и конкретной HTTPS-отправки, не полный benchmark
Speedtest и не подтверждение исправления iPhone до повторного физического теста.
Автономная запись остановлена, её автозапуск отключён. Сами рабочие конфиги
сохраняют порт 3443 после перезагрузки; холодный старт с новым портом отдельно
не проверен. Старые экспорты других клиентов с портом 443 требуют обновления.

## Отдельная проверка hotspot Tatsiana

Последующий отказ не следует смешивать с исходным наблюдением на 443.
На `iPhone (Tatsiana)` (5 GHz, 5220 MHz) TCP SYN к VPS:3443 доходил до VPS,
сервер отправлял SYN-ACK, но его не было на wlan0 Radxa. Отдельные подключения
к тому же VPS на 22 и 443 также не устанавливались. При этом ассоциация Wi-Fi,
DHCP 172.20.10.13 и ping шлюза 172.20.10.1 работали; маршрут к exit и
разрешающий его OUTPUT guard были корректны. Это отказ до TLS, а не
доказательство ошибки ClientHello или авторизации.

После паузы пользователя Tatsiana была на 2.4 GHz (2437 MHz, другой BSSID).
VPN на 3443 восстановился, публичный IP hotspot остался 128.71.189.81.
Через USB повторно прошли Yandex (полный redirect, HTTP 200), Speedtest (HTTP
200), upload 276000 байт (HTTP 200, побайтный echo совпал, 3.62 с).
Изменение режима/перезапуск hotspot коррелируют с восстановлением; точная
причина потерь на прежнем подключении, включая роль драйвера Wi-Fi, не доказана.

Сохранённому профилю Tatsiana через API задан priority=10 (было 0), профиль
Андрея остался priority=0. Это фиксирует предпочтение сети для следующего
физического теста после перестановки USB. Секрет профиля сохранён существующий.
Полный Speedtest upload и повторная работа iPhone после этого ещё не проверены.

## Повторный отказ iPhone: задача остаётся открытой

Запись `run-VixrXnmw/boot-ktORaHIF` содержит USB-запросы iPhone и исходящие
SYN к exit:3443 от 172.20.10.13 без входящих SYN-ACK. DNS-запросы yandex.ru
повторяются без ответов. Пользователь подтвердил: USB подключён к Андрею,
Wi-Fi upstream — Tatsiana; это два разных телефона. После возврата к ноутбуку
плата выбрала доступный hotspot Андрея, и VPN стал ready. Предыдущее успешное
измерение через Tatsiana 2.4 GHz не означает, что проблема повторного старта
устранена. Перевод hotspot на 2.4 GHz сам по себе не стал достаточным решением.

Дополнительно выявлены и исправлены две проблемы выбора Wi-Fi:

- Tatsiana переставала передавать SSID, оставаясь на том же BSSID. При
  `hidden=false` повторное подключение не проходило; после сохранения
  `hidden=true` через API подключение к 172.20.10.13 прошло без открытия
  настроек hotspot. Это исправление обнаружения сети, не доказательство
  восстановления TCP до VPS.
- `Wifi.sync()` включал профили в порядке добавления, поэтому менее
  предпочтительная сеть успевала подключиться первой. В `6f78059` профили
  применяются по убыванию priority. Установлено штатным admin update, 4 Wi-Fi
  регрессионные проверки прошли. После загрузки Tatsiana создаётся первой
  (network id 2, её id_str, priority 10, scan_ssid 1 проверены), Андрей — второй.

Тесты загрузки выполнены с USB в ноутбуке, автономная запись сохранена в
`run-1M0MDlDQ`. Во время последней загрузки телефон Tatsiana уже ушёл;
подтверждён fallback на доступную сеть Андрея и native VPN ready. Проверка
холодного старта с доступной Tatsiana и исправленными профилями не завершена.
Фоновая запись остановлена, её автозапуск disabled. Рабочий порт остаётся 3443,
kill switch active. VPN/фильтры на телефоне не менялись.

Следующий физический тест: оставить USB в ноутбуке, держать Tatsiana доступной,
проверить холодную загрузку и одновременно снять SYN/SYN-ACK с обоих концов.
К проверке iPhone через USB переходить после устойчивого прохождения этого
теста. До этого работу iPhone не считать исправленной.
