# H2: несколько клиентов, медленный получатель и бюджет памяти

Лаборатория проверяет один native exit с 1, 4 и 8 аутентифицированными клиентами.
У каждого отдельные PSK и tunnel IPv4. C++ создаёт и проверяет пакеты; Node
подготавливает временные сертификаты/конфигурации и собирает отчёт.

## Запуск на Mac

После подготовки лаборатории и кэша зависимостей (`--tls-profiles`):

```bash
npm run lab:native:mac -- --h2-budget
```

Команда собирает актуальный код, запускает полную матрицу и сохраняет новый JSON
в `~/Library/Caches/meshpn-clean-vpn-lab/results/`. Контейнер запускается с
`--network=none --cap-drop=all`. Все TCP-соединения проходят по его loopback;
вместо TUN используется socketpair. Firewall, DNS и маршруты Mac не меняются.
После работы VM можно остановить `npm run lab:native:mac -- --stop`.

В уже подготовленной Linux-лаборатории:

```bash
CVPN_BUILD=/lab/worktree/native/clean_vpn/build \
  node scripts/clean-vpn-native-h2-budget.mjs /tmp/new-h2-budget-report.json
```

Существующий отчёт не перезаписывается. Ошибка проверки, нехватка данных или
превышение времени дают ненулевой exit code. Полный отчёт со статусом passed
создаётся только после всех шести случаев. Общий deadline одного случая — 90 s;
он не является целевым временем прохождения. API runner также позволяет 3–30
циклов; расширенная серия используется в [Linux kernel lab](clean-vpn-native-h2-kernel.md).

## Матрица

Для каждого количества клиентов выполняются два варианта:

| Вариант | Client stream receive window | Client connection receive window |
| --- | --- | --- |
| baseline | 1 MiB | 1 MiB |
| browser-credit | 6 MiB | 15 MiB |

Второй вариант включается **только в engine-fixture**. Production engine не
содержит этого переключателя и по-прежнему отвергает профиль с такими окнами.
Лимит каждой прикладной очереди остаётся 1 MiB в обоих вариантах. Exit receive
credit, header limits, HPACK policy, TLS-профиль и авторизация не меняются.
Это эксперимент с кредитом потока, не включение полного профиля Chromium.

Фактические начальные SETTINGS и WINDOW_UPDATE считывает существующий тестовый
observer после SSL_read и до nghttp2; Node отдельно разбирает эти кадры и проверяет
значения. Это инструментированный fixture, не новый внешний browser capture.

## Нагрузка и критерии

В каждом случае — три цикла. Внутри каждого:

1. Две секунды медленного чтения одним клиентом: один 16 KiB пакет примерно
   раз в 50 ms, одновременно exit получает поток пакетов для этого клиента.
2. Прекращение нагрузки и дренирование очередей; затем проверенный обмен всех
   клиентов в обе стороны без переподключения.
3. Две секунды полного отсутствия чтения у всех клиентов кроме одного. При одном
   клиенте второго, здорового peer нет — отчёт не утверждает проверку его прогресса.
4. Повторное дренирование и проверенный обмен. Затем отключение всех клиентов,
   проверка удаления сессий и повторное подключение. Во втором цикле клиенты
   завершаются SIGKILL; в остальных используется команда uplink-off.

Здоровые клиенты должны продолжать обмен во время давления на медленных. Каждый
полученный пакет сравнивается с ожидаемыми байтами и адресом получателя. Потери
пакетов, адресованных медленному клиенту, допускаются существующей bounded drop
policy exit и считаются отдельно. Отчёт не обещает lossless доставку при перегрузке.

Прогон обязан реально создать давление: минимум 3 MiB инжектированных пакетов на
медленного клиента, минимум три resource samples и измеренная заполненность
хотя бы одной очереди каждого медленного клиента не менее 512 KiB за фазу.
Индивидуальные счётчики сохраняются в отчёте. Без этого результат не принимается.

Измеряются отдельно:

- RSS exit, каждого клиента и сумма RSS клиентов;
- текущие логические байты outgoing/network/packet queues;
- receive allocations и queued send memory TLS TCP-сокетов через Linux SO_MEMINFO;
- FD count, число живых/созданных/удалённых H2-сессий;
- прогресс здоровых клиентов и наибольшее измеренное время их обмена.

SO_MEMINFO может оказаться недоступным/усечённым под эмуляцией. Тогда соответствующие
пики записываются как null, `kernelSocketMemoryComplete:false`; это не нулевое
потребление памяти ядром. Остальные проверки выполняются, но такой отчёт не
обосновывает повышение production credit.

Барьер RSS — 128 MiB на процесс; дополнительный рост exit относительно прогретого
baseline ограничен `32 MiB + 4 MiB × число клиентов`. После второго цикла
дополнительный рост RSS exit относительно этого baseline должен быть меньше 8 MiB.
Это пороги ограниченного
теста, не обещание точного расхода памяти в production.

После отключения всех клиентов число FD exit должно точно вернуться к исходному,
число живых сессий и логические очереди — к нулю; created и destroyed совпадают.
Штатное завершение проверяет выход всех дочерних engine. При аварии harness его
дочерние процессы завершаются через Linux PDEATHSIG.

## Границы вывода

Замеры очередей и RSS дискретные. Логические байты не включают всю ёмкость
аллокатора, а SO_MEMINFO здесь охватывает только TLS TCP-сокеты, не всю память
ядра. Короткая серия не доказывает отсутствие длительной утечки. Loopback не
моделирует WAN RTT, loss и пропускную способность; socketpair не заменяет
приёмочные испытания настоящего TUN и маршрутизации.
RSS процесса в macOS-лаборатории также включает расходы эмуляции x86-64;
это измерение данного стенда, а не прогноз расхода RAM на Radxa или VPS.

Даже успешная матрица не меняет production caps автоматически. Для такого решения
нужны отдельный замер пользы больших окон на заданном RTT и более длинный soak.

36 фаз нагрузки и 18 циклов восстановления прошли. Для всех 104 соединений,
включая reconnect, observer подтвердил начальные SETTINGS/WINDOW_UPDATE.
Каждый медленный клиент прошёл индивидуальные пороги нагрузки и заполнения очереди.
Регрессии: CTest 10/10, native TLS profiles + multi-peer 18/18, macOS lab parser
4/4, без пропусков. Multi-peer тест также проверяет 32 клиента и отказ вытеснения
активного владельца повторным подключением с тем же ключом.

При одном клиенте отдельного здорового peer нет. Все измеренные прикладные очереди
остались не больше 1 MiB; после отключений FD exit возвращались к baseline,
живые сессии и очереди — к нулю. Отбрасывание пакетов медленных клиентов при
перегрузке наблюдалось и записано в JSON. Здоровые клиенты продолжали обмен.

Это один короткий прогон под эмуляцией, без фиксированной скорости инжекции;
таблица не доказывает преимущество или причинное влияние размера окна на скорость
и задержку. В частности, пик 159.4 ms не является статистической оценкой.
Память TCP ядра во всех фазах unavailable. **Повышение production credit не одобрено.**
