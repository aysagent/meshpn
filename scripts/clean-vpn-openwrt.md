# Clean VPN для OpenWrt: исследование и план

2026-10-28. **Это проект интеграции, пакетов и OpenWrt-приёмки пока нет.**
Проверены исходники native engine, текущей админки и документация OpenWrt.
На роутерах ничего не устанавливалось. Исследование дополняет
[текущий локальный план](../admin/LOCAL-PLAN.md), не закрывает его оставшиеся этапы.

Дополнение 31 октября: [настоящий OpenWrt VM boot smoke](clean-vpn-openwrt-vm.md)
готов, procd/UCI/respawn/stop прошли на официальном x86/64 image без NIC.
Это не VPN/LuCI/package приёмка; критерии полной версии ниже остаются открыты.

## Требования и решение

Сделать собственное приложение **`luci-app-clean-vpn`** в интерфейсе OpenWrt
с native client/exit. Функциональность должна максимально соответствовать
[нашей админке](../admin/README.md), включая отдельную страницу захвата браузера,
сохранение/выбор профиля и независимого наблюдателя с выгрузкой pcap.
Эти три функции входят в критерии полной версии, не заменяются ссылкой на CLI.

Распространение — **локальная установка собственных пакетов**. Публикация
в официальном feed OpenWrt, публичном каталоге или стороннем магазине не нужна.
Перепрошивка роутера ради приложения также не является исходным требованием.

Предлагаемая упаковка:

| Пакет | Назначение |
| --- | --- |
| `clean-vpn-native` | C++ engine, закреплённые зависимости и браузерные профили |
| `clean-vpn-openwrt` | UCI, procd, ubus, netifd/fw4/DNS adapter, проверка и восстановление |
| `clean-vpn-profile-tools` | Сервер захвата TLS/H2, обработка профилей, независимый pcap-анализатор |
| `luci-app-clean-vpn` | Страницы LuCI, меню, точные rpcd ACL; полная установка включает profile-tools |

Headless client/exit можно устанавливать без UI и инструментов измерения.
Разделение пакетов не должно убирать функции из полной LuCI-установки.
Docker на роутере не требуется: это обычные службы OpenWrt. Контейнерная
сборка и standalone/Docker/Podman runtime остаются отдельными вариантами проекта.

Современный LuCI позволяет сделать JS views, JSON-описание меню и rpcd ACL.
Используем штатную авторизацию LuCI и её сессии, без второго веб-сервера админки,
отдельного пароля `admin` и iframe с существующей Radxa-страницей.
Источник: [структура LuCI-приложения](https://raw.githubusercontent.com/openwrt/luci/master/applications/luci-app-example/structure.md).

## Что уже можно переиспользовать

- [C++ engine](../native/clean_vpn/engine.cc): Linux TUN, boring-tls, проверка
  CA/имени/PSK, TLS-профиль, multi-peer exit, native DNS. Для разных клиентов
  нужны отдельные peer IPv4 и ключи; текущий лимит exit — 32 peers.
- [ServiceNotify](../native/clean_vpn/service_notify.hpp) не зависит от libsystemd:
  foreground service разрешён без `NOTIFY_SOCKET`. Сам engine поэтому не
  требует systemd, но текущие обвязки и гарантия readiness требуют адаптации.
- [Проверка TLS-профиля](../native/clean_vpn/tls_profile.hpp), форматы capture
  bundle, fixtures, сравнения JA3/JA4 и отрицательные тесты — общий контракт.
- Логика candidate → validate → apply → health → rollback из
  [транзакций настроек](../admin/lib/vpn-settings-transaction.mjs) применима
  концептуально. Системные вызовы и хранилище нужно переносить, а не копировать
  systemd/Radxa broker как есть.

Первый поддержанный транспорт OpenWrt — **boring-tls с текущим поддержанным
подмножеством сохранённого браузерного профиля**. `browser_profiles:false` в
capabilities не отменяет `experimental_tls_profiles`: полного воспроизведения
любого браузера пока нет. UI обязан показывать ограничения движка.

`transparent-tls` и `combo-tls` есть в native engine как experimental; их
REDIRECT/SO_ORIGINAL_DST, replay и crash lifecycle требуют отдельных OpenWrt
испытаний. Отдельный native аналог Node-транспорта `tls` не следует считать
готовым. Четыре пункта в dropdown сами по себе не означают четыре поддержанных
режима. Для transparent используется исходный ClientHello приложения;
сохранённый профиль применяется к boring-плечу, включая его в combo.

## Страницы LuCI и соответствие текущей админке

Раздел «Services → Clean VPN», общая строка состояния на его страницах.

| Страница / функция | Поведение в OpenWrt |
| --- | --- |
| Обзор | Время роутера, uptime, CPU по ядрам, RAM, интерфейсы/счётчики, температура при наличии датчика; отдельно процесс, TLS-ready, DNS и доступность exit |
| VPN | Роль client/exit, включение/остановка/restart, автозапуск, endpoint, порт, SNI, проверяемое имя, CA, MTU и доступные engine options; секреты не возвращаются в status |
| Exit / клиенты | Список peers, отдельные ключи/IP, отзыв клиента; публичный listener на WAN включается явно, NAT/forward только для заданного VPN subnet |
| Защита и маршруты | Kill switch, защищённые LAN/интерфейсы, отдельный выбор трафика самого роутера, IPv6-политика; остановка VPN не означает снятие защиты |
| DNS | Состояние dnsmasq/native DNS, локальные зоны, доступность upstream, пробы UDP/TCP; редактирование upstream только после поддержки движком |
| Браузерные профили | Список, import/export/delete, метаданные браузера/версии, совместимость, ожидаемые JA3/JA4; отдельно выбранный candidate и фактически применённый профиль |
| Захват браузера | Start/stop, временная HTTPS-ссылка, сертификат, число/качество образцов, TLS/H2, JA3/JA4, причины несовместимости, сохранение кандидата |
| Внешний наблюдатель | Start/stop, ограничение времени/объёма, фактический exit/uplink, JA3/JA4 из pcap, diff с профилем, потери/неполный захват, скачивание исходного pcap |
| Диагностика | Ограниченные DNS/HTTPS/ping-пробы, логи только своих служб, экспорт отчёта без PSK/закрытых ключей/паролей Wi-Fi |
| Wi-Fi | Scan, сохранённые uplink-сети, выбор/приоритет/удаление, восстановление после неудачного connect; через владельцев OpenWrt, без Radxa Netplan/wpa-файлов |
| Устройство / доступ | Разрешённая management-сеть, локальное имя, сведения о версиях/обновлении; пароль и общесистемные настройки через штатные страницы LuCI |

Функции, которых нет и в нашей админке, не изображаем рабочими:
политики по IP/domain/GeoIP — отдельный будущий этап. Native DNS сейчас имеет
фиксированные upstream `1.1.1.1`/`8.8.8.8`
([реализация](../native/clean_vpn/dns_relay.hpp)); произвольное поле в LuCI
не сделает их настраиваемыми.

Для Wi-Fi нужны scan/connect UX и память нескольких сетей, но не два
конкурирующих управляющих процесса. Подключение клиентского Wi-Fi может
затрагивать AP того же радио: нужен отдельный тест потери доступа и отката.
Текущий лимит Radxa в 256 профилей не является обещанием для любого роутера.

Вход по существующему management-IP/имени OpenWrt. `mpn.local` можно добавить
как опцию через доступный mDNS backend; простая DNS-запись не равна mDNS.
USB-only выбирается при наличии USB Ethernet, иначе явно заданная доверенная
LAN. Установка не меняет hostname, LAN IP, DHCP и доступ к текущему LuCI.
WAN-доступ к админке/capture по умолчанию отсутствует.

## Захват профиля: отдельный TLS endpoint обязателен

Текущий [capture server](lib/native-browser-capture-server.mjs) использует Node
TLS/H2, читает настоящий первый ClientHello и первые H2-кадры. JavaScript
страницы сам по себе не может получить ClientHello браузера. Обычная страница
за штатным HTTPS LuCI не даёт нам весь этот набор измерений.

План: из LuCI запускать отдельный ограниченный capture helper на management-IP
и свободном HTTPS-порту, открывать его ссылку в том браузере, чей профиль нужен.
Это браузер ноутбука/телефона, заходящего на роутер, не браузер внутри роутера.
Helper читает исходный TLS Hello, завершает только собственное TLS-соединение
и измеряет H2. Другие HTTPS-соединения пользователей не перехватываются.

Для базового варианта предлагается C++ helper с теми же pinned TLS/H2
библиотеками, чтобы не требовать Node на небольшом роутере. Это **новая работа**:
capture/build-profile/pcap parser сейчас написаны на JS, одного переноса HTML
недостаточно. Существующие JS-инструменты сохраняются как независимый эталон.
Node-вариант можно использовать для промежуточной лабораторной проверки на
мощном OpenWrt, но он не заменяет приёмку основной упаковки.

Сохраняем ограничения: срок сессии 3 минуты, до 32 образцов, token/authority
проверки, ограниченные соединения/размеры, закрытие после истечения срока
независимо от вкладки. Новый helper должен иметь собственный deadline,
не полагаться на таймер страницы.

Перед полноценным измерением TLS/H2 браузер должен доверять сертификату
capture endpoint. Показываем сертификат/отпечаток и инструкцию; доверие на
клиенте не устанавливаем автоматически и проверку TLS VPN не ослабляем.
Перезагрузка страницы не гарантирует новый cold handshake: UI объясняет
повторное использование соединений, cold/resumed и неполные образцы.
Дальше: образцы → assessment → candidate → native `--check-config` → отдельное
применение с восстановлением. Не включать новый профиль просто после захвата.

## Наблюдатель должен оставаться независимым

Сейчас [observer](../admin/lib/observer.mjs) запускает настоящий tcpdump через
transient systemd unit, а [анализатор](clean-vpn-pcap-fingerprints.mjs) читает pcap.
Для OpenWrt нужен supervisor вместо systemd-run, tcpdump/libpcap и отдельный
bounded parser. Backend не принимает произвольную shell-команду/BPF/путь из UI.

- Снимать на реальном uplink, найденном по маршруту до exit, с фильтром по
  адресу/порту. Не привязываться к `wlan0`: WAN может быть Ethernet, PPPoE, VLAN.
- Привилегии packet capture отделить от веб-интерфейса; непривилегированный
  parser, точные ubus методы, deadline/лимиты действуют при потере LuCI/rpcd.
- Пределы текущей админки — 5–60 секунд, 5000 пакетов, 16 MiB — верхняя исходная
  граница, на слабой плате уменьшаются. Учитывать также память TCP reassembly.
- Исходный pcap скачивается. Результат считается по фактическим пакетам,
  а не со слов VPN engine. Сравнение отдельно показывает активный и candidate
  профиль, timestamp и конкретное новое соединение.
- Без нового handshake, при capture drops, неполном stream или неизвестном
  link type результат `inconclusive/unsupported`, а не `matched`.
- Текущий parser ограничен Ethernet/IPv4/TCP. Для PPP/raw/SLL и других
  encapsulation нужны поддержка и fixtures либо явный отказ, без ложного PASS.
- Пассивный pcap TLS 1.3 не раскрывает зашифрованный H2: сравнение H2 доступно
  capture endpoint, но не этому наблюдателю без дополнительного расшифрования.
  Ключи TLS из VPN для такой проверки не экспортируем.

Проверка паритета: одинаковые эталонные и испорченные pcap прогоняются через
JS и новый parser, затем настоящий OpenWrt handshake проверяется внешним
JS-инструментом вне роутера. Для полной версии обязательны оба направления:
совпадающий профиль и заведомое несовпадение. JA3/JA4 match не доказывает полную
неотличимость браузера, UI не должен этого обещать.

## OpenWrt lifecycle, DNS и защита

Нужен собственный platform adapter, а не запуск существующего systemd installer.
Один владелец процесса: предлагается procd, с netifd-событиями/учётом интерфейса
через adapter. Если позже выбран полноценный netifd protocol handler, не надо
одновременно запускать второй engine из procd. Источники:
[procd](https://openwrt.org/docs/guide-developer/procd-init-scripts),
[netifd handlers](https://openwrt.org/docs/guide-developer/network-scripting).

1. **Запуск:** проверить config, сети/порты/marks, установить защиту, сохранить
   отдельный маршрут к exit через WAN, поднять TUN и engine. `running` procd
   не равен TLS-ready. Нужен канал состояния engine и настоящая DNS-проба.
2. **Firewall:** использовать fw4/nftables и его package includes. Не переносить
   iptables-обвязку с допущением, что nft backend уже решает совместимость.
   Свои chains/sets/marks, без flush чужих таблиц. Пережить fw4 reload,
   WAN reconnect, crash и порядок загрузки. Проверить software/hardware flow
   offloading; до доказанной совместимости не разрешать обход защиты через него.
3. **Область:** отдельно LAN forwarding и локальный OUTPUT роутера. Сохранить
   LAN management/DHCP и связь с exit. IPv6 пока блокируется в защищённой области
   либо полноценно поддерживается; IPv4 tunnel не защищает IPv6 автоматически.
4. **DNS:** штатные dnsmasq/odhcpd сохраняются. DNS LAN → dnsmasq → native
   listener (сейчас peer IPv4:1053) → туннель. Предотвратить петлю локальных
   запросов, прямой fallback, утечки при DHCP/WAN reload. Локальные зоны и DHCP
   продолжают работать. Глобальная смена upstream dnsmasq затронет и незащищённые
   сети: первая версия должна явно ограничить scope либо разделить экземпляры
   по интерфейсам, а не обещать произвольную политику одним переключателем.
5. **Отказ:** kill switch продолжает защищать выбранный трафик после падения
   engine. Выключение защиты — отдельная операция с явным смыслом «прямой выход».
   Плохие часы не лечить отключением TLS-проверки; условный доверенный bootstrap
   требует отдельного OpenWrt backend, перенос systemd/SSH units не достаточен.
6. **Настройки:** UCI хранит публичные параметры/идентификаторы, приватные ключи
   находятся в закрытых файлах. Candidate валидируется движком; журнал содержит
   только изменения, которыми владеем. Откат не восстанавливает целиком чужие
   `/etc/config/network`, `firewall`, `dhcp` поверх ручных правок.
7. **Применение:** нужны и штатная защита доступа LuCI, и проверка VPN/DNS после
   изменения. UCI commit/подтверждение страницы не доказывают VPN-health.
   Остановленный VPN остаётся остановленным после сохранения настроек.

Источники платформенных механизмов:
[fw4 includes](https://openwrt.org/docs/guide-user/firewall/firewall_configuration),
[переход iptables → nftables](https://openwrt.org/docs/guide-user/firewall/netfilter_iptables/netfilter_management),
[DNS/DHCP OpenWrt](https://openwrt.org/docs/guide-user/base-system/dhcp).

pcap/логи/временные измерения — ограниченные файлы в RAM, без постоянной записи
во flash. Ключи, профили, незавершённые транзакции переживают reboot. Для будущих
transparent/combo durable replay нельзя молча положить в `/tmp`: требования
к сохранности и износу flash проверяются отдельно.

## Сборка и локальная установка

Нужен SDK **конкретной версии и target/subtarget OpenWrt**: libc/ABI/CPU должны
совпадать. Бинарник Ubuntu с VPS/Radxa не является OpenWrt-пакетом.
Первую матрицу разумно ограничить x86_64 и выбранным ARM64 target; поддержку
MIPS/старого ARM подтвердить отдельно, включая pinned BoringSSL и atomics.
Не обещать работу на любом роутере до измерения flash/RAM/CPU.
Источник: [OpenWrt SDK](https://openwrt.org/docs/guide-developer/toolchain/using_the_sdk).

В [CMake](../native/clean_vpn/CMakeLists.txt) сейчас есть препятствия упаковке:
пути из предыдущей helper-сборки, `git rev-parse`, FetchContent для Brotli и
nghttp2, тестовые targets рядом с engine. Нужны подготовленные SDK source
archives с хешами/патчами и offline build, раздельные production/test targets.
Сохраняем проверку происхождения зависимостей, а не просто удаляем её:
BoringSSL `a7481f34712bc056a47ab91015536166b3a6cebb` с нашими патчами,
nghttp2 `534b74b72524e962c18c7146470914632ca7eb2d` с private ALPS adapter.
Подмена системным OpenSSL/произвольным nghttp2 ломает контракт профилей.

Сборка на Mac — внутри выделенной Linux Podman/VM, без смены сети хоста.
Если готовый SDK доступен только для x86_64 host, нужна соответствующая Linux
среда/эмуляция либо собственный toolchain; ARM64 target не означает ARM64 host SDK.
На самом роутере ничего не компилируем.

Выход: локальный bundle пакетов, manifest с git revision/SDK/target/хешами,
совместимые зависимости, инструкция установки/удаления. `kmod-tun` берётся
строго под kernel ABI прошивки; нельзя принудительно ставить модуль от другой.
Для полностью офлайн-установки зависимости тоже должны быть в bundle.

OpenWrt 24.10 и старее используют opkg/`.ipk`, 25.12+ — apk/`.apk`.
Это OpenWrt APK, не Android. Локальная установка поддерживается; официальный
feed для наших пакетов не нужен. Источники:
[менеджер пакетов по версии](https://openwrt.org/faq/how_to_install_packages),
[локальные apk](https://openwrt.org/docs/guide-user/additional-software/apk).

Будущая инструкция будет использовать `opkg install /tmp/<package>.ipk`
или `apk add /tmp/<package>.apk` с нашим доверенным ключом подписи.
Для отдельного неподписанного тестового файла существует `--allow-untrusted`,
но это исключение конкретной команды, не глобальное отключение проверки.
Файлы пока не собраны; эти примеры не являются текущей командой установки.

Установка пакета не включает VPN/маршруты/WAN listener автоматически.
Перед применением — preflight; обновление сохраняет secrets/profiles и умеет
откатить совместимую конфигурацию. Package upgrade, rollback настроек и
sysupgrade прошивки — разные процедуры. Нужен явный список сохраняемых данных
при sysupgrade; сами сторонние пакеты не считать автоматически восстановленными.

## Порядок реализации и критерии готовности

1. **SDK / engine.** Выбрать stable release и два target, собрать musl engine
   без сети на стадии compile, проверить capabilities, config и TLS-profile
   handshake. Измерить размеры пакетов/зависимостей, idle/peak RSS и throughput.
2. **Настоящая OpenWrt-лаборатория.** Изолированная VM с procd/netifd/fw4/dnsmasq,
   LAN-клиентом, отдельным management-путём и тестовым exit/WAN. Проверить client
   и exit, два peer, DNS UDP/TCP, kill switch/IPv6, fw4 reload, смену WAN,
   SIGKILL и reboot. Ubuntu/systemd-тесты этого не заменяют.
3. **LuCI + применение.** Все базовые страницы, точные ubus ACL, validate/apply/
   health/rollback, сохранение stopped state, запрет чужих путей/команд,
   защита от concurrent edits. Установка/удаление и прерванное обновление в VM.
4. **Полный профильный workflow.** Capture TLS/H2 → import/save → выбор → native
   apply → независимый tcpdump → diff/pcap download; положительные и отрицательные
   fixtures, deadlines и ресурсные пределы. Без этого полную LuCI-версию не закрывать.
5. **Wi-Fi / устройство.** Сохранённые uplink-сети, scan/connect/recovery,
   management-only доступ и локальное имя. Моделируемые отказы — в lab;
   радио, AP+STA и потеря питания — отдельная физическая приёмка.
6. **Локальный пакет для выбранного роутера.** Установка без перепрошивки,
   проверка доступа/отката и ограниченный пилот. Потом отдельными этапами
   transparent/combo, дополнительные архитектуры и routing policies.

Без Radxa/VPS можно выполнить SDK-сборку, OpenWrt VM, backend, LuCI и capture/
observer workflow. Для конкретного устройства позже понадобятся модель,
`ubus call system board`, версия прошивки, RAM/свободный overlay и схема LAN/WAN.
Сейчас отсутствие этих сведений не мешает исследованию, но не позволяет
заявить совместимость конкретного установочного файла.

**Отсечка:** OpenWrt boring-tls v1 — проверенный client/exit lifecycle и полная
описанная LuCI-цепочка профилей на выбранной матрице, с локальными пакетами.
Это отдельный результат; он не означает готовность всех транспортов,
полную браузерную мимикрию или поддержку любого OpenWrt-роутера.
