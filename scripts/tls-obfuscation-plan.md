# План обфускации и наблюдаемости TLS‑транспорта clean-vpn

Документ фиксирует **итог обсуждений** (чем палится `--type=tls`, что уже закрыто, что делать дальше при ограничении стека **Node.js + Puppeteer**, опционально простой **C++** helper). Реализацию по этому документу можно откладывать; порядок секций отражает разумный приоритет.

---

## 1. Выжимка: что уже улучшено в текущем `--type=tls`

- В открытой части ClientHello **нет** маркера VPN в ALPN (`clean-vpn-tls` убран).
- Зафиксирован **TLS 1.3 only** — сертификат сервера в классическом TLS 1.2 handshake не утекает пассивному наблюдателю так же заметно.
- Маршрутизация VPN vs «публичная» страница — **после** handshake: HTTP преамбула `GET /clean-vpn` + **`Authorization: Bearer`** с time‑windowed HMAC от общего ключа (`clean-vpn-hmac.key` / `--shared-hmac-key`, совместимость с legacy `quic-ext-hmac.key`).
- **SNI в ClientHello** можно отделить от проверки сертификата (`--tls-client-sni` vs `--tls-server-name`); дефолтный сценарий с IP и проверкой `clean-vpn` использовал маскировочный SNI (обсуждалось отдельно).
- На exit добавлена **наблюдаемость** post‑handshake (cover / idle / oversize / vpn / handshake fail + `tls done`), пометка **`[scanner-like]`** при пустых ALPN и SNI в ClientHello.

Итого: для **пассивного** DPI основной «надписи VPN» в открытом ClientHello по ALPN больше нет; активный сканер без секрета получает cover‑ответ.

## 2. Чем транспорт всё ещё может палиться

### 2.1. JA3 / JA4 и родственные отпечатки TLS‑клиента

Клиент `--type=tls` использует **`tls.connect` в Node.js (OpenSSL)** с явными опциями (`ALPN`, список cipher suites только для TLS 1.3, порядок ECDH‑кривых и т.д.). Это почти никогда **не совпадает** с отпечатком реального Chrome: другой набор/порядок расширений, шифров, групп.

**Вывод:** для серьёзного DPI класс «это Node/OpenSSL, не браузер» остаётся отдельным сигналом, **независимо** от того, что в SNI написано `www.google.com` или ваш домен.

### 2.2. Отпечаток TLS‑сервера на exit

Аналогично: ServerHello/выбор параметров формирует стек Node/OpenSSL на VPS. Его тоже можно классифицировать (менее обсуждаемо в СМИ, чем JA3 клиента, но для целевого анализа — да).

### 2.3. Статистический анализ потока («туннель»)

После установления TLS содержимое **не читается** пассивно без ключей. Но возможны эвристики: **долгая симметричная сессия**, относительно ровный двусторонний обмен, паттерн не похожий на типичную загрузку страницы. Это не про JA3, а про **поведение во времени**.

**Частичные смягчения (обсуждалось):** несколько relay/exit, распределение типов транспорта (TLS / WebSocket / WebRTC / QUIC), чтобы не сводить всё к одному профилю на одном IP.

### 2.4. Активное зондирование и «профиль сервиса»

На одном порту 443 могут сосуществовать: успешный handshake для «своих», ответ **«It works!»**, при необходимости **passthrough** чужих ClientHello к `--tls-probe-target`. Цепочка сертификатов при активном подключении должна быть правдоподобной.

**Свой домен + LE (или другой публичный CA) + минимальный реальный сайт** закрывают главный артефакт «странный CN/SAN» для случайного curl, но **не заменяют** поведенческий профиль (заглушка vs полноценный сайт, заголовки, редиректы и т.д.).

### 2.5. Внутри TLS (теоретическая расшифровка)

Для типичного провайдера на магистрали **расшифровать TLS 1.3** без ключей нельзя. Исключения: корпоративный SSL‑инспект на машине пользователя, компрометация конца. Поэтому статические строки в первом HTTP‑запросе (UA, путь) для **пассивного** наблюдателя на канале — не главная угроза; их всё равно разумно не светить в логах на диске.

### 2.6. OpenSSL `unsupported protocol` на exit

Клиенты только с TLS 1.2 (или кривые сканеры) к **TLS 1.3‑only** серверу дают ошибку вида `unsupported protocol` на handshake. Это **не баг** обработки HTTP‑преамбулы, а ожидаемый отказ протокола.

## 3. Идея «tls-chrome через Puppeteer как замена tls.connect»

**В лоб — нет:** Chromium не открывает API «сырой duplex после TLS handshake» для произвольного бинарного протокола так же, как `tls.connect` в Node.

**Что даёт Chrome «автоматически»:** любое **HTTPS**, **WSS**, **WebRTC** из процесса браузера использует **настоящий TLS‑стек Chromium** → JA3/JA4 как у браузера для **этого** внешнего соединения.

В проекте уже близкий режим: **`ws-chrome`** — Chrome держит **WSS** к exit; внешнее TLS‑рукопожатие до WebSocket — браузерное. Имеет смысл развивать **легенду и секреты на своём домене** в этом канале, а не вводить отдельный фиктивный `tls-chrome` только ради имени.

---

## 4. Альтернатива WSS: polling + chunked streaming по HTTP

**Идея:** длинный ответ с chunked‑стримом «порциями» VPN‑данных, по тишине закрыть ответ, при живом keep-alive сделать следующий запрос за новой порцией; uplink — отдельными POST‑батчами (или вторым каналом).

**Плюсы:** выглядит как REST/streaming API; TLS по-прежнему браузерный, если код в странице.

**Минусы:** высокая сложность протокола и состояния сессии; **латентность** (RTT на циклы); uplink почти неизбежно батчами — хуже, чем один duplex WebSocket. Имеет смысл как **запасной план**, если **WSS режут или помечают**, а не как первый шаг.

## 5. Приоритеты реализации (только Node / Puppeteer / при необходимости простой C++)

Ниже порядок от **наибольшего эффекта при простоте** к более тяжёлым шагам.

### Фаза A — «инфраструктура и легенда» (без смены JA3 клиента tls)

| Шаг | Действие |
|-----|----------|
| A.1 | Свой **FQDN**, DNS на VPS, **Let's Encrypt** (`fullchain.pem` / `privkey.pem`) в `--tls-cert-dir`. |
| A.2 | **Клиент:** `--tls-server-name=ваш.домен`, осмысленный **`--tls-client-sni`** (часто совпадает с доменом или поддоменом API). Убрать сценарий «SNI google, IP VPS». |
| A.3 | На том же хосте — **минимальный реальный HTTP** (статика, редирект, простая страница) для случайного посетителя порта 443/80. |
| A.4 | Политика **`--tls-public-name`** и **passthrough**: осознанно решить, нужен ли он в проде; он задаёт уникальный профиль поведения. |

**Эффект:** меньше красных флагов при человеческих и полуавтоматических проверках; цепочка доверия нормальная; SNI согласован с IP/доменом.

### Фаза B — «браузерный JA3» без выхода из экосистемы Node

| Шаг | Действие |
|-----|----------|
| B.1 | Документировать и при необходимости **усилить** режим **`ws-chrome`**: свой домен, WSS, аутентификация (cookie / `Sec-WebSocket-Protocol` / короткоживущий токен; помнить об ограничениях произвольных заголовков на WS handshake в браузере). |
| B.2 | Для пользователей с высоким риском DPI по JA3: **рекомендованный путь — ws-chrome**, а не только `--type=tls`. |
| B.3 | Опционально: второй поддомен (например `api.`) только для **легенды в SNI/URL**; это **не меняет** JA3 Node при `--type=tls`, но помогает истории «backend traffic». |

### Фаза C — усложнение статистического профиля

| Шаг | Действие |
|-----|----------|
| C.1 | Несколько **точек входа** (relay / разные VPS / разные порты), чтобы не кластеризовать один долгий поток на один IP. |
| C.2 | Смешение транспортов (**TLS / WS / WebRTC / QUIC**) под разные задачи или пользователей — уже частично есть в проекте. |

### Фаза D — если WSS начнут блокировать или троттлить

| Шаг | Действие |
|-----|----------|
| D.1 | Спецификация **HTTP polling + chunked downstream** + **POST uplink** (сессионная cookie, idle thresholds, фрейминг поверх чанков — совместимость с текущим uint32+IPv4). |
| D.2 | Реализация на **exit**: отдельный путь маршрутизации (по path/session), без поломки существующего `--type=tls` и ws-chrome. |
| D.3 | Клиент: только **страница + Puppeteer/fetch streaming** в Chromium (без Go). |

### Фаза E — крайний случай: узкий нативный helper на C++

Уместно только если нужно то, чего нет в Node и не хочется тащить в браузер:

- очень специфичный сетевой паттерн с низкой задержкой;
- или тонкая работа с сокетом/TLS на уровне, недоступном стабильно из Node.

Ограничение: **простой**, изолированный бинарь (одна задача), чёткий контракт с Node (stdin/stdout или локальный порт). Без переписывания всего VPN на C++.

**Не входит в план:** отдельный клиент TLS на Go (uTLS и т.д.) — по требованию стека только Node/Puppeteer/(редко) C++.

## 6. Риски и ограничения

- **Полное совпадение с Chrome по JA3 для `--type=tls` без браузера** в рамках только Node `tls` — практически недостижимо (нет полного контроля над ClientHello).
- **Маскировка под «настоящий сайт»** и **маскировка под «настоящий браузерный TLS»** — разные задачи; свой домен закрывает первое лучше, чем второе.
- Любой новый режим (polling, новые path) увеличивает поверхность тестирования и поддержки.

## 8. Резюме одной строкой

**Сначала** свой домен, нормальные сертификаты и осмысленный SNI + минимальный сайт; **для JA3 как у браузера** опираться на **ws-chrome (WSS)**; **`--type=tls`** оставить быстрым Node‑клиентом с пониманием ограничения OpenSSL/JA3; **если WSS заблокируют** — закладывать **HTTP chunked + polling** как тяжёлую запасную ветку внутри Node+Puppeteer; **простой C++** — только точечно при необходимости.
