# Native DNS/TCP: framing и локальная проверка отказов

Продолжение [физической проверки 30 октября](clean-vpn-native-physical-features-20261030.md).
Изменён только способ записи DNS/TCP: двухбайтовая длина и сообщение теперь
передаются в `write_all` одним непрерывным буфером, как рекомендует
[RFC 7766, §8](https://www.rfc-editor.org/rfc/rfc7766.html#section-8).
Это относится и к запросу upstream, и к ответу клиенту, включая приватную `.mpn`.

TCP всё ещё может разделять данные на сегменты. Чтение фрагментированных
сообщений, частичные записи, EINTR/EAGAIN, отмена и прежние deadlines сохранены.
Дополнительный буфер ограничен 65537 байтами. UDP, лимиты работников, проверка
ответов, запрет public fallback приватной зоны и таймаут upstream 1200 мс
не менялись. TCP_NODELAY/TCP_QUICKACK в production не добавлены.

## Воспроизведение задержки

Новый `dns-tcp-latency-test` использует настоящий `DnsRelay`, Linux TCP sockets
и независимые тестовые origin/client внутри отдельного network namespace.
Только тест включает QUICKACK=0 у получателя и моделирует паузу планировщика
2 мс после отдельной отправки префикса через linker `--wrap=send`.
Это контролируемое воспроизведение взаимодействия Nagle/delayed ACK,
а не измерение обычной задержки всех DNS-запросов.

| Один и тот же тест, 5 запросов | До исправления | После |
| --- | --- | --- |
| Полное время на loopback | 82.820–90.610 мс | 0.752–1.008 мс |
| Отдельные отправки двухбайтового префикса | 10 | 0 |

До изменения задержка между префиксом и телом составляла около 40 мс в каждом
направлении. После изменения — микросекунды. Проверка регрессии требует
правильных байтов и отсутствия отдельных отправок префикса; абсолютная скорость
не является условием PASS, чтобы загрузка машины не делала тест нестабильным.
Байтовые хеши и исходные измерения сохранены в
[JSON receipt](../fixtures/clean-vpn-native-dns-tcp-latency-20261030.json).

Дополнительно проверены ответ около 60 КБ, однобайтовая фрагментация входящего
запроса, принудительные короткие записи/EINTR/EAGAIN, два запроса на одном
соединении и ограниченное завершение при неполном префиксе, заблокированной
записи и неполном ответе upstream. Существующий `dns-relay-test` также прошёл:
100 запросов, saturation, возврат FD/threads и приватный DNS.

Запуск только в disposable Linux lab с отдельной сетью, root/capabilities,
маркером `/etc/meshpn-admin-disposable-lab` со значением
`isolated-admin-lab-v1` и единственным интерфейсом `lo`:

```sh
cmake --build /work/build --target dns-tcp-latency-test
CVPN_BUILD=/work/build CVPN_DNS_TCP_LATENCY_TEST=1 \
  node --test scripts/test-native-dns-tcp-latency.mjs
```

Сам runner создаёт ещё один namespace и проверяет неизменность внешних
интерфейсов/адресов/маршрутов/правил. `CVPN_DNS_TCP_BASELINE=1` предназначен
только для сравнения с бинарником, собранным со старым `dns_relay.hpp`.
Обычный CTest этот сетевой тест не запускает.

## Полный engine: TUN, TLS, обновление клиентов и отказы

`test-native-peer-dns-delay-reload.mjs` поднимает client, exit и synthetic origin
в отдельных namespaces внутри NIC-less контейнера. Используется production
network plan, реальный TUN/TLS и приватный registry resolver. На обоих WAN
интерфейсах — netem 40±10 мс, контейнер ограничен половиной CPU. Для combo
добавлена ограниченная искусственная CPU-нагрузка; проверяется packet-ветка,
без параллельной нагрузки HTTPS relay.

В каждом прогоне идут две последовательности UDP→TCP одновременно, всего
96 запросов на фоне 24 SIGHUP с заменой ключа/отзывом другого клиента.
Неизменяемый клиент остаётся в одной сессии. Registry publication в этой фазе
не производится, чтобы не спутать её ожидаемый SERVFAIL с ошибкой native reload.

| Combo, glibc, одинаковые настройки стенда | До | После |
| --- | --- | --- |
| DNS/TCP, 48 запросов: min / median / max | 334 / 393.5 / 470 мс | 166 / 198.5 / 247 мс |
| DNS/UDP, 48 запросов: min / median / max | 92 / 141.5 / 211 мс | 85 / 109 / 195 мс |
| Неожиданные DNS-ошибки | 0 | 0 |

Время включает запуск `dig`, контейнерный scheduling и сетевую задержку.
Разброс UDP показывает влияние загрузки; это bounded сравнительный прогон,
не benchmark и не гарантия выигрыша на любом WAN.

На исправленном boring-tls также прошли 96 запросов и 24 обновления;
DNS/TCP min / median / max — 153 / 195 / 269 мс. Дополнительные baseline
musl-прогоны boring/combo тоже прошли; они не используются для сравнения glibc
до/после. Все пять прогонов и хеши бинарников/логов — в
[отчёте измерений](../fixtures/clean-vpn-native-dns-delay-reload-20261030.json).

Отдельные отрицательные проверки создают pending registry marker и задерживают
правильный ответ backend на 1450 мс. Обе ситуации дают ожидаемый SERVFAIL;
после снятия причины UDP/TCP снова отвечают NOERROR без перезапуска engine.
Счётчик FORWARD для TCP/UDP53 и публичный DNS origin проверяются положительным
контролем, затем подтверждают ноль попыток public fallback приватных запросов.
Процессы, namespaces и временные ключи удаляются после каждого прогона.

Для запуска внутри того же отмеченного disposable контейнера, с `--network=none`,
`--cpus=0.5`, TUN и правами на собственные namespaces:

```sh
CVPN_DISPOSABLE_HOST_NET=1 CVPN_ENGINE=/work/build/clean-vpn-engine \
  CVPN_DNS_TRANSPORT=combo-tls CVPN_DNS_CPU_PRESSURE=1 \
  node scripts/test-native-peer-dns-delay-reload.mjs
```

Можно выбрать `CVPN_DNS_TRANSPORT=boring-tls`. По умолчанию 24 обновления;
`CVPN_DNS_RELOAD_ROUNDS` допускает 8–64. Это не команда для живого VPS/Radxa:
runner требует исходную сеть только с `lo` и пустой список netns.

Production engine и 14 test executables пересобраны из текущего project source
с проверенными кэшированными BoringSSL/nghttp2/Brotli static libraries;
14/14 CTest прошли. Зависимости заново не компилировались, sanitizer-прогон
в эту проверку не входит.

## Граница выводов

Исправление устраняет подтверждённый источник задержки, но пока не измерено
на физическом WAN Radxa↔VPS. Ранее наблюдавшиеся около 200 мс на exit нельзя
считать полностью объяснёнными одним контролируемым loopback-прогоном.
Первый единичный combo `dns_response_mismatch` также остаётся необъяснённым:
старый probe не сохранил RCODE/длительность, а задержка сама по себе ещё
не означает истечение 1200 мс.

Повседневные службы/бинарники Radxa и VPS не обновлялись. Сеть Mac не менялась.
Следующая физическая проверка — тот же изолированный тестовый порт и namespace,
двусторонний DNS capture и сравнение TCP RTT до/после. Включение combo для
повседневной работы этим локальным исправлением не объявляется завершённым.
