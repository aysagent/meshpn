# Локальная проверка ранней загрузки Radxa

Это временная диагностика, не новый kill-switch. Никаких сетевых проб сам
наблюдатель не посылает. Он наблюдает первые 90 секунд после готовности захвата.
Зависимости действуют на следующих загрузках до явного `--remove`.

## Порядок запуска

`tcpdump -i any -y LINUX_SLL2 -Q out` открывает захват, даже если `wlan0`
ещё отсутствует. `Type=notify` разрешает запуск потребителей только после
сообщения tcpdump о готовности и повторной проверки, что `wlan0` ещё DOWN.
Зависимости `Requires/After` добавляются для networkd **service и socket**,
netplan-wpa-wlan0, общего wpa_supplicant и стандартных экземпляров wlan0.
Одного `Before=systemd-networkd.service` для этой задачи недостаточно.

Выбраны свойства [systemd Type=notify / RemainAfterExit](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml).
[tcpdump публикует сообщение listening после активации захвата](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.c).
Нормальное окончание 90 секунд оставляет unit active/exited: зависимая сеть
не останавливается. Ошибка раннего старта блокирует зависимых потребителей.
Обработанный отказ захвата **после READY** даёт `inconclusive`, но не вызывает
ошибку unit и остановку уже работающей сети через `Requires`.
Если `wlan0` уже UP, проверка отказывает вместо ложного подтверждения раннего старта.

Это не перехватывает произвольные скрипты, самостоятельно поднимающие интерфейс,
и не покрывает initramfs. Не добавляется зависимость на USB gadget/rescue/SSH.

## Установка на уже работающем клиенте

Профиль ограничен текущей Radxa: networkd, wlan0, TLS exit на IPv4:443,
активный persistent guard `both:block:tun0:<exit>:22`, настроенный USB rescue.
Перед reboot проверьте реальный вход по USB: `ssh -p 2222 root@192.168.7.1`.
Не перезапускайте guard, networkd или usb-gadget вручную.

```bash
sudo env "PATH=$PATH" node scripts/clean-vpn-boot-capture.mjs \
  --install --exit-ip=154.62.226.216 --apply
```

Без `--apply` — только проверка предпосылок и план. С `--apply` публикуются
новые root-owned файлы и выполняется daemon-reload. Ничего не перезапускается,
текущий capture не стартует, reboot не выполняется. Неизвестные существующие
файлы не перезаписываются. Частичный отказ требует разбора/снятия gates,
а не слепого повторения установки. Не допускаются параллельные администраторы.

После успешного `armed-for-next-boot` и проверки USB-входа можно выполнить
обычный reboot. Через 90 секунд после поднятия сети:

```bash
sudo env "PATH=$PATH" node scripts/clean-vpn-boot-capture.mjs --report
```

Отчёт привязан к boot ID; отчёт прошлой загрузки помечается `stale-report`.
Пока окно не закончилось, статус `capturing`. Копировать блок BEGIN…END.

Helper копируется при установке в `/usr/local/lib/clean-vpn-boot-capture.mjs`.
Один `git pull` не обновляет эту установленную копию. Повторный `--install`
не является обновлением: существующие файлы вызывают отказ. Изменения парсера
требуют отдельной проверенной публикации helper с резервной копией; не нужно
ради этого перезапускать capture, networkd, guard или USB на работающей плате.

## Что считается результатом

- `no-unexpected-egress-observed`: в данном окне есть положительное наблюдение
  исходящих пакетов, нет потерь tcpdump, проверен порядок запуска известных
  потребителей, наблюдались только ARP, ограниченные link-control ICMPv6,
  DHCP или TCP к exit:443.
- `traffic-review-required`: видны прямой DNS/DoT, локальный mDNS, другой публичный трафик,
  частные назначения или неразобранные протоколы. Это материал для разбора,
  не автоматическое доказательство утечки каждого такого пакета.
- `inconclusive`: ошибка, потери, нет положительного наблюдения трафика/UP,
  неполный захват или неподтверждённый порядок.

Парсер читает только заголовки SLL2/IP/портов из ограниченного потока в памяти
(не более 16 MiB). Пакеты и их содержимое не сохраняются. В root-only отчёте
остаются счётчики и до 32 примеров адресов/портов, без DNS-имён, ключей,
паролей или данных приложений. IPv6 extension headers/фрагменты не считаются
заведомо безопасными. Единственное узкое исключение для extension headers —
Linux MLDv2 report с точным Router Alert, hop limit 1 и назначением `ff02::16`;
это служебный локальный multicast, а не прямой доступ к IPv6-интернету.
Поля соответствуют [RFC 3810, §5](https://www.rfc-editor.org/rfc/rfc3810.html#section-5).
DoH не декодируется: внешнее назначение попадёт в review.

Новые отчёты имеют `classifierVersion: 2`. В примерах сохраняется `etherType`
в виде `0x0800`, `0x86dd` и т. п. — значение protocol из SLL2, в том числе для
`other-link-protocol`. Неизвестное значение не становится разрешённым трафиком.
Из старого отчёта без этого поля восстановить протокол нельзя: сырые пакеты
не сохранялись.

UDP к `224.0.0.251:5353` или `[ff02::fb]:5353` выделяется как
`mdns-local-review`: это назначения [локального mDNS](https://www.rfc-editor.org/rfc/rfc6762.html#section-5.1).
Классификация основана только на адресе и порте, без проверки содержимого DNS.
Категория **по-прежнему требует разбора** и не входит в список допустимого
служебного трафика. Другой адрес, порт, TCP или неразобранные расширения IPv6
не получают эту категорию. Правила firewall этим изменением не затрагиваются.

## Полученный отчёт Radxa

На `0e91ddc` пользователь прислал отчёт загрузки
`2e0a15c1-c14b-45e6-aba1-10503fe9f61a`: capture готов на 10.46 секунде при
`wlan0 DOWN`, первый UP наблюдался на 11.04 секунде. Известные активные
потребители запустились после готовности; окно завершилось без потерь.
Итог — `traffic-review-required`, а не полная приёмка:

- 6 пакетов `unexpected-egress` с единственным сохранённым примером
  IPv6 UDP к `[ff02::fb]:5353`, соответствующим назначению локального mDNS;
- 2 пакета `other-link-protocol`, для которых старый парсер не сохранил EtherType;
- остальные категории — ARP, DHCP, link-control и TCP к exit:443.

После загрузки IPv4 DNS/HTTPS и внешний IP прошли проверку; контрольные DNS-имена
наблюдались на TUN, не на uplink. Один рестарт VPN объяснён журналом: на 17.22
секунде ещё не было default route, на 19.54 systemd назначил повторный старт,
после которого клиент заработал. Это не подтверждение коррекции часов из Date:
в предоставленной выборке журнала `clock-date` отсутствует.

**Локальный захват не доказывает доставку пакета за пределы платы и не даёт
гарантии за пределами окна.** Это замена способа проверки при недоступном
роутере, но не эквивалент независимого внешнего наблюдения.

## Снятие диагностики / восстановление через USB

Если Wi-Fi не поднялся, входите на `192.168.7.1:2222` по USB. Следующая команда
удаляет только точные принадлежащие этой диагностике drop-in и unit:

```bash
cd /root/dev/meshpn
sudo env "PATH=$PATH" node scripts/clean-vpn-boot-capture.mjs --remove --apply
```

Она **не останавливает** потребителей и не трогает существующие guard gates,
firewall, VPN, USB или SSH. Отчёт, конфигурация и helper остаются для разбора;
изменённые чужим процессом gates вызывают отказ до удаления файлов.
После снятия можно выполнить reboot для штатного запуска сети. На уже
работающей сети reboot ради снятия диагностики не нужен.

USB rescue уже проверен пользователем после reboot и холодного включения,
но не является заменой UART при аппаратном отказе самого gadget/ядра.

## Лаборатория

`node --test scripts/test-host-boot-capture.mjs` — парсер/классификация/units.
`clean-vpn-boot-capture-lab.mjs <absolute-host-boot-artifacts> <absolute-QEMU-tools>`
— отдельные NIC-less QEMU boots, без общей с хостом ФС. Реальный networkd,
второй независимый активатор интерфейса (модель supplicant), tcpdump и nft guard:
контроль без защиты, с защитой, отсутствие tcpdump, преждевременный UP,
обрыв захвата после READY без остановки сети.
Проверяются также next-boot install/remove на работающей сети. В этих installer
тестах rescue units являются fixtures; реальная авторизация rescue отдельно
проверяется `clean-vpn-usb-rescue-lab.mjs` и пользователем на Radxa.
Это не тест настоящей Wi-Fi-ассоциации, RF-драйвера или boot платы.
