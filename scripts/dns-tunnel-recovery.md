# Простой DNS: владение правилами и восстановление

Это компонент нового default `--dns-mode=tunnel` в CLI clean-vpn.
Сквозной ingress-only VM-прогон TLS/boring-tls/combo-tls прошёл 99 проверок;
базовые host smoke на Radxa и `r` прошли, но длительный пилот/live leak-test
не выполнены. DNS-компонент не устанавливает службы и не меняет настройки resolved/dnsmasq,
`resolv.conf`, default route или sysctl. Не путать с managed DNS installer.

`lib/dns-tunnel-journal.mjs` записывает небольшой журнал в приватный каталог
`/run/clean-vpn-tunnel-dns-<netns>`. В нём только проверяемые параметры режима,
идентичности интерфейсов, контекст boot/net/user namespace, тип firewall backend
и положение в фиксированном плане. Команды из JSON не исполняются.

Порядок работы:

1. Один процесс владеет стабильным `flock`. Его открытый дескриптор наследуют
   mutating helpers: смерть Node не разрешает восстановление параллельно с ними.
2. До каждого сетевого изменения сохраняется intent (`fsync` файла, rename,
   `fsync` каталога). Правила получают собственную случайную метку.
3. Guard и маршруты устанавливаются до listener. Общий runtime открывает
   перехват только по `activate()`, после готовности обработчиков транспорта.
4. После аварии `prepareRestart()` проверяет сохранённый контекст и свои
   правила, ставит временную блокировку DNS и убирает прежний план. Новый TUN
   может получить прежнее имя, но другую идентичность только после этого шага.
5. Новый runtime убирает временную блокировку после готовности своего пути.
   Обычный `close()` восстанавливает сетевой baseline; аварийный
   `close({restore:false})` оставляет правила и журнал для восстановления.
   С `--from-tun-restart-safe` даже штатная остановка сначала закрывает ingress,
   затем оставляет DNS-правила/журнал без listener. Это защищает и запросы
   к DNS на самом шлюзе: одного FORWARD guard для них недостаточно.

Восстанавливается только собственное состояние. Неизвестное/дублированное
правило в нашей области, занятая таблица/priority, новый владелец интерфейса,
другой boot/net/user namespace или смена firewall backend останавливают
восстановление до мутаций. Полный снимок firewall поверх актуальных правил не
заливается. Это не защита от одновременного вмешательства другого root-процесса.

После аварии (или штатной restart-safe остановки) повторите тот же запуск с прежней областью host/from-tun/LAN:
журнал проверяется до создания нового TUN. Для полного отключения сначала
остановите client и, если прямой DNS недопустим, приостановите приложения/peers.
Затем из той же загрузки и network namespace:

```bash
# Только аудит сетевых правил; журнал блокируется на время проверки.
sudo node scripts/clean-vpn-dns-recover.mjs
# Явно убрать собственную DNS-защиту и вернуть прежний прямой путь.
sudo node scripts/clean-vpn-dns-recover.mjs --apply
```

Если запускали с `--dns-state-dir=/path`, здесь добавьте `--state-dir=/path`.
Живой владелец, чужие правила/интерфейсы или другой boot вызывают отказ.
Каталог/lock могут создаваться и при аудите; сетевых изменений без `--apply` нет.
Это отдельный журнал от `clean-vpn-recover.mjs --from-tun=wg0`: для полного
выключения аварийного ingress-клиента сначала восстановите DNS, затем from-tun.
Не удаляйте журнал вручную и не заменяйте восстановление запуском `--dns-mode=off`.

### Остановка и повторный Ctrl+C

Клиент сразу сообщает о начале остановки. Восстановление выводит в stderr
этапы `audit`, `hold`, `rollback`, `conntrack`, `release-hold`, `released`,
число оставшихся операций и затраченное время. JSON отдельной команды recovery
по-прежнему идёт в stdout. `remaining=0` ещё не означает завершение: нужно также
снять временный hold и получить `released`.

Служебные команды DNS и from-tun журналов запускаются в отдельной process group,
но наследуют дескрипторы lifetime-lock. Повторный терминальный SIGINT не должен
прерывать операцию между записью intent и read-back. Аналогично защищены команды
маршрутов/sysctl при остановке клиента. SIGKILL и отключение питания этим не
отменяются: для них остаётся recovery из журнала.

У каждой DNS-команды лимит до 10 секунд, у попытки восстановления — общий
бюджет 120 секунд, проверяемый между шагами; оставшееся время ограничивает и
команду. Это не жёсткая гарантия времени при зависшем ядре/файловой системе:
синхронный `fsync` прервать таким таймером нельзя. При превышении бюджета или
ошибке сохраняются журнал и оставшиеся защитные правила, печатается причина;
автоматического разрешения прямого DNS нет. Старые журналы schema 1 совместимы.

Полная проверка владения выполняется перед восстановлением и после каждой
сетевой операции. Её результат используется как исходный снимок следующего
шага, без повторного чтения того же набора правил; durable intent и read-back
не убраны.

**Граница восстановления:** DNS-журнал не сохраняет старые host-маршруты,
LAN NAT и глобальные sysctl самого VPN. В сквозном host-тесте после SIGKILL
и повторного запуска остался прежний bypass `/32` к exit, хотя DNS-правила
снялись. У host/`--split-default` нет аналога from-tun-журнала для этих настроек.
Не считать успешное восстановление DNS полным откатом VPN после аварии;
такой аварийный тест на удалённом host-клиенте требует отдельного плана доступа.

Проверки:

```bash
npm run test:dns-tunnel
npm run test:dns-tunnel-routing-real
npm run test:dns-tunnel-persistent-real
```

Первый набор включает storage/ownership, ошибки запуска, порядок активации,
прерывания записи и rollback, lifetime lock и повреждённые/чужие данные.
Второй запускает пустые приватные namespace с отвечающими DNS-серверами.
Три области — host, ingress, LAN — проверяются как чистый план и как journal/runtime.
Journal-сценарии действительно убивают отдельный процесс listener/forwarder
через SIGKILL, проверяют отсутствие прямого DNS до/во время восстановления и
возврат ответов через туннель. Проверены также down/delete моделирующего TUN
veth и повторный rollback с возвращением исходных DNS-ответов.

Результат этапа: **6/6 сетевых сценариев (61 проверка)**. Отдельно прошли19
unit-тестов журнала и5 unit-тестов общего runtime в Node suite. Общая регрессия:
**2131/2131 PASS**, без skips, `/var/tmp/meshpn-acceptance-4gp2kj/report.json`.

Переход существующих UDP-сокетов теперь проверен отдельно: тот же сокет получает
baseline-ответ, затем туннельный, затем опять baseline после остановки. Без
точечного сброса conntrack ingress-сценарий воспроизводил ECONNREFUSED при
включении и timeout после отключения. Исправление — `dns-tunnel-conntrack.mjs`:
перед активацией сбрасываются старые DNS-tuples выбранной области; при rollback
с закрытым guard — только tuples нашего DNAT на10.99.0.2:1053. Используются обе
пары адресов/портов, протокол и zone0; общего flush и смены connmark нет.
Существующие TCP DNS-сессии при смене пути требуют нового соединения.

Нужна утилита **conntrack**: её доступность и формат проверяются до установки
правил. Поддерживается обычная zone0; найденные нестандартные зоны отклоняются.
Для ingress/LAN источник должен иметь обратный маршрут через выбранный интерфейс;
асимметричная маршрутизация не угадывается. Лимит128 DNS-tuples на протокол и
deadline10s ограничивают работу cleanup; ошибка оставляет защиту закрытой.
Фильтры соответствуют [руководству conntrack](https://netfilter.org/projects/conntrack-tools/conntrack-manpage.html).
В лаборатории бинарник1.4.8 и зависимости распакованы из Ubuntu packages только
в `/tmp/meshpn-conntrack-tools.856s8f`, системные пакеты не устанавливались.
После исправления:6/6 persistent UDP сценариев и6/6 обычных routing/recovery
сценариев прошли. Общая Node-регрессия:2139/2139 PASS, без skips,
`/var/tmp/meshpn-acceptance-MKY2P8/report.json`.

Границы перечисленных выше компонентных проверок: это не запуск полного
clean-vpn и не проверка TLS-транспорта; для этого есть отдельный CLI-стенд ниже.
Простой режим не управляет lifecycle resolved/dnsmasq; проверка установки этих
служб относится к отдельному managed workflow. Whole-VM reboot, live VPS/Radxa,
DoH/DoT приложений и общий VPN kill-switch этими проверками не подтверждаются.

## Сквозной CLI-стенд

`npm run test:dns-tunnel-cli-real` запускает настоящий client/exit в пустых
namespace и требует `/dev/net/tun` и собранные addon/helper. Если устройства
нет, используется NIC-less `ingress-vm-lab.mjs` с обычными `--tools`, `--kernel`,
`--resolved`, проверкой пакетов и дополнительным
`--dns-conntrack=/absolute/path/to/conntrack`. Для распакованных зависимостей
нужен приватный `LD_LIBRARY_PATH`; host-пакеты не устанавливаются.

Default DNS-матрица: TLS host/ingress/LAN, boring-tls и combo-tls ingress.
`--dns-ingress-only` выбирает последние ingress-проверки для трёх транспортов;
отчёт явно помечается `dnsCoverage=ingress-only`, это не полный host/LAN прогон.
`--dns-host-only` выбирает один TLS host-сценарий с повторным group SIGINT при
rollback; отчёт помечается `dnsCoverage=host-only`. Два subset-флага несовместимы.
Бюджет сценария500s, всего VM45min для полной DNS-матрицы или30min для subset.
Обычный транспортный VM-стенд без `--dns-conntrack` сохраняет прежние30min и
явный `--dns-mode=off`: его сырой UDP53 echo не является DNS-проверкой.

Фикстура проверяет A/AAAA, UDP/TCP, primary/backup, crash/restart, отказ exit,
непрерывные DNS-запросы во время safe stop, DNS самого шлюза и explicit recovery.
Все адреса и DNS endpoints находятся внутри VM/namespace. Результаты и
незавершённые прогоны перечислены в [DNS v1](dns-v1.md); deadline не считается PASS.

Последний ingress-only прогон: **3/3 сценария, 99/99 проверок PASS**, без skips,
`/var/tmp/meshpn-ingress-vm-ky2zPm/report.json`. В каждом сценарии explicit recovery
вернул полный сетевой baseline; VM штатно выключилась. Это не повтор host/LAN
и не подтверждение работы на живых VPS 2/Radxa.
