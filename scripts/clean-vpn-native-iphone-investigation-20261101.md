# iPhone по USB: текущая незакрытая неисправность

Последующее [сравнение полной записи и свежих Safari TLS-сеансов](clean-vpn-native-iphone-cadence-20261101.md)
снова воспроизвело массовые таймауты без телефона. Успешные одиночные проверки
ниже — более ранние контроли, не доказательство устранения неисправности.

Ночная проверка 31 октября — 1 ноября 2026. Исправление packet liveness из
`18644a2` установлено, но пользовательский отказ iPhone **не устранён**.
Автоматический переход transparent → boring пользователь отклонил;
fallback не добавлен. Рабочий endpoint остаётся на **443**.

## Что действительно зафиксировано

В одном интервале Radxa не получала новых USB-пакетов, сосед телефона был
`FAILED`, iPhone не показывал выданный Ethernet IP. Однократное временное
переподключение существующего gadget к тому же UDC восстановило DHCP:
телефон получил `192.168.7.19`, пошёл трафик. Состав gadget, настройки службы
и USB-адрес не менялись. После этого пользователь сообщил об открывшемся
example.org и по-прежнему неработающих Яндексе/Speedtest. Переподключение USB
не является исправлением transparent и не установлено как watchdog.

Из следующей записи восстановлены 395 TCP-потоков и 185 ClientHello.
Запросы Speedtest и два запроса example.org сопоставлены с WAN-потоками по
публичному ClientHello.random. Radxa приняла исходный ClientHello телефона,
но в этих WAN-потоках нет подтверждённых байтов ClientHello и ответного TLS.
На VPS для некоторых потоков виден первый сегмент и отправленный ACK, но
не продолжение ClientHello. Это локализует конкретные отказы до получения
полного ClientHello на exit; причина потерь пока не установлена.
Точного TLS-потока internet.yandex.ru в этой выборке не найдено.

Отдельный ранний поток передал полный ClientHello, ServerHello и последующий
трафик. Его нельзя приводить как пример потери продолжения. Нельзя также
приписывать открытие example.org QUIC: это остаётся непроверенной гипотезой.

## Прямое сравнение с JS

Для 182 пар исходного и изменённого ClientHello выполнена JS-функция
`replaceFirstSniInTcpBuffer()` с **тем же именем**, которое отправил native.
Результат совпал с native побайтно **182/182**, различий нет.
Это проверяет пересборку, а не эквивалентность двух протоколов авторизации.

JS-токен короче: native дополнительно связывает авторизацию с исходным IPv4
и SHA-256 ClientHello, использует более длинное время и префикс `n2.`.
Например, для Speedtest исходные 1540 байт превращаются в 1671 байт native,
а JS-формат даёт около 1614–1615 байт. Эти отличия пока **не доказаны причиной**
отказа; удалять связывание на основании одной длины нельзя.

JS сразу читает входящие байты, а combo native использует `MSG_PEEK` для
выбора ветки, оставляя поток BoringSSL/relay. Контроль на том же внешнем 443
с диагностическим listener прошёл по три раза для consuming read и peek.
Для изоляции SYN только синтетических проб имел MSS 1232; временный NAT match
ограничивался собственным source IP, endpoint, портом и этим MSS. Intent
сохранён до правила, отдельный ExecStopPost удалял точное правило,
RuntimeMaxSec ограничивал стенд. Правило удалено, listener остановлен,
native exit не перезапускался. Это не эквивалент реального combo под нагрузкой.

## Почему пока нет изменения wire format

Ранее один и тот же просроченный ClientHello зависал на 443, но передавался
на временный 3443. Позже **те же байты** проходили на 443. В чередовании
TLS record version 0301/0303 прошли оба варианта; это исключает заявление,
что смена одного байта исправила проблему.

Ещё 24 пробы к настоящему native exit на 443, до четырёх одновременно:
записанный просроченный hello, новый random, короткое имя по форме JS и
обычное публичное имя — получили полный ACK и ответ/EOF. Для просроченной
или неверной авторизации EOF ожидаем; это **не успешный HTTPS**, не проверка
настоящего JS relay и не обращение к исходному сайту.

Chrome через процессный USB proxy открыл example.org, internet.yandex.ru и
www.speedtest.net с HTTP 200. QUIC отключён только в тестовом Chrome.
Замер скорости в этом повторе не выполнялся. Системная сеть Mac не менялась.
Успех ноутбука не заменяет приёмку iPhone.

## Независимые исправления админки

- Статические страницы с query string (`/?usb-check=2`) теперь открываются.
  Прежде наша диагностическая ссылка возвращала 404; Host/Origin/CSRF и точные
  API-маршруты сохраняют прежние проверки. Это не объясняет отсутствие USB IP.
- Для combo UI различает готовность основного туннеля и счётчики HTTPS-ветки.
  Закрытые TCP-соединения не называются успешными HTTPS. Ошибки relay видны
  рядом со статусом, устаревшие данные не объявляются актуальными.
- HTTP/status проверки: **9/9**; настоящий Chrome 156 проверил обе надписи,
  переключение режима и подтверждения питания на fixture, без реальных
  reboot/poweroff. Это отдельная UI-проверка, не исправление native data plane.

`3a1bf76` установлен на Radxa штатным `admin/install.mjs --update`, исходники
доставлены fast-forward через Git bundle до `c3743e3`. После обновления
`/?usb-check=2` возвращает HTTP 200, новые JS assets доступны, broker активен.
Пароль и настройки сохранены. Native client сохранил PID 2209, exit — 866125;
оба активны, guard включён. Временных listener на 3443 и диагностического
NAT-правила больше нет. Это проверка обновления админки без restart движков.

[Санитизированные результаты](../fixtures/clean-vpn-native-iphone-investigation-20261101.json)
не содержат ключей, encoded SNI, сырых hello или pcap. Приватные записи остались
в собственном root-only build-каталоге на Radxa.

Пользователь отклонил повторный телефонный тест до конкретного исправления.
Продолжение выполняется самостоятельно с сохранёнными ClientHello и настоящим
USB-путём с ноутбука. [Исправление FIN до ServerHello и дальнейшие проверки](clean-vpn-native-prehello-fin-20261101.md)
не следует смешивать с первоначальной потерей WAN-пакетов. Проверять доставку
ClientHello, обратные ACK, авторизацию, origin connect и первый ServerHello
нужно отдельно. Объявлять исходную неисправность исправленной или менять её
на fallback нельзя.
