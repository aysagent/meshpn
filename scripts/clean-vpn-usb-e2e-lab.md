# USB: настоящий установщик, перезагрузка, DNS и IPv6 в VM

Этот стенд проверяет Linux USB-клиента через реальный `clean-vpn` TLS/TUN.
Он дополняет прежний `clean-vpn-usb-rescue-lab.mjs --gateway`, где готовность
VPN задавалась fixture. Физическую Radxa и сетевое поведение macOS не заменяет.

Повторные обрывы со сменой DHCP, длинным TCP и снимками ресурсов вынесены в
[USB soak](clean-vpn-usb-soak.md): режим `--soak`, повторный результат 645 проверок,
три цикла обрывов и замер памяти после покоя/GC. Он не заменяет проверки ниже; отдельно отмечены
задержка восстановления exit и рост RSS, требующие дальнейшего исследования.

Большие UDP-пакеты, фрагментация и PMTU через NAT проверяются режимом `--pmtu`:
[описание матрицы и ограничений](clean-vpn-usb-pmtu.md). Это отдельный прогон,
а не вывод об UDP из успешного TCP MSS-теста.

## Запуск

Нужны заранее подготовленный успешный образ `clean-vpn-host-boot-lab.mjs`
(`report.json`, `guest/`, `guest-kernel`) и каталог извлечённых QEMU tools:

```bash
MESHPN_LAB_NODE_HEADERS=/absolute/node/include/node \
node scripts/clean-vpn-usb-e2e-lab.mjs /absolute/HOST_BOOT_BASE /absolute/QEMU_TOOLS_ROOT
node --test scripts/test-usb-e2e-lab.mjs
```

Команды выполняются из корня репозитория на Linux x86_64.
С 2026-10-04 каждый режим пересобирает **текущий** TUN-addon через host `g++`;
`MESHPN_LAB_NODE_HEADERS` указывает на каталог с `node_api.h` (например,
`/home/yurich/.cache/node-gyp/24.13.0/include/node` в текущей лаборатории).
Исходный/скомпилированный код и бинарник записываются в `nativeBuild` с SHA-256.
Режим `--soak-diagnostics` дополнительно инструментирует этот же исходник;
обычные режимы используют production-код без диагностических exports.
Runner запускается без sudo. QEMU: `-nic none`, без host filesystem shares,
без TAP/bridge. Сеть, firewall, часы и systemd основной машины не меняются.
Разрушающие гостевые операции защищены marker в kernel cmdline, проверкой
QEMU, root и настоящего systemd PID1. Не запускать гостевой helper вручную.

Текущие JS/MJS/shell-исходники копируются в образ и хешируются в отчёте.
Kernel проверяется по SHA256 базового отчёта. Node, native addon и зависимости
берутся из доверенного локального базового образа; это не сборка зависимостей
с нуля. SSH-бинарники и их библиотеки берутся с машины запуска, но ключи,
пароли, конфигурация SSH и пользовательские данные с неё не копируются.
PKI, HMAC и SSH-ключи генерируются исключительно внутри VM.

## Первый boot

1. Реальный networkd получает DHCP в изолированной сети. До установки защиты
   проверяется доступность IPv4, IPv6 и DNS UDP/TCP A/AAAA напрямую.
2. Сначала устанавливается зафиксированная старая версия installer/guard/SNAT
   (fixtures с проверяемыми SHA256), чтобы воспроизвести LAN DNS-обход.
   Затем запускается текущий настоящий `install.sh --upgrade-usb-dns`:
   план без записи, stop VPN без снятия guard, публикация wrapper и правил cvks4,
   блокировка DNS при stopped, сохранение PID networkd и rescue-входа,
   повторное обновление без остановки VPN.
   Проверяется профиль
   `USB_GATEWAY=1 KILLSWITCH=1 KILLSWITCH_PERSIST=1 NETWORKD_GUARD=1`.
   Проверяются сохранение PID networkd, настоящий TUN, единственный SNAT,
   оба guard и аутентифицированный rescue SSH.
3. Только USB SNAT удаляется, затем добавляется настоящим `install.sh
   --usb-gateway` дважды. Проверяются потеря USB-egress без SNAT, восстановление,
   отсутствие дублей и отсутствие рестарта VPN/rescue.
4. Выполняется матрица ниже при VPN active, stopped и после повторного start.
5. Фактические опубликованные файлы, enable-ссылки и их хеши сохраняются на
   новом ext4-диске. systemd выполняет штатный reboot с sync/unmount.

## Второй boot

Новый kernel boot ID, тот же ext4-диск. Initramfs восстанавливает **файлы первой
установки**, а не заранее сгенерированные units. Это сохранение выбранных
файлов установки, не полный диск Armbian.

DHCP намеренно задержан: проверяется rescue-вход до получения uplink IPv4
и до готовности VPN, отсутствие преждевременного SNAT. Затем DHCP разрешается,
реальный VPN и SNAT должны запуститься автоматически. Проверяется порядок
guard перед networkd и повторяется матрица active/stop/start.

Полный uninstall проверяется настоящим CLI: удаляются только собственные
основные/guard/SNAT-файлы и правило; rescue и прежний `wlan0 MASQUERADE`
сохраняются. После удаления защиты повторяются положительные контроли
прямого IPv4, IPv6 и DNS. Затем выполняется новая установка **текущим** shell
installer с `USB_GATEWAY=1`, готовность настоящего VPN, DNS/IPv6-матрица,
повторный uninstall и rescue-вход. Завершение — штатный poweroff с sync/unmount.

## Матрица USB-клиента

- HTTPS IPv4: при VPN active сервер видит адрес exit, при stopped запрос
  не проходит, после start снова виден exit.
- IPv6 HTTPS: не проходит active/stopped. У exit в этом профиле IPv6 выключен;
  стенд проверяет отсутствие обхода через uplink для контрольного запроса,
  а не работу IPv6-туннеля.
  Без guard этот же клиент достигает того же IPv6 origin.
- DNS напрямую к публичному resolver и через dnsmasq платы на USB: UDP/TCP,
  A/AAAA. Проверяются ответы и источник каждого запроса на upstream-сервере;
  при stopped не должно быть запроса на upstream. Имена уникальные, кеш выключен.
  Транспорт этих DNS-запросов — IPv4; AAAA-ответ не означает DNS через IPv6.
- Обычный SSH:22 и rescue SSH:2222 проходят аутентификацию во всех состояниях.
- Прямой DNS к LAN IPv4 `192.168.1.1` и ULA IPv6 `fd00:1::1`: UDP/TCP A/AAAA
  после обновления IPv4 при active перехватывается и доходит только до
  публичного resolver с адресом exit. При stopped и для IPv6 блокируется.
  До защиты и после её удаления этот же путь работает; в старой v2 он тоже
  работает и тем самым воспроизводит исправляемый обход.
- DNS-прокси платы намеренно настроен на DNS роутера. При active USB-запрос
  перехватывается до этого прокси; при stopped запрос не достигает роутера.
- Не-DNS LAN HTTPS по IPv4/ULA блокируется active/stopped.
- Дополнительно TCP:38471 и UDP:38472: публичные IPv4/IPv6 и LAN IPv4/ULA.
  До защиты все восемь путей работают. С guard работает только публичный IPv4
  через VPN; при stopped все блокируются. Проверяются уникальные payload ID,
  адрес источника у получателя и отсутствие запроса, не только таймаут клиента.

Вывод сохраняется в `/var/tmp/meshpn-usb-e2e-*/report.json` и `boot-*.log`.
Валидатор требует полный упорядоченный набор проверок обоих boot, положительные
контроли, реальный reboot/poweroff и различающиеся boot ID. Частичный прогон,
таймаут или пропущенный тест не дают PASS. При ошибке собственный тестовый
диск сохраняется для разбора; при успехе удаляется вместе с временным образом.

## Аварийное завершение и длительный обрыв

Отдельный режим того же NIC-less стенда (одна загрузка, текущий fresh installer):

```bash
MESHPN_LAB_NODE_HEADERS=/absolute/node/include/node \
node scripts/clean-vpn-usb-e2e-lab.mjs VERIFIED_HOST_BOOT_BASE QEMU_TOOLS_ROOT --faults
```

- SIGKILL главного процесса VPN: systemd должен автоматически заменить PID,
  восстановить настоящий TUN/SNAT и выход USB через exit.
- Blackhole exit на router FORWARD минимум 120 секунд. Uplink, DHCP и прямые
  тестовые HTTPS/DNS/TCP/UDP origins остаются доступны: отсутствие интернета
  через VPN не должно открывать обход к ним.
- Потеря carrier минимум 120 секунд: networkd отзывает DHCP default и маршрут
  к exit; после возврата carrier DHCP и VPN должны восстановиться автоматически.
- Для двух сетевых обрывов запрещён ручной restart VPN: PID и NRestarts после
  crash-сценария должны оставаться прежними. networkd, guard и rescue также
  не перезапускаются. SSH:22/2222 проверяется аутентификацией во время обрыва.
- Отдельный USB-процесс непрерывно создаёт новые TCP/UDP/DNS-запросы. Проверяются
  его положительный контроль, ошибки при обрыве, успешное завершение и журналы
  принимающих origins: только адрес exit, ни одного прямого или LAN-запроса.
  Это ограниченное активное наблюдение, не захват каждого пакета.

Отчёт имеет `scenario=usb-faults`; частичный набор событий, обрыв меньше 120
секунд, отсутствие восстановления или штатного poweroff не дают PASS.
Для независимой проверки сети после найденного crash-блокера есть
`--network-faults`: тот же стенд без SIGKILL, `scenario=usb-network-faults`.
Его результат не засчитывается как успешная проверка аварийного завершения.
Veth carrier/DHCP не моделирует драйвер Wi-Fi, ассоциацию с AP и прошивку
реального роутера. Физическую Radxa этим тестом не заменяем.

После добавления автоматического recovery его окно в TCG — **420 секунд**:
аудированный rollback трёх журналов и новая DNS-установка. Это соответствует
бюджету штатного service cleanup и не является обещанием задержки на Radxa.
Окно восстановления после сетевых обрывов осталось **180 секунд**.
Во время всех окон монитор и самостоятельный persistent guard остаются включены.
Первый прогон исправления `/var/tmp/meshpn-usb-e2e-6nvVes/report.json` оставлен
как failed: старое окно 180 секунд истекло, но во время последующей диагностики
HTTPS уже вернул адрес exit (примерно через 3 минуты 23 секунды после рестарта).
Исправлена также диагностика стенда: она не предполагает, что клиент навсегда
останется offline после истечения deadline, и не подменяет исходный timeout
ошибкой проверки «stopped» при позднем восстановлении.

Следующий прогон `/var/tmp/meshpn-usb-e2e-KI2bZ5/report.json` восстановил VPN
после SIGKILL и обоих сетевых обрывов, но остался **failed** на итоговом аудите
raw receiver после carrier loss. В том отчёте не были сохранены проблемные
записи, поэтому его нельзя объявить ни полной приёмкой, ни доказанным обходом.
В TCP receiver адрес читался слишком поздно — из уже закрывающегося сокета.
Теперь он фиксируется при accept (включая любые неожиданные адреса, без подмены
на exit); отдельный тест моделирует исчезновение `remoteAddress` при teardown.
Для любого следующего отказа аудита сохраняются первые восемь неожиданных
записей. Сам критерий «только exit, никаких прямых/LAN hits» не ослаблен.

Повтор `/var/tmp/meshpn-usb-e2e-rVIM8l/report.json` также failed и уже сохранил
точную запись: `host=192.168.1.1`, `peer=154.62.226.216`, UDP,
`token=raw-0-136`. Это доставка к частному адресу **через exit**, не прямой
обход VPN через Wi-Fi. При carrier loss пропадали LAN bypass routes, частный
адрес начинал маршрутизироваться в TUN, пакет ожидал reconnect в очереди и
выходил через exit. Поэтому одного условия «USB только в TUN» недостаточно
для заявленного запрета LAN. В `cvks4` добавлены DROP для USB → RFC1918 до
разрешения USB → TUN, независимо от текущих маршрутов. INPUT/DNS DNAT/SSH
этим не меняются. Приёмка до этой правки не является приёмкой новой политики.

После исправлений recovery и метаданных receiver регрессии: **383/383**,
без ошибок и пропусков, `/tmp/meshpn-usb-recovery-all.log`.

Первый аварийный прогон 2026-10-03:
`/var/tmp/meshpn-usb-e2e-0vZnBA/report.json`, **failed**, `real VPN/USB not ready`.
После SIGKILL systemd меняет PID и увеличивает NRestarts, но VPN затем повторно
выходит с кодом 1 (в serial видны 27 рестартов), USB egress не восстанавливается
за трёхминутное окно готовности. Это не успешная crash-приёмка.
Причина, предполагаемая по коду: `runClient` вызывает `hostRoutes.assertAvailable()`
до создания TUN; незавершённый same-boot журнал требует явного recovery.
В первом прогоне journalctl вернул `No entries`, поэтому точная ошибка клиента
в отчёт не попала. Для повторной диагностики добавлен снимок стадии журнала
маршрутов и проверка блокировки/SSH после отказа восстановления; дополнительно
читаются файловые логи базового VM-стенда, если они присутствуют.
Последующее чтение кода выявило и более ранний отказ в `main()` при stale IPv6
journal. Поэтому исправление охватывает оба барьера, а не только IPv4:
в согласованном USB-профиле восстановление DNS/IPv6/IPv4 выполняется совместно
под lifetime-locks и строгим standalone guard, до создания нового TUN.

Повтор с диагностикой: `/var/tmp/meshpn-usb-e2e-mOJxum/report.json`, **failed**,
177 выполненных проверок, но восстановления нет. Журнал IPv4 действительно
остался `active`, `pendingRoutes=6`, `rpFilterPending=true`; именно такую стадию
`hostRoutes.assertAvailable()` отвергает до создания нового TUN.
В состоянии отказа подтверждены неизменные guard/networkd/rescue, входы
SSH:22/2222, блокировка HTTPS/DNS и TCP:38471/UDP:38472 по IPv4/IPv6/LAN,
отсутствие прямых запросов на принимающих origins в наблюдаемом окне.
Это пробел автоматического recovery, не доказательство прямой утечки.
Production-код в рамках этой проверки не изменялся.

Промежуточный сетевой прогон `/var/tmp/meshpn-usb-e2e-aMq6iJ/report.json`
остановлен ошибкой самого стенда: аудит требовал положительную HTTPS-запись
после запуска монитора, но монитор создавал только TCP/UDP/DNS. Добавлен HTTPS
и проверка положительных записей всех трёх получателей до инъекции сбоя.
Этот промежуточный прогон не является сетевой приёмкой или находкой утечки.

## Границы

Изолированные veth вместо USB/Wi-Fi, Linux peer вместо Mac, синтетические
HTTPS/DNS endpoints и PKI. Проверяются конкретные публичные IPv4/DNS и IPv6
пути, не любые протоколы/DoH/DoT, не внешнее наблюдение провода, не потеря питания,
не DHCP/RA реального роутера. IPv6-соседи в стенде **статические**: существующий
host-only IPv6 runtime guard не разрешает unicast Neighbor Advertisement к
ULA/GUA. Первый boot без этого ограничения мог пользоваться старым кешем,
а второй boot отказал на не-DNS IPv6 LAN-контроле. Поэтому данный стенд
изолированно проверяет FORWARD/DNS-фильтрацию при готовом L2-пути, а не выдаёт
PASS для полноценного IPv6-router/NDP-режима. На Radxa остаётся
[отложенный чек-лист](clean-vpn-radxa-next-checks.md).
