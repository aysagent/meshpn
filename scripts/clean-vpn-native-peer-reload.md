# Native exit: применение списка клиентов без restart

Реализован локальный `SIGHUP` для **exit** boring-tls, combo-tls и
transparent-tls. Сигнал не является сетевым API. Отправлять его может только
процесс с соответствующими правами ОС; клиентские endpoint конфиг не меняют.

```sh
# Сначала атомарно опубликовать проверенный конфиг по прежнему пути.
/path/to/engine --check-config /path/to/exit.json
systemctl kill --kill-whom=main --signal=HUP native-daily-exit.service
```

Это команда для engine с capability `peer_reload`, не инструкция сигналить
старому установленному бинарнику: его обычная реакция на HUP может отличаться.
Перед применением проверяется `/path/to/engine --capabilities`.

## Контракт

Перечитывается ровно тот файл, с которым запущен engine. Можно изменять список
`peers`, включая ключи и привязки адресов; поддержана конверсия старого одиночного
packet `secret_path`/`peer_ipv4` в список. Остальные поля должны совпасть с
исходной конфигурацией: listener, сертификаты, HTTP mode, TUN, policy, лимиты,
replay root и имя маскировки этим механизмом не меняются.

Пустой `peers: []` разрешён на exit и означает **deny all**, а не анонимный доступ.
Это позволяет отозвать последнего клиента, сохраняя процесс и listener.

Новый документ полностью проверяется перед изменением активного состояния:
дубликаты ключей/адресов, некорректные поля, доступность ключей, их права,
разделение packet/relay ключей combo и готовность новых replay journals.
Ошибка оставляет прежние identities и соединения действующими.

Неизменённые packet clients сохраняют свои sessions. Удалённые/rotated identities
теряют соединение, незавершённые аутентификации старого поколения закрываются.
Новым подключениям применяется новый список. Relay сохраняет ReplayWindow и
активную квоту неизменённого ключа; удалённые workers получают отмену и закрывают
сокеты в своём цикле, который проверяет отмену при ожидании и перед передачей.
Подтверждение применения означает публикацию нового набора и отмену старых
identities, а не ожидание завершения каждого отменённого worker.

В combo публикация packet peers и relay admission выполняется одной короткой
транзакцией под admission lock. Подготовка ключей/дискового состояния происходит
до неё. Нет промежуточного состояния с новым packet списком и старым relay
admission для новых запросов.

## Replay и ротация

Для нового relay-клиента заранее создаётся и инициализируется его собственный
replay directory. При ротации используется **новый relay id**, а не очистка
журнала старого id. Новые id можно инициализировать отдельным конфигом
transparent exit с `peers: [новая_запись]` и тем же replay root.

Существующие ReplayWindow переиспользуются, не открываются повторно с обходом
file lock. Перенос того же ключа на другой replay path запрещён. Незаконченная
инициализация новой identity приводит к отказу reload целиком. Повторное
добавление ранее удалённого ключа обязано использовать сохранённый journal;
прошлые токены не становятся допустимыми.

## Подтверждение

Engine пишет одну JSON-строку в stdout/journal:

```json
{"version":1,"event":"peer_reload","status":"applied","revision":1,"config_sha256":"…","active_config_sha256":"…"}
```

- `config_sha256`: SHA256 **точных байтов** прочитанного файла, включая пробелы.
  При невозможности прочитать файл — пустая строка.
- `active_config_sha256`: digest последнего успешно применённого документа.
- `revision`: счётчик успешных применений в текущем процессе, начиная с нуля.
- `status: rejected`: активная ревизия/конфигурация не менялись.

Ключи, содержимое конфигурации, пути и подробности исключения не попадают в event.
Успех отправки SIGHUP ещё не подтверждает применение: управляющий процесс должен
дождаться нового события с ожидаемым digest и тем же PID. Несколько сигналов
могут объединиться; несколько операторов должны сериализовать запись конфигурации.
Изменённое содержимое key-файла само по себе не меняет config digest, поэтому
provisioning публикует новые уникальные key paths при ротации.

## Проверки

```sh
node --test scripts/test-native-peer-reload.mjs
node --test scripts/test-native-multi-peer.mjs scripts/test-native-http1.mjs
ctest --test-dir native/clean_vpn/build --output-on-failure
```

`test-native-peer-reload.mjs`: реальные C++ client/exit с fixture packet boundary,
H2/H1, boring/combo: add, невалидный документ, изменение immutable полей,
отсутствующий key, неприготовленный relay journal, rotation, revoke, deny-all.
Проверяются байты пакетов, неизменность PID, отсутствие reconnect постороннего
клиента и соответствие событий digest/revision. Standalone transparent отдельно
проверяется на service SIGHUP, deny-all, rejected change и повторное добавление.

`transparent-quota-test`: настоящие TCP relay workers с двумя идентичностями
за одним адресом. Проверяются live cancellation одной identity, сохранение
другой и её квот, отсутствие origin connect после отказа новой аутентификации,
сохранение durable replay при reload и отказ при переносе журнала.

Новая функциональность проверяется локально в Linux-лаборатории; внедрение в
daily Radxa/VPS и systemd manager acknowledgement — отдельные интеграционные шаги.
