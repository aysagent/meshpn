# H2: память ядра, задержка и повторные подключения

Следующий этап после [короткой H2-матрицы](clean-vpn-native-h2-budget.md).
Запуск на Mac с уже подготовленным кэшем лаборатории:

```bash
npm run lab:native:mac -- --h2-kernel
```

Команда собирает актуальный код, выполняет CTest и запускает отдельный Linux
guest через QEMU/TCG. Guest получает минимальный initramfs с бинарниками,
тестовыми скриптами и модулем netem. У него нет NIC, дисков, host filesystem
shares или сетевых listeners для управления извне. Настройки сети Mac не меняются.
Все соединения client/exit проходят внутри guest по loopback; TUN заменён socketpair.

Контейнер также запускается с `--network=none --cap-drop=all`. Единственный netem
настраивается на `lo` внутри отдельного ядра guest. После завершения guest
выключается. Podman machine можно остановить `npm run lab:native:mac -- --stop`.

## Что проверяется

1. Полная матрица 1/4/8 клиентов, по 3 цикла: окна 1/1 MiB и fixture-only 6/15 MiB.
2. Четыре клиента с `netem delay 20ms` на loopback: ожидаемый RTT 40 ms.
   Фактический RTT проверяется пятью ICMP-пробами до нагрузки; состояние и
   счётчики qdisc записываются до/после. Для обоих вариантов окон — по 3 цикла.
3. Четыре клиента без netem, по 30 циклов для каждого варианта окон. Это минимум
   120 секунд нагрузки на вариант, плюс дренирование, отключения и восстановление.
   Каждый третий цикл использует SIGKILL клиентов, остальные — uplink-off.

Каждый цикл содержит slow-drain и no-drain, проверенный обмен здоровых peers,
очистку сессий/FD и новое подключение. Каждый медленный клиент должен отдельно
пройти пороги инжекции и заполнения очереди. Начальные H2 SETTINGS/WINDOW_UPDATE
сверяются для каждого соединения.

SO_MEMINFO здесь обязателен: неполный ответ или отсутствующий sample любого
активного TLS-сокета не позволяют получить passed. Измеряются rmem_alloc и
wmem_queued. Дополнительный наблюдаемый барьер — не более 32 MiB суммы этих двух
счётчиков на TLS endpoint. Это проверка выборок, не новый лимит ядра.

Проверка RSS после прогрева сравнивает все последующие циклы с одним baseline
после второго цикла, а не с предыдущей выборкой: постепенный рост не скрывается
последовательными малыми приращениями. Допустимый рост — меньше 8 MiB.
Прикладные очереди по-прежнему ограничены 1 MiB каждая.

## Артефакты и границы

Новый JSON и отдельный serial log сохраняются в
`~/Library/Caches/meshpn-clean-vpn-lab/results/clean-vpn-h2-kernel-*.json*`.
Успешный JSON создаётся только после всех трёх этапов и нормального завершения
guest. Serial log сохраняется и при неуспехе. Общий deadline VM — 20 минут;
у каждого отдельного случая есть свой ограниченный deadline.

Это проверка backpressure, изоляции peers и восстановления при задержке, **не
измерение WAN throughput**. Скорость инжекции не фиксирована; bandwidth/loss не
моделируются. TCG влияет на CPU и задержки. SO_MEMINFO охватывает выбранные счётчики
TLS TCP-сокетов, а не всю память ядра. Qdisc измеряется отдельно до/после, не как
непрерывный пик. Серия из 30 циклов не заменяет суточный soak.

Production caps остаются прежними. Успех этого этапа сам по себе не доказывает
пользу больших окон или полную мимикрию браузера; для решения о лимитах остаётся
отдельное сравнение goodput на заданных RTT/скорости канала.

## Результат 2026-10-26

[Отчёт](../fixtures/clean-vpn-native-h2-kernel-report.json): 10 случаев,
168 фаз нагрузки, 84 цикла восстановления и 384 проверенных соединения — passed.
Полный прогон guest занял около 463 секунд. CTest 10/10, macOS parser 4/4.
SO_MEMINFO был доступен во всех фазах. Очереди, FD и число сессий прошли проверки;
здоровые клиенты продолжали обмен при нагрузке на медленных.

| Режим, клиентов | Окна, MiB | Пик RSS exit, MiB | Пик суммы TCP send queued, MiB | Пик суммы TCP receive alloc, MiB |
| --- | --- | ---: | ---: | ---: |
| Без задержки, 8 | 1/1 | 19.3 | 5.7 | 1.7 |
| Без задержки, 8 | 6/15 | 21.7 | 20.6 | 0.9 |
| Netem, 4 | 1/1 | 11.5 | 2.0 | 3.0 |
| Netem, 4 | 6/15 | 12.8 | 7.5 | 8.3 |

TCP-суммы охватывают exit и всех клиентов; максимумы send/receive могут относиться
к разным выборкам. Это не выделение памяти только одним exit.
При заданном RTT 40 ms пять проб дали 45.4–51.9 ms, среднее 48.0 ms;
qdisc обработал 12490 пакетов, drops=0 и финальный backlog=0.

Серии из 30 циклов заняли 144.4 и 150.4 секунд. Максимальный дополнительный RSS
exit после прогрева составил 1608 и 4228 KiB соответственно; оба значения ниже
барьера 8 MiB. Это не доказательство отсутствия утечки на длительном интервале.

Большое окно заметно увеличивает наблюдаемые очереди TCP, хотя RSS приложения
меняется гораздо меньше. Поэтому сохраняем production caps. Следующий этап —
отдельное сравнение доставленного goodput при фиксированных RTT и скорости
канала, с учётом общей памяти и потерь, прежде чем обсуждать увеличение окон.

Сравнение goodput выполнено: [результаты и следующий шаг](clean-vpn-native-h2-goodput.md).
