# Radxa ↔ VPS: проверка новых native-возможностей

Проверка 30 октября 2026 выполнена на физических Radxa и VPS рядом с работающей
daily-парой. Новые экземпляры использовали TCP3443, отдельные network namespace,
настоящие TUN, временные ключи и ограниченные transient systemd units. Сеть Mac,
системный DNS хостов и daily-службы не переключались.

**Основная матрица smoke прошла, но один предыдущий DNS-отказ combo остался
необъяснённым. Это не основание объявлять combo готовым к ежедневной эксплуатации.**
[Машиночитаемый отчёт](../fixtures/clean-vpn-native-physical-features-20261030.json)
содержит хеши, успешные результаты и промежуточные отказы.

## Результаты

| Режим | Физический результат |
| --- | --- |
| boring-tls / HTTP2 | Discovery, настоящий TUN, DNS UDP/TCP, TCP-данные, ротация/отзыв второго клиента — прошли |
| boring-tls / HTTP1.1 | Те же проверки — прошли, сохранённый профиль не изменялся |
| combo / HTTP2 | Одновременно packet DNS/TCP и transparent HTTPS TLS1.2/1.3 — прошли |
| combo / HTTP1.1 | Обе ветки, discovery, DNS и управление вторым клиентом — прошли |
| Дополнительный combo / HTTP2 | Повтор с DNS-capture внутри client/exit namespace — прошёл |
| standalone transparent | 8/8 проверенных HTTPS-ответов: четыре TLS1.2 и четыре TLS1.3, по 163840 байт |

В каждом packet-прогоне manager создавал `laptop` с адресом `10.99.0.3` и
`canary` с `.4`, экспортировал и импортировал отдельные комплекты. Клиентский
source config не содержал `peer_ipv4`: адрес получался через authenticated
discovery, затем проверялась полноценная сессия. Это стабильный адрес
зарегистрированной идентичности, не DHCP lease.

Ротация canary: прежний ключ отклонён, новый принят. Отзыв: discovery отклонён,
`canary.mpn` возвращает NXDOMAIN. Рабочие PID laptop/exit сохранялись, DNS и
TCP laptop продолжали работать. Pending registry marker давал SERVFAIL;
после удаления маркера DNS и передача данных восстанавливались.

Manager использовался с явным `--offline`; координатор отдельно отправлял HUP
только проверенному тестовому PID и требовал ACK с SHA конфигурации. Это проверка
manager + native reload, но не live service-owner установки. Private musl loader
VPS меняет executable identity и не подходит для подмены daily engine.

Radxa собрала текущие engine и тесты: CTest **14/14**. На каждой физической машине
отдельно прошли **14/14** native enrollment/reload/worker-signal проверок в
`PrivateNetwork=yes`. Для VPS использован проверенный amd64 musl комплект со
своими библиотеками, без компилятора/OOM, установки пакетов или изменения ldconfig.

## Независимый наблюдатель

Внешний tcpdump на Radxa `wlan0` снимал только тестовый TCP3443. Offline observer
не использовал телеметрию engine. Во всех пяти успешных packet-прогонах совпали
все шесть ClientHello с сохранённым `chromium-156-bounded-cold-v1`: **30/30**.
JA4 — `t13d0915h2_f91f431d341e_54d72502093d`, сортированный JA3 —
`9fc752c58190630c49e1812906b40077`; сырой JA3 может меняться из-за перестановки
extensions. Для H1 exit выбирал HTTP1.1 из неизменённого клиентского предложения
ALPN: `h2` в JA4 описывает ClientHello, а не выбранный сервером протокол.

Для relay сравнивались исходный ClientHello внутри namespace и реальный внешний
поток: JA3, JA4 и ALPN совпали для **40/40**, **37/37** и **44/44** доступных пар
в трёх combo-прогонах. Один ранний H1 relay поток не попал в исходный capture и
не включён в число совпадений. Отдельный transparent smoke — **8/8** пар.
Потери kernel capture — ноль. Парсер JA3/JA4 общий с проектом; это независимый
съём трафика, не независимая реализация алгоритма и не доказательство полной
неотличимости от Chrome.

Combo HTTPS проверял CA/hostname и содержимое ответа. Origin принимал только
relay-соединение: в локальном отрицательном тесте удаление scoped REDIRECT
ломало HTTPS, поэтому успех нельзя объяснить проходом через packet-ветку.
Synthetic origin разрешён явной политикой только `11.22.33.44:443` внутри
namespace; public-https policy и реальные внешние сайты этим не проверялись.

## Найденное и исправленное

- Экспорт combo-клиента терял explicit `destinations`. Исправление `b038586`
  сохраняет политику; 19/19 unit-проверок и реальные экспорт/import/WAN успешны.
- VPS имеет `noexec` на `/run`. Первый запуск был отклонён до исполнения engine;
  тестовый комплект перенесён в приватный build-каталог проекта. Mount options
  не менялись, после тестов комплект удалён.
- Ошибка переменной в координаторе остановила самый первый этап подготовки
  конфигурации до запуска VPN; исправлена, временные файлы очищены.
- Добавлены [стенд](clean-vpn-native-packet-wan-lab.md) и ограниченный
  `clean-vpn-native-dns-capture.py` для диагностики только в disposable namespace.

## Необъяснённый DNS-отказ

Первый combo/H2 packet-only прогон получил `dns_response_mismatch` после ротации
canary. Старый probe не сохранял RCODE и длительность. Laptop не переподключался,
девять предыдущих фоновых проб прошли. Outbound pcap не выявил retransmission,
объясняющий момент отказа; задержку обратного направления он исключить не может.
Таймауты и квоты native не увеличивались, ошибка не скрывалась retry.

Следующие mixed H2/H1/H2 прогоны прошли. В последнем DNS-capture exit записал
988 пакетов, client — 394, без потерь. Все запросы получили ответы. Пять SERVFAIL
(четыре UDP, один TCP) соответствуют специально созданному pending marker;
неожиданных DNS-ошибок в этом capture нет. UDP RTT клиента: медиана 87.6 мс,
максимум 250.4 мс. Завершающий фоновый echo EOF во время остановки отдельно
отличается от DNS-отказа.

Обнаруженная TCP DNS задержка около 200 мс на exit требует отдельного локального
исследования framing/delayed ACK. Это гипотеза для измерений, не объяснение
первого отказа и не причина менять production лимиты вслепую.

Последующее [локальное исследование и исправление framing](clean-vpn-native-dns-tcp-20261030.md)
воспроизвело отдельный источник TCP-задержки. Физические результаты выше
относятся к исходному бинарнику; причина первого отказа остаётся открытой.

## Итоговое состояние и следующий шаг

Все тестовые процессы остановлены, TCP3443 свободен, временные конфигурации,
ключи и VPS binary bundle удалены. Сохранены локальные приватные pcap/логи и
Radxa build cache. Daily PID/InvocationID и хеши установленных бинарников,
маршруты, firewall, forwarding и DNS совпали до/после; Git checkout обновлён,
установленные daily engine не заменены.

Это bounded WAN smoke через TCP/Unix bridges, не benchmark или длительная
WAN-приёмка. DNS проверялся явно через native stub, не через NSS физического
хоста; reboot и host dynamic-address owner не проверялись. Для boring-tls
следующий шаг — отдельное обновление daily-кандидата с сохранением этих границ.
Для combo сначала нужны локальная проверка TCP DNS latency и повторная
инструментированная диагностика, если единичный отказ повторится.
