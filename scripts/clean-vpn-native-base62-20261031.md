# Native transparent: Base62 и физическая проверка

Исправление `55505b3`, 2026-10-31. Код установлен на действующей Radxa/VPS,
endpoint остаётся `443`. [Свидетельство без ключей и raw SNI](../fixtures/clean-vpn-native-base62-20261031.json).

## Исправленная регрессия относительно JS

Native использовал Base32 для enc-SNI, хотя JS уже использовал более компактный
Base62. Разбиение на DNS labels само по себе не устраняло ограничение полной
длины hostname: имя origin длиной 72 символа отклонялось до соединения с exit.
Это потеря поддержанного поведения при переносе, а не требование безопасности.

Теперь client отправляет `n2.<Base62 labels>.<public-name>` с тем же алфавитом,
что JS: `0-9a-zA-Z`. Labels ограничены 63 символами, всё имя — 253.
Регистр ciphertext сохраняется; регистр public-name несущественен.
Проверки включают фиксированные ответы из JS, ведущие нули, полное восстановление
72-символьного SNI, реальные TLS 1.3/HRR/full/resumed и передачу данных.

Exit также принимает старый `n1` Base32. Криптографический payload, ключи, AEAD,
SHA-256 исходного ClientHello и scope durable replay сохранены. Перекодирование
одного ciphertext между n1/n2 не создаёт новую replay identity. Порядок обновления:
**exit, затем client**. Старый exit n2 не принимает; откат только exit после
обновления client требует согласованного отката клиента.

## Проверенный контракт

| Поведение | Проверка |
| --- | --- |
| Исходный ClientHello возвращается origin без изменения TLS transcript | Реальные TLS 1.2/1.3, HRR, full/resumed; 12 сценариев |
| TCP fragmentation и SNI в нескольких TLS records | 475 layouts, 10 000 mutations |
| Авторизация раньше origin connect, replay после crash | Реальные socket/netns тесты |
| Длинное имя и Base62 не повреждают регистр или labels | JS vectors, 72-символьный SNI, legacy/cross-format replay |
| Combo принимает packet и relay одновременно | Реальные engines и REDIRECT в отдельном netns |
| Работа старого клиента с новым exit | Физические HTTPS и download 1 MiB до обновления client |
| На проводе действительно новый формат | Внешний tcpdump: 20 n2 ClientHello, 0 n1 |
| Сохранённый bounded TLS-профиль packet-ветки | Независимый observer: `matched`, differences=[] |

Лаборатория: CTest 14/14; 4 native transparent + 4 combo/diagnostic integration;
48 JS codec/control-plane/installer/journal проверок в Linux, без skips.
На каждом физическом узле собственная сборка и CTest 14/14. Дополнительные
первые installer прогоны имели ошибки среды — macOS `/tmp` и затем отсутствие
engine mount в контейнере; успешная матрица выполнена с Linux fixture и бинарником.

## Физическая работа после обновления

Mac → временный процессный proxy с `IP_BOUND_IF=en9` → USB Radxa → native combo
→ VPS. DNS proxy этого теста запрашивал A у `192.168.7.1`, outbound сокеты были
привязаны к USB. Системные Wi-Fi, маршруты, DNS и proxy Mac не менялись.

- DNS: A/AAAA по UDP/TCP — 4/4.
- HTTPS с обычной проверкой сертификата: HTTP 200, trace показывает IP exit.
- Download: ровно 1 048 576 bytes.
- Upload: 276 000 bytes, echo совпал побайтово.
- WebSocket Upgrade измерительного сервера на 8080: HTTP 101 через packet-ветку.
- Chrome 156: полный Speedtest, **43,12 / 46,44 Мбит/с**, ping 82 ms.
- Chrome 156: полный Яндекс Интернетометр, **83,51 / 78,13 Мбит/с**, ping 105 ms.

Это функциональные WAN прогоны с браузерным proxy, а не сравнительный benchmark.
Страница Speedtest использует relay для HTTPS 443, выбранные измерительные
серверы на 8080 идут через packet-ветку. Успешная HTML-загрузка отдельно от
завершения download/upload не считалась успешным замером.

До этого два прогона Chrome for Testing 147 после обновления не завершились:
один остался на Connecting, другой после download с upload=0; также зависал
captureScreenshot. Один прежний baseline в том же Chrome 147 завершился.
Причина этой неустойчивости не установлена. В финальном прогоне использованы
установленный Chrome 156 в отдельном временном профиле, отключённый GPU и
бюджет proxy 512 MiB вместо 128 MiB. Эти изменения не позволяют приписать
результат одному отличию версии браузера или объявить все предыдущие отказы
исправленными в engine. Неудачные результаты сохранены отдельно локально.

## Observer и сохранность установки

Pcap ограничен 1500 исходящими пакетами к exit: 22 SYN streams, 21 наблюдаемый
ClientHello; один поток не получил отпечатка, 34 пакета без захваченного SYN
не использованы для восстановления. Tcpdump сообщил 0 kernel drops. Raw pcap
остался приватным на Radxa; наружу выведены агрегаты и отпечатки без raw SNI.

Для packet-ветки проверены параметры сохранённого профиля
`chromium-156-bounded-cold-v1`. JA3/JA4 вычислены отдельно: JA3 одного соединения
не является фиксированным эталоном при `permute_extensions=true`.
Это проверка первого холодного ClientHello, не HTTP/2/browser equivalence.

Оба ELF заменены штатным binary updater с rollback, без сброса ключей, профиля
или replay state. Radxa firewall IPv4/IPv6 и IP rules совпали до/после с
исключёнными счётчиками. Network owner и kill switch остались активными.
На VPS сохранился прежний network owner; IP rules и IPv6 firewall совпали.
Первый IPv4 snapshot VPS включал счётчики, поэтому его hash не служит
доказательством равенства всей таблицы; собственные правила продолжает
проверять действующий owner каждые пять секунд.

Первый build VPS остановлен OOM; повторный прошёл с временным проектным swap.
Swap удалён после сборки, `fstab` не менялся. Действующий exit до готовности
кандидата продолжал работать. Reboot и отключение kill switch не выполнялись.

## Что ещё не закрыто

- Повторная проверка именно iPhone/Safari через физический USB. Успех Chrome
  на Mac не заменяет её и не доказывает причину прежних отказов телефона.
- Native payload длиннее JS: ciphertext `76 + origin hostname bytes`.
  Base62 расширяет диапазон, но не даёт всему диапазону JS тех же границ.
  Слишком длинное имя/невозможный record resize всё ещё закрывают соединение;
  защищённый fallback через boring пока не подключён.
- Exit сохраняет исходный IPv4 назначения; JS выбирает адрес по hostname на
  exit. Это отдельное различие, Base62 его не меняет. IPv6 relay не добавлен.
- При браузерной нагрузке счётчики содержат EOF/shutdown на отдельных relay
  соединениях. Без сопоставления конкретных потоков нельзя объявить каждый
  такой отказ безвредной отменой браузера. AEAD/ClientHello binding и лимит
  hostname в контрольных физических пробах отказов не дали.
