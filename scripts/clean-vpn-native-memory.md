# TUN: точный размер JS-пакета вместо удержания большого read-buffer

2026-10-04. Продолжение [ускорения восстановления](clean-vpn-fast-recovery.md).
Статус: native-тесты, длительный сетевой прогон и проверка крупных UDP/PMTU
на обычной сборке прошли. Физическая Radxa не обновлялась.

## Причина и изменение

В `/var/tmp/meshpn-usb-e2e-XrhAm4/report.json` скорость пяти восстановлений
уложилась в 10 секунд, но RSS вырос с 87 960 до 154 076 KiB и нарушил лимит.
Native-счётчики показали 2 285 не финализированных read-buffer, всего
149 813 010 байт backing storage, при `process.memoryUsage().external` около
6 MiB. Это расхождение, а не доказательство постоянной утечки после GC.

Ранее addon читал каждый пакет в блок 65 535 байт, передавая JS external
ArrayBuffer длиной фактического пакета. Даже маленький пакет удерживал весь
блок до финализации. Теперь addon создаёт ArrayBuffer точного размера через
[`napi_create_arraybuffer`](https://nodejs.org/download/release/v24.13.0/docs/api/n-api.html#napi_create_arraybuffer),
копирует фактические байты и сразу возвращает read-buffer в существующий пул.
API callback не изменён: это по-прежнему массив точных ArrayBuffer, не padded view.
Пул по-прежнему ограничен 64 блоками (менее 4 MiB); в одном callback не более
32 пакетов. Буферы, которые сохраняет JS, теперь имеют только фактический размер.

Цена — одно дополнительное копирование каждого прочитанного пакета.
Это не обещание прироста пропускной способности; throughput на Radxa ещё
не измерен. MTU, максимальный пакет 65 535 байт и batching не менялись.
Нет периодического GC/trim, новых параметров ядра или сетевых разрешений.

Также исправлен error-path `napi_set_element`: текущий read-buffer уже возвращён
в пул, поэтому освобождаются только оставшиеся элементы batch. Раньше буфер,
переданный external ArrayBuffer, мог быть возвращён вручную и затем финализатором.

## Проверки

`node --test scripts/test-tun-native-memory.mjs` собирает отдельную копию addon
и вызывает настоящий `on_poll` через локальную Unix datagram socketpair.
Тест не создаёт TUN, не требует root и не изменяет сеть хоста.

- Точные данные/размеры: 1, 40, 64, 1400, 1500, 8192, 65 535 байт.
- JS сохраняет пакет; многократное переиспользование read-buffer не меняет его данные.
- Отказ выделения ArrayBuffer и `napi_set_element` на каждом из 32 мест batch;
  после каждого отказа native in-use равен нулю, нет дубликатов указателей в пуле.
- Исключение JS callback и последующее успешное чтение.
- Одновременно удерживаются 100 000 маленьких JS-пакетов без принудительного GC;
  native-пул остаётся ограниченным, external native-буферы не создаются.

Полная регрессия перед VM: **531 passed, 0 failed, 0 skipped**.
Новый `--soak-diagnostics` записывает `packetStorage=v8-owned-exact`,
`copiedPackets/copiedBytes` и требует `inUse=0` во всех меж-callback снимках.
Старые отчёты сохраняют прежнюю семантику external-счётчиков.
Дедлайны 10 секунд и предел роста RSS 64 MiB не повышены.

### Длительный прогон — PASS

`/var/tmp/meshpn-usb-e2e-hzYJOt/report.json`: **645 проверок**, 809 TCP-снимков,
7 060 коротких проб, 729 ответов длинного TCP; нагрузочная часть с периодом
покоя — 1 682,45 секунды. Шесть восстановлений, без смены процесса VPN:

| Цикл | Обрыв | Первый USB HTTPS-ответ | С итоговым аудитом |
|---|---|---:|---:|
| 1 | exit blackhole | 7,512 с | 13,220 с |
| 1 | смена DHCP | 7,472 с | 12,237 с |
| 2 | exit blackhole | 6,727 с | 11,168 с |
| 2 | смена DHCP | 7,857 с | 12,526 с |
| 3 | exit blackhole | 6,406 с | 11,127 с |
| 3 | смена DHCP | 7,309 с | 13,215 с |

RSS по снимкам Node: **79,688 → 88,113 MiB** за шесть восстановлений.
В течение 120 секунд без нагрузки около 88,39 MiB; диагностический GC после
180 секунд — 87,59 MiB, последующий разовый лабораторный trim — 80,582 MiB.
Лимит RSS пройден **до** принудительного GC/trim. Эти операции не добавлены
в production и не используются для прохождения нагрузочных проверок.

Все снимки: 32 выделения read-buffer за весь прогон, пул 32, in-use 0,
backing storage **2 097 120 байт**; 40 821 скопированный пакет, 4 783 102 байта
данных, ни одного external slab/finalizer. Дескрипторы в нагрузочных снимках
32–34; отдельный снимок во время GC — 39, следующий снова 32. Снимки дескрипторов
и V8 handles не атомарны; в клиенте есть кратковременные системные команды.
Это не утверждение об отсутствии любых утечек памяти или верхней границе RSS
на любой нагрузке.

SHA-256 production native-исходника:
`cd186cb1ba63d34d76e6930bc72d7acf35e412acfc1c6b89ea16a22760a588a3`.
Диагностика собрана из него; после старта изменён только runner для обязательной
пересборки addon в остальных режимах и связанные тесты, не runtime клиента/addon.
VM штатно завершилась с sync/unmount. Прямой обход и потеря USB rescue
в проверенных сценариях не обнаружены. Это QEMU/Linux peer, не физический Wi-Fi/Mac.

### Обычная сборка: UDP/PMTU — PASS

`/var/tmp/meshpn-usb-e2e-3TaFTd/report.json`: **62 PMTU-сценария + 117 общих
проверок**. Крупные UDP в обе стороны, DF/фрагментация, ICMP MTU 1400/1280,
остановка/возврат VPN, повторная передача 4096 байт и USB SSH:22/2222 прошли.
`nativeBuild.diagnostics=false`, хеш исходного и скомпилированного C++ совпадает
с указанным выше: этот прогон не использовал диагностические native-экспорты.
VM завершилась с кодом 0, sync/unmount и power-down.

Все режимы E2E теперь пересобирают addon из текущего C++, записывая хеши
исходника и бинарника, вместо использования старого addon из базового образа.

## Установка — после публикации

Обычного `git pull` недостаточно: изменился `native/tun_linux/tun_linux.cc`.
Нужны пересборка addon на целевой архитектуре и запуск нового процесса VPN.
Порядок с резервной копией и сохранением USB rescue записан в
[чек-листе Radxa](clean-vpn-radxa-next-checks.md).

H2 PING не требует изменения exit. Исправление памяти относится к любому
процессу, использующему TUN-addon: чтобы получить его эффект на exit, addon
нужно отдельно пересобрать и там. Обновление exit в этой работе не выполнялось.
