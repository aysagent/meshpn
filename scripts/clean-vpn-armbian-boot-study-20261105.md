# Исследование загрузки Armbian на Cubie A7Z — 5 ноября 2026

Read-only исследование: параметры загрузчика, ядра и служб не менялись,
перезагрузка для измерений не выполнялась. Цель — ускорить доступность USB,
админки и VPN, сохранив сеть, защиту от обхода туннеля и аварийный доступ.

## Объект и границы измерений

- Radxa Cubie A7Z, Armbian community `26.11.0-trunk.108`, Debian 13.
- Ядро `6.6.98-vendor-sun60iw2`, systemd `257.13-1~deb13u1`.
- Корень: UFS `/dev/sda1`, EXT4. RAM около 8 ГБ.
- Boot ID: `8635d7f6-385a-4e8e-9b0a-40c87d93086b`.
- USB gadget: `usb0`, `192.168.8.1`; uplink в этой загрузке — Wi-Fi.
  USB-iPhone отсутствовал, `iphone0` и `usbmuxd` не участвовали в старте.
- Native combo-tls, exit `84.201.14.124:443`.
- Дата отчёта — Europe/Istanbul; журнал платы отображал 4 ноября в CET.
  Часы исправлялись во время старта, поэтому сравниваются **монотонные** метки.

Это измерения A7Z, не Zero. Одной загрузки недостаточно для оценки разброса
из-за Wi-Fi, DHCP, накопителя, подключённых устройств и состояния часов.

Исходная загрузка произошла **до** исправления startup race админки и возврата
штатного ramlog, выполненных в предыдущем этапе работы. Поздние рестарты этих
служб не следует принимать за их исходное время boot. Новый холодный запуск
после этих изменений ещё не измерялся.

Источники на плате: `systemd-analyze time/blame/critical-chain`, свойства units,
`journalctl -b -o json` с `__MONOTONIC_TIMESTAMP`, `dmesg`, unit-файлы и скрипты,
`/boot/boot.cmd`, `/boot/armbianEnv.txt`, состав initramfs и установленный пакет
U-Boot. Сеть Mac, VPS и прежняя Zero при исследовании не менялись.

## Что происходит до ядра

Рабочая схема: **питание → BootROM → boot0 → системная прошивка → U-Boot → Linux**.
Это схема назначения стадий, не трасса конкретного старта: точный состав и
порядок внутренних firmware-компонентов нужно подтвердить ранним UART-журналом.

| Стадия | Назначение | Что подтверждено / возможность ускорения |
|---|---|---|
| Питание, reset | Стабилизация питания и начало исполнения CPU | Время не измерено. Не оптимизировать питание ради скорости. |
| BootROM | Встроенный код SoC выбирает начальную загрузку или FEL recovery | Неизменяемый код процессора. Фактический путь выбора носителя не записан. |
| boot0 | Ранняя настройка DRAM, частот, загрузка следующих стадий | В пакете есть `boot0_sdcard.fex` и `boot0_spinor.fex`, по 256 КБ. Это критичный аппаратный код. |
| Системная прошивка / secure monitor | Подготовка окружения CPU, runtime-функции управления ядрами и питанием | Linux обнаружил PSCI v1.1 и SMC Calling Convention v1.2. Точные версии BL31 и наличие/исполнение OP-TEE не установлены. |
| U-Boot | Инициализация устройств, выбор загрузки, возможная пауза автозапуска | Установленная конфигурация имеет заголовок U-Boot 2018.07. Версия реально запущенного загрузчика и его сохранённое окружение не прочитаны. |
| Сценарий Armbian | Чтение настроек, ядра, initramfs, DTB и overlays | Проверен `/boot/boot.cmd`; загружает файлы в RAM и вызывает `booti`. |
| `booti` → Linux | Передача ядру управления и адресов initramfs/DTB | Отсюда начинается измеряемый Linux участок, а не от подачи питания. |

Пакет `/usr/lib/linux-u-boot-vendor-cubie-a7z/` содержит также
`boot_package.fex` около 1,4 МБ и конфигурации сборки. Наличие файлов пакета
**не доказывает**, что именно эти байты сейчас записаны в загрузочную область
носителя или SPI. Источник фактически исполненного bootloader не установлен.

В строках установленного пакета найдено **`bootdelay=2`**. Это кандидат на
устранение двухсекундной паузы, но пока только значение из пакета. Сохранённое
окружение может его переопределять; обещать выигрыш 2 с без проверки нельзя.
При будущем изменении сохранить возможность прервать загрузку для recovery.

Загрузочный сценарий читает:

| Файл | Назначение | Размер / параметры |
|---|---|---|
| `/boot/armbianEnv.txt` | Параметры старта | `verbosity=7`, `console=both`, `bootlogo=true`, `param_otg_mode=peripheral` |
| `/boot/Image` | Ядро Linux | Ссылка на `vmlinuz-6.6.98-vendor-sun60iw2`, около 33 МБ |
| `/boot/uInitrd` | Образ initramfs | Около 14 МБ |
| `/boot/dtb/allwinner/sun60i-a733-cubie-a7z.dtb` | Описание оборудования | Около 187 КБ |
| `radxa-a7z-pwm-fan` overlay | Описание управления вентилятором | Применяется загрузочным сценарием |

Сценарий использует `earlyprintk`, UART `ttyS0,115200` и экран `tty1`.
Само наличие `bootlogo=true` не является измерением стоимости заставки.
**Initramfs читается в память до ядра, но его `/init` исполняется уже после
старта ядра.** Поэтому время чтения образа и время исполнения initramfs —
разные участки.

Для измерения доядерной части нужен UART-захват от подачи питания до
`Starting kernel`, желательно с временными метками принимающей стороны.
Ни точное время этого участка, ни экономия от изменения U-Boot пока неизвестны.

В initramfs установлено `MODULES=most`, `COMPRESS=gzip`, `FSTYPE=auto`,

Для EXT4 root это кандидат на исключение из **раннего** образа; поддержка Btrfs
в основной системе может оставаться. Нельзя без проверки заменять initramfs
на минимальный: нужно сохранить драйверы UFS/SD, EXT4 и аварийную загрузку.

До основного systemd dmesg содержит 713 строк, около 52 КБ текста. При UART
115200 передача такого объёма теоретически занимает около 4,56 с. Это **не
измеренная задержка загрузки**: не все записи обязательно выводились, вывод
может пересекаться с другими работами. Уменьшение console verbosity — кандидат
на A/B-проверку, а не обещание сэкономить 4,56 с. Ошибки, аварийную консоль и
журнал ядра следует сохранить.

### Насколько раньше можно поднять службы

1. **Owner не должен падать только потому, что DHCP ещё не закончен.**
   Между готовностью uplink (15,008) и повторным стартом owner (24,288) прошло
   **9,28 с**. Кандидат: ожидание подходящего default route внутри процесса
   либо реакция на сетевое событие, с остановкой и таймаутами по lifecycle.
   Это не предложение просто бесконечно уменьшить RestartSec и повторять
   recovery. При неизменных остальных этапах ориентир VPN-ready — около
   **29 с вместо 38 с**. Это расчёт по одной загрузке, не результат реализации.
2. **Профилировать подготовку сети, занявшую 10,34 с.** В активных журналах
   40 DNS-операций и 26 combo redirect-операций; код последовательно запускает
   внешние команды и проверяет состояние. Подробных времён каждого этапа нет.
   Можно исследовать уменьшение повторных чтений/вызовов, но нельзя объявлять
   весь интервал устранимым или удалять crash-recovery проверки.
3. **USB уже поднят высоко:** `DefaultDependencies=no`, после local-fs,
   configfs и modules-load, до networkd/resolved. Пересмотр широких зависимостей
   даёт предварительный ориентир 0,5–1 с, не гарантированный результат.
   Нужно сохранить root/configfs/UDC, DHCP и последовательность firewall.
4. **Сохранить порядок vendor firewall → kill switch → networkd.** Он нужен,
   чтобы на старте не появлялось окно прямого выхода. Потеря защиты не является
   допустимым способом ускорения.
5. **Админку можно готовить независимо от внешней сети.** USB socket уже
   слушает около 11,89 с; дальнейшая цель — готовность broker/web без лишнего
   ожидания. Массовый перенос Node/control plane в initramfs не обоснован.
6. **Clock recovery оставить условным**, только после определённой ошибки
   времени, как согласовано с пользователем. Сохраняющие время часы позволят
   избежать неудачной TLS-попытки и recovery; проверку TLS отключать нельзя.
7. Оптимизация ядра/initramfs сдвигает раньше всю цепочку. Приоритет экспериментов:
   console verbosity, лишний Btrfs/RAID6, затем отдельно PCIe для профиля без
   устройств расширения. Суммировать предполагаемые выигрыши без A/B нельзя.

| Интервал | Время |

| От старта ядра до запуска `/init` | ≈7,50 с |
| От `/init` до основного systemd | ≈1,38 с |
| Основной userspace до завершения начальной загрузки systemd | 4,35 с |
| **Базовая система от старта ядра** | **13,236 с** |
| **VPN ready от старта ядра** | **38,149 с** |
| BootROM/boot0/firmware/U-Boot до ядра | **Не измерено** |
| Полное время от подачи питания | **Неизвестный доядерный участок + указанные значения** |

`systemd-analyze time` группирует первый участок как
`8.886s (kernel) + 4.349s (userspace) = 13.236s`; отдельного достоверного
initrd timestamp от systemd нет. Разделение 7,50/1,38 с восстановлено по dmesg.

Следующее исследование перед изменениями: UART с подачи питания, действующее
окружение U-Boot, несколько обычных boot с одинаковой периферией и uplink,
проверка текущего исправленного admin startup и восстановленного ramlog.
Для оптимизации network owner нужна отдельная поэтапная телеметрия в лаборатории.
Пока ни одна предложенная boot-оптимизация не применена.
