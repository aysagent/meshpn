# Native ML-DSA и граница trust-anchor extension

Опциональный cold TLS профиль теперь может объявлять и реально проверять
ML-DSA-44, ML-DSA-65 и ML-DSA-87 (`signature_algorithms`: 2308, 2309, 2310).
Используется реализация закреплённого BoringSSL
`a7481f34712bc056a47ab91015536166b3a6cebb`, без raw extension replay и новых патчей.
Это алгоритмы подписи TLS CertificateVerify, а не новый VPN-транспорт.

## Применение

Пример: [synthetic cold-mldsa](../fixtures/native-tls-profiles/cold-mldsa.json).
Он расширяет прежний synthetic cold-h2 только списком signature algorithms.
Это не измеренный профиль Chrome. Для клиента можно указать его абсолютный
путь в `tls_profile_path` и выполнить обычный
[native --check-config](clean-vpn-native-tls-profiles.md). Для combo поле находится
в `boring`; transparent-ветка сохраняет TLS приложения.

Существующие профили и настройки клиента без профиля сами не изменяются.
Если exit использует обычный RSA/ECDSA сертификат, соединение продолжает
использовать соответствующий классический алгоритм. Наличие ML-DSA в ClientHello
не означает, что сервер выбрал его: это проверяется отдельным handshake-тестом.

В измерении synthetic cold-mldsa JA3 остался прежним, а JA4 изменился:
signature algorithms не входят в JA3. Поэтому совпадение одного отпечатка
не заменяет сравнение полей ClientHello и реальную проверку подписи.

ML-DSA здесь работает в TLS 1.3. Профиль может отдельно объявлять TLS 1.2 с
классическими алгоритмами по прежним правилам; ML-DSA не становится TLS 1.2
алгоритмом. CA, hostname, exporter-bound PSK, ограничения H2 и запрет static-RSA/CBC
cipher suites сохраняются. Неизвестные signature IDs остаются запрещены.

## Что проверяет лаборатория

```bash
npm run lab:native:mac -- --tls-profiles
```

Runner собирает отдельный `profile-credentials-fixture`. Он генерирует временные
ML-DSA leaf keys и сертификаты `localhost`, подписанные временным RSA CA.
Закрытые ключи создаются как новые файлы с mode 0600 и удаляются тестом. Они не
попадают в репозиторий. Production engine не содержит fault-инъекций.

Для каждого из трёх алгоритмов проверяются:

- Успешный настоящий TLS handshake и аутентифицированный packet exchange.
  Fixture фиксирует алгоритм отправленного CertificateVerify и алгоритм,
  принятый клиентом после завершения TLS handshake.
- Независимый TCP observer считывает ClientHello, проверяет фактический список
  signature algorithms и JA3/JA4. Он не получает эти поля из логов engine.
- Клиент без данного алгоритма отвергает соединение с ML-DSA leaf.
- Неверная ML-DSA подпись CertificateVerify действительно отправляется сервером
  и отвергается клиентом; пакеты до авторизации не инжектируются.
- Неверный CA, hostname и PSK не проходят. При неверном PSK TLS handshake сначала
  успешно проверяет ML-DSA, а затем отказывает VPN-аутентификация.

Отдельно проверяются combo, HRR и negotiated ALPS с ML-DSA. Генератор сертификатов
нужен только лаборатории; выпуск production PKI этим изменением не автоматизирован.
RSA CA в тестах означает, что это не испытание полностью постквантовой PKI.

Зафиксированный результат: **10/10 CTest, 17/17 native profile integration,
42/42 JS capture/policy/lab tests**, без пропусков. [Отчёт с hashes и измеренным
ClientHello](../fixtures/clean-vpn-native-mldsa-report.json). Регрессия включает
прежние Brotli/ALPS, ошибки доверия и bounded packet flow. VPS/Radxa и сетевые
настройки Mac этим этапом не изменялись.

## Почему trust anchors пока запрещены

В том же BoringSSL есть `SSL_CTX_set1_requested_trust_anchors` и обработка
extension 51764. Однако комментарий API прямо связывает передачу части списка,
в том числе пустого списка, с получением доступных anchors от сервера и retry.
Настройка extension сама **не меняет проверку сертификата**.

Native пока не имеет такого контракта выбора цепочки и ограниченного retry.
Добавить пустое extension ради совпадения JA3 означало бы объявить поведение,
которое мы не реализовали. Поэтому 51764 остаётся вне allowlist; отчёт показывает
`trust-anchor-selection-and-retry-not-implemented`. Даже пустой список не
превращается в исполняемый профиль автоматически.

Независимый observer теперь проверяет структуру trust-anchor vector и сохраняет
только `empty`, `count`, `idLengths`. Сами IDs могут раскрывать частную PKI,
поэтому не экспортируются. Лимиты: 1 KiB списка, 32 непустых IDs, каждый до 255
bytes. Некорректная/слишком большая структура отвергается. Старые capture bundles
не дополняются выдуманными данными и сохраняют исходные checksums.

Для будущей поддержки нужны отдельные испытания выбора альтернативной цепочки,
предела повторов и отказов, сохранения CA/hostname/PSK и отсутствия импорта доверия
из ответа удалённого сервера. Потребуются дополнительные измерения текущего
браузера в этих сценариях: cold capture одного ClientHello их не доказывает.

## Что дальше

Измеренный Chromium 156 по-прежнему имеет статус blocked. ML-DSA больше не
является блокером; остаются trust anchors, ticket lifecycle, запрещённые cipher
suites и H2 caps. [Политика и отчёт](clean-vpn-native-profile-policy.md) показывают
это явно. До изменения H2 credit следующий отдельный лабораторный эксперимент —
проверить bounded memory/backpressure с несколькими клиентами и медленным exit.
Trust-anchor retry и resumption остаются самостоятельными этапами, без включения
по умолчанию или ослабления проверки сертификата.
