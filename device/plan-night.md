# Ночная работа: две P4, реальный AP+STA и производительность

План на 29 октября 2026; пользователь разрешил запуск и добавление VPN-блока.
Работать по приоритету, запас задач на полную ночь и дольше. Время ниже ориентировочное,
не таймер завершения. Закончив один блок, переходить к следующему.

Продолжение утром: парная трасса локализовала растягивание ACK между SDIO
acceptance Stamp и lwIP input Waveshare. При тестовом ограничении STA до b/g/n
найден и исправлен воспроизводимый STOP→CONNECTED без START с IGMP/mDNS
panic. После исправления запуск и DHCP проходят; сама RF-передача ещё медленная.
Обратная топология, STA b/g/n и снижение мощности не восстановили RF.
Обычные radio overrides возвращены, 8/8 циклов STA/DNS/mDNS/USB на каждой
плате прошли. Контроль A-MPDU off также не помог. Добавлен P4-local UDP peer;
сравнивается APSTA/STA-only клиента. Найден и исправлен пропущенный
esp_wifi_start() при отключённом AP; прежний STA-only вывод невалиден.
Исправленный STA-only не ускорил RF. Новый UDP A/B/A подтвердил сильное
влияние 11ax на uplink Stamp→Wave, но downlink и передача Wave через STA
остаётся плохой. Проверяется только TX A-MPDU Wave; defaults не меняются.
VPN host peer теперь проверяет L4 checksums и разделяет reconnect state;
real TLS I/O и общий host suite прошли. Подробности и незакрытые
пункты — в `reports/2026-10-29-dual-p4-night.md`; весь план не завершён.

## Цель и исходная точка

Устранить зависания и найти измеримое ускорение DIRECT AP+STA на Stamp и
Waveshare. Stamp 12e9e04: AP b/g/n HT20, STA b/g/n/ax; телефон дал 12/11 Мбит/с.
Прежний AP b/g/n/ax на Stamp вызвал длительный C6 backpressure и потери.
Сохранить этот рабочий вариант как контроль. Не обещать заданную скорость.

Обе платы доступны по отдельным USB: Stamp 192.168.12.1, Waveshare 192.168.10.1.
Wi-Fi Mac не переключать. Не менять роутер и не трогать Camic/XIAO.

## 1. Подготовка стенда и откат (примерно 1–2 часа)

- Сохранить идентичности, build, настройки, выбранные профили и исходные
  показатели обеих плат. Секреты хранить только в закрытых локальных файлах.
- Зафиксировать контроль Waveshare до обновления. Собрать и установить общие
  исправления повторного START и памяти Diagnostics, сохранив AP defaults Wave.
- Добавить оркестратор временных соединений плат. Не удалять домашние профили;
  восстановить выбранные профили/приоритеты после каждой серии и при остановке.
- Сделать журнал незавершённой сессии: аварийный выход процесса не должен
  оставлять следующему запуску неизвестную топологию. Проверить восстановление.
- Управлять только через USB с проверкой board и идентичности; прошивки
  последовательные с MAC-проверкой. При USB busy — до 20 повторов через 30 s.

## 2. Двусторонний стенд AP+STA (примерно 2–3 часа)

Топология A: Stamp STA → домашний роутер; Waveshare STA → AP Stamp.
Топология B: Waveshare STA → домашний роутер; Stamp STA → AP Waveshare.
Не соединять одновременно STA обеих плат с AP друг друга.

В каждом направлении разделить измерения:

1. Локальный обмен между платами через AP/STA — один радиопереход без WAN.
2. Клиентская плата → AP исследуемой платы → её STA → локальный сервер
   на Mac в домашней сети — реальная пересылка через AP+STA.
3. USB+STA исследуемой платы — контроль без AP-плеча.

Генератор/приёмник на плате при необходимости доработать: TCP/UDP, ограничение
времени и размера, измерение на приёмнике, sequence/loss для UDP, отмена.
Предпочесть уже существующие endpoints там, где они действительно проходят
нужный путь. Не выдавать synthetic AP-forward за RF-тест. Не допускать, чтобы
Mac отправлял трафик своему локальному IP через loopback вместо стенда.
Путь подтвердить интерфейсами, адресами и изменениями счётчиков обеих плат.
Сначала пройти низкоскоростной контроль, затем запускать нагрузку.

Матрица: TCP оба направления, UDP 4/8/12/16/20/24/32 Мбит/с с адаптивным
уточнением участка потерь; одиночные и двунаправленные потоки. По 3 повторения
для коротких сравнений, одинаковые длительность и размер пакетов.
Сопоставить throughput, RTT, потери, retransmits, STA/AP queues, SDIO credits,
throttle, CPU, internal/DMA memory, температуру и перезапуски.
Учитывать, что длинный HTTP stream занимает HTTP worker: timeout диагностики
сам по себе не доказывает зависание; использовать внеполосные логи и снимки.

## 3. Оптимизация по измерениям (примерно 2–4 часа и дальше)

- Искать, что ограничивает каждый путь: RF, C6 credits, очередь P4, копирование,
  планировщик или собственный тестовый приёмник. Клиентская плата тоже может
  стать ограничителем — менять роли и проверять локальные контроли.
- Изменять один фактор за эксперимент. Приоритеты: fairness STA/AP, обработка
  backpressure, лишние копирования/пробуждения, размеры и возраст очередей,
  согласованность aggregation/buffer settings с конкретным C6 firmware.
- Не увеличивать очереди ради красивой скорости ценой задержки/потерь.
- При исправном стенде провести ограниченное AP b/g/n ↔ b/g/n/ax сравнение
  между C6. Это позволит проверить AX без AX домашнего роутера, но не заменит
  тест с телефоном; рабочий default Stamp вернуть независимо от результата
  peer-теста. Не переходить к HT40/настройкам роутера.
- Подтверждать существенные выигрыши повтором и возвратом к контролю A/B/A.
  Не оставлять эксперимент, который ухудшает стабильность или не даёт выигрыша.
- C6 firmware не менять в рамках этого плана: сначала использовать P4 и
  доступную диагностику; отдельное обновление C6 потребует собственного плана.

## 4. Длительная стабильность и восстановление (2–4 часа)

- Лучший проверенный вариант: 60–120 минут для каждой роли с чередованием
  upload/download, двунаправленного потока, короткой перегрузки и простоя.
- Проверить возврат RTT/очередей/памяти после нагрузки, доступность USB-админки,
  отсутствие непредусмотренных reboot, зависших SDIO очередей и DNS-зависаний.
- Через управление платами проверить отключение/возврат STA, перезапуск AP,
  перезапуск клиентской платы и восстановление DHCP/DNS/NAPT.
- При сбое сначала сохранить evidence и последнюю операцию; затем восстановить
  доступ. Исправить воспроизводимую причину и повторить затронутую проверку.

## 5. VPN без VPS (отдельный обязательный блок, примерно 2–4 часа)

- Привести local VPN lab к текущим обязательным CA/name/date проверкам TLS:
  временный локальный CA/сертификат, доверие на плате, безопасное восстановление
  исходного CA и настроек после теста. Нельзя заменить сохранённый секрет или CA
  без проверенного способа его возврата.
- На обеих P4 проверить TCP/UDP/raw TLS к локальному peer на Mac: framing,
  HTTP/DNS внутри тестового туннеля, MTU/MSS, fragmented/coalesced records,
  partial I/O, обратный трафик USB/AP, доступность админки при нагрузке.
- Свежие TLS handshake: верный сертификат, чужой CA, неверное имя, просроченный
  и будущий сертификат; проверять ожидаемый отказ без перехода в insecure.
- Reconnect/kill switch: закрытие peer, TCP FIN/RST, таймаут, смена транспорта,
  прекращение ответов UDP. Проверять фактическую блокировку контрольного
  трафика, не только флаг connected в UI. У UDP отдельно учитывать отсутствие
  встроенного handshake: не считать connect() подтверждением доступности peer.
- Проверить сохранение WireGuard/прочих профилей и ключей при переключениях,
  ошибки ввода, отмену/повторное Save and apply. WireGuard crypto/packet tests
  и ревью lifecycle — offline; без полноценного peer не объявлять hardware WG
  handshake/интернет проверенными.
- Проверить память и ресурсы после серии успешных/неуспешных соединений,
  обработку WANT_READ/WANT_WRITE, коротких чтений/записей, отмену устаревшей
  конфигурации и двойное освобождение. Исправить найденное, добавить регрессии.
- Сравнить расходы TCP/UDP/TLS на локальном стенде с явным указанием ограничений
  synthetic peer. Удалённый VPS, реальный WAN exit и JA3/JA4 остаются отдельно.

## 6. Дополнительный запас работ

- Две платы одновременно: mDNS, адреса, правильный интерфейс ответа, DHCP/DNS,
  отсутствие взаимного выбора устройства в скриптах, восстановление после
  перезапуска одной платы при работающей второй.
- Автоматизированная регрессия captive HTTP/DNS и hostname после изменений;
  не объявлять автоматическое окно iOS повторно проверенным без телефона.
- Для VPN придерживаться блока 5: не менять глобальную маршрутизацию Mac,
  не выдавать synthetic peer за полноценный WAN exit/NAT.
- Проверить отмену/таймауты тестовых endpoints, ошибки API под нагрузкой,
  границы буферов и корректность telemetry. Покрывать исправления содержательными
  host-тестами; проверять сборки затронутых моделей последовательно.
- Код-ревью собственных изменений, обновление инструкции стенда и устранение
  устаревших утверждений в общей документации.

## Правила завершения и результат

Не останавливаться из-за одного неудачного эксперимента: восстановить контроль
и перейти к следующей обоснованной гипотезе или независимой задаче. Если одна
плата требует физического действия после регламентных повторов, продолжить
доступную работу на второй и offline. Не повторять бессодержательные speedtest.

По команде остановки: безопасно завершить операцию, вернуть домашние профили,
VPN/имена/адреса, остановить временные серверы и установить только проверенные
образы. Исчерпав список, завершить работу честным отчётом, без искусственного
удержания нагрузки ради занятости.

Результат: код и воспроизводимые команды, коммиты/пуш после pull, обновлённый
plan.md, отчёт с матрицей путей и сравнением до/после; сырые данные отдельными
локальными файлами. Отдельно перечислить найденное, исправленное, неподтверждённое
и то, что потребует телефона. Не считать скорость C6-клиента обещанием для iPhone.
