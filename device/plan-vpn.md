# План клиента clean-vpn для XIAO ESP32-S3

Дата исследования: 2026-09-18. База: `e4d0bcb`.
Статус: исследование и план, клиент на плате ещё не реализован.

## 1. Решение и границы

Первый этап — **`socket`**, обычный TCP с кадрами `uint32be(length) + IPv4`.
Это минимальный потоковый транспорт clean-vpn; его парсер и IP-тракт затем
переиспользуются в TLS. Буквально самый короткий wire format у `udp`, но он не
проверяет потоковое кадрирование будущих основных транспортов и в текущем exit
имеет неаутентифицированную смену peer. Поэтому UDP оставляем дополнительным
диагностическим транспортом, а не первым обязательным этапом.

Порядок: `socket` → совместимый TLS-туннель → TLS с точным JA3/JA4 профиля →
`transparent-tls` → `combo-tls`. Название `boring-tls` описывает существующий
клиент clean-vpn, но **не требует BoringSSL на XIAO**. Выбираем TLS-бэкенд по
совместимости, ресурсоёмкости и способности воспроизводить оба отпечатка.

В прошивке сохраняем два отдельно выбираемых транспорта, а не заменяем один другим:

- `tls` — обычный TLS без имитации браузерного ClientHello. Профиль не требуется,
  совпадение JA3/JA4 не является условием подключения. Это постоянный поддерживаемый
  режим, не только временная ступень разработки.
- `boring-tls` — функциональный аналог одноимённого клиента clean-vpn:
  профилированный TLS с обязательным совпадением JA3/JA4. Имя режима сохраняем
  для совместимости терминологии; реализация не обязана использовать BoringSSL.

Оба используют один протокол clean-vpn внутри TLS и совместимы с exit `--type=tls`:
проверка сертификата, exporter/Bearer v2, HTTP handshake и framed IPv4. «Обычный
TLS» означает стандартный криптографический стек, но не произвольное HTTPS-
соединение без туннельного протокола. Код framing/auth/session переиспользуется;
требования к ClientHello различаются. В настройках — явный выбор транспорта;
при отказе профилированного режима автоматического перехода в обычный `tls` нет.

Уточнение требования пользователя для `boring-tls` и IP-ветки `combo-tls`:
JA3 и JA4 должны совпадать с сохранённым
браузерным профилем; проверка обязательна на каждом новом TLS-соединении,
включая reconnect. Успешная загрузка профиля или одна успешная проверка при
старте не заменяют проверку фактического ClientHello каждой сессии.

В этом исследовании источником протокола служат `scripts/clean-vpn.js`, его
непосредственные библиотеки и native helper. Основной код приложения mesh-vpn
не используется как основа переноса и не изменяется. Изменения прошивки,
серверных скриптов, сетевых настроек и запуск exit в эту задачу не входят.
Далее описаны будущие работы в `device/`; точки интеграции с lwIP ещё предстоит
проверить перед реализацией, а не считать уже готовыми.

На плате нужен клиент, на Linux остаётся существующий clean-vpn exit.
Node.js, TUN addon, iptables, Puppeteer и helper-процесс на плату не переносятся.
На первом этапе: IPv4, один exit, одна IP-туннельная сессия; USB-клиент первым,
затем AP и одновременный USB+AP. P4, HT40 и оптимизация USB/Wi-Fi — вне задачи.

## 2. Как устроен существующий clean-vpn

[clean-vpn.js](../scripts/clean-vpn.js) открывает Linux TUN через
`native/tun_linux`, настраивает адреса/маршруты и соединяет поток IPv4-пакетов
с выбранным транспортом. На exit включается forwarding/NAT во внешний интерфейс.
Для Linux-клиента-шлюза `setupClientLanGateway()` делает SNAT LAN-трафика
в адрес клиента туннеля. На XIAO нужен функциональный аналог через lwIP,
а не выполнение Linux-команд.

Общие параметры текущего протокола:

- Клиент `10.99.0.2`, exit `10.99.0.1`; Linux назначает point-to-point `/32`.
- MTU TUN — 1400. Общий программный `MAX_PKT` — 65535; это не рекомендация
  выделять столько RAM на каждый пакет микроконтроллера.
- Передаётся IPv4-пакет, **без Ethernet-заголовка**. ARP/DHCP LAN не туннелируются.
- Для потоков: четыре байта длины big-endian, затем ровно указанное число байт.
  Несколько кадров могут быть объединены в один write; один кадр — разбит
  на сколько угодно read. Нулевой кадр не heartbeat, а ошибка.
- Для UDP, WebSocket и DataChannel границей IPv4-пакета служит сообщение.
- Нет общего обмена конфигурацией, выдачи IP, согласования MTU или протокольного
  session ID в простом `socket`. Адреса/MTU должны совпадать по конфигурации.
- Один активный IP-мост на TUN. Новый клиент не равен ещё одному независимому
  VPN-пользователю. Для стенда выделяем отдельный процесс/порт, не подключаем
  XIAO к рабочей сессии другого клиента.
- `--keep-alive` в скрипте означает idle/lazy lifecycle, а не периодическую
  передачу специального ping-кадра. MVP использует постоянное соединение
  (`--keep-alive=0`) с собственной ограниченной политикой reconnect.

### Инвентаризация транспортов

Имена ниже — фактические значения `--type`, а не разговорные сокращения.

| Тип | Wire / зависимости | Защита и особенности | План для XIAO |
|---|---|---|---|
| `socket` | TCP, `u32be + IPv4` | Нет шифрования/аутентификации | Первый лабораторный MVP |
| `http` | GET `/clean-vpn`, ответ HTTP/1.1, далее те же кадры | Не HTTPS; не обычная передача HTTP-body/chunked и не CONNECT | Не нужен перед `socket`; опционально позже |
| `udp` | Одна UDP-датаграмма = IPv4 | Без шифрования; обычный exit меняет peer по входящей датаграмме | Позже для сравнения с TCP-over-TCP |
| `websocket` | Binary WebSocket message = IPv4, пакет `ws` | В обычном `ws://` нет шифрования; роли listener/dialer настраиваются | После основных, если понадобится |
| `ws-chrome` | Puppeteer/Chrome, HTTP-страница `/clean-vpn-chrome`, WS | Браузерный мост; не самостоятельная криптозащита | Не переносить Chromium на MCU |
| `tls` | Node TLS, ALPN h2/HTTP1.1, Bearer, затем framed IPv4 | Сертификат сервера + channel-bound HMAC Bearer | Отдельный постоянный режим без браузерного профиля |
| `boring-tls` | Клиентский C++ BoringSSL helper; дальше тот же протокол, что `tls` | Профилирование ClientHello, патчи BoringSSL; exit — `tls` | Отдельный режим с точным JA3/JA4; backend на XIAO выбирается независимо |
| `transparent-tls` | Отдельный TCP relay HTTPS с enc-SNI; прочее через plain framed TCP | HTTPS остаётся browser↔origin; **остальной IP-трафик не зашифрован транспортом** | Отдельный экспериментальный режим с явным предупреждением |
| `combo-tls` | HTTPS relay + IP-туннель через boring-tls на одном порту | Exit различает enc-SNI relay и TLS VPN; это два пути, не один TLS stream | Целевой комбинированный режим |
| `webrtc` | `node-datachannel`, ICE/STUN/TURN, WebSocket-сигналинг | DTLS; PSK/HMAC binding сигналинга и fingerprint | Не в первой очереди |
| `rtc-chrome` | Chrome DataChannel, exit `webrtc` | Браузерный вариант WebRTC | Не переносить Chromium на MCU |
| `quic` | `node:quic`, один bidi stream с framed IPv4, ALPN `clean-vpn` | QUIC/TLS; не QUIC DATAGRAM | Отложить |
| `quic-ext` | `@infisical/quic`/quiche, bidi stream, ALPN `clean-vpn-ext` | QUIC/TLS; серверный HMAC stateless retry не равен Bearer VPN-клиента | Отложить |

UDP `--signaling --punch` добавляет отдельный сигналинг и hole punching;
для первого прямого соединения XIAO→VPS они не нужны. `tcp` и `ws` не надо
подставлять вместо фактических `socket` и `websocket`.

## 3. Контракт TLS / boring-tls

Источники: `connectCleanVpnTlsClient()`, `connectCleanVpnBoringTlsClient()`,
`completeCleanVpnTlsSession()`, `establishCleanVpnOverH2()`,
`tlsVpnBearerToken()`, `verifyTlsVpnBearer()`, `wireExitTlsSocket()`.

1. TCP к exit; отдельно задаются адрес соединения, SNI и имя проверки
   сертификата. Нельзя считать их всегда одной строкой. SNI должен попадать
   в VPN-ветку mux exit, иначе соединение может попасть в cover/passthrough.
2. TLS с проверкой доверенной CA и hostname. Для первой совместимой реализации
   ориентир — TLS 1.3, как в основном пути `tls`. Boring helper с профилем
   умеет менять предложение версий; это не основание ослаблять сервер.
3. ALPN по умолчанию `h2`, `http/1.1`. Для первого TLS-клиента явно выбираем
   HTTP/1.1 и соответствующий `--http-vers=1.1` на стенде; не рекламируем h2,
   пока не реализован HTTP/2. Такой ClientHello может отличаться от браузерного.
4. Exporter: 32 байта, label `EXPORTER-clean-vpn-bind`, без передаваемого
   контекста. PSK — общий файл из 32 байт (`clean-vpn-hmac.key` либо явный путь).
   Это ключ прикладной аутентификации, **не TLS-PSK вместо сертификата**.
5. Bearer v2 вычисляется так (`||` — конкатенация байтов):

   ```text
   window = floor(unix_time_ms / 900000)
   digest = HMAC-SHA256(PSK,
       UTF8("clean-vpn-tls-v2:") || exporter_raw_32_bytes ||
       UTF8(":" + decimal(window)))
   bearer = lowercase_hex(digest[0:16])
   ```

   Exporter в HMAC — **сырые байты**, не hex/base64. Base64 у helper используется
   только для IPC с Node. Сервер принимает текущее окно и соседние ±1;
   часы на плате должны быть установлены до соединения.
6. HTTP/1.1: `GET /clean-vpn`, `Host`, `User-Agent`, `Accept: */*`,
   `Authorization: Bearer <token>`, `Connection: keep-alive`. После заголовков
   ответа начинается двунаправленный поток `u32be + IPv4`, не HTTP chunked.
   Валидный ответ exit: `200`, `Content-Type: application/octet-stream`,
   `Connection: keep-alive`. **Одного 200 недостаточно:** на неверный Bearer
   сервер тоже может вернуть 200, но с `text/plain`, `Content-Length` и close.
   Парсер клиента должен отличать cover и сохранять хвост после `CRLFCRLF`.
7. HTTP/2: один открытый POST stream `/clean-vpn`, заголовок Authorization,
   ответ `:status=200`, framed IPv4 в DATA. Нужны SETTINGS, flow control,
   WINDOW_UPDATE, HPACK и обработка закрытия stream/connection; это отдельный этап.

Текущий сервер сохраняет совместимость с Bearer v1 без exporter. Новый клиент
не должен автоматически откатываться к нему. При недоступности exporter —
явная ошибка, не фиктивное «VPN защищён». PSK/exporter/Bearer не писать в
обычные логи и отчёты; существующий `--tls-log-bearer` для обычных тестов не включать.

### TLS-бэкенд: совместимость важнее названия библиотеки

Сейчас Node запускает [helper_main.cc](../native/boring_tls/helper_main.cc),
посылает framed JSON-конфигурацию через stdin и получает `ok/alpn/exporter`.
Затем stdin/stdout передают расшифрованный поток TLS. Это локальный IPC,
**не дополнительный сетевой заголовок** — на XIAO он не нужен.

[CMakeLists.txt](../native/boring_tls/CMakeLists.txt) закрепляет BoringSSL
`a7481f34712bc056a47ab91015536166b3a6cebb` и шесть патчей: порядок TLS 1.3 ciphers,
signature_algorithms_cert, opaque extensions, удаление их дубликатов,
signature_algorithms wire и TLS 1.2 cipher wire/EMS. Это эталон существующей
реализации, не обязательный набор зависимостей прошивки. Другой TLS-бэкенд
допустим, если сохраняет сетевой контракт и фактические JA3/JA4 профиля;
само наличие TLS или похожих настроек такого совпадения не доказывает.

Ранний feasibility gate:

- Собрать минимальный TLS-клиент под Xtensa/ESP-IDF без JSON IPC/POSIX main helper;
  проверить RNG, время, сокеты/BIO, threading, allocator, размер flash/стеков.
- Сравнить штатный/адаптированный Mbed TLS, библиотечный порт BoringSSL и,
  при необходимости, другой поддерживаемый backend. Критерии: управляемость
  ClientHello, доступ к его фактическим байтам, точный JA3/JA4, exporter,
  корректный handshake и память на XIAO. Поддержка нужных возможностей у
  каждого кандидата пока не доказана; выбор не предрешён.
- Backend без воспроизведения профиля пригоден для промежуточного `tls`,
  но не для режима с обязательным профилем. Если другой backend обеспечивает
  профиль и протокол, отдельный перенос BoringSSL не нужен.
- Проверить exporter именно для TLS 1.3 на фактической версии SDK и сверить
  результат с сервером; наличие TLS 1.3 само по себе не доказывает доступность
  нужного exporter API. Если API отсутствует, отдельно оценить обновление/
  адаптацию библиотеки, не самодельную криптографию или отключение binding.
- Измерить пик internal/DMA/PSRAM во время handshake, а не только память idle.
  В [Kconfig ESP-IDF v5.4.1](https://github.com/espressif/esp-idf/blob/v5.4.1/components/mbedtls/Kconfig)
  TLS 1.3 выключен по умолчанию и несовместим с `MBEDTLS_DYNAMIC_BUFFER`;
  входной TLS record buffer нельзя произвольно уменьшить до MTU IP-туннеля.
- Общая документация [сборки закреплённого BoringSSL](https://boringssl.googlesource.com/boringssl/+/a7481f34712bc056a47ab91015536166b3a6cebb/BUILDING.md)
  описывает cross-compilation и `OPENSSL_SMALL`, но не является доказательством
  готового порта на XIAO. Совместимость и стоимость порта пока не установлены.

## 4. transparent-tls и combo-tls — отдельный потоковый proxy

Источники: [runtime](../scripts/lib/transparent-tls-runtime.mjs),
[enc-SNI](../scripts/lib/transparent-tls-enc-sni.mjs),
[rebuild](../scripts/lib/transparent-tls-ch-rebuild.mjs), ветки `runClient/runExit`.

Текущий Linux-клиент перехватывает TCP/443 через OUTPUT REDIRECT и, для LAN,
PREROUTING DNAT; локальный listener — порт 8443. Исходное назначение извлекается
через Linux original-destination API. На XIAO нужен свой ограниченный TCP-proxy
на lwIP с сохранением original destination; Linux-механизм неприменим напрямую.

Для каждого подходящего HTTPS-соединения:

1. Принять TCP от LAN-клиента, собрать первый ClientHello из TCP/TLS-фрагментов.
2. Взять открытый SNI, зашифровать hostname и порт в enc-SNI v2.
3. Пересобрать ClientHello с новым SNI, корректно изменив вложенные длины.
4. Открыть отдельный TCP к exit, передать изменённый ClientHello и накопленный
   хвост, далее проксировать с backpressure и корректным half-close.
5. Exit расшифровывает SNI, разрешает hostname, восстанавливает исходное
   handshake-сообщение и соединяется с origin. TLS остаётся browser↔origin;
   плата не получает ключи HTTPS и не подменяет сертификат сайта.

Это не замена нескольких байтов в IP-пакете: длина SNI меняется, TCP sequence
spaces двух соединений должны вести TCP-стеки. Требуется восстановить исходные
handshake-байты перед origin, а не только получить тот же JA3. Record-разбиение
может измениться; transcript TLS менять нельзя.

Точный enc-SNI v2:

```text
key = HMAC-SHA256(PSK, UTF8("transparent-tls-enc-sni-v2\0"))
plaintext = 0x02 || uint32be(unix_seconds) || uint16be(port) ||
            uint8(hostname_byte_length) || ASCII(lowercase_IDNA_hostname)
wire = nonce[12] || AES-256-GCM(key, nonce, plaintext).ciphertext || tag[16]
SNI = base62(wire), разбитый на labels <=63 байт, + "." + publicName
```

В текущем коде дополнительный AAD не задаётся. Алфавит base62:
`0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ`; регистр
зашифрованного префикса сохранять. Общая длина hostname ≤253 байт, окно времени
±5 минут. Старый base32/v1 и CVPTX не использовать. Окно времени не заменяет
полную защиту от повторов: отдельного replay-cache в enc-SNI библиотеке нет.

Ограничения и решения до реализации:

- Без plaintext SNI текущая реализация отказывает. ECH extension не удаляется;
  GREASE ECH покрыт тестом, но это не доказательство работы всех вариантов
  настоящего ECH/outer SNI, resumption, early data и HelloRetryRequest.
- Настоящий HTTP/3/QUIC — UDP, не TCP/443 relay. В combo он должен идти внутри
  защищённого IP-туннеля, а не напрямую. Для изолированного relay-теста можно
  отключить QUIC только в тестовом браузере, явно записав это в отчёт.
- Длинный SNI, большой/некорректный ClientHello, отсутствие SNI, таймаут и
  исчерпание proxy-слотов должны иметь определённый исход без утечки напрямую.
- В combo безопасный fallback — IP-путь через защищённый туннель. Если TCP
  уже принят proxy, нельзя просто «вернуть кадры в маршрутизатор»: нужен
  исходящий TCP через VPN с передачей сохранённого префикса либо явный отказ.
  После отправки части потока к exit нельзя прозрачно переигрывать соединение.
- В standalone transparent остаточный framed IP идёт открытым текстом,
  включая обычный DNS/HTTP. Это свойство существующего протокола, не исправляем
  молча под тем же именем. Для повседневного защищённого режима нужен combo.
- В combo одна IP-сессия плюс N relay-сокетов. Решение о пути закрепляется
  за потоком; после смены профиля/сбоя старые соединения не переиспользуются.

В исследованной цепочке «страница получения профиля» — JSON по `/ja3-snif`,
а не отдельный полноценный UI-конструктор. `/clean-vpn-chrome` — страница
транспортного моста, не сравнение профилей. Реальная сверка уже есть в helper
и в логах client/exit (`--tls-log-ja3 --ja3-verbose`); отдельный законченный
автоматический end-to-end отчёт expected vs observed для XIAO ещё надо сделать.

### Захват → воспроизведение → независимая проверка

1. На Mac запустить, явно ограничив listener loopback:

   ```sh
   npm run ja3-snif-server -- --host=127.0.0.1 --port=8443 --profile-save-path=/tmp/clean-vpn-browser-profile.json
   ```

   Без `--host` код слушает `0.0.0.0`, хотя некоторые описания называют сервер
   локальным. Fixture-сертификат — только лабораторный. Открыть `/ja3-snif`
   в нужном браузере; для реалистичного SNI использовать тестовое DNS-имя,
   направленное на этот listener, и соответствующий тестовый сертификат.
   Захват по IP допустим, но отсутствие SNI записать как отличие эталона.
2. Сохранить JSON профиля и полный ответ отдельно, с версией браузера/ОС,
   hostname, датой и настройками ALPN. Каждый успешный GET с `--profile-save-path`
   перезаписывает файл; перед следующим захватом сохранить нужный эталон.
3. Передать файл Linux-клиенту через `--boring-tls-clienthello-profile=PATH`.
   Это schema v1: ciphers, extension types, groups, point formats,
   signature algorithms, optional opaque extension bodies, JA3/JA4, UA и TLS info.
4. Проверить не только принятие JSON: helper logs показывают expected/actual
   JA3/JA4, multiset/order расширений, cipher и signature-algorithm differences.
5. Проверить CH независимо на принимающей стороне реального соединения к exit;
   для transparent — до подмены, на exit до восстановления и у origin после
   восстановления. Завершить настоящий HTTPS-запрос, не ограничиваться hash.

Важные особенности текущего кода:

- `permute_extensions` по умолчанию true. Wire JA3 конкретного захвата может
  меняться; локальный `ja3_sorted` — отдельный нормализованный показатель,
  не замена стандартному wire JA3 и не гарантия одинакового поведения.
- `--boring-tls-profile-ja3-strict` требует `permute_extensions:false`.
  При перестановках преобразователь обычно не передаёт expected wire JA3.
  Фиксированный порядок стека тоже не гарантирует совпадения с порядком браузера.
- JA4 mismatch сейчас только warning; строгий JA3 не означает строгий JA4.
  В отчёте нужны оба результата и поля расхождения, не общий зелёный «профиль OK».
- Преобразователь всегда устанавливает `emit_sni:true`, даже если захват по IP
  сохранил `clienthello_emit_sni:false`. Это объясняет часть ожидаемых отличий.
- `user_agent` сохраняется в профиле, но HTTP VPN-запрос в clean-vpn использует
  константу `TLS_VPN_USER_AGENT`. `tls_info.alpn` также не означает автоматическое
  применение ALPN профиля: список задаётся отдельно в конфигурации соединения.
- Копируется не полный ClientHello. Random, key shares, session secrets,
  tickets/binders нельзя слепо воспроизводить из старого захвата. Opaque-поля
  ограничены denylist; даже прошедшее фильтр неизвестное расширение требует
  проверки смысла, длины и совместимости с криптосостоянием нового handshake.
- Совпадение JA3/JA4 не доказывает идентичность браузеру: остаются HTTP/2 SETTINGS,
  порядок HTTP-заголовков, TLS records, resumption и поведение соединения.
  H2 текущего boring-клиента реализует Node, не Chrome.

Для прошивки позже: ограниченный валидируемый формат профиля, version/hash,
размерные лимиты, безопасная загрузка и применение только к новым соединениям.
Не парсить большой JSON на packet hot path. Отчёт проверки хранить файлами:
`profile.json`, `observed.json`, `comparison.json` и краткий Markdown со ссылками.
Не включать PSK/exporter/Bearer; при публикации учитывать чувствительность
hostname, IP, UA и захваченных handshake-данных.

### Контракт нового клиента: строгая проверка каждой сессии

Описанные выше warning-only и optional strict — поведение существующего
Node/helper-клиента, **не целевое поведение прошивки** в режиме профиля.

1. При импорте требовать эталонные wire JA3 и JA4, проверить согласованность
   отпечатков с полями профиля. Версию алгоритма и нормализацию JA4 фиксировать
   вместе с профилем; не сравнивать основной JA4 с альтернативным diagnostic
   fingerprint. Отсутствующий/неподдержанный эталон — ошибка конфигурации.
2. На каждой новой TLS-сессии получить фактически сформированный ClientHello
   из TLS-бэкенда на границе отправки. Вычислять hashes из этих байтов, а не
   из запрошенных настроек. По возможности проверять до выпуска CH в socket;
   после успешного handshake/auth не разрешать VPN payload, пока оба сравнения
   не прошли. Hook должен видеть окончательные handshake-байты, включая
   расширения, добавленные самим стеком.
3. Требовать одновременно `actual_ja3 == profile.ja3_md5` и
   `actual_ja4 == profile.ja4.fingerprint`. Mismatch или невозможность проверить
   — закрыть соединение, `profile_mismatch`/`profile_validation_unavailable`,
   запретить VPN payload; не продолжать с warning, обычным TLS или DIRECT.
4. Повторять проверку при reconnect и resumption. Результат предыдущей сессии
   не кэшировать как разрешение следующей. Первую версию упростить отключением
   resumption/0-RTT. До поддержки HRR и дополнительных ClientHello явно
   определить их проверку; неожиданный непроверенный вариант — отказ, не обход.
5. При одном сохранённом wire JA3 случайная перестановка расширений несовместима
   с точным совпадением: воспроизводить порядок профиля, а не просто отключить
   shuffle и оставить порядок библиотеки. Sorted JA3 — только диагностика.
   Нельзя автоматически переписать эталон под результат выбранного backend.
6. Несовместимые SNI/ALPN, ciphers/groups/extensions выявлять до активации
   профиля. Например, профиль без SNI или с h2 нельзя молча изменить ради
   подключения и назвать совпавшим. Нужен поддерживаемый профиль либо явная
   ошибка; упрощённый HTTP/1.1 этап остаётся отдельно от режима профиля.
7. Независимая проверка на exit/контролируемом принимающем сервере обязательна
   в приёмочных тестах: она сверяет наблюдаемый CH с локальным результатом
   по конкретной сессии. Runtime-проверка каждой сессии локальная и не зависит
   от стороннего сервиса определения JA3/JA4. Серверные captures/логи отдельно
   проверяют, что локальный hook действительно соответствует байтам в сети.

На каждую сессию сохранять ограниченную запись: connection ID, profile hash,
expected/actual JA3 и JA4, результат и причину. При несовпадении — ограниченный
diff полей без секретов; журнал с ротацией, без постоянной записи каждого
соединения во flash. В статусе различать `pending`, `match`, `mismatch` и
`unavailable`, никогда не показывать `match` до фактической проверки.

Этот контракт относится к TLS, который создаёт сама плата для IP-туннеля
(профилированный TLS и IP-ветка combo). В transparent-ветке CH создаёт браузер:
его нельзя подгонять под произвольный профиль без нарушения transcript.
Там проверяется сохранность исходного browser CH после restore; это отдельная
проверка, а не повод подменять профиль браузера на лету.

## 6. Предлагаемая архитектура клиента на XIAO

```text
USB / SoftAP IPv4
    → решение DIRECT / VPN / BLOCK (с закреплением пути потока)
    → NAPT LAN → 10.99.0.2
    → виртуальный IP-интерфейс VPN (MTU 1400)
    → ограниченная TX-очередь → framer → socket / TLS → STA → exit

exit → socket / TLS → framer → ввод IPv4 в lwIP
    → обратный NAPT → нужный USB / SoftAP клиент
```

Для transparent/combo к этому добавляется отдельный ограниченный TCP proxy,
описанный выше. Это проектируемая схема, не уже существующий data path.

Требования интеграции:

- Разделить transport, frame codec, IP adapter и session manager. Один владелец
  socket/TLS; сетевой callback только принимает пакет в bounded queue, без
  блокирующего connect/handshake/send в Wi-Fi callback или lwIP core.
- Виртуальный netif — кандидат на основной способ встраивания. Проверить,
  что реальная версия ESP-IDF/lwIP позволяет корректно совместить forwarding,
  NAPT и выбор egress для двух LAN; при необходимости небольшой scoped hook,
  но не собственный TCP/IP-стек и не общий переписанный маршрутизатор.
- SNAT в `10.99.0.2` обязателен для совместимости с текущим exit без отдельных
  маршрутов на USB/AP подсети. Проверить TCP/UDP/ICMP и обратное преобразование,
  два LAN-клиента с одинаковыми исходными портами, IPv4 fragments/checksums.
- Внешний socket к exit должен всегда идти через STA, а не обратно в VPN.
  Само назначение VPN default route без исключения endpoint создаёт петлю.
  Обновление DNS/IP exit не должно на время отключать правила защиты.
- Управление платой, DHCP/ARP и локальные адреса оставить доступными без VPN.
  Для VPN-selected трафика при обрыве — BLOCK, не DIRECT. Сам транспорт `socket`
  отмечать как небезопасный лабораторный режим и не включать по умолчанию.
- DNS клиентов VPN — через туннель. Bootstrap DNS endpoint и синхронизация
  времени — отдельно ограниченные служебные исключения с явной диагностикой.
  Не отключать проверку сертификата ради неправильных часов. IPv6 в MVP
  не туннелируется и не должен давать обход VPN-selected политики.
- MTU 1400 проверить на ingress LAN с MTU 1500: PMTUD/ICMP fragmentation-needed,
  IPv4 fragmentation и TCP MSS (1360 при обычных IPv4/TCP заголовках).
  Один лишь MSS clamp не решает UDP и DF. Нельзя обрезать большие пакеты.
- RX проверяет длину до выделения памяти, IPv4/IHL/total length, bounds и
  допустимые адреса назначения; ошибки закрывают сессию либо дают явный drop.
  Для MVP договориться с exit о пакетах ≤1400; `65535` из JS не копировать
  в безусловную аллокацию. Проверить, не приходят ли oversized/offload packets.
- На reconnect очистить partial frame, старые очереди и связанные состояния;
  generation ID защищает от доставки пакетов предыдущей сессии. TCP-потоки
  могут оборваться — не обещать бесшовную миграцию без протокола её поддержки.

Ресурсы: исходная оценка, не измеренный бюджет. Начать с 16 TX + 16 RX слотов
по 1404 байта (~44 KiB payload storage в PSRAM), затем измерить overhead pbuf,
очередей и копий. Нужность отдельных RX-слотов подтвердить реализацией ownership.
Служебные структуры/стек/драйверная память учитываются отдельно; internal и DMA
не складывать. Не наследовать host-буферы на мегабайты и 256 queued packets.
Для relay начать с 2 одновременных сессий и CH limit 16 KiB на сессию в PSRAM;
это продуктовый лимит первой версии, не утверждение о максимуме браузерного CH.
Oversize — диагностируемый отказ/fallback по политике, никогда unlimited growth.
Пик TLS handshake и пригодность PSRAM для выбранного backend измерить отдельно.

## 7. Этапы и критерии завершения

### Этап 0 — совместимость и тестовые векторы

- Зафиксировать server commit, транспорт, адреса, MTU, порт и test-only режим.
- Подготовить общие JS/C vectors: разбиение/склейка кадров, bad lengths,
  truncated IPv4, HMAC v2 с известными PSK/exporter/time, enc-SNI/rebuild.
- Для enc-SNI фиксированные nonce/time разрешать только в тестовом harness,
  не в production RNG. Дополнительно JS↔C взаимное декодирование.
- Выполнить минимальную проверку кандидатов TLS-бэкенда из раздела 3,
  включая формирование и проверку JA3/JA4 выбранного профиля.

Готово, когда контракт проверяется тестами, а неизвестные по TLS-порту названы
явно. Не блокировать простой `socket` ожиданием идеального браузерного профиля.

### Этап 1 — socket-туннель с платы, ещё без LAN forwarding

- Настройки endpoint, transport=`socket`, enable; worker/state machine:
  DISABLED → WAIT_UPLINK → CONNECTING → UP → BACKOFF.
- Framer, partial writes/reads, таймауты, ограниченные очереди, retry backoff.
- Контрольный IPv4 ICMP/UDP request к тестовому peer через настоящий exit/TUN
  и проверка ответа. Обычный TCP echo не считать доказательством IP-туннеля.

Готово: повторяемый обмен IP в обе стороны; bad frame/EOF/reconnect не дают
утечки памяти, зависания или доставки хвоста прошлой сессии. Plaintext endpoint
доступен только из тестовой сети/разрешённого адреса, не открытый общий VPN.

### Этап 2 — USB и AP как клиенты туннеля

- Подключить virtual netif, NAPT, endpoint bypass, DNS и правила fail-closed.
- Сначала USB→VPN, затем AP→VPN, затем обе LAN одновременно.
- Небольшие проверки ping/DNS/HTTP/HTTPS, TCP up/down и UDP; подтвердить внешний
  адрес exit и серверный приём. Проверить MTU, два клиента и обрыв STA/exit.
- Настройки/статус в интерфейсе: transport, endpoint, state, last error,
  counters и заметное «без шифрования»; не показывать фиктивное VPN connected.

Готово: маршрутизация проверена packet capture на exit/внешнем интерфейсе,
выбранный трафик не уходит напрямую при аварии, локальная админка остаётся
доступной, обычный DIRECT-режим не регрессирует.

### Этап 3 — отдельный транспорт `tls` (без браузерного профиля)

- TLS 1.3, trust/hostname/SNI, exporter, Bearer v2, HTTP/1.1.
- Стандартный ClientHello выбранной TLS-библиотеки, без требования совпадения
  с браузерным профилем. Отсутствие профиля не мешает включению `tls`.
- Ограниченный HTTP parser различает tunnel ack и cover; не шлёт IP до auth ack.
- При необходимости backend сначала Mbed TLS под честным именем `tls`.
- Сохранить режим в конфигурации/UI и регрессионных тестах после этапа 4;
  `boring-tls` не вытесняет и не переименовывает обычный `tls`.
- Негативные тесты: чужая CA/hostname, неверный PSK, время вне окна, отсутствующий
  exporter, обрезанные headers, 200 cover, abrupt TLS close, повторные reconnect.

Готово: существующий exit принимает v2, весь выбранный IP-трафик зашифрован;
ошибки аутентификации не приводят к v1/plaintext/direct fallback. Измерены
handshake peak memory и sustained throughput, без переноса старых цифр без VPN.

### Этап 4 — отдельный транспорт `boring-tls` (профилированный TLS)

- Подключить backend, прошедший feasibility gate; BoringSSL не обязателен.
- Тот же серверный протокол, что у `tls`, но профиль и строгая проверка JA3/JA4
  обязательны. Это аналог boring-tls по функции, не обязательный порт его helper.
- Импортировать ограниченный профиль, реализовать только поддержанные поля;
  неподдержанные — явная ошибка/диагностика, не игнорирование под видом успеха.
- Сверить expected vs actual на клиенте и независимо на exit, выполнить
  реальные запросы. Сначала выбранный конкретный профиль, не «все браузеры».
- Встроить обязательную строгую проверку обоих отпечатков каждой новой сессии
  по разделу 5, включая reconnect. Негативные тесты: изменить порядок расширений,
  ALPN и состав cipher suites; проверить несовпадение только JA3, только JA4,
  отсутствие hook/эталона и отсутствие VPN payload при любом отказе.
- После смены профиля и обновления backend проверить новые соединения повторно;
  дополнить тест серии соединений проверкой связи локальных результатов с
  независимыми captures exit. Не переносить cached `match` между сессиями.
- При необходимости добавить bounded HTTP/2, только после HTTP/1.1; зафиксировать
  отдельно TLS fingerprint и HTTP fingerprint. Не копировать host H2 settings.

Готово: работают tunnel auth и данные, оба фактических отпечатка точно совпадают
с сохранённым профилем на каждом новом соединении; неверифицированная сессия
не передаёт VPN-трафик. Допустимые отличия JA3/JA4 вместо совпадения не являются
критерием готовности. Если профиль не поддержан/не помещается — явное ограничение,
не «успешное применение». Выбор библиотеки сам по себе на приёмку не влияет.

### Этап 5 — transparent-tls

- Сначала codec enc-SNI + CH rebuild с host tests и bounded parser.
- Затем TCP relay к фиксированному тестовому origin, после — прозрачный LAN
  interception с original destination, half-close и backpressure.
- Проверить фрагментированный CH, хвост данных, долгие/параллельные соединения,
  отсутствие SNI, лимиты hostname/CH/слотов, RNG/time, resumption/HRR/ECH отдельно.

Готово: настоящий браузер завершает TLS с origin без установки MITM CA;
origin получает исходное handshake-сообщение; профиль сравнен в нужных точках.
Standalone plain-IP остаток явно виден в настройках и отчёте как небезопасный.

### Этап 6 — combo-tls

- Совместить защищённую IP-сессию и отдельные relay flows на одном exit-порту.
- Проверить одновременные DNS/UDP/TCP и HTTPS, QUIC внутри IP-туннеля,
  разделение очередей и поведения при падении одной из веток.
- Fallback реализовать согласно разделу 4, без утечки DIRECT/plaintext.

Готово: обе ветки наблюдаемы и работают одновременно; ограничение/ошибка одной
не приводит к неограниченной памяти, starvation или незаметной потере защиты.

## 8. Диагностика и ограниченный объём проверок

Добавить в будущий статус (без секретов): state/transport/session generation,
endpoint и egress, tx/rx packets/bytes, queue full/expired/high-water,
partial/malformed/oversize frames, reconnect reason/count, connect/handshake/auth
timing, TLS version/cipher/ALPN, verify/binding result, профиль version/hash,
connection ID, expected/actual JA3/JA4 и состояние обязательной проверки,
relay active/limit/reject reason, memory peak/minimum/largest block.
`accepted`, `written to socket` и `received by exit` — разные показатели.

После каждого этапа — один короткий функциональный прогон и один негативный.
После работоспособного LAN-туннеля — 3 повтора TCP up/down и небольшой UDP sweep
от низкой скорости, с проверкой **достигнутой sender rate**, loss и длительностей.
Не повторять всю старую матрицу USB/AP на каждую правку parser/auth.
Перед включением по умолчанию — один endurance 30–60 минут и несколько
управляемых reconnect с проверкой памяти и доступности админки.

Предыдущие ~8 Мбит/с USB и результаты STA+AP — baseline без VPN, не ожидаемая
VPN-скорость. TCP внутри TCP может менять поведение при потерях; CPU, TLS,
очереди и однорадиоканальный Wi-Fi измерять отдельно. Оптимизацию начинать
после доказанной корректности, а не с увеличения всех буферов.

Отчёты: JSON/NDJSON, server logs, краткая сводка и при необходимости отдельный
pcap. Агенту — пути к файлам, а не все пакеты/логи в контекст. Для AP-прогонов
переиспользовать существующий workflow переключения Wi-Fi/возврата/доставки
артефактов, когда он доступен; новый Mac/роутер для первого этапа не требуется.

## 9. Что проверено сейчас и что остаётся неизвестным

Проверено чтением фактических веток клиента/exit, а не только их комментариев:
кадрирование, адреса/MTU, HTTP1/H2 handshake, HMAC v2, различие transparent/combo,
helper IPC, экспорт/применение профиля и диагностика wire fingerprint.
Заголовок clean-vpn «без шифрования и авторизации» не описывает все его режимы.

В этой работе выполнено:

```sh
node --test scripts/test-tls-clienthello-ja4.mjs scripts/test-transparent-tls-enc-sni.mjs
```

Результат: 20/20 тестов прошли. Это тесты существующего JS-кода, не подтверждение
портирования C-клиента, работы всей TLS-цепочки или безопасности всех режимов.
Native helper не пересобирался; сетевой exit, TUN и маршруты не запускались.

Открытые вопросы для начала реализации:

1. Какой backend на Xtensa обеспечивает нужный wire JA3/JA4, проверку каждого
   CH и TLS 1.3 exporter при приемлемых затратах памяти/flash/CPU.
2. Точки virtual-netif/NAPT/route integration в прошивке, ownership pbuf и
   предотвращение routing loop при сохранении двух LAN.
3. Максимум реально допустимых TLS/relay buffers и число соединений без
   исчерпания internal/DMA RAM; PSRAM сама по себе этого не гарантирует.
4. Конкретный целевой браузерный профиль: точные JA3/JA4, ALPN и поддерживаемые
   криптографические группы/расширения. Несовпадение не разрешается молча.
5. Совместимость сложных browser flows с transparent relay; не считать
   отсутствие ошибки в GREASE ECH unit test проверкой настоящего ECH.

**Следующая реализация:** этапы 0–1, затем USB→`socket`→существующий exit.
Не начинать одновременно переписывание Wi-Fi, USB, TLS-бэкенда и TCP proxy.
