# Буферы и копирования: аудит XIAO ESP32-S3

Дата аудита: 2026-09-11. Исходники аудита: checkout `b28f3af`. Ниже сохранены исходные находки; статус первого исправления указан отдельно.

## Диагностика DWC2 FIFO и ISR (2026-09-13)

Первый прогон `09ffd5f` не показал выигрыша от double FIFO: receiver
на 9/10M = 8,32/8,40 Мбит/с против 8,52/8,50 в последнем `fd1d770`.
Один WAN-прогон не доказывает регрессию. `configured` подтверждает только
принятие настройки, а прежний NCM completion включает и шину, и обработку.

Добавлен отдельный `CONFIG_MESHVPN_DWC2_TELEMETRY` (в defaults включён).
Генератор проверяет SHA256 установленного DWC2 и меняет только build-copy;
managed_components не редактируются. Очередь 8, пул NTB 6, expiry 50 мс,
event wait 25 мс и double FIFO остаются прежними.

В `usb.dwc2` доступны:

- readback DIEPTXF выбранного NCM IN, GRXFSIZ и GAHBCFG при DCD submit;
  снимок устаревает в idle и инвалидируется при USB reset/close-all;
- refill calls / zero-byte calls / bytes и число обслуживаний TXFE endpoint;
  это не число всех USB-прерываний, начальные заполнения входят в refill;
- DCD submit → completion observation в ISR (`service_*`);
- ISR observation → NCM callback (`task_*`), с четырьмя непересекающимися
  корзинами ≤100 мкс / 100–1000 мкс / 1–5 мс / >5 мс;
- unmatched/overwritten для контроля неполных пар замеров. ZLP учитываются
  отдельно, но не входят в service/task timing.

Service **не равен чистому времени шины**: включает задержку обслуживания
прерывания. Task delay не равен времени входа в ISR. Callback NCM потребляет
отметку до запуска следующей передачи; reset сбрасывает незавершённые пары.
Успешный completion не доказывает доставку приложению на Mac.
Web читает только копию счётчиков под короткой блокировкой, не USB-регистры.
Нет динамической памяти или логирования на каждый пакет. Но счётчики на
каждом refill добавляют overhead: сравнивать с выключенной диагностикой.
DMA Kconfig сам по себе не означает активный DMA: установленный драйвер
выбирает его по аппаратному GHWCFG2. ISR hook здесь относится к slave path
ESP32-S3; при иной аппаратуре требуется повторный аудит.

После прошивки и холодного старта повторить:

```sh
npm run device:perf:usb-down -- 62.84.120.30 --start-delay 60
```

Ожидаемый readback double FIFO — 128 B. Проверить пары service/task,
unmatched/overwritten и refill bytes/call на 6–8M и в насыщении.
`service_max_us`/`task_max_us` — lifetime maxima, не максимумы теста.
Для контроля overhead выключить только `CONFIG_MESHVPN_DWC2_TELEMETRY`;
для сравнения FIFO отдельно выключить `CONFIG_MESHVPN_USB_NCM_DOUBLE_BUFFER`.
Не менять оба параметра одновременно.

Проверено до аппаратного прогона: ESP-IDF 5.4.1 / ESP32-S3 build с
включёнными DWC2 hooks; host-suite ASan/UBSan, включая реальные generated
FIFO writer / slave ISR bodies на модели регистров, NCM callback ordering,
ZLP, reset и границы гистограмм; perf-runner — 31 pass, 1 macOS-only skip.
Модель регистров не заменяет измерение реальной USB-шины.

## Эксперимент: двойной аппаратный FIFO NCM IN (2026-09-13)

DHCP-исправление `fd1d770` проверено двумя холодными прогонами, начало
09:19:58 / 09:50:40 UTC, discovery uptime 9/12 с. В обоих start-delay 60 с
без потерь board/server ping, API errors=0, timing anomalies=0/26.
Прежний стартовый провал не воспроизвёлся. Это подтверждает исправление
наблюдавшегося сценария, а не отсутствие всех возможных DHCP-сбоев.

Остаётся насыщение: при target=10M receiver median 8,45/8,50 Мбит/с,
UDP loss 15,17/14,69%, queue losses 15,17/14,79%. На 6–8M встречаются
короткие переполнения даже при существенно меньшей средней нагрузке.
NTB в насыщении ~7,2 КБ / 6,3 мс; backlog gap ~0,06 мс — около 1%
от этого цикла. Устранение только меж-NTB промежутка не обещает большой
прибавки. Это измерение включает обработку completion, не чистое время шины.

В установленном `espressif/tinyusb` DWC2 по умолчанию
`bm_double_buffered=0`: bulk IN FIFO хранит один USB-пакет (64 B на FS).
Есть штатный pre-init `tud_configure(TUD_CFGID_DWC2)`, позволяющий удвоить
FIFO выбранного bulk IN endpoint. См. [TinyUSB API](https://github.com/hathach/tinyusb/blob/0.21.0/src/device/usbd.h)
и [DWC2 FIFO allocator](https://github.com/hathach/tinyusb/blob/0.21.0/src/portable/synopsys/dwc2/dcd_dwc2.c).
Гипотеза: два пакета в FIFO уменьшат паузы подачи данных между обслуживанием
прерываний. Текущие данные **не доказывают**, что именно FIFO ограничивает скорость.

В defaults включён `CONFIG_MESHVPN_USB_NCM_DOUBLE_BUFFER=y`. До установки
TinyUSB разбирается тот же встроенный FS descriptor, который использует
iot_bridge. Выбирается только bulk IN в data alternate 1 внутри NCM IAD:
EP0x82 без CDC или EP0x84 с CDC. Номер не захардкожен; неизвестный/неоднозначный
descriptor или поздний init дают явную ошибку. Сохраняется default VBUS policy.
Kconfig ограничивает эксперимент ESP32-S3/NCM с максимум одним CDC, без MSC/vendor.
Если bridge перейдёт на пользовательские descriptors, этот путь нужно пересмотреть.

Меняется только аппаратный FIFO сети **64 → 128 B**. Дополнительные 64 B —
память USB-контроллера, не internal/DMA heap и не PSRAM. По реальному allocator
при CDC+NCM заняты 144 из 256 слов FIFO (62 RX + 16 EP0 + 2 CDC notification +
16 CDC data + 16 NCM notification + 32 NCM data), остаётся 112 слов.
CDC FIFO не меняется. Worker queue=8, NCM pool=6, NTB limits, event wait=25ms,
expiry=50ms, копирования, приоритеты, affinity, Wi-Fi и DHCP остаются прежними.
Новых задач/аллокаторов/обработчиков ISR нет; managed dependencies не правятся.

`usb.ncm_double_buffer_configured` и `usb.ncm_in_ep` сохраняются в status.ndjson
и сводке perf. Это подтверждение принятой настройки перед init, **не чтение
регистров**. Старые прошивки показывают unknown, а не disabled.
Host-тесты используют реальные FS descriptors с/без CDC и настоящий allocator
с RAM-регистрами; отдельно проверяют malformed input, поздний init, ошибку
configure, сохранение VBUS policy и сериализацию. Они не моделируют шину/IRQ.

После пересборки/прошивки и отключения/подключения питания:

```bash
npm run device:perf:usb-down -- 62.84.120.30 --start-delay 60
```

Проверить `NCM IN hardware double FIFO: configured`, `capacity=8`, event wait
enabled. Сравнить с двумя `fd1d770` прогонами все queue losses и receiver loss
на 6–8M, throughput на 9–10M, completion mean, ping board/server, API errors.
Не считать снижение одного retry успехом. Затем проверить обычный both/quick,
админку и unplug/replug. Аппаратный эффект ещё не проверен.
Откат: отключить `MESHVPN_USB_NCM_DOUBLE_BUFFER` в выбранном sdkconfig/menuconfig
(при пересоздании конфига — также в defaults), пересобрать и перепрошить.
Не менять одновременно другие размеры или таймауты.

## Сохранение DHCP-аренд при DNS refresh (2026-09-13)

В присланных `ping.ndjson`/`status.ndjson` холодного запуска с `--start-delay 60`
обнаружен общий провал ping платы/сервера: последние ответы в 07:48:08.346/08.359 UTC,
13 подряд пропущенных sequence 168..180, следующие ответы 07:48:11.212/11.218.
В 07:48:10.001 API завершился за 2 мс с **bind EADDRNOTAVAIL 192.168.7.2**:
недоступен локальный IP Mac, а не таймаут HTTP-сервера платы.
До/после окна uptime 61/65 с, NCM initializations=2 без изменения,
Wi-Fi online, прирост queue.full/busy/send_failed/timeout=0.

Найден механизм в коде: наш LAN DNS refresh на STA_GOT_IP/AP_START/BRIDGE_DNS_UPDATE
безусловно останавливал DHCP. IDF 5.4.1 `dhcps_stop()` удаляет список аренд;
последующее renew без сохранённой пары MAC/ciaddr может получить DHCPNAK.
Это согласуется с первым продлением 2-минутной аренды, но сам NAK в исходных
файлах не записан. Удаление адреса на Mac подтверждено на уровне ошибки bind;
окончательная проверка исправления — холодный аппаратный прогон.

`meshvpn_net_apply_lan_dhcp()` теперь читает параметры работающего DHCP и при
совпадении router/DNS offer/lease обновляет только DNS через `esp_netif_set_dns_info`.
GET DNS возвращает boolean 1, SET принимает OFFER_DNS=2: это учтено отдельно.
Остановленный сервер после смены подсети настраивается/запускается как раньше;
реально отличающиеся опции требуют stop/set/start. Ошибка GET не вызывает
предположительный restart, ошибки API не игнорируются, а возвращаются и логируются.

Проверен `iot_bridge` 1.1.0: DNS refresh сам использует live set_dns_info;
остальные stop/start относятся к созданию/смене IP и не изменены.
Managed dependencies не правились. Lease остаётся **2 минуты**, USB queue=8,
event wait/NCM/Wi-Fi без изменений: не маскируем первый renew увеличением аренды.
Host-регрессия моделирует удаление leases на stop, повторные USB/AP DNS refresh,
реальные изменения опций/подсети и ошибки API; не заменяет Mac DHCP packet capture.

Проверка: отключить/подключить питание, сразу запустить
`npm run device:perf:usb-down -- 62.84.120.30 --start-delay 60`.
Ожидаем исчезновение общего ~3-секундного провала и EADDRNOTAVAIL около первого
renew. Полный прогон проверяет и последующие продления. UDP overload на 9/10M
остаётся отдельным явлением и сам по себе не означает регрессию этого исправления.

## База: ожидание NCM completion в USB TX worker (2026-09-12)

Проверка `cc67e8d`, 2026-09-12 20:07 UTC: 1367 busy → 1367 пробуждений,
каждое с успешным повтором; timeout/send_failed = 0. Но `queue.full=1492`,
то есть все локальные потери 1492/41943 = 3,56% против 3,57% у `8a009e0`.
Отказы переместились на вход очереди; end-to-end улучшение потерь не подтверждено.
1398 отказов — в трёх USB UDP down 10M batch, capacity wait mean 5,36–5,84 мс.
USB TCP down 7,68 Мбит/с, UDP down 10M 8,49 Мбит/с с 13,35% receiver loss.
Следующий шаг — runner `npm run device:perf:usb-down -- 62.84.120.30`:
5–10M шагом 1M, 3 × 15 секунд на скорость, отдельная сводка всех потерь очереди.
Настройки прошивки/размер очереди пока не меняются. Увеличение 8 → 16 слотов
рассматривать только после оценки потерь ниже предела, а не ради нулевого
`tx_dropped`. Подробности в [perf-testing.md](../perf-testing.md).

Результат очереди `8a009e0`: API errors 0 вместо 5 у `57f4bc5`, медианы ping в USB UDP down 10M около 42–57 мс вместо 64–151 мс. Но локальные потери **1446 = 858 send_failed + 588 full**, то есть 3,57% от 40537 submitted (прежде 1195/42637 = 2,80%). UDP receiver loss 11,66%; падение одного `usb.tx_dropped` не означает исправления потерь. Память после idle стабильна: internal 18607 B, DMA 10487 B. Это короткий WAN-прогон, не доказательство стабильного выигрыша.

Следующий одиночный транспортный эксперимент: `CONFIG_MESHVPN_USB_TX_EVENT_WAIT=y`.

- При BUSY работник ждёт task notification от обработчика NCM IN completion **после** возврата NTB в пул и обработки следующей передачи/ZLP. Это сигнал повторить попытку, не резервирование буфера. TinyUSB и lwIP не ждут освобождения очереди; только `usb_tx` блокируется на уведомлении.
- Старое уведомление очищается **до** попытки отправки. Событие между BUSY и началом ожидания остаётся pending; очищать его после BUSY нельзя. Используется notification index 0 существующей задачи, без нового semaphore, стека, payload-буфера или per-packet malloc. Семантика описана в [FreeRTOS Task Notifications](https://github.com/FreeRTOS/FreeRTOS-Kernel-Book/blob/main/ch10.md).
- Один абсолютный бюджет 25 мс от начала sync-send, не новый бюджет на каждое пробуждение. 64 попытки остаются аварийным пределом при шквале событий. Ожидание округляется к тикам с запасом до двух тиков; после пробуждения проверяются срок и поколение USB. Mount/umount также будят worker. Ограничение не обещает жёсткие 25 мс на весь вызов: планирование и timeout cleanup внутри `tinyusb_net_send_sync` могут занять дольше. Пока зависимость читает payload, слот не освобождается.
- Пул очереди **8 × 1536 B**, NCM-пулы, приоритеты, affinity, Wi-Fi, копирование и срок pre-send expiry 50 мс не меняются. Переполнение по-прежнему немедленно возвращает ошибку; ожидание может перенести потери из `send_failed` в `full`, что не будет улучшением.
- Опция зависит от worker queue и NCM instrumentation. Если очередь не создалась, остаётся прежний sync/yield fallback. Если опцию выключить, получается контрольный вариант очереди `8a009e0`; отключение телеметрии или профиль не-NCM тоже отключают event wait.

Новая телеметрия `usb.tx_queue`: `event_wait`, `capacity_waits`, `capacity_wakeups`, `capacity_timeouts`, `capacity_disconnects`, `capacity_wait_us`. Wakeups включают disconnect и не гарантируют успешную отправку. Capacity timeout входит в `usb.tx_timeout` и `queue.send_failed`, не складывать повторно. `tx_busy_exhausted` теперь означает исчерпание аварийных 64 попыток либо старый yield/fallback; истёкший бюджет отражается как timeout. Perf сохраняет эти поля и добавляет ожидания/таймауты в batch-таблицу.

Проверки: варианты event wait on/off и sync fallback; событие до/во время ожидания, устаревшее уведомление, общий deadline, disconnect/reconnect; настоящий сгенерированный NCM-драйвер с проверкой, что уведомление приходит после освобождения NTB, в том числе ZLP/error. Сохраняются тесты владения payload, OOM, переполнения и конкурентных producer/worker. Отдельное исправление runner: даже ненулевая потеря ping без ошибки команды даёт `completed-with-warnings`, а не `completed`.

После прошивки повторить `npm run device:perf -- 62.84.120.30 --paths both --quick`. Проверить `event_wait=true`; сравнить **все** потери очереди, UDP loss, ping, API errors, память, throughput. Нулевые drops/retries под перегрузкой не обещаются. Проверить unplug/replug и админку USB/AP. На реальной плате этот вариант ещё не измерен.

## База `8a009e0`: ограниченная очередь и отдельная задача USB TX

База `57f4bc5`: все 117022 busy были при полном пуле и активном NTB; 23734 NTB запущены/завершены без ошибок. USB UDP down 10M агрегировал около 5 кадров/NTB, completion mean 5,38–5,82 мс против backlog gap 0,07–0,08 мс. Память после idle восстановилась; аппаратных ошибок запуска не видно. Это основание отделить ожидание USB от lwIP, а не увеличивать NCM-пулы вслепую.

`CONFIG_MESHVPN_USB_TX_QUEUE=y` включает эксперимент. lwIP берёт свободный слот без ожидания, копирует кадр в принадлежащую очереди память и возвращается. Единственная задача `usb_tx` отправляет его через существующий `tinyusb_net_send_sync`; `tinyusb_net_send_async` не используется. **Алгоритм sync-send оставлен прежним**: 64 попытки / 25 мс event wait / `taskYIELD()` после busy. Новых пауз или event-driven пробуждений пока нет: сначала проверить изоляцию lwIP.

- Пул из **8 слотов по 1536 байт payload**, плюс метаданные, целиком PSRAM; размер фиксирован, без malloc/free на пакет. Слот включает и кадр, который сейчас отправляется: это не 8 ожидающих + ещё один неограниченный буфер. MTU/NCM/Wi-Fi/чужие affinity не менялись.
- Две маленькие FreeRTOS-очереди передают индексы, не payload. `usb_tx` имеет внутренний стек 3072 байта, приоритет 5 (ниже текущего TinyUSB 6), без привязки к ядру. CPU telemetry покажет свободный стек новой задачи. Этот расход internal RAM надо проверить на плате, особенно при HTTPS.
- Переполнение возвращает ошибку немедленно и увеличивает `full`. Кадр старше 50 мс к началу обработки не отправляется (`expired`); это ограничение **возраста перед отправкой**, не строгая верхняя граница полного времени. Активный sync-send удерживает слот до возврата зависимости, включая timeout cleanup. Внешний таймер не освобождает ещё читаемый буфер.
- Mount/umount меняют поколение USB. Старые queued-кадры отбрасываются (`stale`), в sync-send поколение проверяется перед каждой попыткой. При уже отключённом хосте submit отклоняется (`no_host`). Это не отменяет кадр, уже переданный нижнему USB-слою у границы reset; обработку таких передач выполняет TinyUSB. Колбэки не чистят очередь и не освобождают active-слот одновременно с работником. MSC исключён зависимостью Kconfig из-за собственных mount-колбэков библиотеки.
- Ошибка выделения пула/очередей/задачи освобождает частично созданные ресурсы, оставляет прежний sync-путь, пишет предупреждение и `init_failed`. Пул не переносится молча во внутреннюю RAM. В отчёте fallback — warning, а не успешный запуск эксперимента.

API: `usb.tx_mode=queued|sync`, `usb.tx_queue.enabled`, `capacity`, `pending`, `in_use` (включая producer-copy и worker), `worker_active`, lifetime `high_water`. Глубина pending и общий снимок могут различаться на конкурентное enqueue/dequeue. Счётчики:

- `submitted = enqueued + full + no_host + invalid_length + not_ready + enqueue_failed` после завершения producer-вызовов.
- `completed = sent + send_failed + expired + stale`; после полного опустошения `enqueued=completed`, `in_use=pending=0`.
- `sent` — успех sync-send, не подтверждение приложения Mac. `send_failed` дублирует соответствующие ошибки старых `usb.tx_*`; **не складывать их дважды**. Теперь старые `tx_calls/tx_dropped/tx_wait_*` характеризуют работу worker, не все входящие кадры lwIP.
- Все потери очереди = `full + no_host + invalid_length + not_ready + enqueue_failed + expired + stale + send_failed`. `bytes_copied` учитывает реально выполненные producer-копии, включая редкую ошибку публикации после копирования.
- `queue_wait_us` — enqueue/copy-start → начало обработки; `residence_us` — enqueue/copy-start → завершение/отбрасывание. Накопление вместе с `completed`, максимумы lifetime. Время ожидания внутри sync-send по-прежнему отдельно в `usb.tx_wait_us`.

В perf добавлена таблица `USB TX queue by batch`, сохранены все причины отказов и данные NCM. Короткий batch может закончиться до передачи поставленных им кадров; средние вычисляются по кадрам, завершённым в окне счётчиков, в том числе поступившим раньше. Сравнивать USB/AP throughput, UDP receiver loss, ping, API errors и обе группы потерь; один лишь ноль старого `tx_dropped` не является успехом.

Проверки: host ASan/UBSan — все варианты startup OOM, передача после изменения/освобождения исходного буфера, исчерпание 8 слотов, возврат слотов на каждом выходе, epoch/expiry, error после busy, concurrent producers+worker и отсутствие per-packet allocation; тест прикрепления netif с queue/fallback; тесты runner и сборка ESP-IDF. Нагрузочный прогон на реальной плате ещё требуется. После обычной прошивки — прежний `npm run device:perf -- 62.84.120.30 --paths both --quick`; проверить `tx_mode=queued`, админку и интернет через оба интерфейса, затем USB unplug/replug. Для отката эксперимента выключить `CONFIG_MESHVPN_USB_TX_QUEUE` в defaults/menuconfig и пересобрать; NCM-телеметрия останется.

## База `57f4bc5`: возврат к yield и наблюдение за NCM

После прогона `2b41687` пауза в один тик **убрана**, восстановлен алгоритм `6f00e7f`: до 64 попыток, 25 мс event wait, `taskYIELD()` после busy. Старая телеметрия остаётся. Размеры/число NCM-буферов, zero-copy и affinity не меняются.

Причина: в прогоне 20:21–20:25 UTC drops действительно стали 0, busy-ответы упали с 114705 до 14555, но USB UDP down 10M сохранил 10,48% потерь против 10,74%, а ping под этой нагрузкой вырос до медиан 128–175 мс с 27–40% потерь. Вызовов TX в диапазоне (5;25] мс стало 1694 вместо 3. USB upload нестабилен, но в его batch не было busy: приписывать весь провал непосредственно паузе нельзя. Это не успешная end-to-end оптимизация, даже при нулевом локальном drop-счётчике.

Добавлена `CONFIG_MESHVPN_NCM_TELEMETRY=y` в defaults. Сборка создаёт **копию** `ncm_device.c` в build/meshpn-generated, проверив SHA-256 установленного TinyUSB 0.21.0~1; файлы managed_components не правятся. Генератор вставляет наблюдение в существующие события задачи TinyUSB и вызывает исходную отправку ровно один раз, не меняя её обработку ошибок. Изменившийся исходник зависимости вызывает ошибку сборки: нужно перепроверить вставки, а не автоматически менять контрольную сумму.

Новые данные `/api/status → usb.ncm`:

- `pool/free/ready/glue/active/glue_frames`: последний снимок **TX**-пула; `free_min/ready_max` — наблюдавшиеся экстремумы за время работы. `active` означает указатель NTB, которым владеет драйвер; при `start_errors` это не доказательство физически активной передачи. Во время ZLP такого указателя нет.
- `sampled_us/sample_age_ms`: время последнего события, не опроса API. В покое снимок может быть старым. Это событийные наблюдения, **не** доля времени заполнения пула. Метаданные читаются владельцем; getter копирует только защищённый снимок, не трогает NCM.
- `max_ntb/max_datagrams`: согласованные с хостом лимиты на момент события. `ntb_started/bytes_started/frames_started` показывают фактическую агрегацию при успешно запущенных NTB. Байты включают заголовки NCM и padding; число кадров берётся из NDP именно отправляемого NTB, а не индекса текущего собираемого буфера.
- `busy/busy_no_free/busy_active`: отказы `can_xmit` и наблюдавшееся при них состояние. Busy при свободных буферах отличается от полного пула; эти категории не надо складывать как независимые причины.
- `start_errors`, `ntb_completed/completion_errors/bytes_completed`, `zlp_completed/zlp_errors`: результат запуска и обработки завершений. Счётчики NTB и ZLP разделены.
- `completion_timed/completion_us/completion_max_us` и четыре bucket: от успешного вызова USB submit до обработки NTB completion в TinyUSB. Включает USB и задержку обработки события; **не** отдельное время ISR/очереди и не подтверждение приложением Mac. Ошибочные завершения с известным стартом тоже входят в время; байты успешных завершений считаются отдельно.
- `backlog_gaps/backlog_gap_us/backlog_gap_max_us`: от обработки NTB completion до следующего успешного NTB submit, если в момент completion уже были готовые кадры. Может включать промежуточный ZLP; не считать чистым временем простоя endpoint. При reset незавершённые интервалы аннулируются; накопленные счётчики/экстремумы сохраняются, растёт `initializations` (включает начальный init).

Runner сохраняет поля и выводит `NCM transfers by batch`: NTB, средние bytes/frames на NTB, busy при полном пуле, среднее completion/backlog-gap и ошибки. Одновременный AP+USB не удваивает значения. Границы опроса могут разделять старт и completion одного NTB; разницу started/completed одного короткого batch нельзя автоматически считать потерями. Старые прошивки и отключённая инструментация дают unavailable/n/a, не выдуманные нули. Экстремумы — lifetime, не дельты batch.

Проверки: сборка ESP-IDF; host-тест самого generated NCM (заполнение/опустошение шести буферов, NDP-агрегация, ZLP и xfer failures); тест счётчиков, границ времени и reset; тест неизменности исходной зависимости и отказа на неизвестном SHA; тесты сохранения/вывода полей runner. Это не тест реального USB-контроллера, PHY или ISR. Дополнительных payload-копий, очередей и динамических выделений в сборщике статистики нет; его CPU/JSON overhead нужно учитывать.

Аппаратный контроль: обычная прошивка и прежний `npm run device:perf -- 62.84.120.30 --paths both --quick`. Это yield-база **с новыми измерениями**, не чистый откат единственной строки. Для отдельного A/B overhead выключить `MESHVPN_NCM_TELEMETRY` через menuconfig выбранного build и пересобрать тот же build (либо явно поставить `# CONFIG_MESHVPN_NCM_TELEMETRY is not set` в defaults до запуска flash.sh). Тогда оригинальный NCM собирается без вставок, `usb.ncm.available=false`. Вначале получить данные; ожидание события/асинхронную очередь/размеры пулов пока не менять.

## Завершённый эксперимент: один тик между busy-повторами (`2b41687`, откат)

База: прогон `6f00e7f`, 2026-09-11 20:03–20:07 UTC. Все 1166 `tx_dropped` = `tx_busy_exhausted`; timeout/OOM/invalid-state/other-error — 0. Из них 1098 (94,2%) приходятся на USB UDP down 10 Мбит/с, включая прогрев, 66 — TCP, 2 — UDP down 5 Мбит/с. Всего 114705 busy-ответов на 157560 попыток. Только 3 из 44021 вызовов TX заняли больше 5 мс: лимит 64 повторов обычно исчерпывается быстро, а не за 64×25 мс.

Единственное изменение поведения: после `ESP_FAIL` вместо `taskYIELD()` выполнить `vTaskDelay(1)`, **только если осталась следующая попытка**. Сохранены 64 попытки и 25 мс event wait, нет пауз на успешном первом вызове, timeout/OOM/disconnect или после последней попытки. В текущем конфиге 1000 Гц один тик = 1 мс; фактическая пауза зависит от фазы тика и планировщика, это не гарантия сна ровно 1 мс. USB-функции по-прежнему выполняются владельцем, payload не копируется дополнительно, новых очередей/выделений памяти нет.

Гипотеза: дать обработке USB завершений время освободить место, сократить бесполезные попытки и отказы на кратких всплесках. Это не устранение ограничения пропускной способности. До 63 пауз увеличивают задержку общего TCP/IP-потока; особенно важны AP, ping и UDP receiver loss. Полное время TX не ограничено строго 64 мс: кроме пауз есть ожидания внутри зависимости. Длительность видна в существующей гистограмме `tx_wait_*`.

Повторить `npm run device:perf -- 62.84.120.30 --paths both --quick` после прошивки и сравнить таблицы по batch. Успех: меньше `tx_busy`/`tx_busy_exhausted` и TCP drops без регрессии скорости, AP, задержек, API и потерь приёмника. `tx_retried` может даже вырасти, если ранее потерянные кадры теперь успешно принимаются после повтора; само по себе это не регрессия. Снижение одного USB-счётчика при переносе потерь во входные очереди успехом не считается. Аппаратный результат пока не получен; sizes/zero-copy/affinity в этом эксперименте не меняются.

Host-тест проверяет освобождение места с продвижением модельного времени, 63 паузы при 64 busy и успехе на последней попытке, отсутствие пауз на fast-path/конечных ошибках, завершение при ошибке после busy и возможность читать статистику во время паузы. Реальные tick scheduling, USB unplug и NCM/DMA требуют проверки на плате.

## Выполнено в `6f00e7f`: пассивная USB-статистика и причины отказов

- Удалён `tud_network_can_xmit(1514)` из `meshvpn_usb_get_stats`: чтение больше не выделяет и не переставляет NCM NTB и не запускает передачу. Снимок счётчиков защищён коротким spinlock, без USB-вызовов/ожиданий внутри.
- API `can_xmit` и `tx_queue_depth` теперь `null`, а не небезопасный вызов и фиктивный ноль. **Реальная occupancy NCM ещё не инструментирована**: нужен отдельный воспроизводимый патч зависимости со счётчиками внутри задачи-владельца. `tx_busy` её не заменяет.
- Добавлены `tx_calls`, `tx_attempts`, `tx_busy` и причины `tx_dropped`: `tx_busy_exhausted`, `tx_no_mem`, `tx_invalid_state`, `tx_other_error`. Разделение основано на текущем `tinyusb_net_send_sync`: `ESP_FAIL` возвращается при отрицательном `can_xmit`; при обновлении зависимости перепроверить.
- Добавлены накопленное `tx_wait_us`, максимум `tx_wait_max_us`, максимум попыток и четыре непересекающихся временных bucket: ≤1 мс, (1;5] мс, (5;25] мс, >25 мс. Измеряется вся функция TX, включая неудачи, ожидание задачи и повторы, **не** длительность только memcpy или подтверждённая доставка хосту. Начальный no-host входит в `tx_calls` и гистограмму. Накопление 64-битное; дополнительных очередей, payload-копий и динамических выделений нет.
- Сохранена совместимость счётчиков: `tx_retried` — успешно принятые после повторов кадры; `tx_dropped` **не включает** `tx_timeout` и исходный `tx_no_host`. Всего неуспешных вызовов = сумма этих трёх полей; `tx_dropped` равен сумме четырёх новых причин. `tx_busy` — число отказавших **попыток**, а не кадров. Таймаут не доказывает отсутствие передачи: нижний слой может завершить callback у границы таймаута.
- Runner сохраняет все новые поля, включая ранее пропущенный `tx_timeout`, считает дельты по batch и выводит таблицу `USB TX by batch`. Одновременный AP+USB учитывается один раз; административный трафик тоже входит. Max-поля остаются lifetime-показателями в NDJSON, не вычитаются как счётчики. На старой прошивке отсутствующие поля — `n/a`, не ноль.
- Алгоритм 64 попыток / 25 мс event wait, размеры NCM, copy-mode и affinity **не изменены**. Это первый A/B: убрать вмешательство статистики, не одновременно менять обработку перегрузки. Hardware-эффект и снижение `tx_dropped` пока не подтверждены.

Проверки: host-тест вызывает настоящий модуль USB с подставленным TinyUSB, моделирует busy→success, 64 busy, успех на 64-й попытке, timeout/OOM/disconnect/прочую ошибку, границы гистограммы и конкурентный опрос. Сам getter не вызывает `can_xmit` или send; тест падает при таком вызове. Это не моделирование настоящего NCM/DMA и не замена замеров на плате.

Следующий прогон: та же команда `npm run device:perf -- 62.84.120.30 --paths both --quick` после прошивки. Сопоставить drops/таймауты с конкретными TCP/UDP batch и `tx_busy_exhausted`; если основная причина busy, следующим отдельным опытом проверять управление ожиданием/обратным давлением. Нулевой `tx_retried` не самоцель: успешные повторы лучше потерь. Нулевые потери под потоком выше ёмкости выходного канала без ограничения входной скорости не гарантируются.

Область: текущий IPv4 NAT, USB CDC-NCM ↔ Wi-Fi STA и Wi-Fi AP ↔ STA, вспомогательные DNS/web/CPU/logs. VPN ещё не реализован; `scripts/clean-vpn.js` здесь не аудировался. Установленные зависимости: ESP-IDF 5.4.1, iot_bridge 1.1.0, esp_tinyusb 1.7.6~2, TinyUSB 0.21.0~1; см. [lockfile](../dependencies.lock). При обновлении зависимостей выводы перепроверить.

## Короткий вывод

1. Транзит уже обрабатывается пакетами внутри lwIP. Мы не собираем целый файл/ответ в RAM и не записываем проходящий интернет-трафик во flash. Приёмные и передающие очереди всё равно нужны: интерфейсы работают независимо и с разной скоростью.
2. Есть копирования payload на границах драйверов. Самые интересные кандидаты: условная линеаризация цепочки `pbuf` перед USB TX и избирательный zero-copy **Wi-Fi RX**, не глобальное отключение RX-copy.
3. Перенос буфера в PSRAM, устранение копирования и устранение ожидания — три разные оптимизации. Иногда дополнительная копия позволяет раньше вернуть ограниченный драйверный буфер и улучшает скорость.
4. До экспериментов с zero-copy исправить подозрительный путь чтения USB-статистики: он вызывает функцию, которая меняет состояние NCM. Это риск корректности, не просто расход CPU.
5. Крупный потребитель внутренней RAM — NCM-пулы: около **96 КиБ**. Сначала измерять их занятость/агрегацию; не переносить весь USB endpoint pool в PSRAM и не уменьшать вслепую.

## 1. Как проходит payload

Ниже показаны **видимые в открытом коде RAM→RAM копии**, а не полное число аппаратных перемещений. Внутренности бинарного Wi-Fi-драйвера не пересчитывались. Для обычного не фрагментированного IP-пакета:

| Участок | Текущее действие | Владение / следствие |
|---|---|---|
| NCM RX → USB glue | Указатель на Ethernet-датаграмму внутри принятого NTB | NTB принадлежит TinyUSB, glue не получает его в собственность |
| USB glue → lwIP | `pbuf_alloc(PBUF_RAM)` + `memcpy` payload | У lwIP появляется независимая копия; NTB можно переиспользовать |
| Wi-Fi RX → lwIP | При нашем `L2_TO_L3_COPY=y`: `pbuf_alloc` + `memcpy`, освобождение L2-буфера | Тоже независимый payload lwIP |
| lwIP IPv4/NAPT → выход | Обычно тот же `pbuf`, изменение заголовков/контрольных сумм | Полная копия payload ради NAT не делается; исключения вроде фрагментации/ARP-очередей проверять отдельно |
| lwIP → Wi-Fi TX, один `pbuf` | `esp_netif_transmit_wrap(..., payload, len, pbuf)` → `esp_wifi_internal_tx_by_ref` | Передача со счётчиком ссылок уже реализована |
| lwIP → Wi-Fi TX, цепочка | Новый непрерывный `pbuf` + `pbuf_copy`, затем TX by reference | Условная дополнительная копия; частота пока неизвестна |
| lwIP → USB TX, один `pbuf` | Указатель → `tinyusb_net_send_sync` → `tud_network_xmit_cb` | В callback один `memcpy` в выходной NTB |
| lwIP → USB TX, цепочка | Сначала `pbuf_alloc` + `pbuf_copy`, затем тот же USB TX callback | Две последовательные RAM-копии: в промежуточный буфер и затем NTB |

Источники: [bridge_usb.c](../managed_components/espressif__iot_bridge/src/bridge_usb.c), функции `usb_recv_callback`, `usb_input`, `usb_low_level_output`; [tinyusb_net.c](../managed_components/espressif__esp_tinyusb/tinyusb_net.c), `tinyusb_net_send_sync`, `tud_network_recv_cb`, `tud_network_xmit_cb`; [NCM driver](../managed_components/espressif__tinyusb/src/class/net/ncm_device.c), `recv_transfer_datagram_to_glue_logic`, `tud_network_xmit`.

IDF-часть: [wlanif.c](https://github.com/espressif/esp-idf/blob/v5.4.1/components/esp_netif/lwip/netif/wlanif.c), [wifi_netif.c](https://github.com/espressif/esp-idf/blob/v5.4.1/components/esp_wifi/src/wifi_netif.c), [контракт TX by reference](https://github.com/espressif/esp-idf/blob/v5.4.1/components/esp_wifi/include/esp_private/wifi.h). В локальном IDF есть патчи iot_bridge к lwIP; проверен и фактический `ip4_forward`/`ip_napt_forward`, а не только upstream.

Передача `packet_t` в sync USB — маленький дескриптор на стеке с указателем, не копия пакета. Поменять его на ещё один указатель не устранит `memcpy` в NTB. Асинхронный вызов также сам по себе эту копию не устраняет.

### Почему нельзя просто сделать `pipe` Wi-Fi → USB

Здесь разные канальные форматы, NAPT, маршрутизация, проверки входящего интерфейса, очереди и USB NTB-агрегация. Получатель может быть не готов, когда входной драйвер хочет переиспользовать буфер. Практический zero-copy — передавать ссылки на пакеты с явным владельцем до завершения обработки, а не работать «совсем без RAM».

Wi-Fi-драйвер уже содержит собственные RX/TX-буферы и аппаратные границы. Документация отдельно описывает копирование из аппаратного static RX в dynamic RX; отсутствие копии в нашей обвязке не означает end-to-end zero-copy. [ESP-IDF: Wi-Fi buffers](https://docs.espressif.com/projects/esp-idf/en/v5.4.1/esp32s3/api-guides/wifi.html#wi-fi-buffer-configure).

## 2. Сначала корректность: статистика вмешивается в USB TX

В [meshvpn_usb_get_stats](../components/meshvpn_usb/meshvpn_usb.c) выполняется:

```c
out->can_xmit = out->host_ready && tud_network_can_xmit(1514);
```

В установленном NCM `tud_network_can_xmit()` может вызвать `xmit_setup_next_glue_ntb()` и `xmit_start_if_possible()`: выделить NTB из free list, переместить текущий в ready queue, изменить индексы и инициировать отправку. Это **не чистый getter**.

Статистику читают web-обработчики и основной цикл приложения, а нормальный `do_send_sync` исполняется в задаче TinyUSB. В рассматриваемом коде вокруг этих вызовов нет общей сериализации состояния NCM. Побочные эффекты подтверждены кодом; гонка и её вклад в реальные потери/скорость требуют отдельного воспроизведения. Нельзя объявлять это доказанной причиной всех предыдущих сбоев.

Предлагаемое отдельное исправление:

- Убрать вызывающую изменения проверку из чтения статистики. Если поле нужно — публиковать кэшированное состояние, измеренное в задаче-владельце; обозначить, что это снимок, а не обещание успешной отправки.
- Не вызывать `can_xmit` из новой телеметрии для измерения occupancy. Считать события внутри владельца очереди.
- Проверить согласованность снимка `s_stats`: текущий `memcpy` структуры не гарантирует единый момент времени при конкурентных обновлениях. Короткая синхронизация/публикация снимка допустима, но нельзя держать spinlock во время USB-вызовов, ожиданий или HTTP-send.
- Тест: опрос `/api/status`/`api/logs` не меняет очередь, число NTB и факт отправки. Нагрузочный A/B с частым опросом и без него; учитывать, что основной цикл тоже читает статистику.

## 3. Карта памяти и кандидаты

Проверены defaults и map локальной обычной NCM-сборки ESP-IDF 5.4.1 после переноса логов. Это свидетельство размещения в этой сборке, **не heap-замер на пользовательской плате**.

| Буфер / область | Размер и размещение | Что делать |
|---|---|---|
| NCM IN + OUT endpoint pools | 6×8192 в каждую сторону = 98304 байта payload-хранилища; map: `.dram1.6`, размер `0x18010` = 98320 байт у `ncm_device.c.obj` | Большой кандидат на бюджет RAM после замеров occupancy |
| Кольцо логов | 12288 байт теперь PSRAM; в BSS остаётся указатель 4 байта | Уже сделано в `7944268`; подтвердить новой прошивкой |
| CPU raw/next/prev и копия для JSON | Явная PSRAM после `abedf65` | Уже сделано; не возвращать обычный `calloc` |
| CPU опубликованный `s_sample` | В проверенном map `0xc38` = 3128 байт внутренней BSS | Можно отдельно перенести в PSRAM с безопасной инициализацией/обработкой OOM |
| Снимок `/api/logs` | Временный `malloc(12288)` в обработчике | Явно выделять PSRAM; это ещё не перенесённая часть логов |
| DNS query/response работников | 3×2×4097 = 24582 байта PSRAM, выделяются один раз | Уже разумно; не трогать ради bulk-throughput |
| DNS cache | 8 записей, около 20 КБ в PSRAM | Копии нужны для независимости кэша и изменения TTL/ID в ответе |
| DNS jobs | `calloc` структуры с query до 1233 байт на запрос; очередь хранит указатели, не payload | Возможен ограниченный пул в PSRAM для уменьшения allocator churn |
| Стеки задач | HTTP 12288, CPU sampler 4096, DNS workers 3×4096 + listener 3072 байта; есть и другие | Уменьшать только после high-water замеров худших сценариев; не считать это свободно переносимыми данными |

Настройки обычного `malloc` в проверенной сборке: предпочтение internal до 16384 байт и отдельный internal reserve 32768 байт. Маленький `malloc` **не гарантирует** internal и не гарантирует PSRAM: есть fallback, текущая занятость и capability-пулы. Для холодных больших снимков выбирать память явно. PSRAM не заменяет все виды внутренней RAM; доступ при выключенном cache и DMA имеют ограничения. [ESP-IDF: external RAM](https://docs.espressif.com/projects/esp-idf/en/v5.4.1/esp32s3/api-guides/external-ram.html).

В sdkconfig включён `CONFIG_TINYUSB_MODE_DMA`, а `tusb_config.h` помещает endpoint buffers в DRAM. При этом DWC2 выбирает DMA с учётом аппаратного `GHWCFG2.arch`: один CONFIG не доказывает фактическую работу DMA на конкретном контроллере. Зафиксировать режим перед экспериментами. В slave/IRQ-режиме DCD читает/пишет FIFO программно. Ни в одном случае нельзя просто заменить атрибут всего endpoint pool на PSRAM без проверки аппаратуры, cache и контекста обращений.

### Малорисковые следующие шаги по RAM

1. Проверить уже сделанный перенос кольца логов на железе; затем baseline.
2. Отдельно перенести **снимок `/api/logs`** в PSRAM с корректным HTTP-ответом при OOM. Сам снимок оставить: отдача живого кольца по ссылке приведёт к его изменению во время отправки, а удержание mutex на весь сетевой send — к потерям логов/блокировкам.
3. При всё ещё низком internal reserve отдельно перенести `s_sample` CPU. Сохранять независимый снимок для JSON, не сериализовать под mutex. Выигрыш — около 3 КБ размещения, не обещание дополнительных Мбит/с.

## 4. Кандидаты на ускорение пакетного пути

### A. Убрать промежуточную линеаризацию перед USB TX

**Условие:** счётчик реально показывает заметную долю `p->next != NULL` в `usb_low_level_output`.

Сейчас цепочка сначала копируется в новый `PBUF_RAM`, затем в NTB. Можно передавать исходную цепочку в USB callback и копировать её сегменты непосредственно в окончательный NTB (`pbuf_copy_partial` или проверенный обход). Это убирает **одну** копию и одну пару alloc/free для цепочек; для одиночных `pbuf` выигрыша нет.

Нужно изменить согласованно интерфейс bridge/glue и контракт callback, а не только заменить `memcpy`. Сохранить жизнь цепочки до завершения callback; после timeout/disconnect никакой отложенный callback не должен читать освобождённый `pbuf`. Проверить цепочки разной длины, заголовки на границе сегментов, OOM, USB unplug и возврат ошибок. Сначала оставить sync-модель. Wi-Fi TX линеаризацию отдельно не удалять: его API принимает непрерывный payload.

### B. Избирательный Wi-Fi RX zero-copy

Для Wi-Fi IDF умеет `esp_pbuf_allocate` / `PBUF_REF` с custom free, который возвращает L2-буфер драйверу при последнем `pbuf_free`. Это кандидат убрать Wi-Fi→lwIP копию. TX by reference при этом уже есть.

Но глобально выключать `CONFIG_LWIP_L2_TO_L3_COPY` нельзя: тот же переключатель затрагивает USB RX. Нужна раздельная политика: сохранить USB copy и отдельно испытать Wi-Fi reference-path. Правку IDF/bridge делать воспроизводимым патчем/компонентом, не ручной заменой в установленном SDK.

Риски: более долгое удержание Wi-Fi RX-буферов, исчерпание dynamic RX pool, APSTA конкуренция, требования к доступности/изменяемости заголовков при NAPT. Проверять жизнь ссылок, возврат буферов, фрагменты, ARP, потери и largest block. Даже удаление копии может ухудшить throughput, если драйвер раньше возвращал дефицитные буферы благодаря копированию.

### C. USB RX zero-copy — только с новым контрактом владения NTB

В текущем glue `usb_recv_callback` передаёт `l2_buff=NULL`. `tud_network_recv_cb` вызывает renew и возвращает `true`; NCM после последней датаграммы возвращает NTB в free list. Асинхронный lwIP может ещё не обработать помещённый в очередь указатель.

Поэтому простое включение `esp_pbuf_allocate` вместо копии оставляет ссылку на переиспользуемое содержимое. Нужны владельцы/refcount **целого NTB**, custom pbuf на каждую датаграмму и возврат NTB владельцу только после освобождения всех ссылок. Последний `pbuf_free` может произойти не в задаче TinyUSB: возвращать буфер через безопасную очередь/уведомление. Проверить reset/unplug при висящих ссылках и не допустить повторного использования старого поколения.

Цена: одна задержанная датаграмма может удержать весь NTB 8 КБ и остановить RX при исчерпании шести буферов. Возможен гибрид copy-on-pressure, но это существенно более сложный эксперимент. Приоритет ниже A/B. Историческую регрессию снятия L2-copy это объясняет как возможный механизм, но без старого воспроизведения нельзя приписать ей единственную причину.

### D. Sync TX, агрегация и ёмкость NCM

`tinyusb_net_send_sync` передаёт работу в TinyUSB, ожидает event/semaphore. Наш [TX](../components/meshvpn_usb/meshvpn_usb.c) повторяет `ESP_FAIL` до 64 раз с timeout 25 мс на попытку. Это не 64 копии payload: при `can_xmit=false` копирование ещё не произошло. Реальные расходы могут быть в переключениях задач, очереди и ожидании свободного NTB.

`64×25 мс` — не строгая верхняя граница задержки функции: внутри зависимости есть `xSemaphoreTake(..., portMAX_DELAY)` для защиты времени жизни пакета. До переделки нужны распределение полного времени TX, причины выхода и время ожидания отдельно от копирования. Одно только среднее CPU этого не покажет.

Установленный NCM инициирует передачу, если endpoint свободен; следующие кадры могут агрегироваться, пока он занят. Измерить кадры/байты на NTB, negotiated `xmit_max_ntb_size`/`xmit_max_datagrams`, pool low-water, ready high-water, время пустого endpoint при наличии входящих пакетов. Размер CONFIG 8192 не означает, что хост согласовал этот размер и каждый NTB заполнен.

Если пул систематически недоиспользован — отдельный эксперимент **6→5 буферов только в одном направлении**, сохранив размер NTB: потенциально освобождает 8192 байта internal, точный эффект проверить map/heap. Не уменьшать одновременно IN и OUT и не менять retry/агрегацию в том же опыте. Изменения обоих размеров раньше уже улучшали baseline, поэтому экономия RAM может стоить скорости.

Async TX рассматривать позже: bounded queue, явные ссылки на `pbuf`, политика переполнения и освобождение на каждом пути ошибки обязательны. Установленный `tinyusb_net_send_async` не готовый zero-copy-ответ: callback всё равно копирует payload; кроме того, функция разыменовывает результат `calloc` **до проверки NULL**. Этот дефект не находится на текущем sync-пути, но должен быть устранён до использования async.

## 5. Остальное: полезно, но не основной кандидат на Мбит/с

- **DNS jobs:** queue уже копирует только `job_t *`. Пул до 8 jobs (4 queued + 3 workers + listener) уберёт alloc/free на запрос; его стоит ограничить и разместить в PSRAM. UDP worker может работать с owned `job->query` вместо копии в `ctx->query`, но нужно сохранить корректность изменения DNS ID, ключа кэша, TCP fallback и lifetime job. При OOM/перегрузке — ограниченное поведение, не растущая очередь. Это оптимизация DNS latency/heap, не транзитного iperf.
- **DNS cache:** независимые копии response и обновление TTL/ID нужны; не отдавать общий изменяемый cache-buffer нескольким работникам по ссылке.
- **Ingress hook:** копирует 20 байт IP-заголовка и при необходимости 4 байта портов; массив `h[60]` не означает копию всего пакета. Это небольшой расход ради поддержки chained/unaligned pbuf. Не убирать проверки доверенного интерфейса и защиту админки ради такого выигрыша. [meshvpn_net_hooks.c](../components/meshvpn_net/meshvpn_net_hooks.c).
- **Web/CPU JSON:** есть снимки, объекты cJSON и сериализованный JSON. Это не транзитный packet path. Сначала замерить стоимость опроса; при необходимости разделить компактный perf-status и полный список задач. Не делать JSON/HTTP внутри locks и не отдавать изменяемую общую структуру вместо снимка.
- **Логи:** `vsnprintf`, копирование в кольцо и передача прежнему UART writer — служебная нагрузка. Сеть не логируется целиком; не включать per-packet ESP_LOG при замерах. Кольцо и его snapshot выполняют разные задачи, поэтому не считать их дублированием без пользы.
- **MSS/windows:** настройки TCP PCB платы не равны параметрам транзитного TCP хоста. Изменение `TCP_WND` не устраняет найденные копии. Проверять фактические SYN/MTU отдельно.
- **Будущий VPN:** заранее оставить headroom/tailroom под заголовки/AEAD, ограниченные очереди и явное владение пакетом, бинарные routing-наборы вместо JSON на пакет. API конкретного TLS/WireGuard backend ещё не выбран: обещать шифрование in-place или отсутствие копий сейчас нельзя. Потоковый TLS и IP-датаграммы потребуют framing и частичных записей.

## 6. Порядок действий и автоматические проверки

История откатов: [benchmark-gonogo.md](benchmark-gonogo.md), Phase 7–9. Уже откатывали async USB TX (три варианта), глобальный L2-copy off и другие retry-параметры. Не повторять те же переключатели без нового контракта владения или измеренной причины.

Предлагаемый порядок, **по одному изменению прошивки**:

1. Прошить текущий перенос логов, зафиксировать baseline и build identity.
2. Убрать side effects из `meshvpn_usb_get_stats`; подтвердить работой с опросом/без опроса. Это исправление корректности перед настройкой скорости.
3. Добавить дешёвые счётчики/гистограммы, без per-packet логов и выделений памяти:
   - RX copy bytes/count и alloc failures отдельно USB/STA/AP;
   - TX chained packets/bytes и coalesce alloc failures отдельно по выходам;
   - USB sync calls, wait time histogram/max, `ESP_FAIL`/timeout/OOM, реальные NTB occupancy/size;
   - число удерживаемых RX-буферов и время удержания для будущего zero-copy;
   - actual DCD DMA/slave mode один раз при старте.
4. Перенести `/api/logs` snapshot, при необходимости CPU `s_sample`; каждый перенос — отдельный опыт по RAM.
5. При подтверждённых chained pbuf — кандидат A. При неиспользуемом пуле — D с уменьшением одного пула. Если измерения не подтверждают предпосылку, пропустить эксперимент.
6. Избирательный Wi-Fi RX reference-path B; USB RX C и async TX — только после устойчивой предыдущей базы.

Дополнить perf отчёт: сейчас `tx_timeout` не включён в сводные дельты, а в драйвере считается отдельно от `tx_dropped`. `tx_retried` — число успешно отправленных пакетов после повторов, не общее число попыток. `tx_ok` означает принятие USB-стеком, не подтверждение доставки приложению хоста. Для UDP сохранять sender rate/bytes/duration и receiver rate/bytes/duration: целевые 10 Мбит/с и loss=0 не гарантируют, что отправитель действительно выдал 10 Мбит/с.

### Воспроизводимый A/B

Команды runner и требования к Mac описаны в [perf-testing.md](../perf-testing.md).

```bash
# Smoke: сначала проверка сохранения работоспособности
npm run device:perf -- user@SERVER:22 --paths both --quick

# Измерение: без endurance, 15 секунд × 3 повтора, с idle-окнами
npm run device:perf -- user@SERVER:22 --paths both --quick --seconds 15 --runs 3 --idle-seconds 15
```

Для изоляции платы предпочтителен проводной LAN-сервер за роутером; WAN-замер оставить отдельным. Не смешивать LAN/WAN, diagnostic/normal firmware, разный сервер, положение платы, RSSI/канал, режим AP и HTTPS в одном A/B. Сохранить исходные JSON, sdkconfig/map и версии. `single/usb` при включённой AP не является AP-disabled baseline.

Порядок baseline → experiment → baseline полезен против дрейфа радио/температуры. Сравнивать receiver throughput, retransmits/loss, latency, internal/DMA min/largest и API ошибки; несколько байт разницы idle heap не объявлять утечкой. Гистограммы копирования/ожидания тоже потребляют CPU: отдельно оценить overhead инструментирования. Копировать 10 Мбит/с один дополнительный раз — около 1,25 МБ/с payload, но фактическую стоимость в CPU/PSRAM/кэше нужно измерить, а не переносить desktop-оценки на S3.

Готовность изменения: выигрыш повторяется сверх разброса либо появляется нужный запас RAM без значимой регрессии; нет новых drops/таймаутов, зависаний админки, ошибок пакетов и накопления удерживаемых буферов. Если ускорения нет — сложный zero-copy не оставлять «на всякий случай».

Для каждого изменения lifetime обязательны unit/stress-тесты double-free/use-after-free, delayed completion, OOM, queue full, несколько датаграмм одного NTB. На железе: USB unplug/replug, reconnect STA, одновременный AP+USB, scan, сохранение настроек/NVS, HTTP и отдельно HTTPS, затем endurance минимум 30 минут. Host ASan/UBSan не воспроизводит DMA/cache/ISR, поэтому не заменяет аппаратные проверки.

## Что не менялось в рамках исходного аудита

Изначально создан только этот документ. Последующие исправление статистики, NCM-телеметрия, эксперимент с паузой и её откат описаны в начале. Размеры пулов, copy-mode и affinity по-прежнему не менялись. Подтверждённого устойчивого end-to-end ускорения пока нет.
