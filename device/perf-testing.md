# MeshPN performance testing

Цель — отделить предел платы от ограничений USB, Wi‑Fi радиоканала и WAN. Каждый эксперимент меняет только один параметр прошивки.

## Запуск одной командой (macOS)

Подключить XIAO по USB, Wi‑Fi Mac — к AP платы. STA платы уже должен иметь uplink. Закрыть вкладку админки, чтобы её автоскан/новая сессия не мешали измерению.

```bash
npm run device:perf -- user@192.168.1.100:22 --paths both
```

`192.168.1.100:22` — адрес и **SSH-порт** сервера, не порт iperf3. Можно опустить пользователя/SSH-порт. Сервер желательно подключить проводом к тому же роутеру, что и STA платы. Внешний VPS тоже подходит, но результат включает ограничения WAN и может потратить несколько гигабайт трафика.

Для первой проверки стенда (~3 минуты, не полноценный baseline):

```bash
npm run device:perf -- user@192.168.1.100:22 --paths both --quick
```

Полная серия — около **75 минут плюс запуск процессов**: USB/AP отдельно, TCP upload/download (по 5 измеряемых прогонов по 30 секунд плюс прогрев), UDP 5/10 Mbit/s в обе стороны с такими же повторами, одновременный TCP AP+USB, затем 30 минут load/idle. `up` означает Mac → сервер, `down` — сервер → Mac.

Runner сам:

- проверяет зависимости и SSH; находит плату по DHCP gateway, входит в API;
- проверяет scoped route, source IP и принудительно привязывает iperf3/ping к интерфейсу; проверяет маршрут до и после throughput-теста; при возможном обходе платы не принимает результат;
- запускает по SSH два **своих** процесса iperf3 на 5201/5202 (один, если выбран только один путь), без туннелирования тестовых данных;
- собирает `/api/status` каждые ~2 секунды и на границах тестов, ping в idle/под нагрузкой, JSON iperf3 и stderr; ничего не сканирует и не меняет в прошивке;
- сохраняет median/min/p95/max throughput, UDP loss/jitter, TCP retransmits, latency, CPU/температуру, дельты счётчиков и память в сопоставимых idle-окнах;
- удерживает Mac от idle sleep через `caffeinate` и завершает свои серверы при окончании/Ctrl-C/ошибке. Heartbeat по SSH прекращается при аварии runner: удалённый supervisor убирает процессы примерно через 30 секунд даже при потере связи. Есть аварийный предел 6 часов; suite с ожидаемой длительностью >4 часов отклоняется.

Артефакты: `device/perf-results/<timestamp>-<random>/report.md`, `result.json`, `status.ndjson`, `measurements.ndjson`, raw JSON/stderr/ping и исходные маршруты. Каталог исключён из Git. Пароль/token в отчёт не записываются; адреса, версии и телеметрия — записываются. Ctrl-C сохраняет частичный отчёт. Exit codes: `0` — серия завершена, `1` — ошибка, `2` — завершена с проблемами API/link/ping, `130` — прервана. Прогрев не включён в сводку. Пропуски отсутствующих путей видны в warnings; для обязательного сравнения используйте `--paths both`.

### Зависимости и настройки

Установка **не автоматическая**. Если зависимость отсутствует, runner остановится с подсказкой:

- Mac: `brew install iperf3`; старую версию без `--bind-dev` обновить через `brew upgrade iperf3`. Node.js ≥18.
- Linux-сервер (Debian/Ubuntu): `sudo apt-get install iperf3 python3`; Fedora: `sudo dnf install iperf3 python3`.
- macOS-сервер: `brew install iperf3 python`.
- SSH уже должен работать по ключу/ssh-agent без пароля, с проверенным ключом сервера в `known_hosts`. Проверка host key не отключается. SSH-конфиг пользователя учитывается; для alias, не разрешимого обычным DNS, нужен `--server-ip`.
- Сервер должен принимать TCP **и UDP** на 5201/5202. Если есть firewall/NAT/security group, доступ на эти порты нужно разрешить самостоятельно: runner не меняет firewall и не завершает чужой iperf3. Слушатели не требуют авторизации iperf, поэтому доступ желательно ограничить своим тестовым клиентом/uplink.
- macOS может потребовать одноразово разрешить Terminal/Node/iperf3 доступ к локальной сети. Автоматически обойти системное разрешение нельзя. Закрытие крышки/ручной sleep также не является частью автоматизации.

Параметры:

```bash
# Только USB или только AP (другой интерфейс платы не выключается)
npm run device:perf -- user@SERVER:22 --paths usb

# Другие data-порты, без endurance-этапа
npm run device:perf -- user@SERVER:2222 --iperf-port 5301 --soak-minutes 0

# Пароль отличается от тестового admin; берётся из окружения, не из аргументов
MESHPN_ADMIN_PASSWORD='your-password' npm run device:perf -- user@SERVER:22

# HTTPS с доверенным сертификатом; --admin-insecure допустим только явно для теста
npm run device:perf -- user@SERVER:22 --admin-ca /path/to/device.crt

npm run device:perf -- --help
npm run device:perf:test
```

Также доступны `--seconds`, `--runs`, `--idle-seconds`, `--server-ip`, `--admin-url http(s)://BOARD-IP[:port]/` (для статического адреса), `--out DIRECTORY`. По умолчанию `--paths auto`: использовать обнаруженные пути; `both` требует оба. HTTP остаётся HTTP согласно настройке платы; пароль и token на этом локальном участке не зашифрованы. HTTPS-редирект поддерживается, но доверие сертификату нужно задать через `--admin-ca` либо явно отключить проверку через `--admin-insecure`. `--quick` задаёт 3 секунды/2 повтора/no soak; параметры после него могут переопределить эти значения.

Ограничения: физические USB unplug/replug, перезапуск роутера, sleep/resume, AP-disabled baseline и проверка изоляции со STA требуют отдельного управления стендом. Runner не делает DHCP renew, DNS/mDNS-тест и не читает UART/watchdog; короткие сбои между API-опросами могут остаться незамеченными. Память сравнивается после прогрева и в конце одинаковых idle-окон, но два окна сами по себе не доказывают утечку или её отсутствие.

Автотесты проверяют расписание с fake clock, TCP/UDP JSON, обход маршрута, API discovery/login, очистку удалённых процессов, занятый порт, создание полного и частичного отчёта. Это программная проверка; macOS + реальная плата + сервер требуют первого аппаратного прогона.

Основание для привязки интерфейсов: [официальная документация iperf3](https://software.es.net/iperf/invoking.html), [реализация IP_BOUND_IF](https://github.com/esnet/iperf/blob/master/src/net.c), [Apple ping: -b boundif](https://github.com/apple-oss-distributions/network_cmds/blob/main/ping.tproj/ping.8).

## 1. Фиксируем baseline

Команды выполнять из корня репозитория. Перед каждой прошивкой сохранять:

```bash
git rev-parse HEAD
git status --short
git diff -- device/boards/xiao_esp32s3/sdkconfig.defaults
bash device/scripts/test-host.sh
```

Результат host-тестов должен быть чистым. Для аппаратного результата использовать таблицу/JSON с commit, датой, версией IDF, профилем USB, настройками AP/HTTPS, RSSI, каналом и температурой.

## 2. Автоматический локальный throughput-тест

Интернет speedtest не использовать как основной показатель: он смешивает скорость платы с качеством WAN. Поднять `iperf3 -s` на проводном компьютере в той же LAN, куда подключён STA роутера. Клиентом выступает устройство за AP или USB Ethernet.

Для каждого пути выполнить один прогревочный и затем минимум 5 измеряемых прогонов TCP по 30 секунд, сохранить JSON:

```bash
iperf3 -c 192.168.1.100 -t 30 -J > ap-up-01.json
iperf3 -c 192.168.1.100 -t 30 -R -J > ap-down-01.json
```

Повторить для:

| Сценарий | AP | USB | Что измеряет |
|---|---:|---:|---|
| AP traffic | traffic | idle / management | AP→STA NAT |
| USB traffic | idle | traffic | USB→STA NAT |
| AP + USB | traffic | traffic | совместное использование радио и CPU |
| AP disabled | n/a | traffic | контрольный USB baseline |

Реализованный runner выше запускает серии, проверяет код возврата и поле `error` в JSON, извлекает receiver throughput (`end.sum_received.bits_per_second` для TCP), sender `retransmits`, UDP loss/jitter. p95 при пяти прогонах лишь ориентир. Сохраняются stderr, полный JSON и timestamp; не сравнивать одиночный лучший прогон. Для одновременных AP+USB используются два серверных процесса на разных портах: обычный iperf3-сервер не обслуживает два независимых теста одновременно. Ручные команды выше — только иллюстрация; runner дополнительно фиксирует интерфейс.

## 3. Контроль условий

- Один и тот же роутер, канал, положение платы, сервер и клиент.
- На клиенте отключить cellular fallback, сторонний VPN/proxy и параллельные загрузки.
- Не открывать админку во время прогона: scan может временно прервать APSTA.
- Зафиксировать RSSI и negotiated channel width (HT20/HT40); HT40 — только запрос, а не гарантия.
- Для AP и USB использовать разные клиенты либо явно проверять таблицу маршрутов, чтобы телефон не выбрал другой интерфейс.

## 4. Автоматический сбор телеметрии

До, во время и после серии каждые 2 секунды записывать авторизованный `/api/status` в NDJSON; токен не сохранять в отчёте. Поля текущего API:

`uptime_sec`, `build`, `idf`, `wifi.connected`, `wifi.rssi`, `net.ap_channel`, `net.ap_clients`, `usb.host_ready`, `usb.tx_dropped`, `usb.tx_retried`, `net.ap_ip4_rx`, `net.lan_ip4_rx`, `temperature_c`, `memory.internal`, `memory.dma`, `memory.psram`, `cpu`. Timestamp добавляет сборщик. Фактическая ширина HT20/HT40 пока отсутствует в API.

`cpu` — общий снимок, собираемый отдельной задачей раз в 2 секунды независимо от количества читателей. Сохранять `sampled_us`, `sample_age_ms`, `interval_ms`, `collection_us`, `available`; повторяющийся `sampled_us` не считать новым замером. `cores[].load_pct` — оценка 100% минус время idle для одного ядра; ISR отдельно не измеряются. `tasks[].runtime_us` — 64-битный накопительный счётчик, `load_pct` — доля времени одного ядра за интервал. Сопоставлять задачи по `id`, а не имени. `name` — подсказка из списка известных задач, для неизвестных/дубликатов может быть null; `core=-1` означает отсутствие affinity. Начальный, устаревший или слишком длинный интервал даёт null. `stack_free` — минимальный остаток стека в байтах. Сбор ограничен 64 задачами; если снимок не помещается или память недоступна, `available=false`.

Автоматически проверять:

- нет reboot/watchdog/USB disconnect в журнале;
- counters не растут аномально относительно baseline;
- после прогрева свободная память и largest block восстанавливаются до сопоставимых значений в конце одинаковых idle-периодов; сравнивать internal/DMA/PSRAM отдельно;
- AP/USB остаются подняты после серии и после reconnect STA.

Если endpoint ещё не отдаёт поле, фиксировать это как отдельный пробел, а не подставлять ноль.
`minimum_free` — исторический минимум: он по определению не растёт и может снижаться от разовых пиков без утечки. Использовать его для оценки запаса, не как единственный критерий утечки. Статистика FreeRTOS и сканирование watermark имеют накладные расходы: записывать `collection_us` и сравнить скорость с закрытой/открытой админкой. Сбор CPU продолжается при закрытой странице; для сравнения без инструментации нужна отдельная сборка с `CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS=n`.

## 5. Latency и потеря пакетов

Параллельно с `iperf3` запускать `ping` на LAN-сервер (не в интернет) и записывать min/median/p95/max. Отдельно выполнить UDP-тест `iperf3 -u` с фиксированной скоростью 5 и 10 Mbit/s; сравнить datagrams lost и jitter. Это выявляет перегрузку буферов, которую TCP может скрывать ретрансляциями.

## 6. Нагрузочная и регрессионная проверка

Runner выполняет 30-минутный сценарий по умолчанию: throughput около 10 минут, idle около 5 минут, повторить 2 раза (длительность через `--soak-minutes`; учитываются накладные расходы процессов). Затем отдельно перезапустить роутер и проверить автоматический reconnect. После этого выполнить USB unplug/replug, sleep/resume клиента и повторно проверить DHCP, DNS, AP и админку.

Критерии стабильности: нет reset/USB flap, DHCP восстанавливается, AP-клиент получает интернет, админка доступна по USB/AP и закрыта со STA; после прогрева нет устойчивого падения свободной памяти в одинаковых idle-периодах. Перезагрузка роутера, unplug/replug и sleep/resume выполняются вручную, пока стенд не имеет соответствующего управления.

## 7. Как принимать следующий Wi‑Fi эксперимент

1. Прошить образ и убедиться, что boot/AP/USB исправны.
2. Выполнить одинаковую серию baseline и новой версии (не менее 5 прогонов на направление).
3. Сравнивать median и p10, а не только максимум; отдельно учитывать drops/retransmits и стабильность.
4. Оставлять изменение только если прирост повторяется минимум в двух сериях и нет регрессии USB/AP или памяти. Иначе откатывать одним коммитом.

Текущие подробности APSTA и адреса интерфейсов: [apsta-benchmark.md](docs/apsta-benchmark.md). Исторические результаты USB: [benchmark-gonogo.md](docs/benchmark-gonogo.md).

Примечание к истории тюнинга: `bb58487` явно зафиксировал `ESP_WIFI_RX_IRAM_OPT=y`, уже включённый по умолчанию IDF 5.4.1 для нашего S3. Это не самостоятельное ускорение. Текущая база: TX BA 12, RX BA 24, cache TX 48; перед экспериментом сравнивать итоговые sdkconfig, а не только defaults.
