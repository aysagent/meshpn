## Method and return guarantees

The baseline was the exact preserved P4 `2af50a4-dirty` image and factory C6
`network_adapter` (`release/ng-v1.0.2-330-g83efce6`, IDF 5.4 development build).
The temporary native C6 applications used IDF 5.5.5, one STA netif, no Hosted,
SDIO data path, AP, VPN or Wi-Fi configuration storage. P4 acted as a CDC/UART
carrier. Its SDIO pins were switched to inputs during native measurements.
USB HS stayed active. Only the inactive C6 OTA1 slot was used; the original
application remained in OTA0 at `0x10000`.

Before network work, the native program checked C6 identity, verified the
original image, selected it for the next boot, and armed a 300-second return
timer. The host requested an earlier return after each test. The active saved
Wi-Fi profile was sent through a CRC-checked 104-byte UART message into RAM;
passwords were not embedded in images or printed. A random per-run HTTP bearer
token was passed privately to the test client. Client connections used Mac en0.

The local HTTP generators streamed 8 MiB from a fixed block, with a bounded
duration. Uploads counted only complete board receipts. The client had a
20-second observation budget; incomplete downloads are failures, not accepted
throughput results. No external exit or WAN server participated.

Each incomplete download consumed approximately its 20-second budget. B1 also

The larger configuration did not uniformly improve uploads. These are small,
sequential samples with variable link conditions, not capacity acceptance.

B1 used MSS 1440 and 5760-byte TCP send/receive buffers. B2 used MSS 1360,
32768-byte send/receive buffers and a 6144-byte TCP/IP stack, plus Wi-Fi static
RX 16, dynamic RX/TX 64 and RX BA window 32. These match the P4 build's requested
configuration; actual factory-C6 allocations were not independently read back.
Other SDK/build/runtime differences remain. A1/A2/A3 were APSTA, B1/B2 STA-only;
the earlier separate STA-only P4 control was also slow, but is not an identical
simultaneous radio comparison.

### Client timing caveat found during final review

The private A/B/A client decoded a completed chunked response twice before
recording total elapsed time. Its decoder repeatedly copied the remaining
buffer. An offline synthetic 8 MiB response took about 0.84–0.90 seconds per
decode on the review run. Historical raw measurements are unchanged; that
offline overhead must not be subtracted as if it were measured during each test.

The previously reported B2 values **6.65 / 7.48 Mbit/s** are therefore derived
from client totals including decoding overhead, not precise receiver completion
rates or maximum C6 capacity. Completion of the entire body is still verified;
the P4 paths did not complete it within their budgets. Future comparisons should
reuse incremental HTTP reads and record completion before post-processing. The
committed `perf-p4-paths.py` already uses incremental `HTTPResponse.read1()` and
does not use this private decoder.

## Preservation and final hardware state

Full 4 MiB C6 backups were transferred with per-frame CRC, global CRC and SHA-256,
then flushed/fsynced before the host acknowledged them. Before/after native
testing and in the later pre-calibration-restore backup, the C6 bootloader,
partition table, PHY-init partition and entire 1.5 MiB original OTA0 matched.
OTA1 and OTA-selection metadata intentionally changed.

NVS was **not byte-identical**. Offline decoding of live entries identified a
changed `phy:cal_data` blob, including changed chunk layout. Reconstructing the
blob confirmed a content difference, not merely journal movement. Other decoded
logical NVS values matched. The observations do not identify which boot/firmware
regenerated the calibration cache.

For cleanup, a separate helper first saved another verified full backup. After
the host acknowledgment, it restored only `phy:cal_data` from the fresh
pre-native snapshot using `nvs_set_blob` / `nvs_commit`, then read it back and
checked length and every byte. Result was mode 2 / error 0. It did not erase
the NVS partition or other keys. This proves the restoration checkpoint; normal
firmware may refresh its calibration cache later. No claim of final byte-for-byte
NVS partition equality is made.

The exact production P4 image was restored. Final morning control: build
`2af50a4-dirty`, boot 1119, STA connected, AP active, VPN off. The user then
requested a stop; the current control finished and the stopped checkpoint was
saved. On evening resume, USB login returned 200 in 14 ms; the same build was
online with AP active and VPN off, boot 1122 / power-on reset. The gap was not
continuously monitored, so it is not a 12-hour stability test.

## Automation defect found and fixed

A temporary carrier initially failed before C6 OTA because its build environment
had fallen back to IDF 5.4 after a failed activation. It was rebuilt with explicit
IDF and Python environment selection, version checks and PSRAM dependency.
Native network results above were collected from verified IDF 5.5.5 builds.

A later incomplete carrier build exposed another issue: the P4 flash script
could touch USB into ROM before discovering a missing application binary.
Esptool rejected the arguments before writing; ROM recovery used the bound P4
and completed without buttons. Commit `b5f29d7` adds build preflight **before USB
enumeration/reset**: P4 target, nonempty files, manifest/argument agreement,
duplicate offsets and nested response files. It does not certify that a present
binary is newer than source files. All 34 flash tests pass, including cases
asserting zero enumeration, touch, serial open, wait or write on invalid builds.
All four actual P4 image manifests also passed; final hardware restoration used
the fixed script. No XIAO was flashed.
