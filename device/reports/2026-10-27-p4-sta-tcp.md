# P4 STA TCP header investigation — 27 October 2026

Follow-up: the [native C6 A/B/A comparison](2026-10-27-p4-c6-aba.md) is complete,
with factory C6 and production P4 returned. It includes an important caveat about
private-client decoding overhead in the later native download rates.

Status: **slow bulk STA transfers remain unresolved**. VPN off; Mac association,
firewall, router settings and C6 firmware unchanged. P4 alone was reflashed
automatically, bound to `E8F60AE395D0`, without buttons. XIAO was build-only.

## Added observation

Authenticated `GET /api/diag/sta-tcp` reads the latest TCP connection to P4's
STA HTTP port 80. A new SYN tuple/ISN selects it. The last 64 header records
retain time, direction, sequence/ACK, raw window, flags, payload length and
first SACK block/count; overwritten record counts are explicit. No payload,
HTTP headers or credentials are retained. Counters are separate from the ring.

RX is observed before lwIP input; TX after acceptance by host SDIO. Neither
is RF delivery confirmation. Complete contiguous packets have IP/TCP checksums
validated; partial RX header copies are explicitly unvalidated. Every normal
TX frame is contiguous and checked. The trace does not modify packets/settings.
Read it via USB after the test: the HTTP worker is occupied during streaming.

## Measurements and limitations

Mac BPF capture required a sudo password; none was requested. Rootless
`TCP_CONNECTION_INFO` was sampled instead. All tests bind the existing Mac
interface, with no network reassociation. Local STA IP was 192.168.1.11.

Initial build `8a1008b-dirty`:

* USB received a complete 8 MiB response, control passed. The first private
  script continued observing until 20 seconds even after the terminating HTTP
  chunk; its elapsed value is not a USB throughput measurement.
* Two STA downloads received 520192 and 921600 decoded bytes in their respective
  20-second observation windows, both incomplete.
* The first STA socket reported 75192 out-of-order bytes. In its retained P4
  trace, 15 ACKs repeated the same sequence while the raw receive window stayed
  65535. Later ACK progress stopped at a six-byte HTTP chunk-header segment;
  its retry was visible after roughly three seconds. This is evidence of a
  sequence gap/reordering and delayed recovery, not a closed receive window.
* macOS rejected per-socket TCP_MAXSEG 536/1024 with EINVAL before connection.
  These are failed experiment setup, not MSS-controlled measurements. Corrected
  private summary fields are null; original logs remain for audit.
* 1000-byte and 100000-byte uploads returned complete board receipts. This
  does not contradict the preceding 1 MB upload failures or restore capacity.

All-packet checksum build `2af50a4-dirty`, boot 1117:

| Case | Complete response / decoded bytes | Observation |
|---|---|---|
| STA download, default NODELAY | Incomplete / 434176 | 20.067 s |
| STA download, diagnostic NODELAY=0 | Incomplete / 131072 | 20.161 s |
| STA upload 100000 B | Board receipt confirms all bytes | 2.706 s request/response; receive_us=1378038 |
| STA download, default restored | Incomplete / 294912 | 20.160 s |

These are small sequential diagnostic samples, not a comparative capacity
benchmark. NODELAY=0 was limited to one HTTP socket and did not restore the
stream; normal default remains unchanged.

Across those four traces, **1111/1111 outgoing packets had valid IP/TCP checksum
before SDIO**. Per-trace totals were 547, 137, 43 and 384; counters survive ring
overwrite. Large incoming upload packets were often header-only copies and are
not included in the checked-good RX count. Mac out-of-order counters and P4
ACK gaps remain; correct pre-SDIO data does not establish what C6/RF delivered.

The last private script stopped on a retry-handler alias typo after an API
timeout following the final aborted stream. The trace/status were read afterward
without a reset: boot remained 1117, STA online, VPN off. The script's exception
handler was corrected for reuse. No crash or spontaneous reboot was observed.

## Verification and next isolation

ASan/UBSan tests exercise the actual parser: truncated/fragmented headers,
malformed SACK options, unsigned sequence values, SYN retransmit/new ISN, ring
wrap/order, per-direction totals, checksum corruption, immutable input and
unrelated ports. The full host suite and P4/XIAO builds passed; the subsequent
checksum extension passed targeted sanitizer tests and P4 rebuild. Unauthenticated
trace request returned 401. Final USB-bound external HTTPS completed TLS and
returned HTTP 301 in 0.286 s; this is reachability, not a bulk-speed result.

The next useful isolation is a bounded native C6 network test followed by a
verified return to the original image and another P4 control (A/B/A). Preserve
and verify C6 backup/partition/restore tooling first. Test the same AP and keep
Mac association/router unchanged. This can show whether slow recovery requires
Hosted/SDIO/P4; different native SDK/config settings remain confounders if a
native image is faster. No new C6 image was installed during this investigation.

bundles, per-flow traces, before/after status and the `checksum-control/` results.
Raw status, firmware and local test metadata are not committed.
