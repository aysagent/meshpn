# Автономная проверка MeshPN, 25 октября 2026

Запланированные автономные проверки завершены в пределах описанных условий стенда.
Код исправлений: `97bb8d4` + `4fe0f19`. База изменений — `736c670`, ветка `feat/clean-vpn-native-data-plane`.
Основные baseline/soak выполнены на P4 до commit (`736c670-dirty`);
финальные контроли `97bb8d4`/`4fe0f19` указаны отдельно.

## Условия и границы

- Привязанная Waveshare ESP32-P4-WIFI6 `E8F60AE395D0`, USB HS/NCM, ESP-IDF 5.5.5.
- USB gateway `192.168.10.1`, AP gateway `192.168.11.1`, STA DHCP.
- Wi-Fi, маршруты и firewall Mac не менялись. Вторая плата XIAO не прошивалась.
- Внешний clean-vpn/WireGuard exit не запускался. WAN control — публичная
  загрузка CDN через обычный DIRECT, с выключенным VPN.
- Локальный аппаратный TCP/UDP/TLS peer на Mac заблокирован настройкой macOS
  Application Firewall: State=2, Block all incoming connections. Две попытки:
  TCP timeout, ни одного принятого peer соединения; настройки платы восстановлены.
  Это ограничение стенда, не успешная аппаратная проверка VPN.

## Что исправлено

1. **DNS и kill switch.** Cache и in-flight DNS-ответы привязаны к эпохе
   VPN-политики. Ответ старого DIRECT/VPN пути не попадает в новый режим.
   Последний STA TX hook блокирует прямой UDP/TCP DNS при активной туннельной
   политике; сохраняется исключение для явного outer endpoint на порту 53.
   WireGuard bootstrap времени использует числовой NTP endpoint, без прямого DNS.
   Добавлены счётчики `dns.policy_changed`, `dns.vpn_blocked`, `vpn.direct_dns_blocked`.
   IPv6 остаётся заблокирован входным hook; это подтверждено host-тестом,
   аппаратного IPv6 packet capture в этой работе не было.
2. **MTU/MSS/ICMP.** ICMP fragmentation-needed с MTU 1400 формируется до NAPT,
   с исходным LAN IP/портом в quotation. MSS учитывает длину IPv4 options.
   Build-only patch NAPT переводит ICMP errors для TCP/UDP/echo, внешний адрес
   и вложенный tuple/checksums, включая короткие TCP quotations и chained pbufs.
   Новые NAPT/SDIO patches создают build-копии, не правят IDF/managed source напрямую.
3. **Настройки VPN.** Отдельные сохранённые endpoints TCP/UDP/TLS/WireGuard,
   миграция NVS `vpn_cfg1`–`vpn_cfg4` в `vpn_cfg5`, сохранение ключей/Address/DNS.
   Ранее перезаписанный старой прошивкой endpoint восстановить невозможно.
   Исправлены проверка окончания SNI в NVS и очистка пустого SNI через UI/API.
   Сохранение другого транспорта не стирает ещё не отправленный WG key из формы.
4. **Производительность и админка.** Время VPN TX queue, transport read/write,
   RX dispatch/core и TLS mutex, с числом вызовов и раздельными histogram buckets.
   Internet probe выполняется одним фоновым worker и не удерживает HTTP worker
   на пять секунд. Статус можно остановить и скачать JSON; виден признак паузы.
   Открытие страницы читает cache скана, новый скан запускается кнопкой.
5. **P4↔C6.** Радиоснимки собираются менеджером, `/api/status` только читает cache.
   Добавлены длительность/ошибки отдельных SDIO операций и RX drop counters.
   Установленный C6 не отвечает на новый negotiated-PHY RPC: получались
   пятисекундные таймауты каждого снимка. P4 теперь сообщает NOT_SUPPORTED без
   этой команды; native XIAO продолжает использовать getter.
6. **P4 RX memory.** Нагрузка выявила 134 отказа выделения RX packet buffers.
   DMA требуется самому stream read, но его CPU-копии не требуют DMA: эти копии
   и доставляемые Wi-Fi payloads перенесены в PSRAM с соответствующим free callback.
   Ошибка allocation отбрасывает кадр, не вызывает assert. Добавлена проверка
   остатка stream до чтения header/проверки checksum, включая обрезанный хвост.
7. **P4 USB bursts.** После RX memory fix оставались 946 queue-full, 12 expiry
   и два send failure за три загрузки. При этом NCM имел свободные буферы.
   Один 32 KiB SDIO stream может доставить более двадцати кадров, поэтому P4
   получил 64 owned PSRAM слота вместо восьми. Deadline 50 ms сохранён;
   XIAO остаётся с восемью. В следующем идентичном контроле все эти потери — ноль,
   observed high-water 56/64. Следующий контроль уже на установленном итоговом
   коде обнаружил 22 full при 64 слотах (без expiry/send failure). Добавлен запас
   до 128 слотов в PSRAM, с тем же 50 ms deadline. Это ограниченный burst buffer,
   не гарантия отсутствия потерь для произвольной нагрузки и не разгон USB PHY.
8. **Проверки.** Host suite останавливается при UB; исправлены macOS/Bash 3
   fixtures и привязка исходников host mbedTLS/lwIP к ESP-IDF 5.5.5 даже из
   старого терминала с `IDF_PATH` на 5.4. Production I/O проверяется реальным
   mbedTLS, а не только mock-функциями.

Последний WAN control: SDIO RX allocation/oversize/malformed/payload drops — ноль,
ошибки четырёх SDIO I/O операций — ноль. Admin latency median 137.67 ms,
max 310.46 ms. Radio snapshot collection около 78 ms вместо 5.08 s.
Reboot/disconnect в этих трёх загрузках не обнаружен.

В STA handoff были 161 отказ `other_error`, последний код `0x500e`.
В pinned ESP-Hosted этот код возвращает включённый механизм C6 TX throttling.
Теперь он учитывается отдельным `wifi.tx.*.netif_tx_failed`; throttling не отключён.
Он отражает давление на радио/передачу C6 и не входит в USB queue losses или SDIO
read/write errors. Нулевые USB/SDIO drops не означают отсутствие backpressure
во всей цепочке.

Первый 15-минутный USB прогон: 324 × 8 MiB ≈ 2.53 GiB, без наблюдавшегося
ребута/обрыва STA/USB. Admin median 1265.77 ms, p95 1380.30 ms. Локальный download
занимает единственный HTTP worker на время выдачи 8 MiB, поэтому параллельный
status ждёт завершения ответа; это другой режим, чем независимый WAN forwarding.

Заключительный 15-минутный USB/admin прогон новой буферизации: 330 × 8 MiB
≈ 2.58 GiB, boot #57 до/после. Admin median 1248.04 ms, p95 1277.93 ms,
max 1333.75 ms. USB full/expired/send_failed — 0/0/0. Этот прогон предшествует
последнему image: в нём дополнительно установлены guard обрезанных SDIO headers
и отдельный счётчик NETIF TX_FAILED; эти изменения не меняют успешный RX path.

Idle memory и исторические minimum_free включены в JSON summary. Internal/DMA
перекрываются, их нельзя складывать. Исторические minima сами по себе не доказывают
утечку или наличие такого количества свободной памяти в момент снимка.

## Функциональные проверки

- На реальной P4: работающий DIRECT HTTP control до теста; включённый TCP kill
  switch с недостижимым endpoint блокирует HTTP, DNS отвечает SERVFAIL; admin
  доступна. Explicit DIRECT fallback и выключенный VPN снова пропускают HTTP.
- На реальной P4: DF пакет длиной 1400 не получает ложного MTU error; длиной
  1401 возвращает клиенту EMSGSIZE и ровно один `mtu_feedback`, failed=0.
  Исходные настройки восстановлены в `finally`; повтор на новом образе прошёл. После финальной установки отдельный прогон из шести
  проверок подтвердил HTTP/DNS блокировку без exit для TCP, UDP и TLS, доступность
  admin, MTU feedback и DIRECT fallback. Итог `completed`, settings restored=true.
- Host ASan/UBSan: framing, partial I/O, очереди/ownership/epoch, DNS policy/cache,
  NAT ICMP/checksums, маршрутизация, NVS/config/API/UI, radio cache и SDIO RX.
  USB queue проверена с 8, 64 и 128 слотами. SDIO short-header tests используют
  exact-sized allocations, чтобы выход за границу обнаруживал sanitizer.
- Реальный mbedTLS из IDF: 128 IPv4 round trips, параллельные RX/TX потоки,
  peer дробит framed reply на 17-байтовые TLS writes/records. Это host acceptance
  production wrappers/parser; TLS handshake allocator/driver на ESP этим не доказан.
- Сборка XIAO и P4 на ESP-IDF 5.5.5; XIAO — только compile, без прошивки второй платы.
- Node performance runner suite: 56 passed, 0 failed.

Финальный WAN control с queue 128: **37.92 Мбит/с** median,
33.08–38.26, USB full/expired/send_failed **0/0/0**, все SDIO I/O errors и RX
drops — ноль. Observed queue high-water **85/128**, что подтверждает нехватку
64 слотов в повторе. Admin median 144.23 ms, max 226.01 ms. Это три повтора,
а не доказательство универсального loss-free threshold.

## Что остаётся за пределами текущего стенда

- Аппаратный TCP/UDP/raw TLS с локальным peer на Mac: входящие соединения
  блокирует существующая firewall policy. Автоматически ослаблять её не стал.
- VPN через настоящий exit: интернет, exit IP, DNS/STA packet capture, rekey,
  одновременный USB+AP и реальная производительность TLS/WireGuard.
- AP нагрузка/повторный клиент и переключение Wi-Fi Mac не выполнялись.
- Negotiated Wi-Fi 6 на P4 не подтверждён: getter недоступен на данном C6 image;
  observed uplink record сообщает 802.11n, secondary_channel=0 (20 MHz).
- Raw `tls` пока без проверки CA/hostname и tunnel authentication; это известная
  граница реализации, не завершённый защищённый транспорт этапа 3.
