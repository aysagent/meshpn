# Overnight VPN / DIRECT investigation, 30 October

Checkpoint after overnight investigation (05:25 MSK). Performance acceptance
is still failed. This chronological report extends the earlier throughput report;
intermediate temporary states below are superseded by Final state at the end. The reported phone failure is DIRECT upload through Stamp
USB Ethernet. All measurements here use Mac USB and do not reproduce that
phone workload exactly. Mac Wi-Fi, router, firewall and the native VPS process
remain unchanged. Raw results/configuration backups are private ignored files
in `perf-results/night-vpn-20261030/`.

## Stamp controls

DIRECT completed three 4 MiB transfers at 15.99 up / 28.03 down / 16.42 up
Mbit/s. A 40-transfer test (four concurrent requests, five upload/download
cycles) finished with HTTP 200 throughout, no reboot/API error/USB drop, and
internal minimum free 45,804 bytes. This does not establish that phone USB
upload is fixed. The old lwIP-buffer control reached 22.21/31.35/26.92 but
internal minimum free fell to 1,308 bytes; that unsafe memory configuration
was not retained.

An optional P4 AES-GCM record backend now exercises IDF DMA acceleration while
preserving BoringSSL's nonce guards, TLS profile, CA/name verification and
Bearer authentication. Per-connection NIST encryption/decryption/tampered-tag
self-test gates its use. The host cross-check includes 65 independent Node
crypto vectors, fragmented/in-place I/O, nonce sizes, corrupt tags, bounds,
allocation failure and ASan/UBSan. Actual native H2 fixture tests pass with
ALPS on/off (2,368 round-trips each) and malformed ALPS cases. These tests do
not replace hardware testing or constitute a complete cryptographic audit.

Measured SSL_read elapsed time decreased substantially (including socket I/O
and preemption, not isolated crypto time). Enabling Nagle for this transport
with the accelerator produced repeated downloads around 6.5–6.9 Mbit/s, but
long upload still falls near 2 Mbit/s. Enlarging send buffers or H2 DATA chunks
did not establish a stable upload improvement. H2 connection/stream credit
remained available; blocked-credit counts were zero in measured runs.

A 30-second, authenticated outer-TCP header trace is restricted to the current
owned boring-tls socket. It records no payload. It showed missing segments
accepted by the P4 SDIO path with valid checksums, followed by SACK evidence
from the exit. Some retransmissions waited 0.5–0.9 seconds. This does not
locate the loss on the radio, WAN or exit. lwIP's duplicate-ACK condition
ignores some SACK progress when the advertised window changes or ACKs carry
payload. A build-only experiment adds SACK evidence and partial-ACK recovery
on this owned socket, without changing the SDK or PCB ABI. Actual IDF TCP core
tests include multiple losses, wraparound, reordering, timers, output failures
and referenced pbufs under sanitizers. This is not a complete RFC 6582 claim.

Initial short SACK-only upload reached 5.17 Mbit/s, but the long repeat fell
to 1.87. Partial recovery long upload was 2.15 with TX32 KiB and 2.22 with
TX112 KiB. Larger TX queues produced more ingress drops; the experimental
algorithm is not an accepted production fix. Later RX-window results follow below.

## Waveshare controls and recovery

DIRECT remained slow (3.74 up / 3.51 down / 2.23 up) before C6 trials. At boot
1261, uptime 1764, the old C6 again lost authentication with reason 2 while
memory was healthy and host SDIO errors/queue losses remained zero. This
preceded the new C6 diagnostic image.

A fresh 4 MiB C6 backup was saved and verified before trials. Original OTA0,
bootloader, partition table and PHY-init matched the previous backup. The
original factory application is preserved in OTA0; tests use OTA1, no NVS or
PHY erase. First two diagnostic attempts did not prove the new app ran.

The third temporary C6 diagnostic delayed SDIO initialization by five seconds
while preparing rollback. P4's Hosted `sdio_read` task returned on card-init
failure, causing FreeRTOS to abort and reboot repeatedly before the C6 delay
completed. This was an introduced diagnostic fault, not evidence for the
original slow Wi-Fi cause. HS recovery retries failed; the known onboard
CH343 bridge (serial 5B91063477) recovered P4 without user buttons. P4 eFuse
MAC was verified in the same serial session before writing the preserved
production image. The core was saved. Production build 3ba7a9f and the USB
admin returned; authentication reason 2 remained. No other board was reset.
A corrected temporary C6 test schedules rollback without delaying SDIO.

This intermediate recovery did not restore Internet performance. See the final
state below for the images and settings left on both boards.

## Further isolation

Stock TCP recovery with the P4 GCM backend, RX 512 KiB / scale 4 / receive
mailbox 400, TX 32 KiB and Nagle enabled gave 8.58/2.51 and 8.20/2.18 Mbit/s
(download/upload; 8 MiB/4 MiB). No reconnect occurred. A 12 Mbit/s TLS-write
pacer worsened upload to 1.63 and was removed. These results are insufficient
for acceptance of the overall VPN performance.

A temporary Stamp-only diagnostic accepted its outer TLS carrier from Mac USB;
the Mac relayed ciphertext to the unchanged VPS. TLS/profile/HMAC/certificate
checks still ran on P4. Neither Mac Wi-Fi nor firewall was changed. This removes
C6/SDIO and lwIP WAN recovery from the carrier, but changes the network path and
is not normal standalone device throughput. Results: 10.31/5.27 Mbit/s, 518
VPN queue-full decisions on upload. The same USB-carrier comparison with curl
upload capped at 1 MiB/s gave 10.42/8.26 with zero queue-full decisions. Normal
Wi-Fi with that client cap still gave 8.42/1.77, 1150 queue-full decisions.
The carrier code was removed and the normal Wi-Fi image restored afterward.
This identifies multiple contributing limits, not an isolated root cause.

Corrected C6 diagnostic v4 did run (reported 1.4.251) without delaying SDIO and
selected the verified original OTA0 for return. Authentication reason 2 remained.
Later retry attempts hit an unsupported bandwidth configuration; those retries
are not valid association controls. Production P4 and factory C6 were restored.
A subsequent factory-firmware attempt did select Stamp's AP and also failed
with reason 2. Its temporary profile was deleted and the saved home profile
restored. A separate temporary, identity-guarded P4 image now holds only C6 EN
low for 600 seconds before continuing normal startup. It does not erase or
rewrite C6, and is not a proposed production recovery policy.

STA b/g/n-only on Stamp also failed to improve the VPN result: 8.14 down /
1.80 up, 1547 queue-full decisions. The default STA protocol mask is restored
in source. Full host tests and the ordinary software TLS H1/H2/negative suite
pass; AES-GCM wrapper tests now explicitly check nonce-reuse rejection for
both TLS 1.2 and TLS 1.3.

A TX 256 KiB control required capping TCP_SNDLOWAT at 16 KiB (the upstream
sanity check correctly rejects its default half-buffer threshold above the
16-bit readiness limit). With RX512 and stock TCP it worsened results to
7.91/1.34 Mbit/s and 19961 queue-full decisions. Both the larger TX default
and its temporary CMake threshold override were removed. The send-buffer
hypothesis alone does not explain the low upload rate.

The 600-second C6 reset hold completed and the production startup resumed,
but authentication reason 2 remained. Read-only USB hub descriptors show that
the Waveshare parent hub (05e3:0610, path 2-1) uses **ganged** power switching
(characteristics 0x00e0). Independently switching its two Wave ports cannot be
assumed safe for the Stamp/Camic ports, so no hub power command was issued.
The downstream hub's individual switching does not apply to the Wave ports.
XIAO's profiled software-backend firmware also builds successfully; no S3 was
flashed or reset.

After returning Stamp to RX512/TX32, a two-minute local check completed all 18
USB/STA transfers, seven synthetic AP-forward probe pairs, with no API error,
boot change or offline sample. Local USB throughput was 56.37–56.44 up /
41.64–43.97 down Mbit/s (two samples each); STA was 10.45–22.87 up /
4.68–6.34 down (seven each). These directions are Mac → board / board → Mac,
not the WAN VPN directions, and the AP probe is not a phone RF throughput test.

Five actual VPN-connect/download → disable-VPN → fresh DIRECT upload/download
cycles all completed. DIRECT upload was 13.70–17.62 and download 18.43–20.91
Mbit/s, no USB send failure or reboot, internal free returned to 81,303 bytes;
minimum free was 45,288. This fails to reproduce the user's phone-specific
upload stall; it does not prove that case is fixed.

Waveshare is restored to preserved production build 3ba7a9f, factory C6 and its
original enabled VPN setting. Its Wi-Fi authentication failure remains; kill
switch remains enabled. This is a software/config restoration checkpoint only.

Stock TCP timer 25 ms shortened RTO but did not improve transfer speed:
8.35/1.77 Mbit/s, 8461 queue-full decisions. Source and subsequent firmware
returned to 100 ms. The restored normal control gave 6.05/1.66 Mbit/s with
zero queue-full decisions, showing that queue drops alone do not explain
the upload limit. New passive inner IPv4 ECN counters saw 3204/3399 Not-ECT
packets in the download/upload windows, zero ECT/CE; no ECN/AQM mutation
was enabled. A temporary STA-only control is the next radio-mode isolation.

STA-only (AP really inactive, RSSI -57) gave VPN 8.24/2.52 Mbit/s,
13248 queue-full decisions on upload; DIRECT 16.49/19.57/17.39 up/down/up.
This did not isolate a material AP-mode upload improvement. AP configuration
was restored. TCP_NODELAY with AP restored gave 2.58/1.92 Mbit/s, 3484 queue-full
decisions; normal Nagle policy was restored for the next pacing comparison.

A bounded exact-outer-flow SDIO pacing control (500 us minimum between
accepted data frames, queue worker waits outside lwIP) gave 7.97/2.29 Mbit/s,
12396 VPN queue-full decisions. Its header filter passed ASan/UBSan edge cases.
No sustained gain established; temporary pacing source removed. It is not a
production optimization. Saved factory C6 on Wave still reports auth reason 2
at uptime 1600 s / boot 1595; its configuration has not been changed again.

Reducing the VPN queue to 64 packets worsened upload to 0.89 Mbit/s
(download 6.50, 14474 queue-full decisions). Default 256 restored in source.
The P4 GCM connection self-test now checks AES-128 and AES-256 encrypt/decrypt
and invalid-tag rejection; all 65 cross-vectors and wrapper negative/nonce/OOM
tests still pass with ASan/UBSan.

The reverse board-to-board test also failed: Stamp did not associate with
Wave AP; a fresh scan did not see Wave's SSID. Both temporary Wi-Fi profile

beacons are reaching another radio. Explicit dynamic64 on Wave did not cure

(boot 1597); this is not restored Internet service.

P4 USB RX telemetry now counts TinyUSB callbacks, bytes, netif handoffs,
allocation/copy failure, down interface and input rejection separately.
It does not see losses inside the USB controller/NTB parser, and accepted
means handed to lwIP, not delivered over Wi-Fi. S3 explicitly reports this
instrumentation unavailable. Existing USB TX counters cannot diagnose a
phone-to-board receive failure by themselves.

HTTP/3 was checked using an isolated aioquic client bound to the selected
Mac interface (`IP_BOUND_IF`), with normal certificate verification and no
route/firewall/Wi-Fi changes. A small `cloudflare-quic.com/cdn-cgi/trace`

The public nghttp2 HTTP/3 echo control timed out for 256 KiB and returned

A longer VPN -> DIRECT sequence is running with real UDP/TCP DNS requests to
Stamp's DHCP-advertised resolver. Binding curl to USB does not alone test that

## NCM receive defects found in the pinned driver

The TinyUSB NCM parser read NTH fields before checking the received minimum,
used `sizeof(pointer)` for the first NDP offset, and trusted NDP `wLength`
before indexing the final datagram descriptor. It also allowed data ranges to
extend into USB padding beyond the declared NTB block. The generated build
patch now checks each containing range before accessing it. An exact-length
buffer regression triggers ASan heap-buffer-overflow with the old generator;
the corrected real driver passes truncations, oversized/misaligned tables,
padding boundaries and 20,000 deterministic mutations in each of four
notification/telemetry variants, including telemetry disabled under ASan/UBSan.

A separate deterministic RX hang exists: an empty first datagram descriptor
passed validation, then the glue routine retained that NTB without releasing
it or advancing. Empty/half-empty first entries are now discarded before they
enter that queue. Failed USB completions also cannot deliver stale data.
The actual driver callback test feeds more empty blocks than the RX pool can
hold, then a valid packet: buffers recycle and the packet is delivered.
`usb.ncm.rx_blocks` and `rx_rejected` count these OUT completion decisions;
rejected includes empty/zero-length transfers, not necessarily lost Ethernet
frames. Managed dependency files are untouched; source hash pinning remains. The RX
safety patch applies to NCM builds even when diagnostic counters are disabled.

Neither malformed data nor empty blocks have yet been observed from the
user's phone. These are independently reproduced bugs, not proof that they
caused the reported phone upload stall.


The long sequence did catch a later VPN failure (cycle 36): upload reset,
then download received only 606,208/4,194,304 bytes before its 45 s timeout.
The outer connection reported `tls_read`/104, followed by several connect
116 failures before recovering. DIRECT immediately afterward still worked.
This is a failed VPN stability result, not an all-pass soak. No root cause
is assigned from the snapshot alone. A direct Mac TCP-connect control to the
same VPS measured 78.7–79.9 ms; lwIP's 150–200 ms RTT telemetry is coarse and
must not be treated as an exact wire RTT.

## Latest controls and the saved-crash boot loop

TX112 KiB plus exact-owned-outer-TCP SDIO pacing at 1000 us produced three
VPN down/up pairs: 8.14/3.49, 7.18/2.75 and 7.99/2.16 Mbit/s. Upload queue-full
counts were 453, 15828 and 10. The declining repeat does not establish a stable
improvement. Pacing, TX112 and the application coalescing variant are removed;
ordinary TX32/Nagle firmware is restored for the final checks.

A Wave control disabling only USB HS initially did not reach radio startup:
a saved valid crash dump triggered another panic while the application read
its summary. The matching backtrace resolves to `esp_core_dump_get_summary`
→ partition mmap → `esp_task_stack_is_sane_cache_disabled`. The main task's
stack was in P4 SPM/TCM (SP 0x301015e0), which IDF 5.5.5's flash-cache guard
does not accept. Different allocation layout in the preserved older image
explains why that image could boot with the same dump. This is a distinct
startup defect, not evidence for the preceding authentication failure.

P4 crash-summary reading now runs in a short-lived task whose stack requires
INTERNAL|DMA|8BIT, selecting ordinary DRAM rather than SPM. Semaphore/task
allocation failure skips the summary rather than falling back onto the unsafe
caller stack. Tests exercise empty/valid dumps, stack capabilities, join and
both allocation failures under ASan/UBSan. Full host suite passed. On the
actual Wave, the same saved dump was read and logged without erasing it;
USB/admin/network initialization then completed (boot 1630).

The repeated no-HS control now reached network startup and logged its disabled
controller. Across 100 seconds, five STA attempts still failed with reason 2
at RSSI -43/-44, no DHCP IP. Active USB HS operation therefore does not explain
this association failure. The diagnostic image was replaced with the
ordinary HS-enabled image. UART writes verify the known CH343 identity and P4 eFuse in
one serial session; no user button or other board reset was needed. The first
recovery's transient port error was retried after 30 seconds and succeeded.


## Exit-side evidence (read-only SSH)

The existing SSH key also permits read-only observation of the already running
VPS native engine. Its service was neither restarted nor reconfigured. Listener
PID 340197 is `/opt/clean-vpn-native/daily-exit/engine`; CPU load is low. Other
client connections were left untouched.

During a correlated Stamp run, exit TCP advertised sufficient receive space;
Stamp's TX32 KiB frequently remained fully unacknowledged. Rates were 7.44/2.12.
A subsequent capture was restricted to the unique current Stamp flow (MSS1360,
window scale4, matched connection and NAT tuple), textual TCP headers only.
It captured 8788 packets, with zero kernel capture drops. Local outbound
checksum warnings in tcpdump are offload artifacts and are not counted as
corrupted wire packets. That run was 8.28/1.47 Mbit/s.

The exit received five gaps in Stamp's TCP byte stream, initially 2720–5440
bytes each. They filled after 0.64–1.24 seconds. The ordinary exit ACK turnaround
median was 0.17 ms; the large tail is dominated by waiting for missing bytes.
This confirms slow loss/reordering recovery on the P4-to-exit path, but does
not locate the missing packets to C6 radio, SDIO, ISP or another WAN hop.
Metadata/analysis are private files `vps-stamp-tcp-headers.log` and
`vps-stamp-tcp-analysis.json`; no TLS plaintext was dumped.

The native service journal contains `h2_ping_timeout` at 01:21:48.964 UTC;
Stamp changed from up to `tls_read`/104 at 01:21:49.245 during failed soak
cycle36. That strongly correlates the observed outer reset with the exit's
five-second HTTP/2 heartbeat deadline. It does not establish why the ACK was
late. A second service timeout 1.38 seconds later may concern another peer;
these state events lack a peer identifier and must not be attributed blindly.
The earlier upload curl reset preceded this outer timeout by six seconds.

The 2000-us/packet + TX112 KiB control gave 3.43/3.00 Mbit/s, zero VPN queue-full
in that sample, but materially worsened download. Its 250-ms diagnostic Hosted
queue age and pacing were removed; normal age100 ms and TX32 KiB restored.


## Final controls, validation and board state

Disabling only Stamp C6 TX A-MPDU through its init configuration produced
7.70 down / 1.67 up Mbit/s, 119 VPN queue-full decisions. This did not improve
upload. The override was removed, the normal firmware rebuilt and flashed
without buttons; the same bound P4 identity was verified. The final normal
DIRECT sequence completed all three 4 MiB transfers with HTTP200:
13.51 up / 17.57 down / 16.88 up Mbit/s. This is Mac USB, not a phone retest.

Final Stamp: build `d1855e4-dirty`, boot231, STA online, normal C6 2.12.1,
normal TX A-MPDU policy, USB/admin available. VPN enabled=false matches the
saved starting snapshot used by this night's controls. Saved VPN endpoint,
CA, profile and peer credentials are retained. Final Wave: build
`1f52cb6-dirty`, boot1633, ordinary HS-enabled image with crash-reader fix,
USB/admin available, factory C6 restored, VPN enabled=true and kill switch
preserved. Wave STA still reports authentication_expired(2); its Internet
connection is **not restored**. No diagnostic image, relay or workload is left
running. Camic, Mac Wi-Fi/firewall, router and running native VPS are unchanged.

Retained commits: `c1cec96`, `2bfd2eb` (NCM RX), `1f52cb6` (P4 crash reader),
`d1855e4` (P4 TLS acceleration, transport diagnostics and disabled experimental
TCP recovery lab). Normal builds use stock TCP recovery; no pacing or temporary
C6 init overrides remain. Builds completed for Stamp, Waveshare and XIAO;
XIAO was not flashed. Full host suite, actual generated NCM parser with
ASan/UBSan and telemetry-off variants, GCM cross-vectors/negative checks,
software H1/H2 and actual native H2/ALPS tests passed. These checks do not
turn the failed real-world VPN soak into a pass.

A separate compatibility gap was found while reading the current native code:
its HTTP/1.1 `h1-v1` uses POST, chunked bodies and ping/pong control records.
The device H1 implementation targets legacy JS GET/raw framing. Documentation
now distinguishes these; native H1 support remains pending. Current measured
connections use H2, so this gap does not explain their slow throughput.

Next work must distinguish missing outer TCP data on the C6/SDIO/radio path
from WAN loss, and establish why native H2 heartbeat ACK misses its deadline
under load. The native implementation currently starts the deadline when PING
is queued, not when it is written; backpressure is a hypothesis requiring a
controlled native reproduction, not grounds for silently loosening production
timeouts. Phone DIRECT upload requires the original phone USB workload; it
was not reproduced by the successful Mac series. Wave needs a usable radio
association before another honest throughput comparison. Software reset,
factory rollback, alternate AP, C6 EN-low and no-HS controls did not recover it;
changing more throughput defaults without that baseline is not justified.
