# Overnight VPN / DIRECT investigation, 30 October

Checkpoint after overnight investigation (05:25 MSK). Performance acceptance
is still failed. This chronological report extends the earlier throughput report;
The earlier Final controls section is a checkpoint, not the latest state; later continuation sections supersede it. The reported phone failure is DIRECT upload through Stamp
USB Ethernet. All measurements here use Mac USB and do not reproduce that
phone workload exactly. Mac Wi-Fi, router, firewall and the native VPS process
remain unchanged. Raw results/configuration backups are private ignored files
in `perf-results/night-vpn-20261030/`.

## Stamp controls

DIRECT completed three 4 MiB transfers at 15.99 up / 28.03 down / 16.42 up
Mbit/s. A 40-transfer test (four concurrent requests, five upload/download
cycles) finished with HTTP 200 throughout, no reboot/API error/USB drop, and
internal minimum free 45,804 bytes. This does not establish that phone USB
upload is fixed. The old lwIP-buffer control reached 22.21/31.35/26.92 but
internal minimum free fell to 1,308 bytes; that unsafe memory configuration
was not retained.

An optional P4 AES-GCM record backend now exercises IDF DMA acceleration while
preserving BoringSSL's nonce guards, TLS profile, CA/name verification and
Bearer authentication. Per-connection NIST encryption/decryption/tampered-tag
self-test gates its use. The host cross-check includes 65 independent Node
crypto vectors, fragmented/in-place I/O, nonce sizes, corrupt tags, bounds,
allocation failure and ASan/UBSan. Actual native H2 fixture tests pass with
ALPS on/off (2,368 round-trips each) and malformed ALPS cases. These tests do
not replace hardware testing or constitute a complete cryptographic audit.

Measured SSL_read elapsed time decreased substantially (including socket I/O
and preemption, not isolated crypto time). Enabling Nagle for this transport
with the accelerator produced repeated downloads around 6.5–6.9 Mbit/s, but
long upload still falls near 2 Mbit/s. Enlarging send buffers or H2 DATA chunks
did not establish a stable upload improvement. H2 connection/stream credit
remained available; blocked-credit counts were zero in measured runs.

A 30-second, authenticated outer-TCP header trace is restricted to the current
owned boring-tls socket. It records no payload. It showed missing segments
accepted by the P4 SDIO path with valid checksums, followed by SACK evidence
from the exit. Some retransmissions waited 0.5–0.9 seconds. This does not
locate the loss on the radio, WAN or exit. lwIP's duplicate-ACK condition
ignores some SACK progress when the advertised window changes or ACKs carry
payload. A build-only experiment adds SACK evidence and partial-ACK recovery
on this owned socket, without changing the SDK or PCB ABI. Actual IDF TCP core
tests include multiple losses, wraparound, reordering, timers, output failures
and referenced pbufs under sanitizers. This is not a complete RFC 6582 claim.

Initial short SACK-only upload reached 5.17 Mbit/s, but the long repeat fell
to 1.87. Partial recovery long upload was 2.15 with TX32 KiB and 2.22 with
TX112 KiB. Larger TX queues produced more ingress drops; the experimental
algorithm is not an accepted production fix. Later RX-window results follow below.

## NCM receive defects found in the pinned driver

The TinyUSB NCM parser read NTH fields before checking the received minimum,
used `sizeof(pointer)` for the first NDP offset, and trusted NDP `wLength`
before indexing the final datagram descriptor. It also allowed data ranges to
extend into USB padding beyond the declared NTB block. The generated build
patch now checks each containing range before accessing it. An exact-length
buffer regression triggers ASan heap-buffer-overflow with the old generator;
the corrected real driver passes truncations, oversized/misaligned tables,
padding boundaries and 20,000 deterministic mutations in each of four
notification/telemetry variants, including telemetry disabled under ASan/UBSan.

A separate deterministic RX hang exists: an empty first datagram descriptor
passed validation, then the glue routine retained that NTB without releasing
it or advancing. Empty/half-empty first entries are now discarded before they
enter that queue. Failed USB completions also cannot deliver stale data.
The actual driver callback test feeds more empty blocks than the RX pool can
hold, then a valid packet: buffers recycle and the packet is delivered.
`usb.ncm.rx_blocks` and `rx_rejected` count these OUT completion decisions;
rejected includes empty/zero-length transfers, not necessarily lost Ethernet
frames. Managed dependency files are untouched; source hash pinning remains. The RX
safety patch applies to NCM builds even when diagnostic counters are disabled.

Neither malformed data nor empty blocks have yet been observed from the
user's phone. These are independently reproduced bugs, not proof that they
caused the reported phone upload stall.

was not reproduced by the successful Mac series. Wave needs a usable radio
association before another honest throughput comparison. Software reset,
factory rollback, alternate AP, C6 EN-low and no-HS controls did not recover it;
changing more throughput defaults without that baseline is not justified.

### Missing C6 Wi-Fi initialization fields

Compared against the exact registry 2.12.1 source commit
`f45f8ab865a03e409bfe3c22198b0c27727b40d5`, not just latest upstream. The
1.4.7 host protobuf schema stops at field 20. Newer C6 `get_merged_init_config`
unconditionally copies fields 21–24: RX management buffer type/count, HE TB
queue count and HE SIG-B dump flag. Absent protobuf fields decode as zero.
This loses configured RX management count=5 and HE TB queue count=3.

Commit `f08d6a0` serializes the four standard upstream tags using protobuf-c's
unknown-field API, with storage alive for the entire synchronous pack/send
function. It retains the pinned ABI and leaves the old peer free to ignore
new fields. ASan/UBSan tests exercise actual complete RPC packing, exact wire
tags, legacy decode/free, multi-byte and signed values. The full host suite
passed; both P4 firmware builds and automatic flashes completed. C6 firmware,
Wi-Fi profiles and VPN credentials were not rewritten by this fix.

This is a concrete compatibility correction, **not a demonstrated throughput
fix**. Stamp DIRECT controls were 15.65 up /18.55 down /15.00 up Mbit/s. The
first VPN control was 6.07 down /1.41 up, with no reconnect. Waveshare still
reported authentication_expired (2); its association was not recovered.
Raw TCP to the same VPS through updated Stamp delivered about 3.3–5.5 upload
and 21.91 download Mbit/s. Alternating UDP controls after the fix showed
Stamp losses 1.26%/7.64%/5.40% at 8/16/24 Mbit/s; direct Mac Wi-Fi controls
were 0.012%/0.036%/0.132%. At 8 Mbit/s, all 8335 Hosted submissions were sent
directly, with zero queue loss or SDIO write failure, while the VPS received
8229 of 8334 synthetic datagrams. At 16/24 Mbit/s Hosted queue-full added
164/258 drops; expiry remained zero. VPS socket drops were zero and aggregate
UDP/TCP checksum error counters were zero. This separates queue overload at
higher rates from the lower-rate losses after successful host SDIO handoff.

A temporary passive-radio observation using Waveshare C6 is being prepared to
count only Stamp-addressed Wi-Fi data/retry and ACK/BlockACK frames. It saves
no packet bodies, uses no user credentials, and preselects the verified
factory OTA image for automatic return. This trial is not yet a result.

## Passive RF observation and power control (08:10–08:25)

A temporary Waveshare C6 image observed only counters for Stamp's STA MAC on
channel 4; packet bodies were not retained. Before starting Wi-Fi it verified
the preserved original OTA0 image/hash and selected that original for the next
boot. A 300-second timer ended the observer. Waveshare P4 was then reflashed
with its normal image; USB/admin returned, while authentication reason 2 remains.

With normal Stamp power (readback 20 dBm), the 8/16/24 Mbit/s UDP runs lost
0.876% / 1.812% / 4.836% at the restricted VPS receiver. Adjacent Mac controls
lost zero datagrams; VPS socket-buffer drop counts were zero. Mac's existing
connection is **5 GHz/channel 48/802.11ac**, so this is a WAN/server control,
not an equivalent 2.4 GHz RF control. Mac Wi-Fi was never switched.

The observer saw 9100 / 17822 / 26321 Stamp data transmissions, including
845 / 1465 / 2499 Retry-flagged frames, over those UDP windows. Subtracting
retries gives 8255 / 16357 / 23822 first transmissions, close to the VPS counts
8261 / 16366 / 23792. This suggests some loss before first RF transmission,
not necessarily exhausted over-air retries. Promiscuous capture can miss
frames; this is a lead requiring C6-side counters, not proof of a driver bug.
The same raw TCP path (no VPN) delivered about 4.62 and 4.05 Mbit/s upload;
client download was 11.44 Mbit/s in this series.

A temporary, RAM-only 14 dBm Stamp control worsened UDP loss to
2.124% / 4.194% / 25.811%. The observed 8 Mbit/s retry fraction grew from 9.29%
to 15.54%. This control is rejected. Stamp was returned to the ordinary image
and is online again (boot 244). No power override remains in source.

Original C6 code is still on both boards. A pinned Hosted 2.12.1 diagnostic
build is being prepared to count SDIO frames and Wi-Fi driver admission/errors
inside C6; it has **not** been flashed. The next test must retain the original
C6 OTA application and prove rollback before any performance claim.
