# P4: real raw TLS exit, 25 October 2026

Status: incomplete. Small real requests passed; sustained traffic is not accepted yet.

## Confirmed before the failure

Bound Waveshare ESP32-P4-WIFI6, USB HS `en17`, exit `154.62.226.216:443`.
Firmware `d463600-dirty`, boot 64; TLS 1.2 with the user's raw TLS exit.
The user subsequently clarified that the initial exit was a native build;
the later listener was the JS implementation from main. The initial pass
therefore does not establish JS-main hardware acceptance.
Mac Wi-Fi was not switched. No server restart or configuration change was made.

- Outer TLS connection established.
- Board TCP internet probe to `1.1.1.1:443` passed.
- Mac HTTP over USB to numeric `1.1.1.1` returned 301.
- DNS explicitly through `192.168.10.1` resolved `ifconfig.me`.
- HTTPS `ifconfig.me/ip` over USB returned **154.62.226.216**, the exit IPv4.
- HTTPS `1.1.1.1/cdn-cgi/trace` succeeded.

The first 1 MiB CDN download received only 646528 bytes before timing out.
The board rebooted (64 → 65, PANIC); therefore there is no valid sustained
throughput figure and the hardware acceptance test failed.

## Crash evidence

The recovered flash core dump and matching ELF decode to:

```
assert failed: remove_free_block tlsf_control_functions.h:372
(prev && "prev_free field can not be null")
```

Heap corruption was detected during a 72-byte allocation for a USB RX pbuf,
in `TinyUSB → tud_network_recv_cb → usb_netif_input → pbuf_alloc`.
This identifies the detection site, **not the original corrupting writer**.
The recorded task stack headrooms do not demonstrate a stack overflow.

Raw core, ELF, logs and sanitized API samples are retained locally under
`device/perf-results/tls-live-2026-10-25-r6faaU/` (ignored by Git).
They are not included in this report or uploaded.

## Buffer experiment and Wi-Fi blocker

A P4 build with fixed mbedTLS record buffers in PSRAM was compiled and flashed.
It keeps the existing 16 KiB RX / 4 KiB TX limits and disables the ESP-IDF dynamic
record allocation/free wrapper. This is a mitigation candidate, **not a proven
root-cause fix**. XIAO settings are unchanged.

Following the failure/recovery cycles, STA repeatedly reported
`authentication_expired` (reason 2) while VPN was disabled. The saved network
was visible at approximately -48 dBm. Manual profile retry, software reboot,
a temporary b/g/n-only image and the previous known image did not restore it.
The user confirmed no router changes. The b/g/n diagnostic source was reverted.
USB admin remained available; internal free memory was approximately 100 KiB.
Thus the failed retries did not reach TLS and cannot validate the buffer change.

## Server logs

The exit remained listening on port 443. Its `--keep-alive=5` setting closes an
idle raw TCP/TLS session after five seconds; the repeated idle/FIN lines are
consistent with this configuration. They do not establish a TLS protocol error.
An earlier TLS 1.3 preflight against the TLS-1.2-only listener explains one
`unsupported protocol` log; the board's confirmed connection used TLS 1.2.

## Recovery and fixes

- `bfa8a0f`: P4 ROM recovery verifies the eFuse MAC and writes through one open
  esptool connection. The prior read/close/reopen sequence reproduced macOS
  `Device not configured`. Recovery and the final production helper were
  exercised on this bound P4; all written hashes verified and application CDC
  returned. Another interrupted write was recovered after the user offered
  BOOT+RESET. No unrelated board was programmed.
- `5836077`: fixed P4 record buffers in PSRAM; TLS connect errors now retain
  socket/SDK details. Previously every connection failure was overwritten
  with ECONNREFUSED (111), including an observed select timeout.
- Firmware `5836077-dirty` was flashed after removing all temporary radio and
  C6 reset hooks. The tracked source difference at that build was report/plan
  documentation. P4 retains HT20 and its original b/g/n/ax policy.
- Temporary tests included HT20 b/g/n without the newer firmware RPC, a longer
  C6 EN reset and a successful `esp_wifi_restore()` before applying P4-owned
  profiles. STA still reported reason 2; SDIO RX allocation/format drop counters
  were zero. A saved older overnight image also failed STA recovery. These
  observations do not identify the cause of authentication failure.
- Following manual ROM recovery, boot 73 associated and obtained a DHCP IPv4,
  but DIRECT HTTP through USB and the board's outer connection timed out.
  The new JS-main exit remained listening, passed a TLS-1.2 loopback handshake
  and a direct Mac handshake. One process owned its `tun0`; no server settings
  were changed by the test agent.

Checks: 32 flash/binding tests; P4 and XIAO builds; real host mbedTLS fragmented
full-duplex I/O (128 packets). Host loopback does not exercise ESP dynamic-buffer
hooks, P4 DMA or prove heap-corruption repair.

Selected VPN mode was restored to OFF/TCP, with kill switch enabled. The tested
TLS endpoint remains in the per-transport saved endpoints. WireGuard keys were
not exported or changed. A full power removal of both USB supplies was then performed by the user.
Boot 79 still reported `authentication_expired` with VPN OFF. Scan/profile
matched WPA2, one matching AP, -47 dBm, channel 4; bandwidth readback was
20 MHz and secondary channel zero. Re-entering the saved Wi-Fi credential
in the USB admin was requested to exclude a stored credential mismatch;
the password was not requested in chat. No successful fixed-buffer bulk run
or valid TLS speed measurement is claimed.

Next: confirm DIRECT after cold power-up, then repeat JS-main TLS requests,
bulk transfers and a soak. Measure throughput only after complete transfers
without a new panic.
