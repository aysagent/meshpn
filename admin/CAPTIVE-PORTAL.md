# USB captive portal: настройка Wi-Fi без внешней сети

Когда Radxa не подключена к подходящей Wi-Fi-сети, USB-клиент получает
HTTP-перенаправление на **http://192.168.7.1/#wifi**. Нужно войти в обычную
админку и выбрать/сохранить сеть. Пароль, смена `admin`, сессии и CSRF работают
как прежде. Имя `mpn.local` (или изменённое в админке имя) остаётся доступным;
IP в перенаправлении позволяет войти и без mDNS.

Это поддержка классического captive detection, а не гарантия всплывающего окна
на каждой ОС. ОС должна поддерживать USB Ethernet, направить проверку именно
через него и использовать HTTP-пробу. Телефон с мобильной сетью, ноутбук с другим
приоритетным подключением, VPN или защищённым DNS может не показать уведомление.
Тогда откройте адрес выше вручную. Существующие DHCP-настройки USB должны выдать
клиенту адрес `192.168.7.x/24` и шлюз `192.168.7.1`; портал их не меняет.

## Когда включается

Отдельная служба `meshpn-admin-captive.service` проверяет состояние каждые
2,5 секунды. Подходящее подключение — это `wlan0` с `UP/LOWER_UP`,
`wpa_supplicant: COMPLETED`, глобальным IPv4-адресом (не link-local)
и маршрутом `default` через `wlan0` в таблице `main`.

- После двух подряд отрицательных проверок включается портал.
- После положительной проверки перенаправление убирается.
- Ошибка чтения состояния означает «неизвестно» и выключает портал.
- Отказ/остановка VPN, DNS upstream или внешнего сайта не включает портал.
  Внешних проб для этого механизма нет. Wi-Fi отеля с собственным captive portal
  может удовлетворять перечисленным условиям, даже если интернет ещё закрыт.

Это текущая IPv4-конфигурация Radxa (`usb0`, `192.168.7.1/24`, `wlan0`),
не универсальный сетевой менеджер для произвольных интерфейсов.

## Границы сетевых изменений

Только при активном портале, только входящие `usb0` + `192.168.7.0/24`:

| Трафик | Поведение |
| --- | --- |
| UDP/TCP 53 | DNAT на `192.168.7.1:1054`, ограниченный локальный DNS |
| A | Адрес платы, TTL 0 |
| AAAA / HTTPS / SVCB | NOERROR без адресов/подсказок |
| Прочие DNS-типы | REFUSED |
| TCP 80, кроме исходного адреса самой платы | DNAT на `192.168.7.1:18080`, фиксированный HTTP 302 |
| HTTP 80 платы с чужим Host | Только GET/HEAD вне `/api/`: тот же 302, пока статус портала свежий |
| HTTP 80 платы с правильным Host | Обычная админка, без циклического перенаправления |
| HTTPS / TCP 443 | Не перехватывается |

DNS не пересылает запросы наружу. Ограничены размер сообщений, частота запросов,
соединения и таймауты; HTTP-ответчик не принимает настройки, пароль или API.
Собственные INPUT-правила закрывают прямое обращение к служебным портам;
разрешены только нужные USB DNAT-соединения. Нет изменений OUTPUT/FORWARD,
маршрутов, `ip_forward`, DHCP, dnsmasq или `/etc/resolv.conf`.
Kill switch не отключается.

Правила помечены `meshpn-usb-captive-v1`. При остановке удаляются только точные
собственные правила и conntrack-записи переводов в порты 1054/18080. При включении
портала дополнительно сбрасываются **только DNS-соединения USB-подсети на порт 53**:
иначе старый UDP tuple продолжал бы обходить новый DNAT. При перезапуске native
DNS портал восстанавливает приоритет своих трёх PREROUTING-правил; чужие правила
не удаляются и таблицы не очищаются.

`ExecStopPost` повторяет идемпотентную очистку после SIGKILL. Служба связана с
broker: останавливается до удаления `/run/meshpn-admin`, запускается вместе с
ним. Состояние `/run/meshpn-admin/captive.json` не содержит SSID/паролей;
просроченный файл не разрешает исключение из проверки Host в админке.
Обычный restart службы автоматически восстанавливает работу после сбоя.

Современный CAPPORT через DHCP option 114 здесь не объявляется: его API
требует HTTPS с проверяемым сертификатом, которого у локальной HTTP-админки нет.
См. [RFC 8908](https://www.rfc-editor.org/rfc/rfc8908.html) и
[RFC 8910](https://www.rfc-editor.org/rfc/rfc8910.html).

## Установка и контейнеры

На уже установленной Radxa после обновления репозитория:

```sh
sudo node admin/install.mjs --update
systemctl status meshpn-admin-captive.service --no-pager
cat /run/meshpn-admin/captive.json
```

Installer проверяет наличие `ip`, `iptables`, `conntrack`, `wpa_cli`, свободных
служебных портов при первом добавлении и неизменность собственного unit.
Пакеты сам не устанавливает. Потребуется пакет `conntrack`, если его ещё нет.
Новая установка `--apply --native-name=...` также включает службу;
`--remove` останавливает её, очищает правила и удаляет unit.

Обновление перезапускает админку и её broker; файлы Wi-Fi, пароль и настройки VPN
сохраняются. **29 октября версия установлена на физическую Radxa**: проверены
USB HTTP, состояние `wifi_ready`, SIGKILL/restart и очистка при остановке.
См. [физический отчёт](../scripts/clean-vpn-native-physical-20261029-evening.md).
При обновлении нужно иметь USB-доступ и дождаться окончания команды, затем проверить статус.

При Docker/Podman frontend сетевой контроллер остаётся службой **хоста**, как и
существующий privileged broker. Frontend читает статус через уже смонтированный
`/run/meshpn-admin`; новые capabilities и доступ к Docker socket ему не нужны.
Сам HTTP frontend не должен управлять firewall контейнера или хоста.

Для временного отключения до следующего запуска:

```sh
sudo systemctl stop meshpn-admin-captive.service
```

После восстановления службы `systemctl start meshpn-admin-captive.service`
состояние определяется заново. Никаких ручных flush правил не требуется.

## Проверки и оставшийся физический шаг

Регрессии админки и портала:

```sh
node --test admin/test/*.test.mjs
```

На macOS sandbox может запрещать сокеты/метрики; эти тесты выполнены в Linux.
Изолированная интеграция запускается **только внутри нового одноразового
systemd-контейнера** на основе `admin/test/native-host.Containerfile`, без внешней
сети и без host mounts. Скрипт меняет сеть своего контейнера и отказывается
работать без маркера лабораторного образа:

```sh
node /project/admin/test/captive-netns-lab.mjs --apply-disposable-lab
```

В нём настоящие netns/veth, маршруты, iptables, conntrack, kill switch проекта,
HTTP-админка, systemd и ExecStopPost. Эмулированы только ответ `wpa_cli`, broker
для lifecycle-теста и native DNS upstream на отдельном локальном порту.
В installer-fixture убрана только зависимость socket от udev `.device`
(`BindToDevice`): контейнер не публикует такие device units. Это не проверка
загрузки физического USB gadget; его основной unit в проекте не изменён.
Проверяются переходы offline/online/unknown, один и тот же DNS UDP tuple в обе
стороны, чужой интерфейс, HTTPS, SIGKILL/restart, остановка broker и installer.
Результат: [лабораторный отчёт](test/last-captive-report.json).

Осталось физически проверить USB DHCP и обнаружение на нужном телефоне/ноутбуке:
без Wi-Fi открыть портал, войти, подключить Wi-Fi; убедиться, что портал
отключился и обычный VPN/DNS работает. Затем проверить холодную загрузку.
Именно offline-проверка на устройстве пользователя и холодная загрузка нового
controller пока не выполнялись. Сеть Mac не изменялась.
