## Native + существующие владельцы Radxa

Новый временный systemd-адаптер связывает engine и условный clock recovery с
существующим journalled владельцем DNS/маршрутов. Не требует packet IPC.
Реальный Radxa↔VPS прогон с Chromium-derived cold profile прошёл DNS (4/4),
HTTPS (2/2), загрузку 1 MiB, 30 секунд hold и возврат legacy с повторными пробами.
Guard и rollback — verified. При здоровых часах recovery unit не запускался.
Ограниченный SSH time helper отдельно проверен с реальным закреплённым ключом
VPS; часы не корректировались, поскольку уже совпадали.

Не скрыты промежуточные сбои:

- Первый запуск выявил смешение JSON от ExecStartPre `--check-config` с
  runtime status stream. Проверка конфигурации вынесена до запуска unit.
- Второй прогон поднял engine/DNS и восстановил legacy, но одна внешняя HTTPS
  проба не прошла. Он сохранён как **failed**, не включён в успешную приёмку.
- Третий systemd-прогон прошёл полностью. Причина единичного внешнего HTTPS
  отказа не установлена; повторный pass не доказывает отсутствие сетевых сбоев.

Физические часы намеренно не портились и плату ночью не перезагружали.
Cold boot/time-fault сценарии относятся к предыдущему VM-этапу, а не к этой
физической проверке. Временный SSH account/key, его данные и runtime units
после проверки удалены.

## Админка: что проверено

Физическая Radxa: браузерный вход без JS-ошибок, четыре ядра/температура/RAM,
Wi-Fi и guard status, смена пароля и отзыв сессии, возврат исходного auth state,
Wi-Fi scan, создание/удаление отключённого тестового профиля без смены текущей
сети, имя mpn-test→mpn, native `--check-config` при сохранении candidate,
журнал, настоящий USB TLS/H2 capture с проверенным в конкретном соединении CA,
запуск и автоматическое завершение независимого наблюдателя.

Контейнер: Podman ARM64 build; реальный frontend отдельным процессом, UID1000,
read-only root, no capabilities, network=none с loopback, mock UNIX host broker.
Проверены правильный/чужой Host и два inherited socket proxy (HTTP и TLS bytes).
Docker compose рецепт подготовлен; Docker admin-контейнер на физической Radxa
не устанавливался. Поддержка не означает «root/systemd внутри контейнера»:
broker и USB-bound sockets намеренно остаются на хосте.

Тесты API/аутентификации/захвата: 19/19 локально. API + guard: 62/62 на Radxa; финальный объединённый прогон API/guard/capture после обновления — **75/75**, без пропусков.
Отдельно реальные iptables в ARM64 namespace: точная USB-mDNS запись допускается
read-only аудитом, неизвестные/расширенные правила отклоняются, mutation при
shadowed hook отказывается, после снятия собственной записи guard штатно
удаляется. Первый такой lab-запуск в amd64-образе на ARM не поддержал netfilter;
он не считается pass, тест повторён в native ARM64 образе.

После финального обновления HTTP по имени/IP и вход/данные страницы повторно проверены. Повторный screenshot тестового Chrome на Mac завершился CDP-timeout; первый полный screenshot сохранён, настройки Mac ради рендера не менялись.

Физическое переключение на другой Wi-Fi и отключение kill switch не выполнялись.
Wi-Fi connect содержит возврат предыдущего выбора при неуспешном соединении;
его полная приёмка с несколькими реальными AP остаётся отдельным сценарием.

## DNS и следующие границы

[dnsmasq → networkd/resolved](../scripts/clean-vpn-radxa-dns-migration.md) —
исследование по реальной конфигурации. Учтены USB DHCP, две option 6, Bluetooth
pan0 и локальная зона. Ничего из DNS/DHCP/Netplan не мигрировано.

В админке native-настройки пока сохраняются как проверяемый candidate;
профиль legacy-процесса автоматически не меняется. DNS upstream фиксированы
текущим native engine. Смена exit требует общей транзакции route/guard/DNS,
поэтому пока явно отклоняется. IP/domain/GeoIP routing, другие transports,
WPA3/Enterprise и AP не представлены как готовые функции.

Следующая работа: принятие админки пользователем; Wi-Fi roaming/failure matrix;
согласованный installer постоянного native lifecycle и затем физический reboot
pilot. DNS migration — отдельная задача после VM-проверок конкретной схемы.
